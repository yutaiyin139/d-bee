## 三、管理方案：独立项目（推荐，且是既有既定决策）

### 结论
**另起一个独立 git 仓库，不并入 `zilv-mifeng`。** 这不是新拍板，而是遵循仓库里已写死的架构决策：

> `packages/shared/src/constants/index.ts:54-55`
> 「京ICP备2026075565号-**1** = 北京迪蜂科技有限公司门户网站，域名 **d-bee.com.cn**
> 　（**官网不在本仓库，本仓库任何地方都不该出现 -1**）」

### 四条理由
1. **备案号隔离**：并入后 `-1` 号进入本仓库，会与 `verify-legal.mjs` 的双向校验冲突，或造成串号违规。
2. **技术栈隔离**：官网零构建纯静态；主仓库是 React18 + Vite5 + TS + 22 道护栏 + native 构建。记忆铁律已记「native 与 web 共用 `dist/` 会互斥、`build:web` 会删 `dist/legal/`」——再塞一套静态页只会放大这个坑，且护栏扫描范围会被无谓扩大。
3. **发布节奏与责任链不同**：官网改文案即可发；主仓库要过 887 项测试 + 四端验收 + 生产部署 + 铁律 #13 实证。
4. **域名/备案天然独立**：`-1` 门户与 `-2` 产品各自部署，互不牵连。

### 建议目录（放 E 盘，正好是新资产、零历史路径绑定）
```
E:\dev\d-bee-website\
  ├ index.html … 9 页（从现有 app/ 复制）
  ├ assets/
  ├ FACTS.md                  ← 🔴 单一事实清单（见下）
  ├ tools/check-facts.mjs     ← 发布前护栏
  └ README.md                 ← 域名/备案号/部署方式/回滚
```

### `FACTS.md` 必须锁定的字段
主体全称与统一信用代码 · ICP 号 `-1` 与查询链接 · 公安备案号（未下证写「待办 + 期限」）· 软著/商标**真实状态** · **四端真实上架状态**（指向上线主文档 §二）· 三档定价（对齐 `packages/shared`）· 法务文案版本与生效日期 · 二维码真实目标 URL · 每次四端状态变化后同步更新。

### 发布前护栏（轻量，零构建）
`check-facts.mjs` 检查三类：① 每页页脚含 `-1` 且可点击指向 beian.miit.gov.cn；② **禁用词表**（`已上架` / `全平台` / `应用商店` / `自动续费` / `评分 4.9` / `资质齐备` / `备案办理中`）命中即 FAIL；③ 二维码非占位图。新增护栏后**必须红验证**（项目铁律）。

### 双域名分工（避免 SEO 分散与用户困惑）
| 域名 | 备案 | 角色 |
| --- | --- | --- |
| `d-bee.cn` | `-2` | 产品 Web App + 定价页（**已上线**） |
| `d-bee.com.cn` | `-1` | 品牌官网 / 下载落地页 / 法务公示（**整改后可上线**） |

过渡期官网「下载」CTA 建议指向 `d-bee.cn` 的 Web 版或「内测预约」，**不指向尚不存在的应用商店**；两域名互做单向链接。

## 四、`C:\Users\yuty\WorkBuddy` 整体移到 E 盘 —— 评估结论：**不建议**

### 实测数据
| 项 | 值 |
| --- | --- |
| C 盘 | 已用 169.9 GB / **剩余 26.4 GB** |
| E 盘 | 已用 22.9 GB / **剩余 153.2 GB** |
| 整个 `WorkBuddy` 目录 | **约 987 MB**，16 个时间戳会话工作区 |
| 其中 D-Bee 仓库 | **960.4 MB / 62,013 文件**（占 97%，主体是 `node_modules`、`dist*`、归档包等**可再生**产物） |
| 其余 15 个会话工作区合计 | 约 27 MB（多数为空或个位数文件） |
| 硬编码 C 盘路径 | `.workbuddy/memory/**` 中 19 个 md 命中；仓库 `docs/` 中 3 处 `cd` 命令；4 个 automation `memory.md` |
| 应用侧路径绑定 | `C:\Users\yuty\.workbuddy\` 下 `artifact-index/*.json`、`sidebar-list-snapshot.json`、SQLite 索引等**大量**引用会话目录 ID（只读 grep 即命中 ≥20 个 JSON） |

### 四条否决理由
1. **收益极小**：整体搬走只省 **<1 GB**，相对 C 盘 26.4 GB 剩余空间约 3.7%，不解决空间问题；而 960 MB 里绝大部分是可再生构建产物。
2. **该目录不是普通文件夹，是 WorkBuddy 的会话工作区根**：16 个子目录名即会话 ID。移动后**当前会话立即失效**（本会话 cwd 就是 `…\2026-10-17-09-57-18`），工具调用、记忆注入、相对路径全断。
3. **应用内部索引无法手工迁移**：`C:\Users\yuty\.workbuddy` 下的 artifact 索引、侧边栏快照、SQLite 映射库大量记录 C 盘绝对路径；这些是应用托管状态，不属于可批量文本替换的用户文件。
4. **自动化任务会全部跑空**：4 个定时任务的 `cwds` 与其 `memory.md` 都锚在 C 盘会话目录（含本自动化），任务须由平台侧重建，改文件无效。

### 按目的给方案

| 目的 | 推荐方案 |
| --- | --- |
| **只是想给 C 盘腾空间** | ✅ **方案 A：NTFS 目录联接（推荐）**——物理放 E 盘、逻辑仍走 C 盘，应用与全部历史路径零感知：<br>`robocopy "C:\…\目录" "E:\…\目录" /E /COPYALL`（先复制）<br>→ 验证副本 → 源目录改名 `.bak` → `mklink /J "C:\…\目录" "E:\…\目录"` → 验证 → 最后才删 `.bak`<br>🔴 **先备份、逐目录小批、每步验证**；`release/` 里的 vc17 正式包是唯一归档，绝不删 |
| **想把代码统一放 E 盘开发** | ⚠️ **方案 B：只搬 git 仓库**（最独立的一块）：`git clone` 到 `E:\dev\zilv-mifeng` → 更新记忆指针、3 处 docs `cd`、自动化 `cwds` → 在 WorkBuddy 里以新路径重开会话。代价是当前会话与历史上下文需重建，且违反「同一任务只在一个会话执行」的连续性 |
| **整体搬 16 个会话工作区** | 🚫 **方案 C：不推荐**——需同步改应用内部索引 + 重建全部自动化 + 重建所有会话，成本高、收益 <1 GB，风险与收益严重不匹配 |

> ⚠️ 以上均为**方案，本次未执行**。如后续要动，需你明确指定目标目录与范围，先做完整备份，并逐目录验证；我不会自行移动或删除任何文件。

### 一个更划算的替代
如果真实痛点是 C 盘空间，优先清理**可再生**产物（`node_modules` / `dist` / 缓存），或把 `backups/`、`release/` 的历史大文件单独挪到 E 盘并用 junction 挂回；比整体迁移安全得多，且不动会话体系。
