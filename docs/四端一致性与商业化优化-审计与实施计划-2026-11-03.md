> 生成：2026-11-03 ｜ 版本：1.7.3 ｜ 审计范围：web（`src/`）、iOS、Android（Capacitor 复用 `src/`）、小程序（`mini/`，Taro 独立库）

## 〇、结论速览

**好消息**：主端（web/iOS/Android 同源）的商业化与合规逻辑**已经相当扎实**——iOS IAP 核销闭环（延迟 finish + 持久化待核销 + `transaction_id` 全服幂等 + 换账号重放 409）、网关侧验签（bundle_id 钉扎 + x5c 证书链 + 收据只存 sha256）、退款撤销、`GREATEST` 防续订乱序、iOS 价格护栏、AI 显式标识（11-03 刚补）、隐私同意门、七方 SDK 公示。**未发现硬编码真实密钥**。

**真问题集中在小程序端**。小程序是独立代码库，仅通过 `@dbee/shared` 共享常量，`mini/src/lib/` 有 **16 个与主端同名的文件已大幅分叉**（`foodInsight` diff 800 行、`notifications` 318、`validate` 286、`share` 205、`kv` 179）。分叉带来 3 个 🔴 阻断级问题：

| # | 问题 | 级别 | 一句话 |
| - | ---- | ---- | ------ |
| 1 | **小程序无免费录入兜底，且付费墙宣传与功能不符** | 🔴 | 唯一录入路径 = 消耗付费额度的 AI 拍照；额度用尽后**用户完全无法记录饮食**，而付费墙却写着「手动录入全部免费」 |
| 2 | **小程序缺 AI 生成显式标识** | 🔴 | 4 处 AI 输出渲染点全无标识，《标识办法》第四条（2025-09-01 已施行）合规缺口；微信深度合成类目审核同样会查 |
| 3 | **小程序 AI 配额 fail-open** | 🔴 | RPC 故障时回退「先读后写」（并发可超发）、额度查询出错静默返回满额（绕过预检）；与主端 fail-closed 口径**相反** |

另有 5 项 🟠 高、6 项 🟡 中，见 §二。

**商业化判断**：D-Bee 当前定价（¥18/月、¥128/年、¥298/终身）在竞品带里**位置正确**——与薄荷健康年卡（¥128）持平、显著低于自律茄子（年 ¥148–298、终身 ¥328）。**价格不是问题，免费额度的"真实可用性"才是**：自律茄子被差评淹没的核心不是贵，而是「80% 功能收费、连文字输入都要钱、免费试用 3 天强制扣费」。D-Bee 主端的免费设计（3 次/日拍照 + 积分兑换 + 条码永久免费 + 手动录入免费 + 问答免费）恰好是它的反面，**但小程序端把这个优势破掉了**（见 §二.1）。

## 二、风险清单（按级别排序，每条含证据与修法）

### 🔴 P0-1｜小程序无免费录入兜底 + 付费墙虚假宣传

**事实**：
- 小程序首页跳转只有 `goLogin/goScan/goReport/goProfile/goInvite/goCoach/goLeaderboard`（`mini/src/pages/index/index.tsx:342-348`）——**添加餐食的唯一入口是 `goScan`（AI 拍照）**。
- 食谱页不能新建，只能对「拍照识别后存为食谱」的结果点「记一餐」；空态文案自己写明：「拍照识别后，在识别结果里点『存为食谱』即可创建」（`mini/src/pages/recipes/recipes.tsx:120-123,136-142`）。
- 小程序无本地食物库（`mini/src/` 无 `foodsData*`、无 `lookupFood/searchFood`）。
- 但付费墙宣传：「手动录入、体重饮水运动记录全部免费」（`mini/src/pages/paywall/paywall.tsx:38`）。

**风险**：
1. **宣传与功能不符** —— 微信审核（虚假宣传）+ 《消费者权益保护法》风险；且该文件 L43-45 注释显示团队**已经有"文案须如实反映端能力"的原则**（为「扫条码」「文字描述」做过删除），唯独漏了「手动录入」这条。
2. **留存致命伤** —— 免费 3 次/日用尽且无积分可兑时，用户在小程序端**一整天无法记录任何饮食**。这正是竞品自律茄子被差评淹没的同一死穴（「总共就几个功能，全都收费」「想用文字输入，结果发现也是收费的」）。小程序是拉新主入口，此处断裂 = 转化前先流失。

**修法（二选一，建议 A+B 同时）**：
- **A（必做，0.5 天）**：付费墙文案删掉「手动录入」，改为如实描述（同 L43-45 既有原则）。
- **B（建议，2–3 天）**：小程序补**免费手动录入**——最轻实现是「自定义一餐」：用户填名称 + 克数 + 每 100g 营养（或直接填总 kcal），不依赖食物库，写入同一张 `meal_entries`。这是免费兜底，**不消耗任何 AI 额度**，且与主端 `source:'manual'` 口径一致。

### 🔴 P0-2｜小程序缺 AI 生成显式标识（合规硬缺口）

**事实**：小程序 4 处 AI 输出渲染点**全无标识**：
| 渲染点 | 位置 |
| ------ | ---- |
| AI 教练问答（流式） | `mini/src/pages/coach/coach.tsx:128` |
| 报告「本期解读」 | `mini/src/pages/report/report.tsx:423-431` |
| 首页「给你的建议」（onboarding AI 生成 `plan_summary`） | `mini/src/pages/index/index.tsx:256-265,697` |
| 拍照识别结果 | `mini/src/pages/scan/scan.tsx:140-164` |

仅有法务文字声明「属于人工智能生成合成内容」（`mini/src/content/legal.ts:189-195`），**未提显式标识**；`grep AiLabel mini/src/` 零命中。

**风险**：《人工智能生成合成内容标识办法》第四条（一）**2025-09-01 已施行**，要求在交互界面、文字周边加显著提示标识；第八条要求在用户服务协议中说明标识方法与样式。主端 11-03 已补齐，小程序端**未同步 = 同一产品双标**。微信「深度合成」类目审核也会核验标识材料，缺失可能导致类目不过（而 AI 功能必需该类目）。

**修法（1 天）**：
1. 移植 `AiLabel` 到 `mini/src/components/AiLabel.tsx`（Taro 版：`View`/`Text` 替代 `div`/`span`，样式进 `.scss`）。
2. 四处接入，口径与主端**逐字一致**（对话标题徽章 + 输入区上方常驻行；解读标题徽章 + 正文下方行；识别条目名旁徽章；首页建议区行内标识）。
3. `mini/src/content/legal.ts` 四之一补标识方法条款（照主端 11-03 新增那段改写，注意小程序法务文案不可照抄主端——`legal.ts:12-26` 有明示）。

### 🔴 P0-3｜小程序 AI 配额 fail-open（与主端口径相反）

**事实**：
- `mini/src/lib/api.ts:590-595` —— `consumeAiQuota` 在 RPC 抛错时**回退「先读后写」**（`getUsage` → 判断 → `bumpUsage`），非原子，并发可超发；且返回 `allowed:true`（fail-open）。
- `mini/src/lib/api.ts:602` —— `getPhotoQuota` 出错时**静默返回满额** `FREE_DAILY_AI`，绕过额度预检。
- 对照主端 `src/lib/api.ts:424-448` —— RPC 不可用返回 `{allowed:false, degraded:true}`（**fail-closed**），且 `LogSheet.tsx:537-564` 区分「服务降级」（不弹付费墙）与「额度用尽」（引导升级）。
- 注：`consumePhotoQuota`（`:640`）两端都是 fail-closed，一致。

**风险**：云库抖动时小程序端**白送 AI 次数**（资损，每次调用真金白银的模型费）；`getPhotoQuota` 满额假象会让用户点了拍照才在 `consumePhotoQuota` 处被拒（体验断裂）。

**修法（0.5 天）**：`consumeAiQuota` 的 catch 分支改为返回 `{allowed:false, degraded:true}`；`getPhotoQuota` 出错返回 `{..., degraded:true}` 而非满额，UI 侧按主端 `guardAiQuota` 口径处理（降级时**不弹付费墙**，给「服务繁忙请稍后再试」）。⚠️ 需同步补 `QuotaResult` 的 `degraded` 字段（主端已有）。

### 🟠 P1-4｜`mini/src/lib/api.ts:9` 注释与实际架构矛盾（误导维护者）

**事实**：注释称「四端共用同一后端，任一端的读写都会同步」；而同目录 `cloud.ts:14-28` 已更正为「与主工程不是同一后端、数据不互通」。**两份文档性注释直接打架**。

**风险**：后续开发者若信 `api.ts:9`，会写出「在小程序改数据、期望 App 端同步可见」的错误假设（例如演示账户、客服排障、数据迁移方案）。

**修法（10 分钟）**：改注释为指向 `cloud.ts` 的准确表述。**顺带做一次决策**：小程序是否回迁自托管网关（记忆里这是待拍板项⑥，须同步改 `mini/src/lib/cloud.ts` + `legal.ts` 公示主体）。

### 🟠 P1-5｜Android/web 在线支付为占位，四端收费能力不一致

**事实**：`src/lib/payment/wechatPay.ts:169-172`、`alipay.ts:142-145` 的 `fetchPrepayParams` 均 `return null`（注释「TODO(资质就绪后补)」），缺 `VITE_WECHAT_APPID`/`VITE_ALIPAY_APPID` 时 adapter 返回 null → checkout 诚实提示「暂不支持在线支付」（不崩溃）。

**现状评估**：**这不是缺陷，是诚实降级**——变现当前实际只靠 iOS IAP + 兑换码。但「四端收费逻辑一致」这一目标**尚未成立**。

**修法**：依赖商户号资质（记忆里待拍板项④「短信签约/商户号」）。资质到位后补服务端统一下单端点 + 前端 `fetchPrepayParams` 实装。**建议同期决策 Android 端是否也隐藏兑换码**——若 Android 走各应用商店（华为/小米）分发，商店同样可能禁止绕过内购；当前 Android 兑换码可见（`PaywallSheet.tsx:393` 只排除 iOS）。

### 🟠 P1-6｜法务文案双副本漂移

**事实**：主端 `src/content/legal.ts` 更新日 11-02（含七方 SDK 公示、AI 标识条款）；小程序 `mini/src/content/legal.ts` 更新日 10-29，四之一**缺 AI 标识条款**，公示主体不同（小程序为 WorkBuddy 云平台），且声明「免费提供，不销售任何商品，不涉及在线支付」（`:80`）。

**风险**：两端法务口径不同步 = 合规审计时说不清；小程序那句「不涉及在线支付」在补支付能力后**必须同步改**，否则文案造假。

**修法**：法务文案**不建议强行同源**（`legal.ts:12-26` 明示两端主体/能力不同，不可照抄），但应建立**变更联动清单**：任一端改法务 → 检查另一端对应条款。本轮 P0-2 的第 3 步即第一次联动。

### 🟠 P1-7｜小程序无首启隐私同意门

**事实**：`mini/src/app.ts` 为空壳（仅 console.log），无自建隐私门；仅有 AI 使用同意弹窗（`mini/src/components/AiConsent.tsx`，本地 `dbee:ai_consent` + 云端 `ai_consented`，已对齐主端）。

**评估**：微信小程序有平台侧隐私协议机制（`__usePrivacyCheck__` + `requiredPrivateInfos`），**可能已由平台承担**。但仓库内看不到 `app.config.ts` 的隐私配置，**未查明**。

**修法**：先核实 `mini/src/app.config.ts` 是否配了 `__usePrivacyCheck__` 与隐私接口声明；若平台机制已覆盖则**记录结论即可**（不必自建门，避免双重弹窗）；若未覆盖则补。

### 3.3 薄荷健康的护城河与可借鉴点

**护城河（短期无法追赶，不必硬拼）**：160万+ 食物库、18 年数据积累、1.8亿用户、实体商品闭环（减脂餐 ¥690–2090）、体脂秤硬件联动、9 项超级会员特权。

**可借鉴（低成本高收益）**：
1. **打卡送会员时长** —— 薄荷「定期开启减脂打卡活动，完成任务可领取会员时长」。D-Bee 已有蜜糖积分 + 连续打卡体系（`streak7` 送拍照次数），**只差把"积分兑换 Pro 天数"做成运营活动**（`HONEY_PRICE.pro1Day=100`/`pro30Day=2600` 已实现，缺曝光位）。
2. **去广告作为会员权益** —— 薄荷会员特权含「去开屏广告」。D-Bee 无广告，**这反而是可宣传的免费卖点**（"永久无广告"应写进付费墙的免费项）。
3. **减重周报** —— 薄荷会员专属。D-Bee 已有「本期解读」（AI 长文本复盘，Pro 专属），**形态等价，命名可更直白**（"减重周报"比"本期解读"更有获得感）。
4. **咖啡因统计** —— 薄荷会员特权里的细分刚需。D-Bee 食物库若含咖啡因字段，**可低成本做成免费差异化功能**（饮品记录场景高频）。
5. **食物库是硬短板** —— 1175 条 vs 百万级。但 D-Bee 的路线是「AI 识别为主 + 小库兜底」，与自律茄子同路线。**建议不要硬拼库规模**，而是把「AI 识别 + 存为食谱 + 食谱复用」这条链路做顺（小程序食谱页已有雏形），让用户的**私有食谱库**成为留存资产——这是薄荷的大库给不了的。

### 3.4 食卡卡的启示

第三方测评把食卡卡评为「性价比之王：免费功能覆盖 80% 核心需求，拍照识别 <1s、误差 <5%」。**这正是 D-Bee 应该占的定位**——D-Bee 的免费额度设计已接近，缺的是①小程序端补齐免费兜底 ②识别速度与精度的实测数据（可作为宣传素材，但必须先真测）。

1. **vitest EPERM 假绿**：`npm test` 整批跑可能只收集到部分文件（11-03 实测 17/47），`rm -rf node_modules/.vite` 有时无效。**可靠做法 = 逐文件 `npx vitest run <单文件>` 再加总**。
