## 〇、这一阶段到底要做什么

改造方案阶段 2 的目标：让 Web 端「去微信小程序下单」的引导，从**纯文字兜底**（让用户自己去微信里搜）升级为**扫码直达 / 一键直达**。

外部依赖三件（**均无法由代码完成，须人工在微信公众平台操作**）：

1. 小程序**工信部备案通过**（当前用户告知「管局审核中」）；
2. 小程序**已发布**（线上版本存在，静态码才指向真实可用的包）；
3. 在 **MP 后台生成静态小程序码**（指向 `pages/paywall/paywall`）。

在这三件就绪之前，**当前默认构建已经是合规可用的**：售卖开关关闭，Web 只展示价格 + 明示「网页不收款」，引导退化为纯文字（且不出现「下单」字样）。本手册是「三件就绪后如何一步配好」的预案，**不是现在必须执行的动作**。

## 一、工程侧已就绪（无需改动，已验证）

阶段 2 的**配置通道**已在代码里建好并通过构建验证，拿到凭证后只需「填值 + 构建」，不需要改任何逻辑：

| 配置项 | 作用 | 校验 | 验证结论 |
| --- | --- | --- | --- |
| `D_BEE_XPAY_ENABLED` | 🔴 总开关：Web 引导 **与** mini 售卖**同源同值** | 只接受 `true`/`false`，非法值（如 `1`）**构建期 throw** | `=1` 已实测中断构建 ✅ |
| `VITE_MINI_ORDER_QR` | 静态小程序码图片路径（推荐） | 空则不渲染图片，走文字兜底 | `=/mini-order-qr.png` 已实测注入产物 ✅ |
| `VITE_MINI_ORDER_LINK` | URL Link（二期，需 AppSecret 签发） | **只放行 https**，`javascript:`/`data:`/`http:`/相对路径一律过滤为空 | 护栏 W8 纯函数单测覆盖 ✅ |
| `VITE_MINI_APP_NAME` | 小程序名称 | 默认 `自律蜜蜂`（A1 定案值） | — |

**三种凭证形态的渲染优先级**（`MiniOrderGuide.tsx`）：
- 配了 `VITE_MINI_ORDER_QR` → 渲染小程序码图片 +「用微信扫一扫」；
- 否则配了 `VITE_MINI_ORDER_LINK`（且为合法 https）→ 渲染「在手机微信中打开小程序下单」链接；
- 都没配 → 渲染「在微信中搜索小程序『自律蜜蜂』」纯文字，**绝不渲染点了没反应的死按钮**。

## 二、拿到静态码后的落地步骤（5 步）

### 步骤 1 · 在 MP 后台生成静态小程序码

- 登录微信公众平台（mp.weixin.qq.com）→ 目标小程序 → **工具 → 生成小程序码**（或「小程序码及线下物料下载」）。
- 页面路径填：`pages/paywall/paywall`（付费墙页，用户扫码后直达选档）。
- 🔴 **刻意不带商品参数**：Web 只展示定价、档位在小程序内选，因此不需要 AppSecret、不需要 URL Link 签发服务、不需要参数签名。若日后要「点某档直达」，再上 URL Link（二期，需服务端）。
- 下载得到 PNG（建议尺寸 ≥ 280×280，保证扫码清晰）。

### 步骤 2 · 放入 public/

- 将图片重命名为 `mini-order-qr.png`（**固定名**，与下方配置值对应），放到项目根 `public/`。
- vite 会把 `public/` 下的文件原样拷进 `dist/` 根，故构建后路径即 `/mini-order-qr.png`。
- 校验：`ls public/mini-order-qr.png` 存在。

### 步骤 3 · 配置环境变量并构建

在项目根执行（Web）：

```bash
D_BEE_XPAY_ENABLED=true \
VITE_MINI_ORDER_QR="/mini-order-qr.png" \
npm run build
```

构建日志应出现：
```
[vite] ⚠️ 已开启小程序售卖引导（D_BEE_XPAY_ENABLED=true）：……发布前请确认：
① mini 端已用同一变量构建并上传（否则引导指向一个不卖东西的小程序）；
② 静态小程序码已放 public/ 且 VITE_MINI_ORDER_QR 已配置。
```

### 步骤 4 · 🔴 mini 端必须同值构建并上传（同源的硬要求）

Web 开了引导，mini 就**必须**同一次发版一起开售卖，否则用户扫码进去发现「免费提供、不销售」= 虚假宣传。在 `mini/` 目录：

```bash
D_BEE_XPAY_ENABLED=true npm run build:weapp
```

然后按 `docs/待办清单-云库废弃收尾-2026-11-08.md` §十一 完成 mini 上传新版本号 + 重设体验版 + 提审。两端读的是**同一个环境变量名**，一个变量同时决定两端卖不卖，运维不可能只开一端（除非故意分别构建）。

### 步骤 5 · 部署前验收（铁律 #13：生产侧实测）

- 部署 `dist/` 到 `https://d-bee.cn/`（部署流程见 `deploy/`，🔴 绝不跑 `deploy-gateway.sh`）。
- 线上产物解码校验（Web 主端产物是 **UTF-8 直存中文**，不是 mini 的 `\uXXXX` 转义，直接 UTF-8 读）：
  ```bash
  python - <<'PY'
  import glob, os
  js = max(glob.glob('dist/assets/index-*.js'), key=os.path.getsize)
  a = open(js,'rb').read().decode('utf-8','replace')
  for s in ['/mini-order-qr.png','用微信「扫一扫」打开小程序','内完成下单','网页版仅展示价格']:
      print(f"  {a.count(s):>3}  {s}")
  PY
  ```
  期望：四个探针均 `>0`。
- 真机微信扫码 → 进小程序付费墙 → 确认能选档下单 → **同一账号在 Web 看到 Pro 生效**（依赖阶段 4 权益互通，当前未上线，见改造方案 §四）。

## 三、🔴 当前为什么「不开」——发布决策前置

**默认构建 = 开关关闭**，这是刻意的安全默认。要开启引导，以下必须**全部**就绪（缺一即虚假宣传 / 审核驳回）：

- [ ] 小程序工信部备案通过（当前：管局审核中）；
- [ ] 小程序已发布，静态码指向真实可用版本；
- [ ] 静态小程序码已生成并放 `public/mini-order-qr.png`；
- [ ] mini 端虚拟支付前置全部就绪（`mini/src/lib/xpayEnabled.ts` 文件头 ①~⑥ + 待办清单 §十一 的 6 项）；
- [ ] mini 端已用 `D_BEE_XPAY_ENABLED=true` 构建并上传新版本；
- [ ] 🟠 `LEGAL_UPDATED` 是否刷新（全体老用户重弹同意窗）—— **留产品拍板**，本手册不擅自决定。

**在上述全部就绪前，Web 保持默认构建（零引导字样），与 mini「免费提供」公示一致 —— 这本身就是合规状态，不需要为了「有引导」而提前开。**
