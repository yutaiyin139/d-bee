## 一、硬性政策门槛（2026-10-23 核查）

### 1.1 中国区上架强制 ICP 备案号 ⚠️ 最高优先级外部流程

- Apple「App 信息」页面有 **ICP 备案号字段**：向中国大陆供应的 App 必须按工信部要求提供有效备案编号。
- **中国企业开发者被强制执行**；ICP 号码和 App 元数据（名称等）必须与工信部备案信息**一致**。
- 特殊类别（游戏需版号、图书需出版许可、新闻/宗教需专门许可）——**D-Bee（健康饮食记录）不属于任何特殊类别**，只需标准 App 备案。
- 依赖链：App 备案通常要求**已备案域名 + 服务器在中国大陆**（腾讯云 150.158.51.106 满足）→ 我们的「备案域名 + HTTPS」数据面切换工作与 App 备案是**同一条线**，一次办完。
- 参考：《备案材料清单.md》已备好材料清单；主体注册（等公章）是前置。

### 1.2 Xcode 26 构建截止日

- **2026-04-28 起**，上传到 App Store Connect 的构建必须用 **Xcode 26+（iOS 26 SDK）**。
- 今晚编译环境已要求 Xcode 26+（Capacitor 8 硬要求），**天然满足**，无额外动作。

### 1.3 新年龄分级系统

- **2026-01-31 起** Apple 启用新年龄分级体系；提交新 App/更新时 ASC 会要求回答**新的分级问卷**。
- D-Bee 预期分级：4+（无暴力/色情/赌博内容；健康饮食类）。提交时按实回答即可，无代码动作。

### 1.4 审核指南 3.1.2（订阅）合规要点

| 要求                                  | 现状                                              | 动作         |
| ----------------------------------- | ----------------------------------------------- | ---------- |
| 订阅期 ≥7 天、跨设备可用、持续价值                 | ✅ 月/年订阅 + entitlements 云端存储                     | 无          |
| **付费墙内**含可用的《使用条款》(EULA) + 《隐私政策》链接 | ❌ **缺失**（PaywallSheet 无任何法律链接，LegalPage 只能从页脚进） | **代码改造 ⑤** |
| ASC 元数据（App 描述/订阅信息）也含两链接           | ⏸ 提审时填写                                         | ASC 配置 ⑩   |
| 被计费金额是最醒目价格元素                       | ✅ 已接商店本地化价格（轮 7 `dfa3191`）                      | 无          |
| 恢复购买入口                              | ✅ 付费墙已有「恢复购买」按钮                                 | 无          |

## 二、代码侧缺口（我可立即做，合计约 1 天）

### ⑤ 付费墙补法律链接（3.1.2 硬要求，缺了必被拒）

- 现状：`PaywallSheet.tsx` 无 ToS/隐私链接；`LegalPage` 由 `App.tsx` 顶层 state 控制，但 `PaywallSheet` 拿不到 `setLegal`。
- 改造：把 `onOpenLegal` 传入 `PaywallSheet`（或经 context），在付费墙底部加一行  
  「购买即表示同意《使用条款》与《隐私政策》」，点击打开对应 LegalPage。
- 同时核对 `src/content/legal.ts` 中 terms/privacy 正文是否含**订阅条款要素**（价格、周期、自动续期说明、取消方式）——3.1.2 要求 EULA 覆盖这些；不足则补一段「订阅与自动续费说明」。

### ⑥ iOS 版隐藏兑换码入口（3.1.1 拒因）

- 现状：付费墙内兑换码输入框对**所有平台**展示，且文案「在线支付…正在接入中，上线前可先用兑换码体验完整功能」明示兑换码是付费替代通道——Apple 会认定为绕过 IAP。
- 改造：`isIOS()` 时隐藏兑换码区块与该文案（web/Android 保留，它们不受 App Store 规则约束）。
- 注意：**邀请中心的蜂蜜兑换（redeemHoney）不用动**——那是用应用内 earned 积分兑换，属 3.1.1 允许的虚拟货币范畴，不是外部付费通道。只藏「输入外部兑换码」这一个入口。

### ⑦ 审核演示账户（✅ 10-28 已落地：邮箱 + 密码）

- 问题：登录靠验证码（手机短信 / 邮箱 OTP），审核员没有我们的手机号也收不到我们邮箱的信 → 无法进入 App → 必被拒（2.1 App Completeness）。
- **已采用方案**：邮箱 + 密码账户 `dbeesupport@163.com` / `888888`，并在 `AuthScreen.tsx` 新增「邮箱密码登录」入口（SDK `signInWithPassword`，注册时已带密码）。填报口径与备注原文见《AppStore产品页-填报包-2026-10-28.md》§六。
- 建号方式：云端 `signUp` 必须带 OTP 验证令牌、云端用户管理接口只读 → 用 `tools/setup-review-account.mjs`（send / verify / check 三步）走一次真实邮箱验证码注册。
- ⚠️ **备注必须写清登录路径**：邮箱通道默认显示「获取验证码」，密码登录是文字链入口，审核员若不知道点它会卡在发码环节 → 依然 2.1 被拒。
- ❌ **原「固定测试手机号 + 演示码」方案对 iOS 无效**：`DEMO_PHONE`/`DEMO_CODE` 实现在**自建网关**（`server/lib/config.mjs`、`server/lib/app.mjs:42`），而 iOS 端目前仍连云端（`VITE_NATIVE_ENDPOINT` 从未注入 → 回退 `CLOUD_HOST`）。HTTPS + 域名切换完成、三端指向 `https://d-bee.cn` 之后，网关侧那套才具备实际意义；届时若仍想保留手机号演示通道，注意 `DEMO_CODE` 不得等于 `SMS_MASTER_CODE`（`888888`，`config.validate` 会拒启动）——**本次的演示密码正好是 888888，两者不可混用于同一套配置**。

## 四、App Store Connect 配置（账号就绪后，约半天）

1. **建 App**：Bundle ID `cn.com.dbee.app`（与工程 `capacitor.config.ts` 一致；⚠️ 弃用史：`com.dbee.app` 被抢注 → `cn.dbeehealth.app` 不可用 → 定案 `cn.com.dbee.app`，2026-10-25），SKU 自定，主要语言 zh-Hans。
2. **App 信息页**：填 **ICP 备案号**（1.1，中国区必填）、分类（健康健美）、年龄分级问卷（1.3 新版）。
3. **IAP 商品 3 个**（ID 必须与代码 `PRODUCT_IDS` 逐字一致）：
   - `dbee_pro_monthly`：自动续期订阅，¥18/月，订阅组 `dbee_pro`
   - `dbee_pro_yearly`：自动续期订阅，¥128/年，**同一订阅组**
   - `dbee_lifetime`：非消耗型，¥298
   - 每个商品需：中英文名称/描述、审核截图、定价。
4. **付费应用协议**：接受协议 + 对公银行 + 税务信息 → 状态「有效」是沙盒/生产购买的前提。
5. **共享密钥**（App-Specific Shared Secret）：生成后配到服务端 `APPLE_SHARED_SECRET`（A1 部署项，见五）。
6. **App 隐私标签**：如实申报数据收集（手机号、健康数据、饮食记录、照片）——需与 `legal.ts` 隐私政策一致。
7. **元数据**：描述、关键词、支持 URL、营销 URL；**订阅信息区填 ToS + 隐私政策 URL**（3.1.2 第二处要求——需公网可访问的 URL，依赖备案域名 + HTTPS，可先临时挂 GitHub Pages 过渡）。
8. **演示账户**：按 ⑦ 已落地方案填邮箱 + 密码 `dbeesupport@163.com` / `888888`，**备注必须写清登录路径**（登录页 →「邮箱」tab → 文字链「已有密码？点此用密码登录」），备注原文见《AppStore产品页-填报包-2026-10-28.md》§六。⚠️ 提审前须先跑通 `node tools/setup-review-account.mjs check` 确认该账户已注册可登录。
9. **截图与创意素材**（两套独立资产，比例不同不可互相缩放）：
   - **设备截图（必填）**：Apple 2026-10 起 iPhone 必填槽位为 **6.3" 中型屏 1179×2556 / 1206×2622**（旧资料写的「6.9"+6.5" 必传」已过期）；本工程 `TARGETED_DEVICE_FAMILY="1,2"` → **iPad 13" 同为必填**（2048×2732）。各 5 张已出，见《填报包》§五。
   - **创意素材（选填）**：产品页面标题 / 搜索结果版位的横版营销图，16:9 → **5244×2950（仅 PNG）**、3:2 → **3840×2560** 与 **1920×1280**；**不得含 alpha 通道**。3 张已出，见《填报包》§五·补。

## 五、服务端（我可做）

| 项           | 内容                                                                                                    | 依赖                                                                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **A1 部署**   | 执行 0037 迁移（apple 核销 RPC 分支）+ 网关配 `APPLE_SHARED_SECRET` 等 env → 验签端点 `/.cloud/payment/apple/verify` 生效 | 无外部依赖，随时可做；**但注意：iOS 数据面当前=云库，A1 只对「数据面切回自建」后生效**。切回前 IAP 核销仍走云库 RPC 的 fail-closed 分支 → 生产购买会「支付校验失败」。所以 **A1 与数据面切换必须同批完成**，否则上架后 IAP 不可用 |
| **数据面切换**   | iOS endpoint 从 `CLOUD_HOST` 切到自建网关                                                                    | **备案域名 + HTTPS**（与 1.1 同一条线）                                                                                                               |
| **短信切换**    | 🟢 **审核已通过（10-27）**。一条命令：`SMS_PROVIDER=tencent DBEE_PROD=1 SMS_TENCENT_*=... bash deploy/deploy-gateway.sh`（脚本自动摘除万能码）。⚠️ 连带效应：`DBEE_PROD=1` 会使 Apple 收据默认只收 Production → 提审期须同时带 `APPLE_ALLOWED_ENVS=Sandbox,Production` | ~~短信协议签署（等公章）~~ ✅ 已解锁                                                                                                                  |
| **webhook** | App Store Server Notifications V2 URL 配到 ASC                                                          | 备案域名 + HTTPS + A1                                                                                                                          |
| **演示账户**    | 邮箱 + 密码账户 `dbeesupport@163.com`/`888888`（⑦ 已落地；原「测试手机号固定验证码通道」对 iOS 无效，因 iOS 连云端而非自建网关）→ 提审前跑 `node tools/setup-review-account.mjs check` 确认可登录 | 提审前完成                                                                                                                                      |

**关键结论：IAP 生产可用的完整链条 = A1 + 数据面切换 + 备案 HTTPS + ASC 商品/付费协议。** 四者缺一，上架后购买就会失败。这意味着**首次提审的构建必须等数据面切换完成**——否则用户付款后权益不到账（比被拒更糟）。

## 六、构建与提审流程（一切就绪后）

1. Mac：Xcode 26 → `Product → Archive`（Release，签名用企业证书 + `cn.com.dbee.app` 的 Distribution provisioning profile）。
2. Organizer → Distribute App → App Store Connect → Upload。
3. ASC 选构建 → **TestFlight**：内部测试（自己人，即时）→ 外部测试（可选，需 Beta 审核）。
4. TestFlight 里跑**沙盒购买全链路**（真实 Apple 沙盒账户）：购买→核销→权益到账→恢复购买→退款通知（webhook）。**这一步通过才有资格提审**——它验证的正是五的完整链条。
5. 填齐元数据/截图/分级/演示账户 → 提交审核。
6. 首次审核周期通常 24~48h；被拒后按 Resolution Center 回复整改（常见拒因已全部预防，见 1.4 表）。
