## 1. 为什么是亮点

| 维度 | 逐家厂商 SDK | Health Connect 统一层 |
|---|---|---|
| 接入成本 | 华为 / 小米 / vivo / OPPO 各一套：开发者账号、服务申请、签名指纹、审核 | 一套系统级 API，一次授权 |
| 维护成本 | N 套 SDK 版本、N 份资质年审、N 个后台配置 | 1 套 |
| 设备覆盖 | 只覆盖该品牌自家手环/手表 | 所有愿意写入 Health Connect 的 App 与设备（含第三方手环、体脂秤） |
| 与现有架构 | 每家一个适配器 | 与 `healthkit.ts` / `android.ts` **同构的第三适配器**，门面/UI/计算零改动 |

- 是既有决策「不直连手环、只读系统健康平台」的**自然延伸**，不是新增一条技术路线。
- 产品话术方向：**一次连接，通吃穿戴设备**。但对外文案必须以 §5 的 HC-0 实测覆盖表为准，
  不得宣称「全机型支持」（避免 §7 的宣传风险）。

## 2. 现实约束（诚实标注，不因「亮点」隐去）

- **国行覆盖率**：华为运动健康、vivo 健康、欢太健康（OPPO/一加）**未集成** Health Connect；
  小米 Mi Fitness 部分版本可在「第三方数据共享」里手动开启，但**重启会静默掉线**。
  国际版厂商 App / Wear OS / Zepp / Fitbit 等写入较完整。
- **系统条件**：Android 14 起 Health Connect 并入系统框架；低版本需安装 Health Connect APK。
  国内 ROM 是否预置、是否被裁剪，**必须用真机矩阵验证**，不能按 AOSP 文档推断。
- **权限与审核**：健康数据读取权限不是普通运行时权限；若走 Google Play 分发需提交健康类应用声明、
  隐私政策与数据用途说明。国内应用市场分发另需评估其健康数据合规要求。
- **合规**：健康数据属敏感个人信息，需单独告知 + 单独同意、撤销即删（隐私政策 §五 待拍板）。
  🔴 `legal.ts`「不构成医疗诊断」红线——即使读到心率/睡眠，也不得给诊断结论或疗效承诺。
- **结论**：亮点 = 架构与产品方向；覆盖率 = 需分期推进的工程事实。Health Connect 与厂商 SDK
  **并行不冲突**：前者覆盖广，后者覆盖 HC 未集成的国行机型且数据更全。

## 3. 目标架构

```
穿戴设备 / 厂商 App ──写入──> Health Connect（系统聚合层）
        ──读──> DbeeHealth Android 插件（Health Connect Client）
        ──> src/lib/health/connect.ts（第三适配器）
        ──> src/lib/health/index.ts 统一门面 ──> Dashboard（现有计算零改动）
```

- **新增 `src/lib/health/connect.ts`**：与 `healthkit.ts` / `android.ts` 同接口
  （`requestAuthorization` / `fetchToday` → `{ steps, activeKcal, status }`），沿用 7 态 `HealthSyncStatus`。
- **门面分派优先级**：iOS → HealthKit；Android → **Health Connect 优先**，
  厂商 SDK 作为补充覆盖；两者都无 → 引导（沿用 `healthStatusHint`，不引入第四态）。
- **品牌白名单升级为能力探测**：从 `SYNCABLE_ANDROID_VENDORS` 的「厂商白名单」
  改为「运行时是否具备 Health Connect 能力」，UI 只按真实能力显示连接入口。
- **`profiles.health_vendor`**：建议在 HC-2 一并引入，记录数据来源并解决
  同账号跨 iPhone / 安卓的单布尔串台问题（当前 `health_connected` 无来源字段）。
- **计算口径不动**：`max(手动 burnKcal, activityKcal)` × `ACTIVITY_EATBACK_RATIO = 0.5`，
  步幅法估算兜底；新增数据源只提供输入，不改业务规则。

## 4. 数据范围分期

| 期 | Health Connect 数据类型 | 落到 D-Bee | 约束 |
|---|---|---|---|
| **HC-1** | `StepsRecord` / `ActiveCaloriesBurnedRecord` / `DistanceRecord` | 当天 `steps` / `activeKcal` | 与现有两指标严格对齐；活动能量口径须核对是否含 BMR（华为方案 §4.1 同款风险） |
| **HC-2** | `WeightRecord` / `BodyFatRecord` | 体重打卡（手动 → 自动建议） | 隐私政策单独同意；只做记录，不做诊断 |
| **HC-3** | `SleepSessionRecord` / `HeartRateRecord` | 仅展示 | 🔴 不得出诊断色带 / 燃脂心率 / 疗效承诺 |
| **不做** | 血压 / 血糖 / 血氧 / ECG | — | 医疗化风险 + 资质，超出产品边界 |

## 5. 里程碑与验收

| # | 内容 | 交付物 | 验收 |
|---|---|---|---|
| **HC-0** | 真机覆盖率矩阵：品牌 × Android 版本 × 厂商 App 版本 → 能否写入 HC、重启是否掉线 | 《Health Connect 可用性表》 | 真机实测（需用户本人提供设备）；对外文案以此表为准 |
| **HC-1** | 插件接口占位 + 权限声明 + 隐私政策文案预留 | 零功能代码，可先合入 | 不依赖资质；四端护栏不回归 |
| **HC-2** | 读 steps / activeKcal + 7 态 status + 现有 `max` / 50% 计算不变 | 真同步可用 | 真机读数与厂商 App 数值对齐（小时级延迟允许）；红绿产物探针 |
| **HC-3** | 多源去重：同时段同类型按 `source` + 时间窗取聚合值，防步数翻倍 | 去重规则 + 护栏 | 双源并存时消耗不得虚高 |
| **HC-4** | 厂商 SDK 与 HC 双通道并存时的数据优先级 / 冲突处理 | 决策记录 | 与 P2 逐个推进节奏对齐 |
| **HC-5** | 对外表述、分享卡片、「一次连接」话术合规复核 | 文案清单 | 法务口径 + 不构成医疗诊断 |

每阶段一律走铁律 #13：**真机实测 + 红绿探针 + 四端护栏**；本地绿不等于线上绿。
护栏新增/放宽必须先红验证（本轮已示范：7 条新断言精准变红 → 改后 120/120 绿）。

## 6. 与其它主线的关系

- **华为 / 小米 SDK**（用户 17:51 拍板）：后面与软著 / App 备案**逐个推进**，本轮不启动。
  HC-0 覆盖率表出来后再评估哪些品牌仍值得单独接 SDK，避免重复投入。
- **vivo / OPPO**（用户 17:51 拍板）：生态合作申请**暂缓**。若 Health Connect 生态成熟，
  这两家可优先走统一层，而非逐家商务谈判。
- **iOS / Apple 健康**：用户确认已真机验证，与 Android 侧共用门面与计算口径，互不干扰。
- **微信小程序**：微信运动自成体系（`wx.getWeRunData`），不受 Health Connect 影响。

## 7. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 国行覆盖率低 | 「一次连接」宣传翻车 | 对外按 HC-0 实测表分机型表述；UI 按能力探测显示 |
| 用户未开启 / 重启掉线 | 步数恒 0，误以为没运动 | 7 态 `status` + `healthStatusHint` 给完整排查路径（沿用现有机制） |
| 多源重复计数 | 消耗虚高 → 越减越肥 | HC-3 去重 + 现有 `max` / 50% 口径不变 |
| 合规 / 审核 | 敏感个人信息、Play 健康类应用审核 | 隐私政策 §五、单独同意、撤销即删；医疗化数据不做 |
| 四端不一致 | 某端文案 / 状态不同 | 新增护栏钉死 shared 真源，改前红验证 |
