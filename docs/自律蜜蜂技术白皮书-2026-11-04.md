## 摘要

自律蜜蜂（D-Bee）是一款 AI 驱动的个人饮食与生活习惯记录软件。用户对着餐盘拍摄一张照片，系统即可自动识别菜品、估算分量与热量，并给出三大营养素及微营养素分析；扫描包装条码可秒速获取营养标签；同时支持饮水、体重、运动打卡，每日能量目标与实际消耗实时联动。

本软件在工程上的核心特征是**「一套业务逻辑、四端交付」**：单一 React 前端经 Capacitor 混合壳编译为 Web / iOS / Android 三端，另以 Taro 构建小程序端，通过独立共享包 `@dbee/shared` 收敛权益规则与数值口径，并以**自动化一致性护栏**（可执行测试）将跨端一致性从人工约定变为机器强制。

在算法层面，本软件采用**「本地规则引擎优先、AI 模型兜底」**的分层设计：食物画像、营养素配比、风险与益处发现等可确定性计算的部分，全部由纯函数离线引擎完成，不消耗用户 AI 配额、不产生网络请求；仅在拍照识别等真正需要视觉模型的环节调用大模型。这一设计在降低推理成本的同时，保证了分析结果的可复现与可解释。

在数据层面，本软件以 PostgreSQL 行级安全（RLS）策略 + `SECURITY DEFINER` 函数构建多租户隔离，用户标识以 HMAC-SHA256 加盐哈希存储、不落明文，支付核销经 Apple 官方验签与 JWS 三级证书链校验（含根证书 SHA-256 指纹钉扎）。

**合规声明**：本软件输出的所有热量与营养数值均为参考估算值，不构成医疗诊断、治疗建议或任何疗效承诺。软件定位为饮食记录与健康生活工具，不属于医疗器械或医疗服务范畴。

## 一、产品定位与设计理念

### 1.1 产品定位

| 维度 | 定位 |
|---|---|
| 品类 | 移动互联网 · 个人健康管理工具（饮食记录细分领域） |
| 一句话定位 | 「让每一口都吃得明白」—— AI 智能饮食伴侣 |
| 核心交互 | 拍照识别 + 条码扫描 + 多类型打卡 |
| 商业模式 | 免费版永久可用 + Pro 订阅 / 终身买断，统一定价 |

### 1.2 三条设计原则

**原则一：不卖「AI 神奇」，卖「能坚持下来」。**

市面同类产品普遍将 AI 识别作为核心付费点，并把免费额度压到极低（用户拍照两三次即触发付费墙）。自律蜜蜂的取舍相反：免费版提供**每日 3 次 AI 拍照识别 + 2 次积分兑换识别**、条码扫描**永久不限次**、AI 文字问答**不限次**（仅带防刷限流）、近期饮食报告免费可看。付费解锁的是「更长期限的报告回看、无限次识别、个性化膳食规划与数据导出」，而非「能不能用」。

**原则二：能用规则算清楚的，不用模型猜。**

食物画像引擎（`src/lib/foodInsight.ts`）是**纯函数、完全离线、不调用任何模型**的实现。它输出「这餐碳水偏多 / 蛋白质不足 / 钠超标」这类判断时，走的是确定性的阈值与配比计算，因此结果可复现、可解释、不消耗用户 AI 配额、断网可用。AI 额度只保留给「识别」这类真正需要视觉模型的环节。

**原则三：对外承诺必须由代码实证，不由营销文案决定。**

「永久无广告」在产品中是一条**代码常量**（`FREE_NO_ADS_ITEM`），其成立依据是全仓检索广告 SDK 关键字（admob / pangle / 穿山甲 / gdt / 优量汇 / unityads / adsense，以及小程序 `createRewardedVideoAd` / `createInterstitialAd` / `createBannerAd`）**零命中**，且法务文本已公示该承诺。代码注释中明确写入：将来若接入任何广告变现，必须先删除该常量并同步修改法务文本，否则构成虚假宣传。

## 二、总体架构

### 2.1 架构真相：不是四套代码，是两套

一个常见的误解是「四端 = 四套代码」。实际架构是**两套源码 + 一层共享**：

```
┌─────────────────────────────────────────────────────────────┐
│                   packages/shared (@dbee/shared)             │
│   权益规则 · 配额常量 · 定价 · 数值格式化 · 日期格式化 · 类型   │
│                    ← 唯一真相源，多端引用 →                    │
└──────────────────────────────┬──────────────────────────────┘
                               │
        ┌──────────────────────┴──────────────────────┐
        │                                             │
┌───────▼────────┐                            ┌───────▼────────┐
│   src/ (主端)   │                            │  mini/ (小程序) │
│ React18+Vite5+TS│                            │    Taro 4.3.0   │
└───────┬────────┘                            └───────┬────────┘
        │                                             │
   Capacitor 8.5.3                              编译为微信/支付宝
        │                                       /抖音小程序
   ┌────┼────┐
   │    │    │
┌──▼─┐┌─▼──┐┌▼────┐
│Web ││iOS ││Andr │
└────┘└────┘└─────┘
```

- **主端 `src/`**：经 Capacitor 混合壳同时产出 Web、iOS、Android 三端。三端共用同一份 React 代码，平台差异只通过 `src/lib/` 抽象层处理。
- **小程序 `mini/`**：Taro 4.3.0 独立工程（小程序运行时与 WebView 差异过大，无法共用 React 代码），但**业务规则从 `@dbee/shared` 引用**，不复制常量副本。

### 2.2 服务端与数据层

| 层 | 技术选型 | 说明 |
|---|---|---|
| 接入层 | Nginx | 反向代理、TLS 终结 |
| 网关层 | Node.js 22.22.2（ESM） | `server/index.mjs` + 13 个 lib 模块 |
| API 层 | PostgREST 16.4 | 直接将 PostgreSQL 表暴露为 RESTful API |
| 数据层 | PostgreSQL 17.11 | RLS 行级安全 + `SECURITY DEFINER` 函数 |
| 部署环境 | Ubuntu（腾讯云轻量服务器） | 单机部署 |

**为什么网关是 Node 而不是数据库 RPC**：Apple IAP 验签最初计划在 `verify_payment_order` 函数内用 `pg_net` 外呼 Apple，但生产服务器 PostgreSQL 17.11 实测无 `pg_net` 扩展。最终架构决策为**验签落在 Node 网关**（负责外呼 Apple + 报文校验），数据库只保留 `settle_apple_purchase` / `revoke_apple_purchase` 两个 `SECURITY DEFINER` 函数负责**原子落库**。职责分离清晰：网关管外部通信与校验，数据库管事务与一致性。

## 三、核心技术实现

### 3.1 AI 视觉识别链路

**两段式模型策略**：文本理解与视觉识别统一走支持图片输入的模型（DeepSeek `deepseek-flash` 系列 / 百炼 `qwen3-vl-plus`）。这里有一个工程细节值得记录：DeepSeek 官方于 2026-07-24 退役了 `deepseek-chat` 与 `deepseek-reasoner`，仅保留 `deepseek-flash` 与 `deepseek-v4-pro`，且**只有 flash 系列接受图片输入**——向其他模型传图会返回 `400 This model does not support image`。因此网关的 `GET /.cloud/llm/models` 必须为视觉模型显式标注 `supportsImages: true`，前端 `pickModel(needVision)` 正是按该字段过滤的；缺这个字段会直接导致拍照识别报「暂无支持图片识别的模型」。

**流式契约**：云 SDK 的 `create()` 强制 `stream: true`（非流式请求会抛 `request_stream_required`），流必须以 `data: [DONE]` 结束，否则抛 `gateway_stream_interrupted`。前端 `collectText` 只读取 `chunk.choices[0].delta.content`。这套契约是逆向 SDK 行为后确认的，写入网关模块头部注释作为实现约束。

**推理开关**：部分模型默认开启深度思考（`enable_thinking`），而视觉识别任务并不需要长链推理，开启后纯属算力空转并显著拉高首字延迟。网关在请求体顶层注入 `enable_thinking: false`（开关 `LLM_VISION_ENABLE_THINKING`），可通过环境变量回退而无需改代码。

**文本问答的独立日限额**：文本请求不计入业务额度（产品口径为「只有拍照识别计费」），但**不能因此不设防**——否则等于对外提供一个每日 200 次的免费通用 LLM 代理，直接白烧 API Key。安全审计后为此增设了独立的 `textLimiter`（不再与视觉共用 `usageLimiter`）。

网关当前实测的三个限流器均为**自然日窗口**（`windowMs: 86_400_000`，key 带北京时间日历日 `dayKey()`，午夜自然换新桶）：

| 限流器 | 定义位置 | 默认上限 | 环境变量 | 作用域 |
|---|---|---|---|---|
| `usageLimiter` | `app.mjs:48`（注入 `llm.mjs`） | **200 / 日** | `LLM_DAILY_CAP` | 视觉请求（有 claim，走 `llm_gate` 业务额度） |
| `textLimiter` | `llm.mjs:191` | **50 / 日** | `LLM_TEXT_DAILY_CAP` | 文本问答独立限额 |
| `fallbackLimiter` | `llm.mjs:184` | **8 / 日** | `LLM_PACKAGE_DAILY_CAP` | 包装识别（条码兜底，无 claim） |

运行时按 `wantVisionReq` 二选一取用日限额器（`llm.mjs:289`）：视觉请求走 `usageLimiter`，文本走 `textLimiter`。

`fallbackLimiter` 刻意**不复用** `usageLimiter`：因为 `RateLimiter.hit()` 不支持按 key 覆盖 limit，混用会让兜底通道错误地继承 200/日的宽松上限。超过上限直接返回 **429**，避免慢请求堆积成雪崩。另有 `activeStreams` 并发流计数保护。

> ⚠️ **一处代码注释与实现不一致（2026-11-04 实测发现，已在本文如实记录）**：`packages/shared/src/rules/index.ts` 的头部注释写「AI 文字问答……免费用户带限流保护（**1 分钟最多 3 次**防刷）」，但服务端**实际实现的是 50 次/日**的日限额，`server/lib/llm.mjs` 中检索 `60_000` / `60000` **零命中**，即不存在任何分钟级限流器。
> 本白皮书以**代码实测行为**为准（50 次/日）。该注释疑为早期设计遗留，建议后续修正注释或按原设计补回分钟级限流——两者取其一，不宜长期并存，否则对外文案可能引用到与实际不符的限流口径。

**服务端权益闸门（fail-closed）**：这是本软件一处重要的安全设计演进。早期额度校验完全依赖客户端自觉调用 `consume_photo_quota`——攻击者携带合法 JWT 直接 POST `/.cloud/llm/chat/completions` 即可无限使用视觉模型，白烧 API Key 费用。

修复方案（迁移 0039）：视觉请求由数据库 `llm_gate` **原子核销**一条当日额度占用记录（`ai_quota_claims`）。正常前端流程「先 consume 后调 LLM」必然留有 claim 可核销；绕过前端的裸调没有 claim，落入包装识别日配额（有界）后被拒绝。

更关键的是**失败策略从 fail-open 改为 fail-closed**：此前数据库查询异常时选择放行（代码注释承认是刻意为之），风险是 `llm_gate` 依赖的连接池一旦抖动，视觉额度校验整体失效。现改为查询异常或返回畸形时**直接拒绝**视觉请求——宁可错拒，不可漏放。

**识别成功才扣次**：`releasePhotoQuota` 返回 `boolean`（而非 `void`），用于在识别失败时退还预占额度。这是产品承诺「识别失败不扣次数」的技术保障，且退还本身可能失败，UI 须按真实返回值措辞，不得假装成功。

**关于识别精度**：本软件已建成完整的精度评测工具链（`tools/ai-mape/mape.ts`），采用**四指标并报**而非单看 MAPE：

| 指标 | 作用 |
|---|---|
| MAPE | 相对误差（排除真值为 0 的样本并显式计数） |
| WMAPE | 抗小真值放大 |
| MAE | 带单位的绝对误差 |
| **Bias（有符号）** | 判断系统性偏移方向 |

判据逻辑：MAPE > 15% 且 \|Bias\|/MAPE ≥ 0.6 → 判定为 **systematic**（优先改 prompt）；< 0.6 → **random**（考虑换模型）。特别地，**MAPE ≤ 15% 但 \|Bias%\| > 10 仍判 systematic**——这条规则来自一次真实的自我纠错：用模板样本实测时，热量 MAPE 12.76% 看似达标，但 Bias 为 -17.29%（系统性低估）。对于减脂场景，系统性低估热量会累积成用户减脂失败，且该状态下不应做任何精度营销。

> 🔴 **精度数据现状**：工具已就绪，但**实测需要真机 + 样本餐（≥20 条、覆盖 4 个热量档）**。在完成实测之前，本白皮书**不对外表述任何精度数字**。这是刻意的克制，不是遗漏。

### 3.2 本地食物画像引擎

`src/lib/foodInsight.ts` 实现「风险发现 + 益处探索」双通道分析，其设计约束有三条：

1. **纯函数、完全离线、不调用任何模型**——不消耗 AI 配额，断网可用，结果可复现、可解释；
2. **计算层保持全精度，只在展示层插值那一刻舍入**；
3. **输出条数受控**：单条画像最多 3 项风险 + 3 项益处（`uniq(tags, 3)`），权重并列时按插入顺序保留靠前者，避免信息过载。

**为什么坚持「计算层不舍入」**：画像引擎中的 protein / fiber 等数值**既用于阈值判断**（如 `protein >= 20`、`fiber >= 6`、`fRatio < 0.4`）**又用于文案插值**。若在计算源头把 `11.666…` 舍成 `11.67`，阈值判断就建立在已失真的值上；更糟的是 `fRatio` / `cRatio` 这类派生比例会二次放大误差。

这条纪律源自一个真实缺陷：「饮食体检」页曾显示 `11.666666666666666 g/100g`——份量换算系数 `r = 100 / grams` 产生的无限循环小数被直接模板插值。修复方式不是「在源头舍入」（那会污染阈值判断），而是定义本文件**唯一允许的格式化入口** `const g = (n) => fmtNum(n, 2)`，仅在 8 处插值点调用，阈值判断保持原值不动。

### 3.4 条码识别：两段式解码策略

```
优先：浏览器原生 BarcodeDetector
      （Android Chrome 自带，零依赖、省电、逐帧快）
   │
   └─ 不支持时（如 iOS Safari）
        ↓
兜底：zxing-wasm（动态 import）
      WASM 由本包自带，locateFile 指向本地资源
      → 不依赖任何 CDN，保证国内网络可用
```

工程细节：zxing 解码器体积接近 1 MB，因此所有相关代码走**动态 import**，只有真正使用扫码功能的用户才会下载，不影响主包体积。支持码制覆盖零售商品常见类型：EAN-13、EAN-8、UPC-A、UPC-E、Code-128、Code-39、ITF、Codabar。条码数据源为 Open Food Facts，**永久免费不限次数**（不消耗 AI 额度）。

**条码营养查询的降级设计**（`src/lib/off.ts`）：该模块职责单一——把条码换成「每 100g 营养」。接口无需 API Key 且返回 `Access-Control-Allow-Origin: *`，可直接在前端调用，无需经网关中转。

这里有一个必须正视的数据现实：**中国包装食品在 Open Food Facts 的覆盖很薄**（实测多数国产零食返回 `not found`）。因此查询结果被建模为三态联合类型而非「有/无」二态：

```ts
type BarcodeLookup =
  | { status: 'found'; product: PackagedFood }
  | { status: 'not_found' }              // 库中无此条码 → 触发降级
  | { status: 'network_error'; message: string }  // 网络故障 → 与"无数据"区别对待
```

区分 `not_found` 与 `network_error` 是刻意的：前者应引导用户改走**拍照识别包装营养表**（AI 读表，带 confidence 并按 §5.4 规则标识），后者应提示重试而非误导用户「这个商品没有营养信息」。这与 §3.1 的 `releasePhotoQuota` 返回 `boolean` 属同一设计取向——**失败必须如实上报，不得吞成空值或假装成功**。

### 3.5 跨端 Origin 转发（原生网络层适配）

这是一个隐蔽但关键的问题。云端按 **Origin 精确匹配**校验客户端，Web 端能正常工作是因为自托管站点的 Nginx 反代中显式覆写了 `Origin` 与 `Referer` 两行头。

原生端没有 Nginx：请求在 WebView 中发出，而 `Origin` 属于 fetch 规范的 **forbidden header name**，JS 侧无论如何设置都会被 `Request` 构造函数过滤掉（已实测验证）。症状极为隐蔽——**发码 / 验码返回 200，但 signup / signin 一律 401 `invalid_grant`**；且 refreshToken 句柄同样绑定 Origin，令牌续期会一起失效。

解法是自研原生插件 `dbee-origin-proxy`：让请求经原生 HTTP 栈转发，由原生层强制注入这两个头（等于把 Nginx 那两行搬进 App）。

接入方式上有一处刻意的克制：云 SDK 官方支持注入自定义 fetch（`WorkBuddyCloudOptions.fetch`），因此**不 patch `window.fetch`**、也不动 CapacitorHttp 已有的补丁，影响面严格限定在云 SDK 自己的请求上，Web 端与其他网络调用一行代码都不变。该抽象层同样**不静态 import 任何 Capacitor 插件包**，只做运行时鸭子类型探测，保证 Web 构建产物零新增依赖、体积不变。

插件另提供 `requestStream`（chunk 经 Capacitor 事件逐块回传），本层据此构造 `ReadableStream`，使 LLM 的 SSE 可增量消费，实现教练回复的打字机效果。取消语义归一为 `End` 而非 `Error`，且取消绝不回退到缓冲重发；在途流注册表在 `finally` 中移除。

## 四、数据一致性与工程质量

### 4.1 数值口径：全站唯一实现

`packages/shared/src/numfmt.ts` 是全站**唯一**的数值舍入与格式化实现，任何新增数字展示都必须走它，**禁止自行编写 `toFixed` 或 `Math.round(n * f) / f`**。

| 函数 | 职责 | 语义 |
|---|---|---|
| `roundTo(n, 2)` | 计算层 → 数值 | 异常归 0（防 NaN 传染求和） |
| `fmtNum(n, 2, opts)` | 展示层 → 字符串 | 去尾随零，异常返回 `—` |
| `pct(n, 0)` | 百分比格式化 | **入参已是百分数**，不再乘 100 |
| `balancePercents(values, 100)` | 供能比配平 | 最大余数法 |

**精度约定**：克数类营养素（蛋白质 / 碳水 / 脂肪 / 膳食纤维 / 添加糖）保留 **2 位小数**；kcal 与钠 mg **取整**。

**为什么不用 `Math.round(n * 10**d) / 10**d`**——三个理由：

1. **大数溢出精度**：`1e21` 经此路径得到 `999999999999999900000`；
2. **负数 .5 方向不一致**：`Math.round(-2.5)` 得 `-2`，而 `toFixed` 给 `-3`，两种口径混用会产生不可预期的偏差；
3. **乘法误差会「凑巧」掩盖逻辑错误**：这是最危险的一条，它让本该暴露的 bug 沉默通过测试。

需要说明的一个非缺陷现象：`1.005 → "1.00"` 不是 bug，其 IEEE-754 double 的真实值为 `1.0049999999999998934`，舍入结果正确。

**纪律：计算层全精度，只在展示层插值那一刻舍入。** 绝不「先舍入再参与计算」。一个真实反例：报告页供能比曾用**已取整的日均值**反算，导致 `18 + 37 + 46 = 101%`，已修复为全精度计算后再用最大余数法配平。

### 4.2 跨端一致性护栏：从口号到机器强制

「改代码前先考虑各端一致」若只停留在口头约定，必然随迭代失效。本软件将其固化为**可执行测试** `tools/four-end-consistency.test.ts`——6 道护栏、10 项断言：

| # | 护栏 | 类型 |
|---|---|---|
| 1 | 日期禁用 `toLocaleDateString`（必须走 `formatCnDate`） | 禁止式 |
| 2 | 定价禁止硬编码（必须引用 `PRICE_*` 常量） | 禁止式 |
| 3 | 手写舍入快照基线 **7 处** | **快照式** |
| 4 | 会员文案必须走 shared `memberSubText` | 禁止式 |
| 5 | AI 同意门无门清单快照 **4 页**（调 AI 页面总数 **8**） | **快照式** |
| 6 | 刻意分叉处必须留说明注释 | 约束式 |

**快照式护栏的语义是「只准减不准增」**：基线数字变少说明历史债已清理，此时**必须同步更新基线**，否则护栏失去侦测力。

**放宽基线后必须做「红验证」**：临时注入一条违规，确认护栏真会报红。本次实践中注入 `Math.round(x*10)/10` 到 `Onboarding.tsx`，护栏精准报出 `:123,449`，随后 `cp` 备份恢复并 `git diff` 确认干净。这一步不可省——否则「把基线从 4 条改成 5 条」可能顺手把护栏改成永远绿，等于删掉了护栏。

### 4.3 一致性问题三分类

护栏实践催生了一个方法论上的补充。原本跨端差异只有两类，实测发现存在第三类：

| 类别 | 定义 | 处理规则 |
|---|---|---|
| **必须一致** | 同一功能在各端应表现相同 | 不一致即为 bug，**必须修** |
| **刻意分叉** | 因平台特性有意做出不同实现 | 必须留说明注释，护栏校验注释存在 |
| **功能覆盖差异** | 同一功能一端有、另一端完全没有 | **必须做产品决策**：补齐，或明确记录为刻意省略 |

第三类的发现过程很典型：主端有「已减重 X kg / 较起始 +X kg」的体重变化展示，而全 `mini/src` 检索「已减重 \| 较起始」**零命中**。这不是写法分叉，是功能缺失。定性时的纪律是**必须查全端、不能只看同名文件**——`mini/src/pages/profile/profile.tsx` 的注释已明说趋势图刻意改为列表，但未说明变化文案的去向。

> 对于减脂类产品，体重变化是核心正反馈。小程序若承担首发获客角色，建议补齐（工作量小，走 `@dbee/shared`）；若选择不补，也必须写进护栏注释记为刻意省略，否则下次仍会被当作疑点重查一遍。

### 4.4 测试体系与一处重要教训

测试框架为 **vitest**（`npm test` = `vitest run tools/`），当前基线 **10 个测试文件 / 190 项断言**。另有 IAP 自测 `tools/iap-selftest.mjs` 47 项。

**🔴 vitest 并行会静默丢测试文件并「假绿放行」**——这是本项目踩过最深的一个坑，值得完整记录：

- 本机在并行模式下偶发 `EPERM ...\Temp\<x>\ssr\<hash>` 错误（源于宿主对文件系统写入的拦截）。vitest 将其归入 `Unhandled Errors` 打印，但**不影响退出码**。
- 被卡住的测试文件**完全不进入统计**，而 **exit code 仍为 0**。
- 同一份代码的实测对照：并行 `8 files / 150 tests`（假绿）vs 串行 `10 files / 190 tests`（真相）——**丢失 2 个文件、40 项断言**。所谓「全绿」是假的。

修法：在 `vite.config.ts` 中设置 `test.fileParallelism = false`。**写在配置文件而非 npm script 里**，这样 `npx vitest run xxx`、IDE 测试按钮等所有路径都生效（脚本参数只覆盖 `npm test` 一条路径）。代价是耗时从 9.4s 增至 15.9s，这个代价值得付。

由此沉淀出两条纪律：

1. **「exit code 会不会非零」必须显式 `echo $?` 验证**，不能凭有无报错输出推断。此前六次采样曾据 stderr 有字便判定 exit=1，得出「不会假绿」的错误结论，被后续实测推翻。
2. **每次跑完必须核对 `Test Files` 数 == `ls tools/*.test.ts | wc -l`**，少一个就是有文件被吞。

其他工程纪律：

- 改计算逻辑必须**红绿验证**：先回退到旧逻辑确认真的会红，再恢复确认转绿。
- 测试红时**先分清是代码错还是断言错**，不为凑绿而改动产品行为。
- 文档里每个数字与每条「代码会做 X」的承诺，**都要能被一条命令验证**。实践中曾出现文档写了代码里根本不存在的护栏（`grep -c` = 0 命中），等于制造了一份假保险。

## 五、安全与数据保护

### 5.1 身份层：不存明文

```
原始标识（手机号 / 邮箱）
   ↓ 归一化（剥到 11 位裸号；兼容 +86 / 86 / 0086 / 空格 / 短横线）
   ↓ HMAC-SHA256(标识, IDENT_PEPPER)
   ↓
app_users 表：只存哈希，不存明文
   ↓
owner_id：19 位纯数字串（与云端已迁移的业务档案同构）
```

**PEPPER 不可省略**：11 位手机号空间仅 10^11，无密钥哈希可被穷举反查。`IDENT_PEPPER` 存于服务器本地 `deploy/gateway/.secrets.local`，**永不进入代码仓库**。

一处归一化细节必须两端严格一致：SDK 会把 `13800000000` 归一成 `+86 13800000000` 后作为 username 上传，而登录时前端传的是裸号。两边都必须落到同一个哈希，因此统一剥到「11 位裸号」再哈希——否则会出现「发码用裸号、登录用 +86」对不上的问题。

对外展示一律掩码（`138****1234`），长度不足时全掩，绝不泄露完整号码。令牌版本机制（迁移 0042）支持强制失效。

> ⚠️ **运维红线**：`IDENT_PEPPER` 一旦被重置，全站用户身份永久失效且不可恢复。因此改网关配置**绝不使用整体重渲染模板的部署脚本**（缺失 `.secrets.local` 时会触发随机重置），一律走**手术式脚本**（只改目标键，并断言 env 非目标部分的 SHA-256 前后一致）。服务器侧预检放在重启之前——此时网关仍跑旧配置，回滚零风险。

### 5.2 多租户隔离：RLS + SECURITY DEFINER

PostgreSQL 行级安全策略承担用户数据隔离，规模实测：**64** 处启用 RLS、**70** 条策略、**132** 处 `SECURITY DEFINER`。

核心安全铁律：

- **发放权益的函数必须 `SECURITY DEFINER` + 入参白名单**；
- **涉及权益的表必须 `REVOKE authenticated` 的 INSERT / UPDATE / DELETE**——因为 **RLS 挡不住直写**。这是最容易被忽略的一点：许多人以为加了 RLS 就安全，但拥有表写权限的角色可以绕过策略直接写入。权益类表的正确做法是收走写权限，所有变更只能通过 `SECURITY DEFINER` 函数进行。
- 单条 SELECT 中表达式求值顺序未定义，`set_config` 混用函数时必须用 `WITH s AS MATERIALIZED` 固化求值顺序。
- `BYPASSRLS` 属性已收回（迁移 0033）。

数据库迁移采用**编号 + 审计**管理（44 个迁移文件）。审计实测结论：33 个编号中 28 个生效、3 个失效、1 个弃用、1 个 void（`pg_net` 方案）。配套审计工具 `tools/migration-audit.sh`，纪律是**先修工具再修数据**。

涉及双库（自建库 + 云库）的闸门变更必须**双库同步打补丁**：自建走 migrations，云库走 MCP 并在 `db/cloud-patch-0039/` 留档，另有探针脚本校验两库对齐。

### 5.3 支付安全：Apple IAP 全链路验签

**客户端购买验签**（`POST /.cloud/payment/apple/verify`）设五重边界，每一条都对应一个真实攻击面：

| # | 校验 | 防御的攻击 |
|---|---|---|
| 1 | 必须携带网关签发的 Bearer JWT | 权益发给「当前登录用户」，不发给收据持有者 |
| 2 | 收据必须过 Apple `verifyReceipt`（status = 0） | **绝不信任**客户端自报的 `product_id` / `transaction_id`，一律以 Apple 返回报文为准 |
| 3 | `receipt.bundle_id` 必须等于 `APPLE_BUNDLE_ID` | 防止拿别家 App 的合法收据换本 App 会员（`verifyReceipt` 对任何 App 的收据都返回 0） |
| 4 | `transaction_id` 在 `apple_transactions` 表中 **UNIQUE** | 同一笔交易全服只能核销一次；换账号重放同一收据会被「已归属他人」拒绝 |
| 5 | 沙盒 / 生产自动切换（状态码 21007 / 21008） | 提审期间沙盒账号可正常购买 |

**服务端通知验签**（App Store Server Notifications V2）走完整的 JWS 五步校验：

```
Apple POST { signedPayload: "<JWS>" }
  ① JWS 头 x5c 三级证书链，链尾必须逐字节等于仓库内置的 AppleRootCA-G3
     （SHA-256 指纹钉扎：63343abf…3e9179，2026-10-23 自
      apple.com/certificateauthority 下载）
  ② leaf / intermediate 逐级验签 + 有效期检查
  ③ leaf 必须含 Apple 专用扩展 OID 1.2.840.113635.100.6.11.1
  ④ ES256 验 signedPayload 本体
  ⑤ payload.data.signedTransactionInfo 是嵌套 JWS，同样流程再验一次
```

处理的通知类型：`SUBSCRIBED` / `DID_RENEW`（续订核销）、`REFUND` / `REVOKE`（撤销权益），其余仅落库留痕（`apple_notifications` 表）。

**幂等与容错策略**：webhook **永远尽力返回 200**——处理失败也先落库，因为 Apple 收到非 200 会重试造成堆积；**唯一例外是验签失败返回 400**（那不是 Apple 发的）。

**StoreKit 2 核销时序铁律**：**服务端核销成功才调用 `finish()`**；退款交易只 `finish` 不送核销。

> 🔴 **一处已识别的架构风险（支付渠道差异）**：Apple 是**拉模式**（客户端主动验签），微信 / 支付宝是**推模式**（权威信号是服务端异步回调，通常晚于客户端核销）。现有设计若直接接入，会出现「用户已扣款，App 却报支付校验失败」——这是**主路径而非边缘情况**。解决方案是核销改为「查订单状态 + 有限重试」并新增 `settling` 中间状态。另外 `getAdapter` 目前**无分发渠道维度**，接入华为渠道前必须补齐（华为强制 IAP Kit，且购买页禁止展示支付方式名称）。

### 5.4 隐私保护

| 项 | 实现 |
|---|---|
| 真实健康档案 | **不入库**（`0030-full-selfhost-mirror.sql` 已 gitignore） |
| 用户标识 | 只存 HMAC 哈希，不存明文手机号 / 邮箱 |
| 健康数据读取 | 只读系统平台（HealthKit / Health Connect），原生能力**必须返回显式状态，禁止吞成 0 / 空**；仅在 `isUsableHealthStatus(status)` 为真时才写回 |
| 广告 SDK | 全仓检索广告关键字**零命中**，无任何用户画像与广告追踪能力 |
| 隐私政策 | 单一真源 `src/content/legal.ts`，构建时自动生成静态 HTML（零 JS 可爬） |
| 同意门 | `PrivacyGate` / `AiConsent` 组件，收集范围实质变化时通过 `LEGAL_UPDATED` 版本化机制让老用户重新确认 |

**隐私公示的两条工程纪律**（源于真实踩坑）：

1. **禁止跨端照抄**。两个数据库不互通、公示主体不同。撰写法务文本前必须核对真实链路，**只写确实存在的能力**。每条第三方链接必须 `curl` 验证返回 200，且引用的文件要「与我方关系匹配」。配套自动校验脚本 `deploy/verify-legal.mjs`。
2. **能力公示必须以「包内实际能力」实证，不以旧文档、不以 import 语句为准**。例如健康插件在 Android 端目前是阶段骨架、恒返回 `not_ready`，其 HMS 依赖被注释掉——那么公示就必须写「资质申请中、当前不读取」，**不可谎报能读**。判断数据流向要看变量的真实去向（如 `healthSteps` 只进入渲染与估算，在 `api.ts` 中零命中，才敢写「不上传」）。

**AI 显式标识**：依据《人工智能生成合成内容标识办法》（国信办通字〔2025〕2 号，**2025-09-01 已施行**），实现 `src/components/AiLabel.tsx` 组件提供徽章与行内（`inline`）两种标识形态，接入教练问答（`CoachSheet`）、报告解读（`ReportScreen`）、记录解析（`LogSheet`）三处。

判定函数 `isAiDraft()`（定义于 `LogSheet.tsx:184`）的口径是：

```ts
it.source === 'photo' || it.source === 'text'
  || (it.source === 'barcode' && it.confidence !== undefined)
```

即拍照与文本解析**全标**（两者全量走大模型）；条码识别**仅在带 `confidence` 时才标**——因为只有「AI 读包装营养表」才属 AI 生成，而纯扫码命中 Open Food Facts 商品库的数据是确定性数据，不属 AI 生成内容，**不应标识**；手动录入不标。

配套的 `estimateHint()` 按置信度分档提示用户「这是约数」并支持一键修正：

| 条件 | 提示文案 |
|---|---|
| `confidence >= 80` | 营养表识别较可靠 |
| `confidence >= 60` | 营养表可能不够清晰，请核对 |
| `confidence < 60` | 营养表识别置信度低，建议手动核对 |
| 无 confidence（餐盘识别） | AI 估算，份量请按实际核对 |

这一设计的意义在于：标识不是「贴个 AI 标签了事」，而是把**不确定性程度**如实传递给用户，让「约数」这件事在界面上可见、可纠正。

## 六、构建与发布体系

### 6.1 双层护栏：构建期 + 运行时

本软件对「端点钉死」这一高风险配置错误设了**两层独立护栏**：

| 层 | 位置 | 执行时机 | 行为 |
|---|---|---|---|
| 构建期 | `vite.config.ts` | Node 构建过程中 | 缺 endpoint 直接 throw，构建失败 |
| 运行时 | `cloudConfig.ts` `resolveNativeEndpoint` | App 启动时 | 硬断言 endpoint 值 |

`native-release` 模式不注入 endpoint 会 **exit 1** 并抛出「必须设置 `VITE_NATIVE_ENDPOINT`」；`native-internal` 模式需显式 `VITE_ALLOW_CLOUD_NATIVE=true`，此时 exit 0 但 **warn**「此产物禁止上架」。

**为什么构建期护栏必须写在 `vite.config.ts` 而不能放在业务代码里**：webpack / Vite **不执行**被打包模块的顶层代码。实测教训是——小程序端曾把 throw 写在 `mini/src/lib/backend.ts`，它只在小程序启动时才触发，**误配的包照样 `build:weapp` exit=0 发出去了**。修法是在构建配置（Node 构建期执行）里调用**同一个** `resolveBackendTarget()` 函数，两层复用同一实现，不会漂移。

### 6.2 一处必须知道的构建陷阱

🔴 **打原生包绝不能使用 `npm run build`**。原因是护栏代码会被死代码消除优化成无条件 throw，导致 JS 首行即炸；而 CSS 已加载完成，页面呈米白色，**极易被误判为「白屏 bug」而非「用错了构建命令」**。

自检判据：`grep -c "禁止直接复用 Web 产物" dist/assets/index-*.js` 必须为 0。诊断构建问题必须**真实构建两种产物做对照**，不能只看单侧。

🔴 **native 构建会覆盖 `dist/`，与 Web 产物互斥**（共用同一目录）。`vite build --mode native-release` 与 Web 的 `npm run build` 都写 `dist/`，而 `cap sync` 从 `dist/` 拷入 `android/app/src/main/assets/public`。后果是：跑完 native 构建后 `dist/` 里就是**钉死了 endpoint 的原生产物**，此时若跳过构建直接部署 Web，会把 native 产物误推到 Web 服务器。纪律是 **native 构建后、部署 Web 前，必须重新 `npm run build`**，并比对线上 `index-*.js` 文件名与本地 `dist/assets/` 一致。

### 6.3 产物自检的判据纪律

🔴 **产物自检必须以 `index.html` 引用的入口 js 为唯一真源**：

```bash
ENTRY=$(grep -oE 'assets/index-[A-Za-z0-9_-]+\.js' dist/index.html | head -1)
# 再查 dist/$ENTRY
```

**干净构建本就有 2 个 `index-*.js`**（另一个是入口动态 import 的 chunk，hash 稳定）。曾把「>1 个 = 构建残留」写进操作手册，实际是**错误判据**——它比没有判据更危险，会让人反复 `rm -rf` 重打却始终「不通过」。

由此确立的纪律：**任何「产物自检」命令写进手册前，必须在干净构建的真产物上实跑，且要能区分合法产物与异常产物。**

### 6.4 法务静态页生成

`npm run build` 会自动执行 `tools/gen-legal-static.mjs`，产出 `dist/legal/{terms,privacy,disclaimer}/index.html`——**零 JS 可爬**（部分应用商店硬性要求）。单一真源是 `src/content/legal.ts`；`build:native*` 不生成（原生端不需要）。备案号走 `VITE_ICP_BEIAN`，未传即整块不渲染，避免出现假备案号。

一处精细的实现细节：法律文案中的 `**强调**` 由两端渲染器各自转 `<strong>`。静态生成侧的 `rich()` 函数**必须先转义后加粗（顺序不可颠倒）**；两端都带**成对性守卫**——当 `**` 数量为奇数时**剥除星号降级**（保留星号会让裸标记露出，而奇偶错位分段会让漏标记之后的正文全部被误加粗）。修改文案后须验产物 `grep -o '\*\*' | wc -l` = 0。

## 九、技术演进与后续规划

### 9.1 已解决的关键技术难题

| 难题 | 解决方案 |
|---|---|
| iOS Safari 无 `BarcodeDetector` | 动态加载 zxing-wasm 兜底，WASM 本地自带不依赖 CDN |
| 原生端无法设置 `Origin` 头（forbidden header） | 自研 `dbee-origin-proxy` 原生插件，由原生 HTTP 栈注入 |
| 客户端绕过额度校验白烧 API 费用 | 服务端 `llm_gate` 原子核销 + fail-closed 策略 |
| 权益表被直写绕过 RLS | `REVOKE authenticated` 写权限 + 强制走 `SECURITY DEFINER` 函数 |
| 苹果收据跨 App 重放 | bundle_id 校验 + transaction_id 全服唯一约束 |
| 无限小数直接插值到 UI | `numfmt` 单一舍入口 + 「计算层全精度」纪律 |
| 供能比求和不为 100% | 最大余数法配平（`balancePercents`） |
| vitest 并行静默丢测试文件 | 强制串行 `fileParallelism = false` |
| 误用 Web 构建产物打原生包（白屏） | 构建期 + 运行时双层护栏 |
| 跨端数值/文案/日期口径漂移 | `@dbee/shared` 单一真相源 + 6 道可执行一致性护栏 |

### 9.2 后续技术方向

1. **四端数据面统一迁回自托管**。当前 Web 端已切自建 PostgreSQL，Android / iOS / 小程序仍走云库。已拍板最终四端统一迁回自托管，切换开关代码已就位（默认零行为改变），待 ICP 备案完成 → DNS A 记录 → HTTPS 证书就绪后执行。真正的技术工作量不在改 endpoint，而在**身份模型对齐**：云库 uid 形如 `wx:<openid>`，自托管 owner_id 是 19 位数字串，`ident_kind` 约束目前只允许 phone / email，网关尚无微信登录端点。好消息是 22 个 RPC、11 张表与 RLS 策略已全部在自托管侧就位，SDK 路径前缀 `/.cloud` 与网关完全对齐。

2. **多渠道支付适配**。补齐 `getAdapter` 的分发渠道维度，核销时序改为「查订单状态 + 有限重试」并新增 `settling` 中间状态，以兼容微信 / 支付宝的推模式异步回调。

3. **健康数据源深化**。当前只读系统平台健康数据（HealthKit / Health Connect）。华为、小米需先完成企业入驻与应用上架，之后替换 `dbee-health` 插件的骨架实现为真实方法体。

4. **AI 识别精度实测**。工具链已就绪（四指标并报 + systematic / random 判据），待真机与样本餐（≥20 条、覆盖 4 个热量档）完成后开展实测。在此之前不对外表述任何精度数字。

5. **数值口径历史债清理**。护栏扫出 7 处手写舍入历史债（两端 `Onboarding` 各 1 处、两端图表默认格式化各 1 处、主端资料页 3 处）。这**不是纯机械替换**——`fmtNum` 异常返回 `—` 且默认去尾随零，会改变 `placeholder` 语义，属有产品影响的重构，须逐处确认展示预期（尤其图表轴刻度与体重变化文案）。
