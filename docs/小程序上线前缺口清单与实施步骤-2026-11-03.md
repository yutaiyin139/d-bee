## 二、代码层真缺口（3 项，按严重度排序）

### 🔴 缺口 1 · AI 同意门只覆盖 2/4 个入口（PIPL 单独同意）

`mini/src/content/legal.ts:194` 对用户承诺：

> 「在你首次使用上述**任一** AI 功能前，我们会另行弹出说明并单独征得你的同意」

实际调用 AI 的有 4 处，只有 2 处有门：

| AI 调用点 | 函数 | 有 `AiConsent` 门 |
| --- | --- | --- |
| `pages/coach/coach.tsx:129` | `askCoach` | ✅ `:236` |
| `pages/scan/scan.tsx:178` | `recognizeFoodFromImage` | ✅ `:381`（且与平台隐私门串联两道） |
| `pages/onboarding/onboarding.tsx:119` | `generatePlan` | ❌ **无** |
| `pages/report/report.tsx:181` | `generateReportInsight` | ❌ **无** |

- **性质**：承诺与实现不符 = 隐私政策虚假陈述。用户填完引导问卷，数据未经单独同意就送进大模型。
- 🔴 **两端共有**：主端 `src/pages/Onboarding.tsx:155`、`src/pages/ReportScreen.tsx:205` 同样无门（主端只在 `CoachSheet.tsx:132`、`LogSheet.tsx:604,673` 有）。所以这不是「mini 落后于主端」，是两端一起漏。
- **修法**（二选一，见 §六拍板项 B）：
  - **补门**：两处照 `coach.tsx` 模式加 `aiConsentOpen` 状态 + `<AiConsent kind="plan|report">`。onboarding 的难点是 `loadPlan()` 由 `next()` 自动触发，需改成「进 result 步先弹门，同意后才 loadPlan」。
  - **改文案**：把 `legal.ts:194` 的「任一」收窄为实际有门的入口。**不推荐**——引导计划与报告解读确实在传用户数据给大模型，收窄文案等于放弃合规。

### 🔴 缺口 2 · 登录页无任何协议展示（小程序审核 + PIPL 告知）

`pages/login/login.tsx` 全文 258 行，**零处**「隐私」「协议」「同意」字样：
用户点「微信一键登录」或输入手机号前，看不到《用户协议》《隐私政策》入口，也没有勾选框。

- 对比主端：`src/components/PrivacyGate.tsx` 实现了国内安卓商店硬四要素（独立弹框、不可跳过、不默认勾选、协议可点开全文、不同意即退出），且挂在 `main.tsx:23` 包在 `<App />` 最外层以保证**同意前零网络请求**。
- mini 侧现状：平台层授权门有（`lib/privacy.ts`，管 errno 112），业务层首启同意门**没有**。
- **须区分两层，别混为一谈**：
  - 平台层（微信自动弹《用户隐私保护指引》）→ 已覆盖，靠 `privacy.ts` 主动触发；
  - 业务层（我方展示协议 + 征同意）→ **缺失**。小程序是否必须自建全屏 PrivacyGate 取决于微信审核口径，但**登录页放协议链接是确定要做的**（成本远低于全量 PrivacyGate）。
- **修法**：`login.tsx` 底部加一行「登录即表示同意《用户协议》《隐私政策》」，两个链接 `navigateTo` 到 `pages/legal/legal?id=terms|privacy`（该页已存在且可独立打开）。是否再加「不勾选不能登录」的 checkbox，见 §六拍板项 C。
- ⚠️ 若采纳全量 PrivacyGate：小程序页面栈由微信管理，**做不到** web 那种「App 根本不挂载」，只能做全屏遮罩组件逐页拦截，工程量与漏拦风险都高。**不建议在上线前做。**

### 🟡 缺口 3 · 提醒开关「可见但不可用」（与 P2-A 导出按钮同类）

`pages/profile/profile.tsx:486-509` 渲染两个可打开的 Switch：「每日打卡提醒」「饮水提醒」。
实际行为：

- `lib/notifications.ts:16` → `const CHECKIN_TEMPLATE_ID: string = ''`（**空**，未回填模板 ID）；
- `:46` → `if (!CHECKIN_TEMPLATE_ID) return 'no_template'`，静默降级、**不告知用户**；
- `:79` → `enableWaterNotify()` 只写本地 kv，**连订阅都不发起**（注释：「模板 ID 就绪后扩展」）。

结果：用户把两个开关都打开 → 界面显示已开启 → **永远收不到任何提醒**，且无任何提示。

- 这正是 P2-A 修掉的「导出按钮点下去转圈但拿不到文件」同一类问题：**可见但不可用 = 误导用户**。
- **修法**（三选一，见 §六拍板项 D）：
  1. **诚实置灰**（对齐 P2-A 的做法，推荐）：两行加 `line-badge`「即将上线」角标 + Switch 禁用，或点击后 toast 说明「提醒功能即将上线」。
  2. **让它真能用**：去 mp 后台申请订阅消息模板 ID 回填。⚠️ 微信订阅消息是**一次性授权**——用户同意一次只能推一条，做「每日打卡提醒」需每次进小程序重新拉授权，体验与实现成本都要评估。
  3. **直接删掉这个区块**：最省事，但会丢掉「后续要做提醒」的 UI 位置。

## 四、🔴 硬阻断（后台与资质，非工程能解）

### 阻断 1 · 小程序主体变更（`docs/收费模块-前置条件待办清单.md` 4.1 = `[!]`）

- 当前仍是**个人主体**，须变更为「北京迪蜂科技有限公司」。
- 流程（`docs/主体注册后-实施计划.md` §B1.3 已查证官方口径）：入口【设置】→【主体信息】→【小程序主体变更】；四步 = 同意协议 → 信息填写 → 授权验证 → 支付 ¥300（**不退**）→ 审核 1–7 工作日。
- ✅ **本项目可免公证**（官方免公证情形第 1 条：个人→企业且个人即为企业法人）。替代材料：申请函再上传一遍 + 法人身份证正反面 + 手持申请函照片；申请函「原主体」处须**本人签名 + 按手印**，且**不可委托代办**。
- ✅ **不换 AppID**，`wxb7c7122de9c3ab1f` 一行都不用改，代码零改动。
- ✅ 无旧商户号绑定冲突（小程序尚未开通收款）→ 不会触发「变更失败且 ¥300 不退」。
- ⚠️ **审核通过后 7 天内**须完成：管理员确认 → 退出重登 → 签服务协议。**超时流程自动终止、申请作废、钱不退**。
- 🔴 **时序坑**：变更后必须重做小程序备案，而**新备案完成前不能提交发布新版本**。

### 阻断 2 · 小程序备案（4.2 = `[ ]`）

- 主体变更后统一社会信用代码改变 → 属主体资质变更，走「**先注销原备案 → 新主体新增备案**」，不支持直接变更。
- 周期：平台初审 1–2 工作日 + 管局 1–20 工作日。
- ✅ 宽松点：**备案期间小程序可正常使用**（与网站域名备案「注销即停站」不同）。
- 🔴 但**备案完成前不能提交发布新版本** → 这就是「先发修复版还是先变更主体」这个拍板项的来源（§六 A）。

小程序所有网络请求的域名必须在 mp 后台「开发 → 开发管理 → 开发设置 → 服务器域名」的 **request 合法域名**里，且要求 **HTTPS + 已备案**。当前 mini 实际请求：

- 🔴 **风险**：`workbuddy.host` / `workbuddy.cn` 的备案主体是**腾讯**，不是北京迪蜂科技。微信对合法域名要求「域名备案主体与小程序主体一致」，第三方域名需走授权流程。

   - 测试**逐文件跑再加总**（防 `node_modules/.vite` 陈旧导致 EPERM 静默丢测试文件的「假绿」）：
     `CI=true NO_COLOR=1 npx vitest run <f> 2>&1 | sed 's/\x1b\[[0-9;]*m//g' | grep -E "^[[:space:]]*Tests[[:space:]]"`；
   - **产物用 unicode 转义搜中文**（小程序产物里中文是转义形式，如 `\u5373\u5c06\u4e0a\u7ebf`）。
9. **提交前凭据扫描**（既有纪律，不可跳过）。

### 阶段 2 · 后台配置（你操作，代码无法覆盖）

10. **mp 后台《用户隐私保护指引》**（`lib/privacy.ts` 文末清单）：
    勾选**实际调用**的信息类型，仅两项——
    - 「收集你选择的照片或视频信息」← `Taro.chooseImage`（`scan.tsx`）
    - 「访问你的摄像头」← `chooseImage` 的 `sourceType` 含 `'camera'`
    用途如实填「用于拍摄或选择餐食照片，由 AI 识别食物并估算营养」。
    ⚠️ **不要勾未使用的类型**（位置、通讯录、运动健康）——多勾属超范围收集，是 PIPL 风险。
    ⚠️ 提交后需等审核（快几小时，实测有反馈约 40 分钟生效），然后开发者工具**重新编译**才解除 errno 112。
    🔴 **代码勾不出这个声明**：后台未声明时 `needAuthorization` 恒为 false，`privacy.ts` 会「看似正常」放行，然后在真机 `chooseImage` 处才炸。**开发者工具测不出来，只在真机/体验版暴露。**
11. **提审页的「采集用户隐私」也要勾**并与后台声明一致（后台设置管开发环境，提审页设置管线上环境，**两处不一致仍会 112**）。

## 六、🔴 需你拍板的 4 个决策点

### A · 先发修复版，还是先变更主体？（**最优先，卡所有排期**）

`docs/收费模块-前置条件待办清单.md` 4.1 已记「🔴 P0：先发修复版，再发起变更」，理由是变更后新备案下来前不能发版（1–20 工作日）。

- **选项 A1（文档既有倾向）**：阶段 1 修完 → 立即提审发布 → 发布成功后再发起主体变更。
  - 优点：不被备案期冻结发版；主体变更后的备案期不影响已上线版本运行。
  - 风险：以**个人主体**上线一个含健康数据的应用，`docs/主体注册后-实施计划.md:481` 提示审核可能质疑主体一致性（备案主体/隐私政策主体已是公司，小程序主体还是个人）。且**隐私政策已公示「北京迪蜂科技有限公司」为运营主体**，与个人主体的小程序存在口径不一致，审核可能驳回。
- **选项 A2**：先变更主体 + 备案 + 类目 → 全部就绪后再发版。
  - 优点：主体与隐私政策公示一致，审核风险最低。
  - 代价：上线时间被备案期（最长 20 工作日）推迟。
- **我的建议**：先做阶段 0 第 1 步（核实合法域名）。若域名这条走不通、必须等 `d-bee.cn` 备案，那么**主体变更与备案可以并行推进**，A2 反而不额外增加总时长；若域名能直接加，则 A1 更快但需接受主体不一致的驳回风险。

### B · AI 同意门（缺口 1）怎么修？

- **B1（推荐）**：补门，让实现匹配承诺。onboarding 需把「进 result 步自动 `loadPlan()`」改为「先弹 `AiConsent`，同意后再生成」。
- **B2**：改 `legal.ts:194` 文案，把「任一」收窄到有门的入口。**不推荐**（等于放弃这两处的 PIPL 单独同意）。
- 📌 若选 B1，**主端同样两处也该补**（`src/pages/Onboarding.tsx:155`、`src/pages/ReportScreen.tsx:205`），否则两端承诺与实现继续分叉。这会动到 `src/`，超出「优先只改 mini」的默认边界，需你一并授权。

### C · 登录页协议（缺口 2）做到哪一步？

- **C1（推荐，最小合规）**：底部加「登录即表示同意《用户协议》《隐私政策》」+ 两个可点链接。
- **C2**：C1 + 未勾选 checkbox 时禁用登录按钮（更严格，但增加流失）。
- **C3**：全量自建 PrivacyGate 对齐主端。**不建议上线前做**（小程序页面栈由微信管理，做不到「App 不挂载」，只能逐页遮罩，工程量与漏拦风险都高）。

### D · 提醒开关（缺口 3）怎么处理？

- **D1（推荐，对齐 P2-A 做法）**：加「即将上线」角标 + Switch 禁用/点击 toast 说明。诚实、零后台依赖、可立刻做。
- **D2**：去后台申请订阅消息模板 ID 让它真能用。⚠️ 微信订阅消息是**一次性授权**，「每日提醒」需每次进小程序重拉授权，体验与成本都要评估。
- **D3**：删掉整个「通知提醒」区块。最省事，但丢掉后续 UI 位置。

## 七、明确不做的事（防范围蔓延）

- ❌ **不接支付**：付费墙已刻意整改为「不展示任何价格、不提供任何支付入口」（`paywall.tsx:24-39`），与法务声明一致。接支付须等商户号（阻断在主体变更），且**必须同步改 `legal.ts` 口径 + 走小程序虚拟支付**。
- ❌ **不把兑换码改成付费/加客服微信开通**：`paywall.tsx:36-39` 已记明这是下架级风险（小米「不得引导异常交易」/华为「切支付」二级违规）。兑换码**必须保持「免费获得」属性**。
- ❌ **不动 `health/index.ts` 占位**：`isHealthConnectable()` 恒 false 是刻意的诚实降级（`getWeRunData` 需「运动健康」类目资质，资质申请中），Profile 页据此隐藏入口。接步数前须先补后台隐私声明，否则 errno 112。
- ❌ **不实现 `share.ts` 导出**：已按 P2-A 如实置灰加角标，`doExport`/`doExportCsv` 入口短路不发网络请求。真实导出待后续接入 `wx.shareFileMessage`。
- ❌ **不做回迁自托管**：被 H1 硬阻断（`d-bee.cn` 无 DNS / 未备案 / 无 HTTPS）。endpoint 开关代码已就绪（`lib/backend.ts` 双确认门 + 构建期护栏），扳开关等备案。
- ❌ **不启用 `checkin` 页**：需先补日期/餐次/删除编辑/积分徽章结算，否则会绕过首页结算造成两端数据不一致。
