## 二、代码层真缺口（3 项，按严重度排序）

### 🔴 缺口 1 · AI 同意门只覆盖 2/4 个入口（PIPL 单独同意）

`mini/src/content/legal.ts:194` 对用户承诺：

> 「在你首次使用上述**任一** AI 功能前，我们会另行弹出说明并单独征得你的同意」

实际调用 AI 的有 4 处，只有 2 处有门：

| AI 调用点 | 函数 | 有 `AiConsent` 门 |
| --- | --- | --- |
| `pages/coach/coach.tsx:129` | `askCoach` | ✅ `:236` |
| `pages/scan/scan.tsx:178` | `recognizeFoodFromImage` | ✅ `:381`（且与平台隐私门串联两道） |
| `pages/onboarding/onboarding.tsx:119` | `generatePlan` | ❌ **无** |
| `pages/report/report.tsx:181` | `generateReportInsight` | ❌ **无** |

- **性质**：承诺与实现不符 = 隐私政策虚假陈述。用户填完引导问卷，数据未经单独同意就送进大模型。
- 🔴 **两端共有**：主端 `src/pages/Onboarding.tsx:155`、`src/pages/ReportScreen.tsx:205` 同样无门（主端只在 `CoachSheet.tsx:132`、`LogSheet.tsx:604,673` 有）。所以这不是「mini 落后于主端」，是两端一起漏。
- **修法**（二选一，见 §六拍板项 B）：
  - **补门**：两处照 `coach.tsx` 模式加 `aiConsentOpen` 状态 + `<AiConsent kind="plan|report">`。onboarding 的难点是 `loadPlan()` 由 `next()` 自动触发，需改成「进 result 步先弹门，同意后才 loadPlan」。
  - **改文案**：把 `legal.ts:194` 的「任一」收窄为实际有门的入口。**不推荐**——引导计划与报告解读确实在传用户数据给大模型，收窄文案等于放弃合规。

### 🔴 缺口 2 · 登录页无任何协议展示（小程序审核 + PIPL 告知）

`pages/login/login.tsx` 全文 258 行，**零处**「隐私」「协议」「同意」字样：
用户点「微信一键登录」或输入手机号前，看不到《用户协议》《隐私政策》入口，也没有勾选框。

- 对比主端：`src/components/PrivacyGate.tsx` 实现了国内安卓商店硬四要素（独立弹框、不可跳过、不默认勾选、协议可点开全文、不同意即退出），且挂在 `main.tsx:23` 包在 `<App />` 最外层以保证**同意前零网络请求**。
- mini 侧现状：平台层授权门有（`lib/privacy.ts`，管 errno 112），业务层首启同意门**没有**。
- **须区分两层，别混为一谈**：
  - 平台层（微信自动弹《用户隐私保护指引》）→ 已覆盖，靠 `privacy.ts` 主动触发；
  - 业务层（我方展示协议 + 征同意）→ **缺失**。小程序是否必须自建全屏 PrivacyGate 取决于微信审核口径，但**登录页放协议链接是确定要做的**（成本远低于全量 PrivacyGate）。
- **修法**：`login.tsx` 底部加一行「登录即表示同意《用户协议》《隐私政策》」，两个链接 `navigateTo` 到 `pages/legal/legal?id=terms|privacy`（该页已存在且可独立打开）。是否再加「不勾选不能登录」的 checkbox，见 §六拍板项 C。
- ⚠️ 若采纳全量 PrivacyGate：小程序页面栈由微信管理，**做不到** web 那种「App 根本不挂载」，只能做全屏遮罩组件逐页拦截，工程量与漏拦风险都高。**不建议在上线前做。**

### 🟡 缺口 3 · 提醒开关「可见但不可用」（与 P2-A 导出按钮同类）

`pages/profile/profile.tsx:486-509` 渲染两个可打开的 Switch：「每日打卡提醒」「饮水提醒」。
实际行为：

- `lib/notifications.ts:16` → `const CHECKIN_TEMPLATE_ID: string = ''`（**空**，未回填模板 ID）；
- `:46` → `if (!CHECKIN_TEMPLATE_ID) return 'no_template'`，静默降级、**不告知用户**；
- `:79` → `enableWaterNotify()` 只写本地 kv，**连订阅都不发起**（注释：「模板 ID 就绪后扩展」）。

结果：用户把两个开关都打开 → 界面显示已开启 → **永远收不到任何提醒**，且无任何提示。

- 这正是 P2-A 修掉的「导出按钮点下去转圈但拿不到文件」同一类问题：**可见但不可用 = 误导用户**。
- **修法**（三选一，见 §六拍板项 D）：
  1. **诚实置灰**（对齐 P2-A 的做法，推荐）：两行加 `line-badge`「即将上线」角标 + Switch 禁用，或点击后 toast 说明「提醒功能即将上线」。
  2. **让它真能用**：去 mp 后台申请订阅消息模板 ID 回填。⚠️ 微信订阅消息是**一次性授权**——用户同意一次只能推一条，做「每日打卡提醒」需每次进小程序重新拉授权，体验与实现成本都要评估。
  3. **直接删掉这个区块**：最省事，但会丢掉「后续要做提醒」的 UI 位置。

## 二·五、四端一致性实证审计结果（用户硬要求，2026-11-03 已修复）

> 用户原话：「**四个端的业务逻辑、收费用户及免费逻辑必须一致**」。以下是逐项核代码的结论，
> 已提交 `7d61151`。

### 先说架构事实（避免把「四端」理解错）

| 端 | 业务代码来源 | 说明 |
| --- | --- | --- |
| Web | `src/` | Capacitor `webDir: dist` |
| iOS | `src/` | 同上，`ios/` 目录**无独立 TS 业务代码**（已实证） |
| Android | `src/` | 同上，`android/` 目录**无独立 TS 业务代码** |
| 微信小程序 | `mini/src/` | 独立 Taro 4 工程 |

**所以「四端」实际是两套代码**：`src/`（web/iOS/Android 共用）与 `mini/src/`。一致性 = 这两套一致 + `server/`、`db/` 与两套前端一致。

### 审计结论：核心逻辑一致，真分叉只有两处（均已修）

**✅ 已验证一致的部分**（核过源码，不是推断）：

| 项 | 结论 |
| --- | --- |
| `calcBmr` / `calcTdee` / `calcTarget` | 两端**逐字一致** |
| `streak.ts`（连续打卡） | 实质差异 **0 行** |
| `report.ts`（周报逻辑本体） | 一致 |
| 服务端闸门（额度/权益） | 两库同源（migration `0039`），**不靠前端判断** |
| 数值舍入口径 | 已统一到 `packages/shared/src/numfmt.ts`（P1-A），两端 import 同一实现 |
| 付费墙文案差异 | 均为**刻意的端能力差异**且带注释（小程序无支付入口、iOS 只用 App Store 真实价） |

**🔴 真分叉 1 · 定价三副本（已修）**

同一个「月费 18 元」在仓库里有三份互不引用的副本：

| 副本 | 位置 | 原状 |
| --- | --- | --- |
| `PRICE_PRO_MONTHLY = 18` | `shared/constants` | 常量，**没人引用它做展示** |
| `PRODUCTS[].price = 18` | `shared/rules` | **内联字面量**，未引用常量 |
| `PRICE_TAG = '¥18 / 月'` | `src/pages/PaywallSheet.tsx` | **硬编码字符串** |

改价必漏改其一（且不会报错）。**修法**：`PRODUCTS` 改引用 `PRICE_*`、删除 `PRICE_TAG`、新增纯函数 `priceTag(p)` 从 `PRODUCTS` 生成文案。三档文案与旧硬编码**逐字一致**，线上展示零变化（由测试锁定）。

**🔴 真分叉 2 · 会员状态两份副本（已修，这个是用户可感知的 bug）**

`mini/src/pages/profile/profile.tsx` 的会员状态**完全是假的**：

- `const [pro, setPro] = useState(false)` / `lifetime` 声明后**从未被赋值**，也没 import `getEntitlement` → 付费用户在「我的」页永远显示「**免费版 + 升级按钮**」；
- 免费档把剩余拍照次数**硬编码成「今日剩拍照 3 次」**，真实额度可能是 0 → 用户点拍照才被 fail-closed 拒绝（体验割裂）；
- 缺 lifetime 的「已通过兑换码 XXX 永久解锁」与 pro 的「有效期至 X」两个分支。
- 讽刺的是：同端 `coach`/`report`/`scan`/`paywall` 四页**早就在拉** `getEntitlement`，只有本页漏了。

另外「有效期至 X」这句在两端共 **3 处**独立实现，全部直接调 `new Date(iso).toLocaleDateString('zh-CN')`（主端 `ProfileScreen`、`PaywallSheet`，mini `paywall`）。`toLocaleDateString` 的输出由各端 JS 引擎的 ICU/locale 数据决定，**web/iOS/Android 与微信小程序并不同步** —— 那不是「一致」而是「碰巧一致」，且这类分叉不会报错。

**修法**：新增 `packages/shared/src/datefmt.ts`（`formatCnDate` / `proUntilText` / `proNoticeText`）确定性拼串、不依赖 locale；会员副标题四分支下沉为 shared 的 `memberSubText`，**两端调同一个函数**（不是两份需人工对齐的副本）。mini profile 补权益拉取 + `useDidShow` 刷新（`navigateTo` 开付费墙、兑换成功 `navigateBack` 回来时页面仍在栈中、`useEffect` 不重跑）。

### 🟡 刻意保留的差异（**别当 bug 抹平**）

额度读不到时的行为两端**不同，且 mini 更严格是对的**：

| | 主端 | mini |
| --- | --- | --- |
| `getPhotoQuota` 失败 | 返回满额 `FREE_DAILY_AI`（fail-open 展示，P0-B 前的旧语义） | 返回 `{ totalRemaining: 0, degraded: true }`（fail-closed，P0-B 后补） |
| 展示层 | 显示满额数字 | 显示「今日拍照额度暂时读不到」，**不谎报数字** |

理由：显示一个读不到的额度等于向用户谎报 —— 他可能据此以为还能拍照，实际会在识别时被 fail-closed 拒绝。**宁可少显示，不可显示与真实额度不符的次数。**

### 验证与护栏

- 新增 46 项测试：`tools/price-single-source.test.ts`（18）+ `tools/mini-profile-member.test.ts`（28）；
- 全量 9 文件 **180 项**逐文件跑全绿；三端 typecheck 过；主端 `npm run build`（含 3 份法务页）与 mini `build:weapp` 过；
- 两端**产物**实测：日期分隔符 `charCode = 47`（正斜杠）、零 `toLocaleDateString` 调用、6 处会员文案均落在 shared chunk；
- 🔴 红绿验证 3 轮（防假绿）：分隔符改横线 → 8 红；删 null 守卫 → 8 红（**抓到 `有效期至 1970/1/1` 与 `NaN/NaN/NaN`**）；还原硬编码 3 次 → 8 红。

> 📌 踩坑记录（已写进代码注释）：`new Date(null)` **不报错**而返回 epoch（1970-01-01），
> `new Date(undefined)` 才是 Invalid Date。`pro_until` 对 lifetime 用户恒为 null，
> 少了守卫就会显示「有效期至 1970/1/1」。另：终端字体把 `/` 渲染得几乎和 `-` 一样，
> 肉眼判断分隔符会误判，**只有 `charCodeAt` 这类布尔断言能定论**。

### 3. 第一步 · DNS A 记录（备案下证后做）

**在阿里云云解析 DNS 控制台**（域名列表 → d-bee.cn → 解析设置）添加两条：

| 记录类型 | 主机记录 | 记录值 | TTL |
| --- | --- | --- | --- |
| A | `@` | `150.158.51.106` | 600（10 分钟，便于调试） |
| A | `www` | `150.158.51.106` | 600 |

**验证生效**（本地就能查，不用登服务器）：

```bash
python deploy/dnscheck.py d-bee.cn        # 走 DNSPod DoH（doh.pub），国内可访问
python deploy/dnscheck.py www.d-bee.cn
# 期望：[A] Status=0 且 -> d-bee.cn A 150.158.51.106
```

> 📌 `dnscheck.py` 用 DoH 查询，**绕过本地 DNS 缓存**，比 `nslookup` 更能反映真实权威解析结果。生效后本地 `nslookup` 可能还要等缓存过期，别被误导。

### 4. 第二步 · HTTPS 证书（脚本已就绪，不用手写命令）

**推荐方案：Let's Encrypt + certbot（脚本 `deploy/setup-https.sh` 已写好）**

跑法（走既有部署通道，`__DOMAIN__` 等占位符由 `deploy/dbee-ssh.py` 替换）：

```bash
# 单域名
DBEE_HOST=150.158.51.106 DBEE_USER=<user> DBEE_PWD=<pwd> \
DBEE_DOMAIN=d-bee.cn DBEE_CERT_EMAIL=<你的邮箱> \
bash deploy/deploy.sh https

# 多域名 SAN（一张证书覆盖多个域名，推荐）
DBEE_HOST=150.158.51.106 DBEE_USER=<user> DBEE_PWD=<pwd> \
DBEE_DOMAIN=d-bee.cn \
DBEE_DOMAINS='d-bee.cn www.d-bee.cn' \
DBEE_CERT_EMAIL=<你的邮箱> \
bash deploy/deploy.sh https
```

脚本会做的事（已核对源码）：前置检查每个域名是否解析到本机 IP（**未解析就直接退出，不会白跑**）→ 装 certbot → 签 SAN 证书并 `--nginx` 自动改写配置 → `--redirect` 把 80 做 301 到 443 → `nginx -t` 复检 → 端到端 curl 自测 → 自动续期由 certbot 的 systemd timer 接管（90 天有效期，自动续，**不用记到期日**）。

**certbot 的四个前置条件**（`setup-https.sh` 头部注释已写明，缺一即失败）：
1. A 记录已解析到本服务器公网 IP 且生效（脚本会自己校验并拦下）；
2. **80 端口能从公网访问**（HTTP-01 校验）—— 🔴 记得先在**腾讯云安全组**放行 80 与 443；
3. 已完成 ICP 备案（大陆服务器未备案时 80 会被拦截，校验必然失败）；
4. 每个域名在 nginx 里都有对应 `server_name` —— ✅ **这条已满足**：`switch-nginx-selfhost.sh:43` 的 `SERVER_NAME` 默认值已含 `d-bee.cn www.d-bee.cn`（预认领，在 DNS 未生效时也无副作用）。

**验证证书**（签完后）：

```bash
curl -sI https://d-bee.cn/ | head -1          # 期望 HTTP/2 200 或 301
echo | openssl s_client -servername d-bee.cn -connect d-bee.cn:443 2>/dev/null \
  | openssl x509 -noout -dates -subject -ext subjectAltName
```

**证书方案对比**（为什么选 Let's Encrypt）：

| 方案 | 成本 | 有效期 | 续期 | 微信小程序可用 | 评价 |
| --- | --- | --- | --- | --- | --- |
| **Let's Encrypt（certbot）** | 免费 | 90 天 | ✅ **systemd timer 自动续** | ✅ | **推荐**：脚本已就绪、零人工维护 |
| 腾讯云免费 DV 证书 | 免费 | 1 年（现多为 90 天） | ❌ 手动申请+手动部署 | ✅ | 国内集成好，但到期要人工换，容易忘 |
| 阿里云免费证书 | 免费 | 3 个月 | ❌ 手动 | ✅ | 有效期短且需手动，不如 LE |
| 付费 OV/EV 证书 | ¥1000+/年 | 1 年 | ❌ 手动 | ✅ | 小程序不要求 OV/EV，纯浪费 |

> 微信小程序只要求「受信任 CA 签发 + 证书链完整 + 域名匹配 + TLS ≥ 1.2」，**不要求付费证书**。Let's Encrypt 完全满足，且 `certbot --nginx` 默认配置 fullchain（证书链完整）。

### 5. 第三步 · 微信公众平台加 request 合法域名

路径：mp.weixin.qq.com → 【开发】→【开发管理】→【开发设置】→【服务器域名】→ request 合法域名 → 添加 `https://d-bee.cn`。

🔴 **微信的特殊限制**（与浏览器不同，容易踩；以下均据官方文档《网络》页核实，2026-11-03）：
- 域名只支持 **https**（request/uploadFile/downloadFile）与 **wss**（socket）协议；
- **端口规则（官方原意，此前本文档写错过）**：https 域名**可以配置端口**，但配置与请求必须**完全一致**——
  配了 `https://d-bee.cn:8443` 就只能向这个带端口的 URL 发请求；**不配端口则请求 URL 也不能带端口（连默认 `:443` 都不行）**。
  本项目直接用不带端口的 `https://d-bee.cn`（默认 443），最简单、无坑；
- **不能用 IP 地址或 localhost**（所以 `150.158.51.106` 永远加不进去，必须用域名）；
- 域名**必须已 ICP 备案**，且备案主体须与小程序主体一致（拍板 d-bee.cn 后天然满足）；
- **不支持配置父域名代子域名**：配 `d-bee.cn` 不等于放行 `x.d-bee.cn`，用到哪个子域名就得配哪个；
- `api.weixin.qq.com` 不能被配置为服务器域名；
- 证书要求：**受信任 CA 签发**（iOS 明确不支持自签名证书）、部署域名与证书颁发域名一致、**信任链完整**、TLS ≥ 1.2（certbot `--nginx` 默认满足全部四条）；
- 每月修改次数**有限制**（官方文档对第三方平台口径为 50 次/月；普通小程序另有「5 次/月」的流传口径，官方网络文档页未写明——**以 mp 后台实际提示为准**，别反复试错浪费次数）；
- 添加后需**重新编译**开发者工具、真机需**重进小程序**才生效。

### 6. 🔴 坑清单（每一条都会让你白等一天以上）

① **备案期间不要加 A 记录**（`docs/备案材料清单.md` §7 已记腾讯云官方规则）：
   - 未备案域名解析到大陆服务器会被自动拦截，访问只看到备案提示页；
   - 更严重的是**可能导致备案被驳回**（管局会查解析状态）。
   - 本站当前无 A 记录、线上走 IP 直连，**业务不受影响**，安心等下证。
   - 💡 便利做法：可先在阿里云把两条 A 记录**录好并设为「暂停」状态**，下证后一键启用（需确认当前控制台支持记录暂停；若不支持就下证后再加，多花 10 分钟而已）。
   - ⚠️ 注意「接入备案」规则相反（初审通过就要解析过去才解除拦截）—— 本站属**首次备案**，按上条执行。

② **腾讯云安全组忘记放行 80**：certbot 的 HTTP-01 校验走 80 端口，安全组没放行就会一直卡在校验超时，报错信息不会告诉你是安全组问题。签发前先在控制台确认 80/443 对 `0.0.0.0/0` 放行。

③ **DNS 生效前就跑 certbot**：脚本有前置检查会拦下（好事），但你会以为脚本坏了。先用 `dnscheck.py` 确认解析生效再跑。

④ **把官网域名混进主 server 块**：`switch-nginx-selfhost.sh:17,41` 已警告——`d-bee.com.cn`（公司官网）由独立的 `__CORP_SERVER_NAME__` server 块承载，**不要**加进主块 `SERVER_NAME`，两块重复声明同一域名会触发 nginx `conflicting server name` 告警。签证书时若要一起签，用 `DBEE_DOMAINS` 传全列表即可（SAN 证书支持），但 nginx 的 server 块归属别搞混。

⑤ **忘记回迁当天要先补服务端微信登录链路**：DNS+HTTPS+白名单都就绪、开关一扳，小程序会**登录失败**——因为自托管网关**没有** `/v1/login-wechat` 路由、`app_users.ident_kind` 也不允许 `wechat`。这三件是回迁清单 §四 的内容，**必须在扳开关之前做完并沙盒验证**。

⑥ 🔴 **绝不用 `deploy/deploy-gateway.sh` 改生产配置**：`load_secret` 缺失会 `rand_hex` 重置 `IDENT_PEPPER` → **全站身份永久失效**（所有用户被登出且无法恢复）。改网关配置一律走 `deploy/apply-vision-key-update.py`，且**预检放在重启之前**（网关仍跑旧配置，回滚零风险）。

### 7. 一句话总结

## 六、🔴 需你拍板的 4 个决策点

### A · 先发修复版，还是先变更主体？（**最优先，卡所有排期**）

`docs/收费模块-前置条件待办清单.md` 4.1 已记「🔴 P0：先发修复版，再发起变更」，理由是变更后新备案下来前不能发版（1–20 工作日）。

> 🔄 **2026-11-03 晚更新**：用户已拍板小程序**必须用 d-bee.cn**，而 d-bee.cn 在 ICP 备案下证前
> 既不能加 A 记录、也不能签 HTTPS 证书、更进不了微信白名单（§四·五）。这意味着：
> **小程序上线时间已经被 ICP 备案下证日期钉死了**，「先发修复版」这个选项的可行性已改变——
> 因为修复版同样必须连一个合法域名，而现在唯一的合法域名路线（d-bee.cn）正卡在备案上。

- **选项 A1（文档既有倾向）**：阶段 1 修完 → 立即提审发布 → 发布成功后再发起主体变更。
  - 优点：不被备案期冻结发版。
  - 🔴 **拍板后的新问题**：若小程序必须连 d-bee.cn，而 d-bee.cn 未备案 → **A1 现在走不通**（发出去的版本连不上后端）。
    除非暂时仍用 WorkBuddy 云域名过渡（但那正是本要被替换掉的第三方域名，主体不一致的驳回风险还在）。
  - 另一风险（原文仍成立）：以**个人主体**上线含健康数据的应用，审核可能质疑主体一致性
    （备案主体/隐私政策主体已是公司，小程序主体还是个人；`docs/主体注册后-实施计划.md:481`）。
- **选项 A2**：先变更主体 + 备案 + 类目 → 全部就绪后再发版。
  - 优点：主体与隐私政策公示一致，审核风险最低；且与 ICP 备案**本就同向**（都指向企业主体），
    两条备案可并行推进，不额外增加总时长。
  - 代价：上线时间被备案期（最长 20 工作日）推迟。
- **我的建议（拍板后更新）**：**走 A2**。理由是拍板 d-bee.cn 后，ICP 企业备案已是**必经之路**且周期最长，
  小程序主体变更与它能并行，A2 不再有「额外推迟」的代价；而 A1 需要小程序在过渡期继续依赖第三方云域名，
  既保留了主体不一致的驳回风险，又与「必须用 d-bee.cn」的拍板方向相悖。
  ⚠️ 但这条取决于一个**待你确认的事实**（§五 阶段 0 第 1 步）：你说的「备案主体已变更为北京迪蜂科技」
  指的是 **ICP 备案**还是**小程序主体变更**？两者时序不同，会直接改变排期。

### B · AI 同意门（缺口 1）怎么修？

- **B1（推荐）**：补门，让实现匹配承诺。onboarding 需把「进 result 步自动 `loadPlan()`」改为「先弹 `AiConsent`，同意后再生成」。

### C · 登录页协议（缺口 2）做到哪一步？
