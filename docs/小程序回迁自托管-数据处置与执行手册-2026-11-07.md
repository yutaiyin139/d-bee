## 二、为什么判「不能迁移」（四条硬证据）

1. **云库没有身份表。** MCP 列出的 17 张表里**没有 `app_users` / `schema_migrations`**；身份主体在 WorkBuddy 平台侧 TCB。云库 `profiles` 的 26 个列里也**没有任何 phone / email / openid / unionid** 字段，只有 `owner_id`。→ 无法建立「云库账号 ↔ 自建库登录凭证」的映射。
2. **owner_id 体系不同构。** 云库业务数据 owner_id **全部是 19 位数字**（`210…` / `211…`），`LIKE 'wx:%'` 命中 **0 行**；而 0043 规定 mini 微信用户在自建库的 owner_id 是 **`wx:<openid>`**。两边对不上。
3. **自建库没有对应身份行。** 生产实测 `app_users`：email 2 / phone 5 / **wechat 0**，业务表里 `wx:` owner 也是 0 行。RLS 按 `auth.uid()` 隔离，把云库 19 位数字的行搬进去，没有任何登录态能匹配 → **孤儿数据，谁都看不到**；还会和自建库现有 22 profiles / 101 meal_entries 测试数据混在一起制造脏数据。
4. **要做成「可用迁移」必须走路 B**（建 `openid → owner_id` 映射表、全业务表批量改写、处理 `honey_ledger_once(owner_id,reason,ref_id)` / `ai_usage UNIQUE(owner_id,usage_date,feature)` 等部分唯一索引）。为一批已确认要放弃的测试数据做高风险映射，与「不乱增复杂度」纪律相悖。

> 📌 边界澄清：**「放弃导入」≠「数据已销毁」**。云库实例本身未删除，17 张表仍可只读导出；若日后只想要一份离线归档，可单独做全量快照（MCP `mode=read` 逐表导出到 `db/backups/`），但**不进自建库**。本轮未做全量导出，因用户授权的是「不能迁移就放弃」。
