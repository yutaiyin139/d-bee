## 二、数据盘点（代码实证，非推测）

### 2.1 现有表（`db/schema.sql`）

`profiles` / `meal_entries` / `weight_logs` / `water_logs` / `exercise_logs` / `recipes` / `entitlements` / `ai_usage` / `quota_bonus`。

关键字段：

| 表 | 可直接用于健康档案的字段 |
| --- | --- |
| `profiles` | `nickname` `gender` `age` `height_cm` `start_weight_kg` `current_weight_kg` `target_weight_kg` `activity_level` `goal` `weekly_rate_kg` `daily_calorie_target` `protein_target_g` `carb_target_g` `fat_target_g` `health_connected` `health_connected_at` `step_goal` `created_at` `plan_started_at` `updated_at` |
| `weight_logs` | `log_date` `weight_kg` `note` |
| `meal_entries` | `log_date` `meal_type` `food_name` `grams` `calories` `protein_g` `carb_g` `fat_g` `sodium_mg` `fiber_g` `added_sugar_g` `source` |
| `water_logs` | `log_date` `amount_ml` |
| `exercise_logs` | `log_date` `name` `minutes` `calories` |
| `recipes` | `name` `items` `created_at` |

### 2.2 现有 API（`src/lib/api.ts`）

`getProfile()` `listMealsBetween()` `listLoggedMeals()` `listRecentMeals()` `listWeightLogsAsc()` `listWaterByDate()` `listExerciseByDate()` `listRecipes()` `exportAllData()`。

### 2.3 现有可复用纯函数与组件

| 能力 | 位置 |
| --- | --- |
| 报告聚合（近 7/30 天、营养素供能比、体重趋势） | `src/lib/report.ts`：`computeReport()` `kcalByDate()` `dayTone()` `monthCompareFromMeals()` |
| 图表 | `src/components/Charts.tsx`：`LineChart` `BarChart` `RatioBar`；`Ring.tsx`：`Ring` |
| 透明化说明 | `src/components/TransparencyNotes.tsx` |
| BMI 真源 | `packages/shared/src/healthPlan.ts`：`calcBmiCore()` `bmiBandOf()` `HEALTH_PLAN_BMI_BANDS`（`#8FB8D9 / #79B98A / #E8B95C / #D98174`，档位「偏瘦/标准/偏重/超重」）、`HEALTH_PLAN_BMI_DISCLAIMER` |
| 基础代谢 | `calcBmrCore()`（全精度）+ `numfmt.ts` `roundTo()`（展示层插值前舍入） |
| 日期键 | `packages/shared/src/datefmt.ts`：`dateKeyFromIso()` `diffDateKeys()` `shiftDateKey()` |
| 健康数据源 | `src/lib/health/index.ts`：`getHealthVendor()` `isHealthConnected()` `connectHealth()` `syncFromHealth()` `estimateActivityKcal()` |
| Sheet 外壳 | `src/components/Sheet.tsx`（`role="dialog"` `aria-modal` + `useModalA11y`） |

### 2.4 🔴 库中**完全不存在**的字段（全仓 grep 实证）

`体脂率` `腰臀比` `腰围` `臀围` `血糖` `用药` `疾病史` `过敏史` `饮酒史` `吸烟史`（对应 `body_fat` / `waist` / `hip` / `glucose` / `medication` / `allergy` 等）。

结论：图 2、图 3 中「维度数据 / 生理指标 / 健康史」三块**无数据可复用**。若要做，必须新建字段 + 迁移 + 录入 UI，且血糖/用药/病史属于**敏感个人信息与医疗健康数据**，会牵动隐私政策与会员协议正文（进而触发 `LEGAL_UPDATED` 与全体老用户重弹同意窗）。本轮规划明确**不做**。

## 三、目标形态

| 项 | 规划 |
| --- | --- |
| 入口 | 「我的 › 健康档案」列表菜单第 2 项；不新增路由，底部仍是 3 个 tab（今天 / 报告 / 我的），不建个人主页 |
| 形态 | **单态 `HealthRecordSheet`**：复用 `Sheet.tsx` 外壳，Sheet 内纵向滚动；无 segment、无本地 `selectedGoal`、无 tab 切换状态 |
| 锚点 | 顶部 4 枚胶囊（核心指标 / 健康数据源 / 饮食管理 / 运动记录），点击 `scrollIntoView` 定位；只是锚点，不是状态切换 |
| 视觉 | 保持自律蜜蜂：米白底 `--bg #fbf8f1`、白卡、`--ink-1/2/3`、蜂蜜黄小面积强调（竖条 / 进度 / 主数值折线）、14px 圆角、8px 内卡圆角、0.5px 级描边。不引入薄荷绿主色、卡通形象、AI 头像 |
| 四端 | 主端 `src/` = Web/iOS/Android 共用；mini `mini/src/` Taro 同构；文案与聚合纯函数下沉 `@dbee/shared/healthRecord.ts` 作单一真源，两端只做薄适配 |

## 四、四段板块详规

### 4.1 核心指标（数据直出）

| 展示 | 数据源 | 口径 |
| --- | --- | --- |
| 体重 `54.0 kg` | `profiles.current_weight_kg`，缺则取 `weight_logs` 最新一条 | `roundTo(...,1)`，展示层插值前舍入 |
| 近 7 次体重迷你折线 | `listWeightLogsAsc()` | 复用 `LineChart`（或轻量 polyline）；无记录时显示「还没有体重记录」而非空卡 |
| 当前 BMI `18.7` + 四段色带 + 档位 | `calcBmiCore(height_cm, current_weight_kg)` → `bmiBandOf()` → `HEALTH_PLAN_BMI_BANDS` | **必须 import shared 真源**，禁止另写阈值/色值；档位文案用「标准」，不用「正常」；`aria-label` 与三角指示器沿用 V1.7.6 四重非色彩编码；必带 `HEALTH_PLAN_BMI_DISCLAIMER` |
| 身高 / 目标体重 / 基础代谢 | `height_cm` / `target_weight_kg` / `calcBmrCore()` | 基础代谢展示值 `roundTo(...,0)` |
| 最后更新 | `weight_logs` 最新 `log_date` → 回退 `profiles.updated_at` → `created_at` | 日期键走 `datefmt.ts` |
| 单态目标徽标 | `GOAL_LABELS[profile.goal]` | 只渲染当前一态，不遍历 `GOAL_LABELS` |

**不展示**：体脂率、腰臀比、腰围、臀围（无数据）。

### 4.2 健康数据源（改名 + 复用现有连接）

| 展示 | 数据源 |
| --- | --- |
| 连接状态（已连接 / 未连接 + 厂商名，如 Apple 健康 / Health Connect / 华为 / 小米） | `getHealthVendor()` `isHealthConnected()` `health_connected` `health_connected_at` |
| 今日步数 / 步数目标 | `syncFromHealth().steps` / `profiles.step_goal`（默认 6000） |
| 活动消耗估算 | `estimateActivityKcal()` / `syncFromHealth().kcal` |

未连接时显示一句中性引导「连接健康数据源后，这里会显示步数与活动消耗」，**不放营销 CTA、不诱导付费**。「连接/断开」复用「我的」页既有开关，档案页只做只读展示，避免两处写状态。

**不展示**：血糖、用药、疾病史、过敏史、饮酒史、吸烟史。

### 4.3 饮食管理（复用报告聚合）

| 展示 | 数据源 |
| --- | --- |
| 今日热量摄入 / 目标 | `listMealsByDate()` 或 `computeReport()`；目标取 `daily_calorie_target` |
| 早 / 午 / 晚 / 加 四柱 | 按 `meal_type` 分组求和，复用 `BarChart` / `kcalByDate()` |
| 三大营养素供能比 | `computeReport()` → `RatioBar({segments})`；蛋白/碳水/脂肪按 4/4/9 kcal 换算 |
| 饮水 | `listWaterByDate()` 求和 / `waterTargetMl(weightKg)` |
| 可选补充 | 钠 / 膳食纤维 / 添加糖（`meal_entries` 已有字段），默认收在「更多」里，不占首屏 |

时间口径默认**今日**；如需「近 7 天」口径，拍板时一并说明（复用 `rangeDays(7)`）。
零记录时显示「今天还没有记录饮食」，不显示 `- 千卡` 之类空值卡。

### 4.4 运动记录（改名 + 复用运动记录）

| 展示 | 数据源 |
| --- | --- |
| 本周次数 / 累计时长 / 消耗估算 | `listExerciseByDate()` 按 `weekOf()` 汇总 `minutes` `calories` |

**不做**燃脂心率、心率区间、疗效/减脂承诺（用户 11-14 已拍板「燃脂心率暂时不做」，且 `legal.ts` 非医疗建议红线）。板块名用「运动记录」，不用「运动燃脂」。

### 4.5 底部透明化说明

复用 `TransparencyNotes` 组件，至少覆盖：数值来自已填资料与每日记录、为自我记录用的估算值、**不构成医疗诊断或治疗建议**、身体不适请咨询专业人士。文案下沉 shared，禁止两端硬编码。

## 五、不采用清单与理由

| 参考图元素 | 判定 | 理由 |
| --- | --- | --- |
| 「健康关注：没有发现任何异常，你的健康状态真的很稳定！」 | ⛔ 不采用 | `legal.ts:384` 与 `HEALTH_PLAN_NOTES` 明确不构成医疗诊断/健康评估；此类结论属医学判断 |
| 卡通头像 / AI 女生助手头像 / 红点 | ⛔ 不采用 | 与自律蜜蜂视觉语言不符；项目无 AI 助手人设 |
| 拟人化引导（「我才能看见你悄悄的改变~」「补一下…我才能避开不适合你的建议」） | ⛔ 不采用 | 改中性说明文案，避免暗示个性化医疗建议 |
| 「正常」标签 | ⛔ 改「标准」 | 与 shared BMI 档位一致，避免诊断色彩 |
| 空值占位卡（`- %` / `- 厘米` / `- mmol/L`） | ⛔ 不采用 | 库中无字段，摆空卡等于暗示未来要做录入；改为整段不展示 |
| 「完善进度 34%」 | 🟠 待拍板 | 口径需重定义为「资料填写完整度」而非「健康档案完善度」，且明确不代表健康评估；详见 §八-1 |
| 四段横向 tab 切换 | 🟠 改锚点 | 保持单态，不引入切换状态 |

## 六、合规与技术红线（沿用项目铁律）

1. 🔴 零 `plan_summary`：旧 AI 建议文案会与当前目标矛盾（V1.7.5 已定纪律）。
2. 🔴 零 `forecastGoal()`：达成日只属于体重管理方案；档案页不做目标预测，避免两个口径。
3. 🔴 数值口径唯一权威 `@dbee/shared/numfmt.ts` / `src/lib/numfmt.ts`；计算层全精度，只在展示层插值前 `roundTo()` 舍入；禁止自写 `toFixed` / `Math.round(n*f)/f`。
4. 🔴 BMI 只 import `healthPlan.ts` 真源，禁止另写阈值、色值、档位词。
5. 🔴 不改 `LEGAL_UPDATED`、不改法务三页正文、不新增敏感个人信息收集；不做医学诊断词、疗效承诺、燃脂心率。
6. 🔴 零新增表 / 零新增字段 / 零迁移 / 零后端接口 / 零网关改动；不跑 `deploy-gateway.sh`。
7. 🔴 护栏断言三条铁律：一个 `it()` 一条断言、匹配「实际使用」而非「标识符出现」、断言在 `stripComments()` 后的代码上做；新增护栏必须做退化红验证。
8. 🔴 两层构建产物互斥（native 构建会覆写 `dist/`），发版前按既有零删除备份流程处理。
