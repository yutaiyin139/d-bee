# 健康数据源方案（运动健康对接总规划）

> 2026-10-18 · 随 iOS 连接缺陷修复一并成文。
> 结论先行：**D-Bee 不直连手环，只读"系统健康平台"**。手环/手表的数据由厂商 App
> 自动汇入系统健康平台，D-Bee 只对接平台层，一套读法通吃所有穿戴设备。

---

## 1. 背景与本次修复

### 1.1 iOS 连接缺陷（本次已修）

**现象**：首次点击「连接 Apple 健康」能弹出系统权限页，选完设置后界面无变化；
之后再点按钮无任何反应。

**根因**：Apple 的 `HKHealthStore.authorizationStatus(for:)` 对**读取**类型恒返回
`.notDetermined`（苹果刻意不向 App 暴露"读授权"是否被允许）。旧 Swift 插件用
`sharingAuthorized` 判断读授权，永远为 false → 授权弹窗走完后插件仍上报
`authorized:false` → 前端判为失败；第二次点击时系统判定"已询问过"不再弹窗，
流程静默完成 → 表现为「按钮再也触发不了」。

**修复**（已落地，待 Mac mini 首次构建验证）：

| 层 | 改动 |
|---|---|
| Swift 插件 | 删除伪 `authorizationStatus` 查询；`requestAuthorization` 改为上报 `completed`（授权流程走完即 true，真实数据以 `fetchToday` 为准） |
| `lib/health/healthkit.ts` | 接口对齐：`{ completed }`；移除不可靠的授权状态探测 |
| `lib/health/index.ts` | `connectHealth()` 流程走完即存云端 `health_connected:true`；`syncFromHealth()` 直接拉数据；新增 `disconnectHealth()` |
| Dashboard | 连接按钮加 loading 态（「连接中…」），杜绝"点了没反应"观感 |
| 我的 > 健康数据源 | 显示连接状态（未连接/已连接），**始终可点击重新授权**，已连接时可「解除连接」 |

**设计原则**：读授权不可探测是 Apple 的硬约束，业界通行做法（自律茄子等）都是
"流程完成即视为连接 + 数据兜底"。D-Bee 的连接状态真源 = 云端
`profiles.health_connected`（用户意图），数据真源 = `fetchToday` 实际返回。
步数恒为 0 时在「健康数据源」页引导用户到
`iOS 设置 > 健康 > 数据访问权限 > 自律蜜蜂` 手动勾选。

### 1.2 用户诉求

1. 连接失败后必须仍能重新触发连接（✅ 健康数据源页常驻入口）。
2. 全面规划手环、华为运动健康、小米运动健康等数据源。
3. 按终端类型出不同连接 UI，但不过度设计，确保简洁好用。

## 2. 核心架构决策

### 2.1 只读"系统健康平台"，不直连手环（关键决策，勿推翻）

```
手环/手表 ──(蓝牙)──> 厂商健康 App ──(自动同步)──> 系统健康平台 ──(只读)──> D-Bee
        华为手环→华为运动健康        iOS: Apple 健康(HealthKit)
        小米手环→小米运动健康        Android: Health Connect
```

理由：
- **蓝牙 GATT 直连手环** = 每个品牌一套协议（华为 BLE 私有协议、小米 BLE 私有协议），
  开发/维护成本极高，且 手环 App 的数据更全（睡眠、心率）——直连得不偿失。
- 系统健康平台是官方聚合层：华为运动健康、小米运动健康都支持把穿戴数据
  同步到 Health Connect（Android）或 Apple 健康（iOS）。
- D-Bee 只需要步数 + 活动能量两个指标，读平台层即可覆盖"任何品牌手环"。

### 2.2 分层（沿用既有架构铁律：平台差异只走 src/lib 抽象层）

```
src/lib/health/
  brand.ts       品牌识别（UA + 平台探测，纯函数，已就绪）
  index.ts       统一门面 connectHealth / disconnectHealth / syncFromHealth
  healthkit.ts   iOS 适配器（dbee-health 插件）
  healthconnect.ts   Android 适配器（阶段 2，dbee-health 插件加 Android 实现）
业务代码只 import index.ts，不嗅探品牌/平台。
```

数据模型：沿用 `profiles.health_connected` + `health_connected_at`；
若未来同时多源连接，升级为 `health_vendor` 字段（当前单源，不过度设计）。

## 3. 分终端路线与 UI 形态

| 终端 | 数据通道 | 能力 | UI 形态 | 阶段 |
|---|---|---|---|---|
| iPhone | Apple 健康（HealthKit） | 真同步 | Dashboard 连接 chip → 系统授权 → 步数/活动能量卡；我的 > 健康数据源 管理页 | ✅ 阶段 1（已实现，待 iOS 构建回归） |
| Android（小米/OPPO/vivo/荣耀等） | Health Connect | 真同步（厂商健康 App 写入 HC 后可读） | 与 iOS 同一套真连接 UI，换文案与图标 | 阶段 2 |
| 华为（HarmonyOS 4 及以下 / 安卓版） | 华为运动健康 App：普通安卓无公开读取 API；华为 Health Kit 开放平台需企业开发者资质 + 数据合规审核 | 引导 → 阶段 3 真同步 | 阶段 1：引导行（App 名 + 跳转提示 + 手动记录兜底）；阶段 3：申请 Health Kit 后接真同步 | 阶段 1 引导（已实现）/ 阶段 3 评估 |
| 微信内置浏览器 | 微信运动无读取 API | 说明 | 提示文案，不显示连接按钮 | ✅ 已实现 |
| 普通浏览器 / PWA | 无 | 无 | 不显示连接入口 | ✅ 已实现 |

### 3.1 阶段 2：Health Connect（Android 真同步）

- 在 `dbee-health` 插件加 Android 实现（Health Connect SDK，minSdk 26+，
  需要 Android 14 起系统内置 / 低版本装 Health Connect APK）。
- 读 `StepsRecord` + `TotalCaloriesBurnedRecord`（activeEnergy 对应物），
  聚合逻辑与 Swift 侧一致，前端零改动（门面层已封好）。
- 前端 `brand.ts` 增加 `'health-connect'` 能力探测：`isHealthConnectAvailable()`。

### 3.2 阶段 3：华为 Health Kit（有资质后再做）

- 前提：企业开发者账号 + 华为运动健康开放平台申请（数据处理协议、隐私合规）。
- 拿不到资质就永远停在引导行，不阻塞主线。

### 3.3 小米运动健康

- 无公开第三方读取 API（截至 2026-10）：永久引导行 + 依赖阶段 2 的
  Health Connect（小米运动健康 App 支持同步数据到 Health Connect）。

## 4. UI 原则（不过度设计清单）

1. **入口只有一个语义**：Dashboard 运动卡 = 数据展示 + 首次连接；
   我的 > 健康数据源 = 状态管理（重连/解除/排查）。不在别处再放按钮。
2. **每个终端只出现一种形态**：真同步 / 引导 / 隐藏，三选一，不做混合态。
3. **状态只有三态**：未连接（可点）、连接中（loading）、已连接（数据展示 +
   可解除）。禁止"连接失败/部分授权"等第四态——读授权不可探测，无法如实呈现。
4. **连接失败永远有路可走**：失败提示必须包含「可在 我的 > 健康数据源 重新连接」。
5. **不做自动重试、不做授权状态轮询**：数据拉取跟随页面加载 +
   `visibilitychange`，拉到什么展示什么。
6. **文案给路径不给悬念**：步数为 0 的排查文案直接给系统设置的完整路径。

## 6. 健康数据源与手动运动的计算关系（2026-10-18 定稿）

**第一要点：运动数据合理，健康数据源是手动运动的有效补充，不是替代。**

| 场景 | 结果 |
|---|---|
| 拿得到健康数据（活动能量 > 0，或步数 > 0 可估算） | 参与「已消耗 / 净摄入」计算 |
| 拿不到（未连接 / 无数据） | 完全不影响，手动运动照常按 `burnKcal` 计算 |
| 活动能量 vs 手动运动 | **二者取较大值**，不叠加（见下） |

**为什么取较大值而非叠加**：Apple 健康的活动能量 `activeEnergyBurned` 是全天累计，
天然已包含用户手动记录的那次运动（骑车/散步等）。若再叠加 `burnKcal`，同一次运动
会被算两次、虚高消耗 → 用户"越动越能吃"，违背减脂目标。取 `max(burnKcal, activityKcal)`
保守不虚高，且当健康数据源缺失时自然退化为纯手动运动，二者边界清晰。

实现（`src/pages/Dashboard.tsx`）：
```
effectiveBurnKcal = max(burnKcal, activityKcal)   // 手动 vs 活动，取大
netKcal = 摄入 − effectiveBurnKcal × 50%           // 活动部分仍按 50% 计入「可吃回」
```
「已消耗」总览与「热量环形卡」用 `effectiveBurnKcal`；「运动」卡标题仍显示
手动运动自身的 `burnKcal`（手动记录是独立事实，不被吞掉）。

## 5. 验收清单（Mac mini iOS 首次构建时执行）

- [ ] 首次点「连接 Apple 健康」→ 系统权限弹窗出现 → 允许 → 按钮变已连接、步数/活动能量出现
- [ ] 首次弹窗点「不允许」→ 仍显示已连接（Apple 约束），到「我的 > 健康数据源」点重新授权 → 去 iOS 设置勾选 → 回 App 数据出现
- [ ] 已连接后杀 App 重开 → 自动同步，无需再授权
- [ ] 「解除连接」→ 云端 health_connected=false → Dashboard 恢复连接按钮
- [ ] 再次点连接 → 无弹窗直接完成（系统已询问过）→ 数据恢复同步
