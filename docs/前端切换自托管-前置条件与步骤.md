## 二、执行步骤（按依赖顺序，不可跳步）

### 第 1 步：搭 auth/JWT 网关（先打通登录）

**为什么先做**：数据库侧 `auth.uid()` 兼容层已就绪，但 `badge_stats` / `leaderboard` 等函数依赖
`request.jwt.claim.sub`（JWT），不是 `app.user_id`。登录必须先打通，后续所有 RPC 才有身份。

**要实现的端点**（对齐前端 `AuthScreen.tsx` 实际调用，已核对）：
- `POST /.cloud/auth/v1/verification` ← 前端 `cloud.auth.sendOtp({ phone })`
  - 返回 `{ verificationId, isExistingUser }`
- `POST /.cloud/auth/v1/token` ← 前端 `cloud.auth.verifyOtp({ phone, verificationId, isExistingUser, token })`
  - 验码通过 → 查/建 `profiles` 里对应 `owner_id` → 签发 JWT（`sub` = owner_id）
- `GET /.cloud/auth/v1/user/me` ← 前端 `cloud.auth.getSession()`
  - 解 JWT 返回用户信息
- `POST /.cloud/auth/v1/refresh` ← 会话续期

**关键点**：
- JWT 载荷 `sub` = 原 owner_id（如 `2109869577155379200`）
- 网关在每笔 DB 请求前 `SET LOCAL app.user_id = <sub>` **并**注入 `request.jwt.claim.sub`（两者都要，
  前者给 RLS，后者给 badge_stats/leaderboard 这类函数）
- 验证码通道先用「日志打印 + 万能码」，跑通后再接真短信

**验收**：手机号登录 → 拿到 JWT → 查询只返回自己的数据（RLS 生效）。

### 第 2 步：搭 REST 兼容端点（数据读写，工作量最大）

**为什么最重**：`src/lib/api.ts` 已把 ~20 个业务函数收口在 `db()` 一个函数里，底层是
`cloud.database.from(table)` 的 PostgREST 语义链式查询。切换只需替换 `db()` 底层，业务函数体不动。

**要实现的端点**：
- `POST /.cloud/database/rest/v1/<table>`（或对齐 SDK 实际路径）
  - body：`{ select, filters: [{op, column, value}], limit, order, data }`
  - 支持 select / insert / update / delete / eq / in / gte / lte / order / limit / maybeSingle
- `POST /.cloud/database/rest/v1/rpc/<fn>` ← `callRpc()` 的 23 个业务函数
  - consume_ai_quota / consume_photo_quota / get_photo_quota / get_today_photo_count /
    grant_photo_bonus / release_photo_quota / bind_invite / count_invitees / settle_invite_checkin /
    grant_honey / redeem_honey / redeem_by_code / unlock_badge / badge_stats / leaderboard /
    refund_checkin_* / expire_stale_honey / create_payment_order / verify_payment_order / invite_throttled 等

**实现策略（推荐，代价最小）**：不做通用 REST DSL，直接把 `api.ts` 的业务函数逐个映射成自建
SQL/存储过程。因为 `db()` 已收口，只在 `db()` 底层换自建 HTTP 客户端即可。

**验收**：打卡 / 记餐 / 兑换 / 榜单 / 邀请 全链路 CRUD 在自托管上跑通。

### 第 3 步：搭 LLM 代理（AI 识别 + 教练）

**要实现的端点**（对齐 `src/lib/ai.ts`，已核对）：
- `GET /.cloud/llm/models` → 返回模型列表，含 `id / supportsImages / isDefault` 字段
- `POST /.cloud/llm/chat/completions` → OpenAI 兼容，**必须 SSE 流式**
  - 前端 `collectText` 写死只支持流式，逐 chunk 回 `delta.content`

**关键坑**：
- `pickModel` 需要 `supportsImages === true` 的模型（图片识别），否则拍照识别报错
- 必须流式，代理侧对齐即可，**不要改前端**

**验收**：拍照识别能出 JSON；`askCoach` 能流式回文本。

### 第 4 步：切换发布（替换 Nginx 上游，前端零改动）

1. 把①+②+③合并成一个 Node 服务（如 `server/index.mjs`），`systemd` 托管，监听 `127.0.0.1:8080`

4. IP 直连验证 → 域名/HTTPS（等 ICP 备案）

## 四、风险提示

1. **不要动前端**：`cloudConfig.ts` 同源反代策略 + `api.ts`/`ai.ts` 收口层，是「零前端改动」切换的关键，务必保持。
2. **iOS IAP 验签（0029）**：依赖服务器能访问 Apple 验签域名，自托管后需确认服务器网络出口可达。
3. **微信登录/支付**：依赖营业执照 + AppID，自托管后仍暂缓，不影响手机号 OTP 登录。
4. **云库还活着**：切换期间云库可用，可随时回滚（改回 nginx 上游即可）。
5. **备份**：切换前对 dbee 库再做一次 `pg_dump` 全量备份，防止误操作。
