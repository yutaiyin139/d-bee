# 各端逻辑梳理 + iOS 编译卡点排查报告

> 生成：2026-10-24 ｜ 触发：用户在 Mac mini（Xcode 27.1）上无法编译，要求「再次详细梳理各端逻辑、排查原因、做好内部测试」
> 结论速览：**三端代码本身正确、Xcode 27.1 兼容性已核实通过；无法编译的根因是 Mac mini 环境状态（Xcode active developer path 损坏 + shared 包未构建 + SPM 首次解析），不是代码缺陷。**

## 一、三端架构总览

D-Bee 是「一套 React 源码 + Capacitor 混合壳 + Taro 小程序」的多端架构，核心业务规则抽到 `packages/shared`（单一真相源），三端共享。

| 端 | 承载方式 | 数据面 endpoint | 现状 |
|---|---|---|---|
| **Web** | Vite + React，部署 `http://150.158.51.106/`（自托管） | `window.location.origin`（Nginx 同源反代到自建网关） | ✅ V1.7.0 已发布 |
| **Android 原生** | Capacitor 8.5.3 + `https://localhost` WebView | 绝对 HTTPS（`CLOUD_HOST`，经 OriginProxy 原生插件代发） | ✅ 全过，V1.7.0(11) |
| **iOS 原生** | Capacitor 8.5.3 + `capacitor://localhost` WebView | 同上（OriginProxy / CapacitorHttp） | ⏸ 待 Mac 首次构建 |
| **小程序三端** | Taro 4.3.0（微信/支付宝/抖音） | 云库直连 | ✅ 编译通过，待真机联调 |

### 数据面 endpoint 解析（`src/cloudConfig.ts`）

三层优先级，是理解「各端连哪」的关键：

1. `VITE_CLOUD_ENDPOINT` 显式注入（排查用，最高优先）
2. **原生分支**：`detectNative()` 为真时，取 `VITE_NATIVE_ENDPOINT`（构建时注入），否则回退 `CLOUD_HOST = https://zilv-mifeng.app.workbuddy.host`
3. **Web 分支**：取当前 `window.location.origin`（Nginx 同源反代），本地开发回退云端

**关键点**：原生 WebView 的来源（`capacitor://localhost` / `https://localhost`）不能作为 endpoint，必须钉死绝对 HTTPS 地址，靠 OriginProxy 原生插件注入 `Origin/Referer` 头绕过 CORS 预检。

## 二、iOS 编译卡点完整排查（五个报错/风险点，逐个定性）

### 卡点 1：`failed to resolve import "@dbee/shared"`（vite build 阶段）— ✅ 已定性，代码侧可改进

**根因**：`packages/shared` 的 `dist/` 在 `.gitignore`（第 2 行 `dist/`）里，**不入 git**。Mac 全新 clone 后 `dist/` 不存在，而 `vite.config.ts` 没配 alias、根 `package.json` 也没有 `postinstall`/`prepare` 钩子自动构建 shared，于是 vite 解析 `@dbee/shared`（靠 `node_modules/@dbee/shared` symlink + `package.json` 的 `exports` 指向 `dist/index.js`）失败。

**这是纯环境问题，不是代码 bug**，但暴露一个**可改进的工程缺陷**：首次 clone 必须手动 `cd packages/shared && npm run build`，容易漏。

**建议（内部测试前置改进）**：在根 `package.json` 加 `postinstall` 钩子自动构建 shared：
```json
"scripts": {
  "postinstall": "npm run build -w packages/shared"
}
```
> 注意：当前根 package.json 未声明 `workspaces`，`-w` 需先补 `"workspaces": ["packages/*", "native-plugins/*"]`。或简化为 `postinstall: "cd packages/shared && npm run build"`（不依赖 workspaces，改动更小、更稳）。**需在 Mac 上验证 `npm ci` 后 shared 是否自动构建。**

### 卡点 2：`missing package product 'CapApp-SPM'` — ✅ 已定性，首次解析/缓存问题

**根因**：Xcode 未解析本地 SPM 包或缓存陈旧。`CapApp-SPM` 依赖图含 2 个远程包（`capacitor-swift-pm` 8.5.3、`ion-ios-camera`）+ 5 个本地包，首次必须联网拉远程包，网络不通/缓存陈旧都会导致 product 解析失败。

**修法**：`File → Packages → Reset Package Caches` → `Resolve Package Versions`；清 `~/Library/Caches/org.swift.swiftpm`。

### 卡点 3：`CocoaPods is not installed` + `xcrun: invalid active developer path` — ✅ 已定性，环境问题（核心卡点）

**根因**：`xcrun` 失败是主因，`CocoaPods is not installed` 是连带误报。

- D-Bee **纯 SPM，仓库从无 Podfile**（已 `find ios -name Podfile*` 证实为空），**不需要也不该装 CocoaPods**。
- Capacitor CLI 判定包管理器的逻辑（`config.js:361`）：`ios/App/CapApp-SPM` 目录存在 → `'SPM'`；否则回退 CocoaPods 分支 → `which pod` 失败 → 误报。`CapApp-SPM` 目录其实一直都在（`git ls-tree` 证实从 `74ff3c2` 起就在仓库）。
- **真因是 Xcode active developer path 损坏**：升级 Xcode 27.1 后 `/var/db/xcode_select_link` 指向失效位置，`xcrun --find xcrun` 报 `failed to locate xcrun`。

**修法**：`mdfind "kMDItemCFBundleIdentifier == 'com.apple.dt.Xcode'"` 找真实路径 → `sudo xcode-select -s <真实路径>/Contents/Developer` → `sudo xcodebuild -license accept` → `sudo xcodebuild -runFirstLaunch`。

### 卡点 4：Xcode 27.1 兼容性 — ✅ 已核实可用，无需降级

三项硬性前置全部满足：

1. **UIScene 已完整采纳**（Apple TN3187：iOS 27 SDK 构建的 App 不采纳 UIScene 会「编译成功但启动即崩」）：
   - `SceneDelegate.swift` 存在，用 `CAPBridgeViewController` + `SceneDelegateProxy.shared` 正确转发
   - `Info.plist:90-108` 有完整 `UIApplicationSceneManifest`
   - `AppDelegate.swift:36-43` 实现 `configurationForConnecting`，`config.delegateClass = SceneDelegate.self`
2. **swift-tools-version 5.9**（4 个 Package.swift 全是）：Capacitor 8 官方默认值，**Capacitor 8 尚不支持 Swift 6，勿升级**
3. **platforms .iOS(.v15)** 低于 iOS 27 SDK，无冲突

### 卡点 5（新发现，潜在编译风险，非阻塞）：StoreKit API 传参类型

`DbeeIapPlugin.swift`：
- 第 37 行 `Product.products(for: Set(ids))` ✅ 正确（显式 Set）
- 第 61 行 `Product.products(for: [productId])` ⚠️ 传的是数组字面量，而 StoreKit 2 签名是 `Set<String>`

**判断**：数组字面量 `[productId]` 在参数类型明确为 `Set<String>` 时可隐式推断为 Set，**大概率编译通过**，但属首次编译需留意的点。**不擅自改**（Windows 无法验证 Swift 编译），若 Mac 上此处报错，改 `Set([productId])` 即可。

### 卡点 6（2026-10-30 22:00 新增，实测踩中）：真机纯白屏 = 用 `npm run build` 打的原生包

**现象**：iPhone 16 真机打开 App 纯白/米白屏，无报错弹窗、无加载指示器；Xcode 编译通过、`cap sync` 正常。
极易误判为「public/ 没同步」——但那修法（`npm run build && cap sync ios`）恰恰**会复现同一个白屏**。

**根因（已用构建产物实证）**：整改 #1（`39a576b`）在 `src/cloudConfig.ts` 的 `resolveNativeEndpoint()`
加了 fail-closed 护栏：
```ts
if (import.meta.env.PROD && mode !== 'native-release' && mode !== 'native-internal') throw new Error(...)
```
用 `npm run build`（MODE=`production`）构建时该条件**恒真**，被打包器死代码消除成**无条件 throw**：
```js
function b5(){throw new Error("原生 App 必须使用 build:native 或 build:native:internal 构建…")}
function E5(){if(N5())return b5();…}          // N5=detectNative，iOS 上恒真
const lo={resourceId:…,endpoint:E5(),…}       // 模块级 publicConfig，import 时立即求值
```
`publicConfig` 是**模块级常量** → JS 首行即炸 → React 连 `PrivacyGate` 都没机会挂载 → 白屏。
CSS 已加载故呈米白色（`#FBF8F1`）。**这是确定性故障，不是偶发。**

**判定（30 秒，装机前就能识破）**：
```bash
grep -c "禁止直接复用 Web 产物" dist/assets/index-*.js   # 0=✅正常；≥1=🔴白屏包
grep -oE 'function b5\(\)\{.{0,120}' dist/assets/index-*.js
#   function b5(){return ku}       ✅ 返回 endpoint 常量
#   function b5(){throw new Error( 🔴 白屏包
```
实测对照：`production` 产物 = 无条件 throw；`build:native:internal` 产物 = `return ku`
（`ku="https://zilv-mifeng.app.workbuddy.host"`），护栏字符串计数为 0。

**修法**：按数据面选对 mode 重打 —— 内测 `VITE_ALLOW_CLOUD_NATIVE=true npm run build:native:internal`；
上架 `VITE_NATIVE_ENDPOINT=https://d-bee.cn npm run build:native`；然后 `npx cap sync ios`。

**教训**：`ios/App/App/public` 是 gitignore 的（`ios/.gitignore:4`），Mac 上的包内容**完全由 `cap sync`
决定**，构建 mode 选错会被忠实同步进去。**代码侧加了构建期护栏，文档侧必须同步改**——本手册与
《今晚-Mac编译执行手册》旧版教的正是 `npm run build`，护栏于是退化成「无声白屏」。已入架构铁律 #10。
