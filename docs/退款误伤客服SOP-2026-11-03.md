## 一、这份 SOP 解决什么问题

苹果退款会**自动**回收会员权益。回收逻辑对「权益来源混合」的用户存在一处**已知误伤**，
误伤后用户会来找客服，而当前**没有任何客服文档**说明如何核实、如何补发、补多少。

`db/migrations/0037-apple-iap-settlement.sql:318-324` 原文已声明这条边界：

```
-- ⚠️ 已知边界：蜜糖兑换 pro 后又苹果购买 pro（source 变 apple），退款会
--   连带清掉蜜糖那段时长。发生率低且宁可少给不可多给（退款白嫖是资损），
--   真发生走客服补发（redeem 通道仍在）。
```

**本 SOP 的第一条结论就是：上面那句「redeem 通道仍在」的补救建议不成立，照做会造成资损。**
详见第二节。

---

## 二、🔴 先纠正一个危险的补救误区

审计注释建议「走客服补发（redeem 通道仍在）」。**两条现成通道都不能用来补发**：

| 通道 | 实际行为 | 为什么不能用于补发 |
| ---- | -------- | ------------------ |
| `redeem_by_code(code)`<br/>（`0012-redeem-server-and-invite-throttle.sql:27`） | 写 `plan='lifetime'`、`pro_until=NULL`、`source='redeem'` | 兑换码发的是**终身买断**。用它补「被清掉的 30 天蜜糖 Pro」= 把 30 天赔成永久，**资损远大于原损失** |
| `redeem_honey('pro30Day')`<br/>（`0039-rpc-trust-boundary.sql`） | 扣 2600 积分 → 加 30 天 pro | ① 是 `SECURITY DEFINER` + `auth.uid()`，**只能由用户本人在客户端会话里调**，客服无法代调；② 会**再扣用户 2600 积分**，用户积分本已被那次兑换扣过，等于让他再付一次钱 |

且经全量核查：**当前不存在任何「管理员/客服代补发」的 RPC**。
所有写 `entitlements` 的函数（`redeem_by_code` / `redeem_honey` / `settle_apple_purchase`）
要么是 `auth.uid()` 自服务，要么是苹果报文驱动。
**因此补发只能由运营人员直连数据库手工执行**（第四节），这也是本 SOP 存在的核心理由。

## 三、误伤是怎么发生的（机制）

`entitlements` 表**一个 owner 只有一行**（`UNIQUE (owner_id)`），
`source` 记录的是**最后一次发放来源**，不保留历史分段。

```
entitlements(id, owner_id UNIQUE, plan, pro_until, redeemed_code, created_at, updated_at, source)
```

时间线：

1. 用户用 2600 积分兑 30 天 Pro → `redeem_honey('pro30Day')` 写入 `plan='pro', source='honey'`
2. 用户又在 App Store 买了 Pro → `settle_apple_purchase` 把该行改成 `source='apple'`
   （`0037:228` / `0037:242`：`source = CASE WHEN plan='lifetime' THEN entitlements.source ELSE 'apple' END`）
3. 苹果退款 → `revoke_apple_purchase` 执行：
   ```sql
   UPDATE entitlements SET plan='free', pro_until=NULL, source=NULL
    WHERE owner_id=v_owner AND source='apple';
   ```
   这一步命中的正是**那一行**，于是**蜜糖兑的 30 天一起被清掉**。

### 🔴 比审计描述更严重的一点（本次核查新发现）

`redeem_honey` 的**续期分支不写 source**（`0039`）：

```sql
ELSIF v_plan = 'pro' AND v_until IS NOT NULL AND v_until > now() THEN
  UPDATE entitlements SET pro_until = v_until + make_interval(days => v_days), updated_at = now()
   WHERE id = v_ent;          -- ⚠️ 没有 SET source='honey'
```

即：若用户**先有苹果 Pro**，之后再用积分续期，蜜糖天数会**并入 `source='apple'` 那一行且不留任何标记**。
后果有两层：

- 退款时同样被一并清掉；
- **更麻烦的是无从追溯**——`entitlements` 单行结构里完全看不出「其中有多少天来自蜜糖」，
  客服不能只看 `entitlements` 就决定补几天，必须回查 `honey_ledger`。

### 好消息：蜜糖 Pro 兑换在账本里可精确识别

`redeem_honey` 写 `honey_ledger` 时，两类兑换的 `ref_id` 不同：

- **Pro 天数兑换**：`reason='redeem'` 且 **`ref_id IS NULL`**
- AI 拍照兑换：`reason='redeem'` 且 `ref_id` 形如 `'ai-YYYY-MM-DD-HHMMSSMS'`

所以「这个用户历史上用积分换过多少天 Pro」是**可精确查证的**，不必猜。见第四节查询。

## 四、客服处理流程

### 前置

- **客服邮箱**：`dbeeSupport@163.com`（两端 `legal.ts:47` 一致公示。
  🔴 2026-10-27 由 `support@d-bee.com.cn` 改来——原域名无 MX 记录收不到信，别再往旧地址发）
- **数据库连接**：见 `docs/自托管数据库远程连接指南.md`
- 所有操作**只读优先**：先跑查询确认事实，再决定是否执行写操作

### 步骤 1 · 定位用户与那笔退款

```sql
-- 用 Apple 交易号 / 原始交易号定位（用户能提供 App Store 收据里的交易号）
SELECT transaction_id, original_transaction_id, owner_id, product_id, plan,
       purchased_at, expires_at, environment,
       revoked, revoked_reason, revoked_at, settled_at
  FROM apple_transactions
 WHERE transaction_id = $1 OR original_transaction_id = $1;
```

要点：
- `revoked = true` + `revoked_reason IN ('refund','revoke')` → 确认权益确实被系统回收过
- `environment` 若是 `Sandbox` → 是沙盒测试交易，不是真实用户，按测试处理不必补偿
- 记下 `owner_id`，后续全部以它为准

### 步骤 2 · 核对通知留痕（确认退款是苹果侧真实下发的）

```sql
SELECT notification_type, transaction_id, processed, error, received_at
  FROM apple_notifications
 WHERE transaction_id = $1 OR original_transaction_id = $1
 ORDER BY received_at DESC;
```

- `notification_type = 'REFUND'` / `'REVOKE'` 即触发源（`server/lib/iap.mjs:480`）
- `processed=false` + `error='txn_not_found'` → 通知到了但没找到交易，权益其实**没被回收**，
  那用户投诉的可能是别的问题，不要按误伤补发

### 步骤 3 · 查证用户到底损失了多少蜜糖 Pro 天数

```sql
-- 该用户历史上所有「积分兑 Pro」记录（pro1Day=100 → 1 天，pro30Day=2600 → 30 天）
SELECT id, amount, reason, ref_id, created_at
  FROM honey_ledger
 WHERE owner_id = $1
   AND reason = 'redeem'
   AND ref_id IS NULL          -- 🔴 关键：只取 Pro 兑换，排除 ai 拍照兑换
 ORDER BY created_at DESC;
```

天数换算：`-100` → 1 天，`-2600` → 30 天。

**只补「因这次退款而被连带清掉」的那部分**，判断依据：
兑换时间**早于**步骤 1 查到的苹果购买时间（`purchased_at`）的蜜糖兑换，才可能是被吞掉的；
且需人工判断这些天数在退款时**是否还没到期**（已过期的天数本来就该没了，不补）。

### 步骤 4 · 执行补发（运营手工 SQL）

> ⚠️ 写操作，执行前把查询结果与用户诉求截图归档。**必须先 SELECT 后 UPDATE**。

```sql
-- 4.1 先看当前状态（留档）
SELECT id, owner_id, plan, pro_until, source, updated_at
  FROM entitlements WHERE owner_id = $1;

-- 4.2 补发 N 天 Pro（N = 步骤 3 核定的天数）
--     source 写 'support' 以便与正常发放区分、日后对账
UPDATE entitlements
   SET plan       = 'pro',
       pro_until  = COALESCE(GREATEST(pro_until, now()), now()) + make_interval(days => $2),
       source     = 'support',
       updated_at = now()
 WHERE owner_id = $1;

-- 4.3 复核
SELECT plan, pro_until, source FROM entitlements WHERE owner_id = $1;
```

说明：
- 用 `COALESCE(GREATEST(pro_until, now()), now())` 而非直接 `now()`：
  若用户当前还有未到期权益则在其后叠加，已过期/为空则从现在起算，避免把剩余时长清零
- `source='support'` 是新引入的取值。已核实 `entitlements.source` 现有取值仅三种：
  `apple`（`settle_apple_purchase`）/ `honey`（`redeem_honey` 首次插入）/ `redeem`（`redeem_by_code`）。
  🔴 **务必不要写 `'apple'`**，否则这笔补发权益下次退款又会被 `revoke_apple_purchase` 清掉
- 若用户投诉的是「积分被扣了但没到账」（另一种故障），补的是**积分**不是 Pro：
  ```sql
  INSERT INTO honey_ledger (owner_id, amount, reason, ref_id, expires_at)
  VALUES ($1, $2, 'support_refund', 'ticket-' || $3, now() + make_interval(days => 365));
  ```
  ⚠️ `reason='support_refund'` 两端前端都无对应中文名（`REASON_LABEL` 在主端
  `InviteCenter.tsx:28` 与小程序 `mini/src/lib/invite.ts` 各有一份副本，均无此 key），
  靠 `REASON_LABEL[l.reason] ?? l.reason` 兜底，流水页会显示原始 key `support_refund`。
  若在意显示效果，需同步给两份副本加该 key（顺带记一笔：这两份 `REASON_LABEL`
  是典型的四端分叉，属 P2-B 同类问题）。

### 步骤 5 · 归档

每单记录：用户标识（`owner_id`）、Apple 交易号、核定损失天数、补发内容、执行人、日期。
建议直接在 `docs/` 下建 `客服工单台账.md` 追加，或用工单系统。

## 五、范围边界（不要误判适用范围）

- ✅ **本 SOP 只覆盖苹果 IAP 退款**。全仓核查确认：退款自动回收逻辑**仅存在于**
  `server/lib/iap.mjs`（`REFUND`/`REVOKE` 分支）。
- ⚠️ **微信支付 / 支付宝目前没有自动退款回收通路**（`server/` 下无相关处理）。
  这两个渠道若发生退款，权益**不会自动回收**（即不会误伤，但存在退款不回收的资损敞口）。
  属独立问题，不在本 SOP 范围，见第六节决策点 2。
- ⚠️ 小程序端**当前无支付入口**（`docs/P1-D在线支付实装前置清单-2026-11-03.md` 已核实），
  故小程序用户不会遇到本问题；其 Pro 全部来自兑换码或积分。

## 六、🔴 待拍板决策点

### 决策点 1：是否从根上消除误伤（推荐做，但需排期）

现在的根因是 `entitlements` **单行 + source 只记最后一次**，无法表达「同一用户的多来源分段权益」。
三个方案：

| 方案 | 做法 | 代价 | 评价 |
| ---- | ---- | ---- | ---- |
| **A（最小改动，推荐先做）** | 给 `redeem_honey` 续期分支补 `source='honey'`，或加 `has_honey_segment bool` 标记；`revoke_apple_purchase` 命中带蜜糖标记的行时改为「只回收苹果部分」或「转人工」 | 改 1–2 个 SQL 函数 + 一次迁移 | 至少让「有蜜糖分段」可被识别，退款不再盲目清零 |
| **B（正确但重）** | 新增 `entitlement_segments(owner_id, source, days, granted_at, consumed_at)`，`pro_until` 由各段汇总 | 改 3+ 个 RPC + 迁移 + 对账 | 彻底解决，但触及权益核心链路，风险高，宜独立立项 |
| **C（不改代码）** | 仅靠本 SOP 人工兜底 | 0 | 发生率低时可接受，但每单都要人工核账，不可规模化 |

**建议**：先 C（本 SOP 已就绪，可立即兜底），排期做 A。B 除非投诉量上来否则不急于动。

### 决策点 2：微信 / 支付宝退款回收缺失是否要补

当前这两个渠道退款后权益不回收（资损敞口）。但：
- 微信/支付宝支付**尚未正式上线**（资质未就绪，见 `P1-D在线支付实装前置清单`），暂无真实退款场景；
- 建议**在支付正式上线前**再补，届时随支付 adapter 一起做，避免现在为不存在的流量写代码。
