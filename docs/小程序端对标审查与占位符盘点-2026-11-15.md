## 1. 审查范围与方法

## 2. Q1｜数据导出：故意为之的完整证据链

### 2.1 两端代码对照

| | 主端（Web / iOS / Android / Mac） | mini |
| --- | --- | --- |
| 入口 | `src/pages/ProfileScreen.tsx:726-760`：Pro 显示可点「导出」按钮 | `mini/src/pages/profile/profile.tsx:774-795`：三分支 |
| 逻辑 | `:363-401` `doExport()` / `doExportCsv()` → `exportAllData()` → `src/lib/share.ts` | `:397-434` 先过 `guardExport()` 再走同名流程 |
| 落盘 | `src/lib/share.ts`：Web 用 `createObjectURL + a.download`；原生用 Capacitor Filesystem 写文件 + Share 面板（`files: [file://URI]`） | `mini/src/lib/share.ts:34-56` `exportJSON` / `exportText` 恒返回 `{ channel:'none', message: 占位提示 }` |
| 单一真源 | 无（本就可用） | `mini/src/lib/share.ts:27` **`isExportAvailable = false`** |

mini UI 三分支（`profile.tsx:779-794`）：

- 非 Pro → `Pro ›` + 点击拉付费墙（与主端一致，11-08 补齐）
- Pro 且 `!isExportAvailable` → 整行降饱和 + **「即将上线」角标**；点击仍给「可通过邮箱申请副本」提示
- 可用时 → 显示「导出 / 导出中…」

`guardExport()`（`:384-395`）在 `!isExportAvailable` 时提前 `return false` 且**刻意不发网络请求**，所以 `exportJSON` / `exportText` 的占位函数体在运行时**根本不可达** —— 用户看到的是角标和邮箱兜底提示，不是「敬请期待」转圈。

### 2.2 判定为「故意」的 9 条证据

1. `mini/src/lib/share.ts:14-26` 文件头长注释：明确写「UI 与实现共用的单一真源」「未来实装只改这里返回 true」，并说明 P2-A 之前「可见但不可用」是误导、必须修。
2. `mini/src/pages/profile/profile.tsx:769-773` 注释：刻意「不禁用点击」，因为邮箱路径是 PIPL 第 45 条数据复制权的真实兜底，不能因补 Pro 门控把权利入口藏掉。
3. `mini/src/content/legal.ts:276` 隐私政策第五条如实声明「数据导出功能正在接入小程序端，当前版本暂不可用；……可通过邮箱提出」。
4. `packages/shared/src/content/transparency.ts:110-116` 对外透明度文档：「导出能力存在端差异（mini 的 `isExportAvailable=false`，入口显示「即将上线」），故本段**不承诺『现在就能导出』**」。
5. `mini/src/pages/paywall/paywall.tsx:96-98` 权益清单**刻意删掉**「+ 数据导出」，理由写死：宣传即为不符、与 legal.ts §五冲突。
6. `tools/release-readiness.test.ts` 护栏 19-D：「主端 PRO_ITEMS 比 mini 恰好多『+ 数据导出』一条」+「**两端差异说明注释必须存在（防被当成 bug 顺手抹平）**」。
7. `tools/four-end-consistency.test.ts:1193`：「数据导出必须有 Pro 门控，且非 Pro 仍保留 PIPL 邮箱兜底」。
8. 历史决策链：`docs/四端一致性与商业化优化-审计与实施计划-2026-11-03.md` P2 #9 → P2-A 加角标/置灰（commit `932451c`）；`docs/待办清单-云库废弃收尾-2026-11-08.md` 补 Pro 门控并保留邮箱兜底；`docs/四端收费一致性核验与合规实施总纲-2026-11-09.md` #8 登记为「**真实端能力差异，不抹平**」。
9. 今日 `docs/智能设备功能梳理-2026-11-15.md` 的「零假功能」原则一脉相承：宁可标「接入中 / 即将上线」，不做看起来能点的假按钮。

**结论**：这是被实现、UI、法务、护栏四层同时锁住的**有意产品决策**。它规避的是「Pro 付费权益宣传了却拿不到」的合规风险，代价是 Pro 用户在小程序端看到「即将上线」会困惑 —— 属产品待办，不属缺陷。

### 2.3 一个可讨论的点：技术上并非「平台做不到」

微信开放文档 `wx.shareFileMessage`（基础库 2.16.1+，参数 `filePath` 只需本地/临时路径，**限制：仅在点击行为时调用**）配合 `wx.getFileSystemManager().writeFile(wx.env.USER_DATA_PATH/...)` 即可把 JSON/CSV 转发到聊天。这与「用户主动点导出」天然契合，也与今天规划的微信运动「禁止生命周期自动调用」同构。

所以 mini 导出是**排期/技术债**，不是能力缺失。实装要点（若拍板）：写临时文件 → `shareFileMessage` → `isExportAvailable` 改 `true` → 同步恢复 PRO_ITEMS「+ 数据导出」、改写 `legal.ts` §五与 `transparency.ts`、放宽护栏 19-D 并做红验证；**必须真机验证微信客户端对 .json / .csv 的接受度**，社区资料在此点上口径冲突，只认官方文档 + 实测。

## 5. 新发现：通知提醒是比导出更隐蔽的同类问题

- **主端**：`src/lib/notifications.ts` 有真实调度 `syncLocalNotifications()`（Capacitor LocalNotifications，固定 ID、先取消再排程、权限状态可查）；UI 用 `notifSupported`（`ProfileScreen.tsx:689`）**条件渲染整块**，插件不存在时宁可不显示，注释原话「显示一个点了没反应的开关，比不显示更伤信任」。
- **mini**：`mini/src/lib/notifications.ts:16` `CHECKIN_TEMPLATE_ID = ''` → `requestCheckinSubscribe()` 恒返回 `no_template`，从不申请授权；`enableWaterNotify()` 只写偏好。UI（`profile.tsx:741-764`）**无条件渲染两个 Switch，且无任何说明文字**（主端还有「每天 20:00 提醒记录饮食」「9:00~21:00 每 2 小时」的 sub 文案，mini 连这个都没有）。
- 法务 `mini/src/content/legal.ts:257` 已如实写明「仅在小程序本地保存开关偏好，尚未接入微信订阅消息，因此不会向你推送消息」——**合规上无瑕疵**，但普通用户不会读隐私政策才去拨开关。
- **护栏盲区**：`tools/docs-quota-consistency.test.ts` 护栏 24-D 只断言两端 `kvGet('notif.checkin','0')` 默认值；全 `tools/` 中**没有任何一条**检查 `CHECKIN_TEMPLATE_ID`、`requestSubscribeMessage` 或 `isNotificationsSupported`。即：护栏保证「默认关」，不保证「打开后真有提醒」。同理，护栏 19-D 只钉权益清单文字差异，不钉「清单之外 UI 上还有哪些假开关」。

**建议**（三选一，待拍板）：① 两个开关加一行「仅保存偏好，暂不推送」说明（最小改动、最诚实）；② 对齐主端按能力条件隐藏；③ 直接申请订阅消息模板 ID 实装（工作量大，需后台操作）。

## 6. 护栏盲区与建议补强

现有护栏是「**已登记差异的精确快照**」，不是「能力可达性检查」。建议补一条「占位能力清单」护栏：把 `isExportAvailable`、`CHECKIN_TEMPLATE_ID`、`XPAY_SALE_ENABLED`、`isNotificationsSupported` 这类单一真源集中登记，并断言「凡能力为 false 的入口，UI 必须有角标 / 说明 / 条件隐藏之一」，否则红。这样 A2 这类「无标注假开关」将来不会再从缝里冒出来。按项目铁律：新增护栏须先写断言 → 红验证 → 再动源码。
