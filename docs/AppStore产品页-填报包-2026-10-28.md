### 21:9 与 16:9 的区别：原生尺寸 vs 通用素材（选哪个？）

Apple 官方表格里「产品页面标题」这个版位有**两行**：21:9（3840×1646）和 16:9（5244×2950）。二者不是二选一的重复项，性质不同：

| | 21:9 3840×1646 | 16:9 5244×2950 |
|---|---|---|
| 性质 | **header 版位原生尺寸** | **universal 通用素材**（一图服务两版位） |
| 会被裁切吗 | 不按别的比例裁（但仍受设备/方向/语言影响） | 会被 header 按 21:9、被 search 按 3:2 分别裁 |
| Apple 模板 Art Safe Area | **1646×661 居中**（占画布 17.2%，中心 y=50%） | 1402×962，中心在 **39% 画布高**（仅占 8.7%） |
| 格式 | PNG / **JPEG** 皆可 | **仅 PNG** |
| 推荐用途 | 只投 header 版位时用它，可用面积大得多 | 想一张图同时覆盖两个版位时用它 |

**结论**：若只为「产品页面标题」这一个版位出图，**优先 21:9**——安全区占画布 17.2%（vs universal 的 8.7%），是后者约 2 倍，构图从容得多，且允许 JPEG。16:9 通用素材仅在需要「一图两版位」时才用。

⚠️ **两张安全区的垂直中心不同**（21:9 居中 = 50%，universal 偏上 = 39%），代码里按 ratio 分别取值，不可混用——`shot-creative.mjs` 与 `verify-creative.mjs` 均已用 `ART_SAFE[ratio]` 表驱动。

### ⚠️ 关键发现：16:9 是「通用素材」，会被两个版位裁切，且 Apple 官方安全区极小

Apple 官方表格把 16:9（5244×2950）同时列在 **product page header** 和 **search results** 两行——它是**一张图服务两个版位**的 universal asset，不是某个版位的原始尺寸。《Asset Best Practices》两条硬要求：

- *"keeping key aspects of your art within the safe area defined in each template"*（核心元素必须落在每个模板规定的安全区内）
- *"确保焦点图案位于构图的中心，以防止出现任何不必要的裁剪"*

第三方实测 Apple 官方 PSD 模板里的 `Art Safe Area` 图层（2026-09-24 下载，文件日期 2026-08-05）：

| 模板画布 | Art Safe Area | 位置 | 占画布 |
|---|---|---|---|
| header 3840×1646 | 1646×661 | 居中 | 17.2% |
| search 3840×2560 | 2168×1030 | 居中 | 22.7% |
| **universal 5244×2950** | **1402×962** | 水平居中、垂直中心在 **39% 画布高** | **仅 8.7%** |

> 📌 两个「安全区」口径必须分清，此前一度混淆：
> · **几何裁切交集** = 21:9 保宽裁高 + 3:2 保高裁宽的交集 = 中央 **84.4% × 76.2%**。这只保证「居中裁切下不被切掉」。
> · **Apple 官方 art safe area** = **26.7% × 32.6%**（1402×962）。这是 Apple 给的设计红线，远小于几何交集——因为 Apple **不公开裁切算法**，实际版位还可能因设备/方向/语言产生额外裁切。
> **应以官方 art safe area 为准**，几何交集只能作为「至少不会被切」的下界。

**结论：UI 界面截图不该放在 universal 素材里。** 业界对 8.7% 安全区的通行判断是「只放 logo 或单一主体，不要放 UI 界面」；而 Apple 对搜索结果版位的原话恰是 *"展示亲身体验。可以考虑分享界面、内容或游戏画面"*、对顶部横幅则是 *"聚焦单个清晰明确的理念。视觉上过于密集或杂乱的素材资源会削弱冲击力"*。因此：

- **16:9（默认 brand 布局）**：核心内容（App 图标 + 品牌名 + 主标题 + 合规角标）全部收敛进 1402×962 安全区；安全区外只放装饰（蜂巢纹理、光斑、CSS 绘制的手机剪影），**不含任何文字与 logo**，被任何版位裁掉都不损失信息。副标题与 3 条特性在此布局下不展示（安全区装不下，且 Apple 要求「聚焦单个清晰明确的理念」）。
- **3:2 两张（showcase 布局）**：满幅展示真实 UI 截图 + 副标题 + 3 条特性。这两张是版位原始尺寸、**不被裁切**，UI 界面正应放这里。

`…-showcase.png` 是 16:9 的满幅 UI 备选版（视觉冲击更强），**默认不用**：它只满足几何裁切交集，不满足 Apple 官方 8.7% art safe area。若要上传，须先在 **ASC 预览工具**（Product Page Information → 预览，支持 iPhone/iPad、横竖屏、多语言、明暗模式）确认两个版位都显示完整，再决定。

### 画面构成与合规处理

### 渲染策略（可复现）

CSS viewport = 目标像素 / 2，`deviceScaleFactor = 2` → 精确像素且文字矢量光栅化不糊：

```
3840×1646 → viewport 1920×823  @2x   （1646/2=823 整除；比例 2.3329 vs 官方 21:9=2.3333，
                                        官方标注本身即取整值，以 3840×1646 为准）
5244×2950 → viewport 2622×1475 @2x   （2950/2=1475 整除；与理论 16:9 的 2949.75 差 0.25px，
                                        官方标注本身即四舍五入值，以 5244×2950 为准）
3840×2560 → viewport 1920×1280 @2x
1920×1280 → viewport 960×640  @2x
```

页面 `creative-assets.html` 全部用 `vw` 单位 + `[data-ratio='21x9'|'16x9'|'3x2']` 三布局，同一份 DOM 等比适配三种画布比例；布局由 `body[data-layout='brand'|'showcase']` 切换（21:9 与 16:9 默认 brand，3:2 恒为 showcase）。

**21:9 的专属处理**：该画布纵向只有 823 CSS px，两行标题会挤压 661px 高的安全区，且 Apple 对顶部横幅要求「聚焦单个清晰明确的理念」→ 文案变体额外提供 `headlineWide`（单行、无 `<br>`），仅在 `ratio=21x9 && layout=brand` 时启用；品牌行也从竖排改为横排以省下纵向空间。

```bash
node deploy/verify-creative.mjs                       # 先验证布局（含 Apple art safe area 断言）
node deploy/shot-creative.mjs                         # 出全部 4 个尺寸（variant 0）
node deploy/shot-creative.mjs --variants 3            # 每个尺寸出 3 个文案变体（便于 A/B 与本地化替换）
node deploy/shot-creative.mjs --only 21x9             # 只出 3840×1646（产品页面标题）
node deploy/shot-creative.mjs --only 21x9 --variants 3
node deploy/shot-creative.mjs --only 16x9             # 只出 5244×2950
node deploy/shot-creative.mjs --only 16x9 --layout showcase   # 16:9 满幅备选版（文件名带 -showcase 后缀）
```

依赖：playwright（全局 workspace，同 `shot-store.mjs` 的加载方式）+ Python PIL（去 alpha）。showcase 布局依赖 `deploy/screenshots/store/iphone-{report,today,log}.png`，若缺失先跑 `node deploy/shot-store.mjs --iphone`（brand 布局不需要截图，只需 `public/icon-512.png`）。

⚠️ 写临时 playwright 脚本时记得复用 `findCachedChrome()` 回退逻辑——本机 playwright 默认找的 `chromium_headless_shell-1243` 不存在，只有完整 chromium，不回退会直接报 `Executable doesn't exist`。


> 🔧 **踩过的坑（均已修）**：
> 1. **flex `min-width:auto` 导致缩放永不触发**：`.phones` 作为 flex 子项被内容撑到不收缩，`fitPhones()` 测得 `avail == need` → 溢出 stage（首测报 `手机组 452 ⚠️溢出`）。修法：`.phones` / `.phone-stack` 显式 `min-width:0`；测量改用各 `.phone` 的 `getBoundingClientRect` 并集而非 `scrollWidth`（后者不含 `transform: scale/translateY` 与负 margin 的视觉影响，与溢出检查口径不一致）；且**不要**给 `.phones` 加 `overflow:hidden`，否则手机投影被硬切成直边。
> 2. **CSS 特异性互搏**：`body[data-layout='brand'] .copy`（0,2,1）被 `.stage[data-ratio='16x9'] .copy`（0,3,0）压过，导致 brand 尺寸全部未生效（表现为 headline 仍按 showcase 的 3.5vw 渲染、超出安全区）。修法：15 条 16:9 showcase 覆盖规则统一加 `body[data-layout='showcase']` 前缀，让两套布局互斥而非互搏。
> 3. **`.footnote` 移入 `.copy` 后定位包含块变化**：`.copy` 必须是 `position:static`，否则其内部的角标绝对定位会以 `.copy` 为包含块而非 `.stage`。
> 4. **numpy 内容包围盒被背景渐变干扰**：首版用「与四角底色不同的像素」判边界，因背景有径向渐变而判为左 0.0%/右 0.0%（误报满幅）。改用深色亮度阈值（`lum<45` / `<90`）定位手机边框与文字才得到真实边界。

### 在 ASC 哪里上传（与设备截图不是同一个入口）

创意素材走 **Asset Library（素材资源库）**，不在版本页的「截屏」区域：

1. ASC → 我的 App → 选择 App → 左侧 **Asset Library（素材资源库）**
2. 点「+」→ **上传创意素材**（不是「上传预览和截屏」）
3. 选中文件上传 → 给每个素材起一个便于排序的内部名（建议 `placement_ratio_theme_locale_version`，例如 `universal_16x9_brand_zh-Hans_v1`、`search_3x2_ui_zh-Hans_v1`）
4. 查看每个素材的 **Works With（适用于）** 字段，确认它被识别为可服务的版位
5. 提交前用 **Product Page Information → 预览工具**逐个版位核对（支持 iPhone/iPad、横竖屏、多语言、明暗模式）——**这是唯一能看到真实裁切的地方**，因为 Apple 不公开裁切算法
6. 提交路径二选一：
   - **首个版本尚未获批** → 创意素材必须**随第一个 App 版本一起提交**（Apple：*"If your app has no approved version, include the asset in the same submission as your first app version."*）——**本 App 属于这种情况**
   - 已有获批版本 → 可在 Asset Library 里单独 `Add for Review`，或随版本一起提交
7. 管理素材需要 **Account Holder / Admin / App Manager** 角色（Marketing 角色可上传但不能单独提交）

⚠️ 注意事项：
- 素材只能在状态为 **Prepare for Submission** 时删除；之后只能**归档**（归档后不能用于新版位，但可取消归档）。
- 单独提交的素材会**按 App 的最新版本**审核——意味着素材宣称的功能必须与当前线上/在审版本一致（2.3.14）。
- **创意素材不会自动用于 Apple Ads**：Apple Ads 只接受 3:2 文件，若将来投放付费搜索需另建专用 3:2 素材。

### 是否必须上传？

**选填。** 若不提供搜索结果创意素材，Apple 会退回展示 In-App Events / App 预览 / 截屏。考虑到本次是首次提审、且素材需随首个版本一起提交，建议：
