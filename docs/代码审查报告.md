## 二、排查结果：干净的部分

1. **没有任何 TODO / FIXME / 占位注释**。`src/` 里 `placeholder` 命中的全部是输入框的 `placeholder` 属性（ legitimately 表单提示），`mock` 命中的只有 `preview-main.tsx` —— 这是刻意隔离的本地预览入口，**不挂在 `index.html` 主入口上，`vite build` 不会打包它**（已在构建产物里核实）。
2. **没有 `as any`、`@ts-ignore`、`debugger`、`console.log` 残留**。所有 `throw new Error` 都是面向用户的中文错误兜底，属于正常错误处理。
3. **前后端链路无假数据**：`api.ts` 每个读写都带 `error.message` 兜底与「记录不属于当前账号」的越权检查；`owner_id` 一律由数据库 `DEFAULT auth.uid()` 填充，前端不传，RLS 兜底。
4. **`db/schema.sql` 与代码完全对齐**：`meal_entries.health_score / ai_note / quantity_text / image_url` 等列都有写入路径（其中 `health_score` 此前只写不读，见下文修复）。

## 三、发现并已修复的缺陷

### 1. `health_score` 是「只写不读」的死数据（半成品功能） ✅ 已修
AI 每次识别都生成 0–100 的健康分（prompt 里专门要求），落库到 `meal_entries.health_score`，但**全项目没有任何一处展示它**。模型在白花钱、数据库在白存。
→ 修复：纳入新的食物画像引擎（见第四节），作为评分的另一半依据，并在界面上标注「N 项参考了 AI 评分」。

### 2. 可读份量被覆盖丢失 ✅ 已修
`LogSheet` 保存时把 `quantity_text` 硬写成 `` `${grams} 克` ``，把 AI / 商品库给出的「1 碗」「1 包（50 克）」整段丢掉。记录列表里只剩一个干巴巴的克数。
→ 修复：保留原始描述，格式化为「1 碗（200 克）」；用户手动改过份量时才回退为克数（避免描述失真）。

### 3. 12 种运动里 4 种永远选不到 ✅ 已修
`Dashboard` 用 `EXERCISES.slice(0, 8)` 渲染选项，**HIIT / 羽毛球 / 篮球 / 爬山没有入口**，但 MET 数据一直都在、`exerciseKcal` 也支持它们。
→ 修复：改为横向滚动的完整列表（`.chips-scroll`，超出可滑动，不换行不遮挡）。

### 4. 首页没有页脚 —— 备案合规风险 ✅ 已修
`SiteFooter`（法律文档入口 + 备案号）只在登录页和「我的」页出现。**备案号下来后，网站首页底部必须展示备案号**，否则就是违规。
→ 修复：`Dashboard` 底部补 `SiteFooter`，`App.tsx` 相应传入 `onOpenLegal`。

### 5. 数据导出缺 `ai_usage` ✅ 已修
`exportAllData` 导出了档案 / 饮食 / 体重 / 饮水 / 运动，但漏了 `ai_usage`。AI 使用记录同样是个人数据，缺它意味着「数据可携带权」的导出不完整。
→ 修复：导出包补上 `ai_usage`，并在类型与注释中说明原因。

### 6. 死代码清理 ✅ 已删
`formatDateCN` 在首页改版后失去全部调用方，属于死代码，已删除。

## 四、新增功能

### 1. 食物画像引擎：风险发现 + 益处探索（核心新增）

**设计立场**：这是纯函数、完全离线、**不消耗 AI 额度**的规则引擎。理由——「这食物有什么问题」是可以用营养学规则算清楚的，不该烧模型额度；而 AI 额度留给「拍照识别」这种真正需要模型的环节。断网也能用，结果可复现、每条结论都带数字依据（如「脂肪提供了 52% 的能量」）。

判定维度：

| 维度 | 风险示例 | 益处示例 |
|---|---|---|
| 能量密度 | ≥400 kcal/100g「热量密度高」 | ≤80「低热量密度」 |
| 脂肪供能比 | ≥50%「高脂」/ ≥35%「偏油」 | ≤25% 且蛋白足「脂肪比例适中」 |
| 蛋白质 | — | ≥20g「蛋白质很高」/ 高蛋白低脂 |
| 碳水 | 含糖饮料 / 碳水占比高（有分类豁免） | — |
| 食物分类 | 快餐外卖 / 零食糕点 / 调味品 | 蔬菜 / 菌菇 / 水果 / 水产 / 蛋奶 / 豆制品 / 坚果 |
| 名称关键词 | 油炸·红烧·腌渍·高钠 | 全谷杂粮·清蒸·白灼·无糖 |

- 输出：**健康友好度 0–100** + 五档结论（很值得吃 / 可以放心吃 / 适量就好 / 建议控制份量 / 尽量少吃）+ 风险、益处标签各最多 3 条
- **刻意的防误导规则**：水产与坚果不按脂肪供能比判「高脂」（它们的脂肪以不饱和为主）；水果蔬菜不因碳水占比高被误判；克重不可信时自动跳过「每 100g」类结论；AI 的 `health_score` 与规则分各占一半
- **自检**：`tools/insight-selftest.ts` 对全部 1180 条内置食物断言（分数不越界、标签不超 3 条、无「低分却无风险标签」的矛盾），代表性条目实测：米饭 48 / 苹果 88 / 薯片 12 / 鸡胸肉 95 / 三文鱼 98 / 可乐 56 / 西兰花 98 / 鸡蛋 70 / 油条 24

## 五、需要决策、暂未改动的事项

| # | 事项 | 说明 | 建议 |
|---|---|---|---|
| 1 | **兑换码在前端硬编码** | `REDEEM_CODES` 是客户端常量，打开浏览器开发者工具即可读到 3 个码；且校验在前端，绕过前端直接写库也可行 | 属于「真实支付未接入」这个已声明状态的一部分。接入支付时一并把校验挪到服务端（建一张 `redeem_codes` 表 + RLS），现在单独改意义不大 |
| 2 | **拍照的图片不落库** | `image_url` 列恒为 `null`，拍照识别的照片不留存 | 倾向保持现状：存图增加存储成本与隐私暴露面，且当前无照片浏览功能。若要支持「回看这一餐拍了什么」再启用 |
| 3 | **兑换即永久 Pro** | `pro_until` 恒为 `null`（`isPro` 支持过期时间但没人设置） | 等真实定价策略定了再启用，属于产品决策而非缺陷 |

### 如实声明的「未实现功能」
仅一项：**在线支付（微信 / 支付宝 / 应用商店内购）尚未接入**。这不是隐藏占位——付费墙上明写了「在线订阅正在接入中，上线前可先用兑换码体验完整功能」，代码注释与 `docs/` 也有记录。除此之外，界面上每一个可点的按钮背后都有真实实现。
