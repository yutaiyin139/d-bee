### 2.5 🔴 新增真缺口 D0：没有度量，所以「一点点减少」不可证伪

**这是本次梳理最重要的新发现，且完全不在 §1.2、不在路线图 §1.4、不在《四端序列》里。**

实证（2026-11-12 全仓搜）：

| 检索 | 结果 |
| --- | --- |
| `analytics` / `trackEvent` / `埋点` / `事件上报` / `funnel` / `retention` / `留存` / `漏斗`（`src` `mini/src` `server` `db/migrations` `tools`） | 仅 2 文件命中，且均为**自然语言「留存」**：`legal.ts:356`「不会在设备上留存副本」、`server/lib/otp.mjs:5`「长期留存」→ **分析基础设施零命中** |
| 现成只读报表 / cohort 脚本 | 零命中（搜到的 `db/functions.sql`、`otp.mjs` 等均为词面误命中） |
| 网关访问日志 / request log | 零命中 |
| `ai_usage` 表（`0002:154-162`、`0030:143-`） | 有 `owner_id` / `usage_date` / `feature` / `count` / `created_at`，**只能算按日用量** |
| `meal_entries` 表（`0030:81-100`） | 有 `owner_id` / `log_date` / `created_at` / `source` / `food_name` / `calories` 等，**天然可算 DAU / WAU / D1·D7·D30 留存 / 连打分布 / source 构成** |

**结论**：不需要新建埋点、不需要新表、不需要第三方 SDK、不需要迁移。`meal_entries` + `ai_usage` 两张现有表，用**离线只读 SQL 报表**（只读账号、`-tA`、绝不 `2>/dev/null` 掩盖错误——遵循项目 psql 铁律）就能覆盖约 80% 指标。

🔴 **这个设计恰好与品牌红线同向，而不是冲突**：不采集新数据、不上传、不外包统计，只对自己已有的业务表做聚合。「连统计都不外包」可以成为「不收集」承诺的一部分；反之若引入第三方分析 SDK，会当场打脸。

**但有一个硬前置**：数据面必须先闭环。当前 mini 旧包仍连旧云库、真实用户仍在写入（§1.2 关键路径），分裂数据面上的 DAU / 留存全部失真。而闭环的最后 2 步（重传体验版、停云库）**只能用户本人做**。所以：

> **等待期第一优先级不是写报表，是把用户本人那 2 步的前置条件全部备齐，让 T+7 计时尽早启动。** 工程侧在此之前只能做「报表脚本 + 指标字典 + 护栏」，不能宣称已有度量。

## 三、等待期的正确用法（战略）

### 3.1 为什么不该在这 6–12 周堆功能

| 理由 | 依据 |
| --- | --- |
| **没有真实用户，留存优化是盲目的** | Web 已上线但双开关 false、mini 旧包数据分裂、Android 未分发、iOS 未上架；此时调「7 日留存」没有可信样本 |
| **路线图 W3 明确「真正拉 7 日留存」，但 W2 闸门优先级高于任何新功能** | 路线图 §四 |
| **一人团队最稀缺的是不可逆决策的注意力**，不是代码量 | 路线图 §七范围护栏的立意 |
| **很多「补缺口」会被上架后的真实反馈推翻** | 例如「免费 3→5 次」必须先拿真实用量成本（W1.2 已标红） |

**所以窗口期的产品原则是**：只做「不依赖用户量也能确定正确」的事——清口径、立承诺、闭环数据面、建度量、攒结构性资产；把「依赖真实分布才能定」的事（提额、方案库、社交、UGC 聚类、长图定价）明确推到闸门之后。

### 3.2 三轨模型

```
轨道 ①  可信数据面  ── 用户本人 2 步（重传体验版 → T+7 → 停库）
        └ 前置备齐：build:weapp 重构建、体验版 6 项验收清单、包体积复测、上传脚本
              ↓ 解锁
轨道 ②  可度量 + 可信任  ── D0 离线报表 / 指标字典 / D2~D7 零风险整改
              ↓ 提供验收手段
轨道 ③  结构性资产  ── D10 PCM 端侧一期（＋ D8/D9 记录体验作为其前置闭环）
              ↓
        闸门解锁后：三轨合成一次「有数据、有信任、有复利」的放量
```

三条轨道**依赖关系是硬的**：① 不通，② 的数字不可信；② 不通，③ 的四个可证伪标志（修正率、命中率、导出/删除、红线不破）无法测量；③ 不在窗口期起步，闸门下来时手上只有「功能补齐」，没有差异化。

### 3.3 优先级判据（每条待办都过一遍）

按以下顺序筛，**前一条不满足就不进下一条**：

1. 是否**零生产风险**、可独立回滚？
2. 是否**不依赖真实用户量**就能判断正确？
3. 是否**不碰 `LEGAL_UPDATED` / 不开收款开关 / 不碰网关部署脚本**？
4. 是否**解锁后续项**（数据面、度量、编辑闭环）？
5. 是否**能写成可证伪验收**（否则不排期）？
6. 是否属于 **C 类**（能在超越维度上累积）？

据此，窗口期优先级序列：**D1 前置备齐 > D0 度量 > D2/D3/D5/D6/D7 零风险整改 > D12 显性化 > D10 PCM > D8/D9 记录体验（需迁移） > D4 退款工具（资损口，单独评审） > 一切 L4 可选项**。

### 3.4 「一点点」的机制：指标字典 + 每次迭代对比基线

「一点点减少」不是一句鼓励，是一个**迭代闭环**：

```
定义指标字典 → 取当前基线（窗口期第 1 次） → 每完成一张交付单重算一次
   → 对比：这一项让哪个数字动了？动了多少？ → 没动的项不重复投入
```

- 基线必须在**数据面闭环之后**取（否则作废重取）；在此之前只交付「脚本 + 字典」，不发布数字。
- 每次迭代在当日日志追加一行指标快照，形成时间序列；这是「一点点」唯一的证据。
- 🔴 **禁止在拿到真实分布前拍脑袋定阈值**（PCM 详案 §5.1 与路线图 W1.2 同一纪律）。

### 5.3 为什么薄荷难跟，以及我们的红线

- 它的核心资产是**共享的公共食物库 + UGC 贡献 + 社区流量**；叠一层「个人覆盖层」会稀释公共数据一致性、增加审核与合规成本，且与其「大家共建一个库」的飞轮方向相反。
- 它的商业模式依赖会员 / 电商 / 广告，**「尽量不收集、端侧优先、不上传」是它不能讲的承诺**；我们能讲，是因为本来就小、本来就自托管、隐私政策本来就写了「其他用户无法查看」。
- 🔴 **反过来这正是我们的风险**：端侧不同步会伤换设备体验；一旦用户量起来、为同步而上云，就会重新背上薄荷那套合规与审核成本。所以「不收集」必须是**长期品牌红线**，不是一期的技术妥协——这也是 P0.8 要把它写进对外承诺的原因（写出去 = 自己给自己上锁）。
