# 数据库迁移审计与实施计划

> 2026-10-23 · 对服务器 `150.158.51.106` 的 `dbee` 库做**逐对象实测审计**（非文档推断）。
>
> 结论先行：**33 个迁移里有 3 个从未生效、1 个只生效了一半**，其中半个是 **P0 级可越权漏洞（已实证可利用）**：
> 任何登录用户可一条 HTTP 请求把自己改成终身会员。根因不是「忘了跑」，而是**镜像生成器的三类系统性缺陷**
> + **没有迁移追踪表**——所以这些在镜像重建（`0030`，10-20~10-22）时丢失的遗漏，
> 直到本次审计（10-23）才有机会被发现，中间没有任何自动机制能拦住。

## 一、审计方法（为什么这些结论可信）

文件头的「状态」标注不可信：33 个迁移里**只有 0001 写了状态行**，`db/README.md` 的「已执行/待执行」表格**只记到 0003**。
所以本次一律以**服务器库的真实状态**为唯一真相源，三类探针：

| 探针 | 手段 | 能判定 |
|---|---|---|
| 存在性 | `information_schema.columns/tables`、`pg_proc`、`pg_constraint`、`pg_policies`、`pg_indexes` | 建表/加列/建函数/建约束/建策略/建索引 类迁移 |
| **版本性** | `pg_get_functiondef()` + 版本特征串比对 | **`CREATE OR REPLACE` 覆盖式迁移**——函数「存在」≠「是最新版」，这是最容易漏判的一类 |
| **可利用性** | `BEGIN … SET ROLE authenticated … ROLLBACK` 事务内真实越权写入 | 权限漏洞到底是理论存在还是真能打通 |

越权测试**全程在事务内 `ROLLBACK`**，测试后复核 `entitlements` 仍为 0 行、无任何 `EXPLOIT-TEST` 残留，数据零污染。

## 三、四个问题的详细分析

### 1. 🔴 P0 · 0015 部分失效 → 可白嫖终身会员（已实证）

**0015 的原话**（文件头，2026-10-16 写）：

> `honey_ledger` / `entitlements` / `quota_bonus` / `ai_usage` / `badges` / `invite_links` 这 6 张表
> 表级 GRANT 给了 authenticated 全权限。这意味着任何登录用户可以：
> - 直接 `UPDATE entitlements SET plan='lifetime'` **免费拿终身会员**
> - 直接 `UPDATE ai_usage SET count=0` 清零免费额度
>
> 函数白名单「治标不治本」——表级直写通道一直敞开着。

**实测结果：6 张表里 4 张封住了，2 张没封。**

| 表 | `authenticated` 实际持有 | 0015 要求 | 判定 |
|---|---|---|---|
| `honey_ledger` | `SELECT` | SELECT | ✅ 已封 |
| `badges` | `SELECT` | SELECT | ✅ 已封 |
| `quota_bonus` | （无） | REVOKE ALL | ✅ 已封 |
| `invite_links` | `INSERT,SELECT` | SELECT,INSERT | ✅ 已封 |
| **`entitlements`** | **`DELETE,INSERT,SELECT,UPDATE`** | SELECT | 🔴 **敞开** |
| **`ai_usage`** | **`DELETE,INSERT,SELECT,UPDATE`** | SELECT | 🔴 **敞开** |

全库统计：`authenticated` 仍持有 **25 个写权限**，逐项拆解后 = **19 个设计允许 + 6 个违规残留**：

```
设计允许（业务日志表，用户本来就要能写）  19
  profiles(3) meal_entries(3) weight_logs(3) water_logs(3)
  exercise_logs(3) recipes(3) invite_links(1)
违规残留（0015 明确要 REVOKE 却没生效）    6   ← 就是这 6 个构成 P0
  entitlements(INSERT,UPDATE,DELETE)  ai_usage(INSERT,UPDATE,DELETE)
```

**违规残留应为 0，实测 6。**

**越权实证**（事务内 ROLLBACK，数据零污染）：

```sql
-- 下例中的 <UID> 代表任一真实用户的 owner_id（19 位数字串），本文档已脱敏，不落真实值。
BEGIN;
SET ROLE dbee_web;                                  -- PostgREST 的连接角色
SET LOCAL request.jwt.claim.sub = '<UID>';
SET LOCAL request.jwt.claim.role = 'authenticated';
SET ROLE authenticated;                             -- ← PostgREST 每个请求都这么干
INSERT INTO entitlements (owner_id, plan, source)
VALUES ('<UID>','lifetime','EXPLOIT-TEST')
ON CONFLICT (owner_id) DO UPDATE SET plan = EXCLUDED.plan;
-- 结果：🔴 INSERT/UPDATE 成功，plan 已变 lifetime
ROLLBACK;
```

对照组 `honey_ledger` 同样操作 → `ERROR: permission denied for table honey_ledger`（证明封堵机制本身是有效的，只是漏了 2 张表）。

**为什么这是「真实可利用」而不只是「理论可利用」**——完整攻击链每一环都已实测确认：

1. `entitlements_own` 策略是 `FOR ALL USING (owner_id = auth.uid()) WITH CHECK (owner_id = auth.uid())`
   → RLS **只挡跨用户越权，不挡改自己的行**。改自己的会员等级完全合法通过。
2. 网关 `dbproxy.mjs:36` 的 `ALLOWED_METHODS` **含 `PATCH`/`POST`/`DELETE`**，且**没有任何表白名单**
   （纯透传，注释明确写「不解析也不改写」）→ 网关层不拦。
3. PostgREST 未设 `db-schemas` 限制，默认暴露整个 `public` schema，`entitlements` 在内 → 数据面层不拦。
4. `pg_has_role('dbee_web','authenticated','MEMBER') = t` → `SET ROLE` 可达。

**攻击者只需**：正常登录拿 JWT，然后发一个 HTTP 请求
`PATCH /.cloud/database/rest/entitlements?owner_id=eq.<自己> {"plan":"lifetime"}`
→ 永久会员到手，一分钱不付。同理 `PATCH ai_usage` 可把免费额度清零，无限用 AI。

> ⚠️ 当前 `entitlements` 表 **0 行**、`payment_orders` **0 行**——因为还没开始收费。
> **这意味着现在修是零成本零风险的；一旦上线收费，这就是直接的收入漏洞。**

### 2. 🔴 0016 完全未生效 → 库层无数据完整性兜底

## 四、根因分析：为什么这些遗漏没人发现

### 根因 1（最关键）· 镜像生成器**只输出 GRANT，从不输出 REVOKE**

`db/gen-full-mirror-sql.py` 全文只有 **1 处** `REVOKE`：

```python
# gen-full-mirror-sql.py:421
parts.append('REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon;')
```

`TABLE_GRANTS` 字典里 `entitlements`/`ai_usage` 明明写的是 `'SELECT'`（**符合 0015 意图**），
生成的 SQL 也确实只有 `GRANT SELECT`：

```sql
-- 0030-schema.sql:498-499（= 0030-full-selfhost-mirror.sql:498-499，服务器执行的就是这个）
GRANT SELECT ON public.entitlements TO authenticated;
GRANT SELECT ON public.ai_usage TO authenticated;
```

**但 `GRANT` 是追加语义，不撤销已有权限。** 写权限是 `0002` 在 10-13 建库时给的：

```sql
-- 0002-mirror-to-local-pg.sql:226-229
GRANT SELECT, INSERT, UPDATE, DELETE
  ON public.profiles, public.meal_entries, public.weight_logs, public.water_logs,
     public.exercise_logs, public.entitlements, public.ai_usage   -- ← 7 张表全给了写权限
  TO authenticated;
```

0015 的 `REVOKE` **从未在 dbee 库上执行过**（它在云库上执行了，所以生成器抓到的 `TABLE_GRANTS` 是对的），
而 0030 镜像**只会再 GRANT 一次 SELECT，不会 REVOKE 掉 0002 留下的写权限**。

> 💡 这与 0033 踩的是**同一个坑**：`dbee_app` 的 `DELETE` 权限也是 `GRANT` 追加语义留下的，
> 0033 的修法正是「先 `REVOKE ALL` 再精确 `GRANT`」。**同一个教训在两个地方分别踩了一次。**

**为什么偏偏漏这 2 张表？** 已实证的关联是：0002 建库时授权的那 7 张表
（`profiles`/`meal_entries`/`weight_logs`/`water_logs`/`exercise_logs`/`entitlements`/`ai_usage`），
其中被 0015 要求收权的正是 `entitlements` 和 `ai_usage`，**两张全部失效**；
而 0015 要收的另外 4 张表（`honey_ledger`/`badges`/`quota_bonus`/`invite_links`）**不在 0002 的授权清单里，全部封住**。
这个「在 0002 清单内 → 失效；在清单外 → 生效」的完全对应关系，与根因 1（GRANT 追加语义、镜像不输出 REVOKE）严格吻合。

> 注：「0015 是否在云库上执行过」这一点**未实测**（本次审计只连了自托管库）。
> 但不影响结论与修法——无论 0015 当初在云库生效与否，dbee 库的当前事实就是这 2 张表可写，且 0034 的修法相同。

### 根因 2 · 生成器**完全不抓 `pg_constraint`**

生成器读取的系统目录只有两个：

```
pg_indexes              1 处
information_schema.columns   1 处
```

外加一个**硬编码的 `UNIQUE_CONSTRAINTS` 字典**（人工维护的 PK/UNIQUE 清单）。
`CHECK` 约束、外键、触发器**没有任何抓取逻辑**。

`0030-schema.sql` 里 16 处 `CHECK` 字样，**全部是 `CREATE POLICY … WITH CHECK (owner_id = auth.uid())` 子句**，
一个数据完整性约束都没有。→ 0016 的丢失是**必然**结果，不是偶然。

同理：服务器实测**外键 0 个、用户触发器 0 个**——这两个数字与镜像一致（本来就没设计），不是遗漏。

### 根因 3 · `CREATE OR REPLACE` 覆盖式迁移**无法用存在性判定版本**

0017/0019/0020b/0024/0025/0026/0027 全是覆盖式改函数体。函数「在」不代表「是最新版」，
只能靠函数体特征串比对——**这是本次审计才发现必须做的第二类探针**。

0026/0027 恰恰都是这一类，且都是「文件存在、函数也存在，但函数体是旧版」，
所以**从任何存在性检查都看不出来**，只能读函数体。

### 根因 4 · **没有迁移追踪表**

`to_regclass('public.schema_migrations')` → **NULL**。
状态全靠：①文件头注释（33 个里只有 1 个写了）②`db/README.md` 表格（只记到 0003）。
**两者都严重滞后，且没有任何自动校验机制。**

这是「为什么没人发现」的答案：0016/0026/0027 都是在云库上执行的（云库才是当时的真相源），
10-20 切自托管时用镜像重建 dbee 库，**镜像丢了三样东西**，而重建后**没有任何机制比对「迁移清单 vs 库实际状态」**。

#### P0-2 前端配套：`ai_usage` 降级路径必须一起改（否则 REVOKE 会打断功能）

`src/lib/api.ts:402` 的 `consumeAiQuota` 有个**静默 `catch {}` 降级**：

```typescript
} catch {
  const used = await getUsage(usageDate, feature)      // 读 ai_usage（SELECT，保留，不受影响）
  if (used >= limit) return { allowed: false, … }
  await bumpUsage(usageDate, feature, used)            // ← 直写 ai_usage（REVOKE 后必抛错）
  return { allowed: true, … }
}
```

`bumpUsage`（api.ts:347）直接 `.update()` / `.insert()` `ai_usage`。REVOKE 之后这条降级路径会失败。

**关键判断：这个降级路径本身就是漏洞。** 它绕过 `consume_ai_quota` 的服务端原子限制，
在并发下会互相覆盖（注释自己承认「并发下会互相覆盖」），**正是 0015 要封堵的东西**。
所以正确修法不是「保留降级」，而是：

> **降级路径改为 fail-closed**：RPC 不可用时返回 `{allowed:false}`（拒绝服务）而不是 fail-open（静默直写）。
> 理由：AI 调用有真实成本，fail-open 等于「数据库函数一出问题就免费无限用」；
> 而 `consume_ai_quota` 走的是网关 → PostgREST RPC，与主链路同生共死，它挂了业务本来也不可用。

`entitlements` 侧无此问题：前端只有 `getEntitlement()` 的 `select('*')`（读），无写调用，REVOKE 后零影响。

#### P0-3 修 `gen-full-mirror-sql.py`（否则下次重建库会**再丢一遍**）

这是**根因修复**，不做的话 P0-1 的成果会在下次镜像重建时全部丢失：

1. **输出 `REVOKE` 段**：在 `TABLE_GRANTS` 生成的 GRANT 之前，先对 `authenticated` 无条件
   `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM authenticated;`，再按字典精确 GRANT
   ——**照抄 0033 的「先 REVOKE 再 GRANT」范式**。
2. **抓 `pg_constraint`**：生成 `contype='c'`（CHECK）的 `ALTER TABLE … ADD CONSTRAINT`，
   别再依赖硬编码字典。顺手把 `contype='f'`（外键）也抓上（当前为 0，但将来会有）。
3. **`UNIQUE_CONSTRAINTS` 字典改为实抓**：硬编码字典是漂移源头（云库加了约束，字典不会自动更新）。

#### P0-4 建迁移追踪表 + 校验脚本（**根治「没人发现」**）

```sql
CREATE TABLE public.schema_migrations (
  version      text PRIMARY KEY,        -- '0034'
  name         text NOT NULL,           -- 'security-and-integrity'
  applied_at   timestamptz NOT NULL DEFAULT now(),
  applied_by   text,
  checksum     text                     -- 迁移文件 sha256，防「改了已应用的迁移」
);
```

配套 `tools/migration-audit.sh`：把本次审计的**三类探针固化成可重复执行的脚本**，
输出「迁移清单 vs 库实际状态」的差异表。纳入 `tools/db-healthcheck.sh`，部署后必跑。

> 这条的价值最高：P0-1 修的是**这次**的漏洞，P0-4 修的是**「下次还会再发生」**。

### P1 · 支付链路（Android 企业注册已完成，这条线现在解锁了）

#### P1-1 Apple IAP 验签放 Node 网关（0029 方案作废）

- 已实测 `pg_net` 在自托管环境**不可用** → 0029 永久作废。
- 落点：`server/lib/payment.mjs` 补 `provider='apple'` 分支（App Store Server API / verifyReceipt），
  验签通过后写 `payment_orders.status='paid'` + `entitlements`，`source='apple'`。
- 库端 `verify_payment_order` 保持 `RETURN false` 恒拒（它是最后一道防白嫖闸门，**不要改成 true**）——
  真实发放走网关的 SECURITY DEFINER 路径或专用 RPC。
- ⚠️ **必须在 P0-1 之后做**：否则「网关能写 entitlements」和「用户也能写 entitlements」混在一起，
  无法区分合法发放与越权。REVOKE 之后，写 `entitlements` 的**唯一通道**就只剩服务端函数，可审计。

#### P1-2 Android 支付渠道（企业注册完成 → 新增工作量）

`payment_orders.provider` 是 `text` 且**无 CHECK 约束**（实测），加 `'google'`/`'wechat'`/`'alipay'` 无需改表结构。
但 `verify_payment_order` / 网关验签都只规划了 `apple` 分支，需要：

- 微信支付 V3 回调验签 + 支付宝异步通知验签（2026-10-25 拍板：Android 走微信 + 支付宝，放弃 Google Play）
- 商户号密钥管理（**只存服务器，不入库不入 git**）
- ⚠️ 华为/小米渠道各自还有独立支付 SDK —— 国内安卓商店内购按实际上架优先级再排；
  Google Play Billing 仅海外分发需要，当前不立项。

#### P1-3 `payment_products` 权限缺口（实测发现，非遗漏而是设计缺失）

`payment_products` 有 3 行商品数据，但**对 `authenticated` 无任何权限**（不在 `TABLE_GRANTS` 字典里）。
前端目前不直读该表（定价走 `PRODUCT_IDS` 常量 + `create_payment_order` 服务端查价），**所以暂不报错**。
但「金额由服务端查价」这条设计需要服务端能读它 → 确认 `dbee_app`/SECURITY DEFINER 函数的读取路径通，
或显式 `GRANT SELECT ON payment_products TO authenticated`（只读，无风险）。
