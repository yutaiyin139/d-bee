## 四件套

### ① 自建 auth/JWT 网关（接 auth.uid() 兼容层）

**目标**：让前端 `cloud.auth.*` 的调用落到自建服务，签发 JWT，DB 侧 `auth.uid()` 能读到 `sub`。

- [ ] 选型：Node（复用现有栈，`deploy/` 已有 Python/Node 混合，建议单文件 Node 服务，零新框架依赖）
- [ ] 端点实现（对齐前端已用到的 6 个方法）：
  - `POST /.cloud/auth/v1/verification`（等价 sendOtp：发验证码）
  - `POST /.cloud/auth/v1/token`（等价 verifyOtp：验码 → 签发 JWT + refresh token）
  - `GET /.cloud/auth/v1/user/me`（等价 getSession：解 JWT 返回用户）
  - `POST /.cloud/auth/v1/refresh`（续期）
- [ ] JWT 载荷：`sub` = 原 `owner_id`（如 `2109869577155379200`），密钥服务端持有
- [ ] DB 桥接：网关在每笔 DB 请求前 `SET LOCAL app.user_id = <sub>`（或注入 `request.jwt.claim.sub`），
  这样 `0002` 里已写好的 `auth.uid()` 兼容函数**原样生效**，RLS 隔离照常
- [ ] 验证码通道：临时用「控制台打印 + 开发后门」跑通链路，再换短信（微信暂缓，不阻塞）

**验收**：手机号登录 → 拿到 JWT → 查询只返回自己那行（复用 0002 末尾的 `SET ROLE authenticated` 自检法）。

### ② LLM 代理（替代 cloud.llm）

**目标**：让 `src/lib/ai.ts` 的 `cloud.llm.chat.completions.create`（SSE 流式）打到自有模型。

- [ ] 端点：
  - `GET /.cloud/llm/models`（返回模型列表，含 `supportsImages` / `isDefault` 字段）
  - `POST /.cloud/llm/chat/completions`（OpenAI 兼容，**必须支持 SSE 流式**，否则 AI 教练/识别退化）
- [ ] 模型选择：可直连任一 OpenAI 兼容 API（DeepSeek / 通义 / 智谱等），**图片识别需选多模态模型**
- [ ] 关键坑（`src/lib/ai.ts` 已写死「只支持流式」）：代理必须逐 chunk 回 `delta.content`，
  `collectText` 是按 SSE 累积文本解析 JSON 的，**不要改前端，代理侧对齐流式即可**
- [ ] 鉴权：复用 ① 的 JWT，网关校验后放行，模型 key 只在服务端

**验收**：拍照识别食物能出 JSON；`askCoach` 能流式回文本。

### ③ `/v1/*` REST 兼容端点（替代 cloud.database）

**目标**：让 `api.ts` 的链式查询（select/insert/update/delete + 过滤器）落到自建 REST。

- [ ] 端点：`POST /.cloud/database/rest/v1/<table>`（或对齐 SDK 实际路径），body 携带
  `{ select, filters: [{op, column, value}], limit, order, data }`
- [ ] 实现策略（**推荐，代价最小**）：不做通用 REST DSL，而是**把 `api.ts` 的 ~20 个业务函数
  逐个映射成自建 SQL/存储过程**。因为 `api.ts` 已经把所有表访问收口在 `db()` 一个函数里，
  只需在 `db()` 底层换成自建 HTTP 客户端，业务函数体完全不动
- [ ] **必须重放 0025~0029 迁移**（本地镜像缺 0024 后的业务函数/新表）：
  - 0025 兑换上限 5→2；0026 新手发积分；0027 邀请频限；0028 榜单；0029 IAP 验签
  - 逐条执行 `db/migrations/0025~0029`，注意它们依赖 0020~0024 已存在的函数/表（需先补 0020~0024）
- [ ] RLS/权限：`0002` 已建好 authenticated/anon 角色 + 16 策略 + GRANT，复用即可

**验收**：打卡/记餐/兑换/榜单/邀请 全链路 CRUD 在自托管上跑通。

### ④ 切换发布（替换 Nginx 上游 + 前端零改动）

**目标**：把线上流量从「连云」切到「连自托管」，前端代码不动。

- [ ] 起网关服务（①+②+③ 合并成一个 Node 服务，systemd 托管，端口如 127.0.0.1:8080）
- [ ] 改 Nginx：`/.cloud/` 的 `proxy_pass` 从 `https://dbee_cloud` 改成 `http://127.0.0.1:8080`，
  去掉 Origin/Referer 覆写（自建网关不再校验来源），`proxy_buffering off` 保留（SSE）
- [ ] 灰度：先 `DBEE_HOST=... bash deploy/deploy.sh` 推一份静态 + 新 nginx，IP 直连验证
- [ ] 域名/HTTPS：等 ICP 备案后再绑域名（中国大陆服务器对外 Web 必须备案）

## 风险与最小影响提示

- **数据已在手**：`0002` 已备份 10-18 快照到自有服务器，云库即使被删也不丢核心数据。
  唯一缺口 = 10-18 之后约 2 天增量，**云若恢复第一时间补差量**。
- **增量数据回填**：若云恢复，先跑 `db/gen-mirror-sql.py` 用最新快照重生成，再做增量 INSERT。
- **微信登录/微信支付**：依赖营业执照 + 官方 AppID，自托管后仍暂缓，不阻塞登录（手机号 OTP 优先）。
- **iOS IAP 验签（0029）**：`pg_net` 外呼 verifyReceipt 依赖服务器网络出口，自托管后需确认
  服务器能访问 Apple 验签域名，否则 iOS 购买卡「校验失败」。
- **不要动前端**：`cloudConfig.ts` 同源反代策略 + `api.ts`/`ai.ts` 收口层，是本次切换「零前端改动」
  的关键，务必保持。
