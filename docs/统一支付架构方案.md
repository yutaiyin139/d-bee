# D-Bee 统一支付架构方案（跨 iOS / Android / Web / 小程序）

> 状态：前期规划（2026-10-17）
> 目标：企业资质办理期间，先行启动 iOS IAP 的技术方案与代码骨架，同时把
> 支付抽象层设计成「一次设计、四端复用」，避免各端各写一套、后续返工。
>
> 前置结论：苹果 App 与「企业营业执照」完全解耦，可立即推进；
> 微信 / 支付宝 / 小程序仍卡在营业执照，仅做设计预留，不写死代码。

---

## 一、设计目标与原则

**各端只做两件事，其余全部收敛到服务端：**

1. 发起支付：调用各自平台支付能力，拿到「支付凭证」
2. 回传凭证：把凭证交给服务端统一核销

**权益落库、幂等、防重、订阅续期/过期/退款管理，全部走服务端统一 RPC，各端零差异。**

原则：
- **不静态 import 任何原生支付插件**（沿用 wechat.ts / originProxy.ts 的「运行时鸭子类型探测」，
  保证 Web 构建零新增依赖、包体积不变）。
- **服务端是唯一信任源**：客户端只负责「发起 + 回传」，不能自行写权益。
- **幂等是硬约束**：同一笔交易重复回传（网络重试/切后台回来）绝不重复发权益。

## 二、统一订单模型（四端共用一张表）

所有支付方式（苹果 IAP / Google Play / 微信 / 支付宝）映射到同一张 `payment_orders` 表：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint identity | 主键 |
| owner_id | text | 购买人 auth.uid() |
| order_no | text UNIQUE | 客户端生成的幂等订单号 |
| provider | text | apple / google / wechat / alipay |
| product_id | text | dbee_pro_monthly / dbee_pro_yearly / dbee_lifetime |
| plan | text | pro / lifetime |
| months | integer | pro 商品的月数（lifetime 忽略） |
| amount_cents | integer | 金额（分） |
| currency | text | 默认 CNY |
| status | text | pending / paid / cancelled / refunded |
| provider_txn_id | text | 平台交易号（防重键） |
| receipt_payload | text | 原始凭证（iOS receipt / 微信 prepay 结果等） |
| created_at / updated_at | timestamptz | — |

**双保险防重**：
- `order_no`（客户端幂等键，UNIQUE）
- `provider_txn_id`（平台唯一交易号，服务端据此判重）

## 三、三层架构

### 第 1 层：支付适配器接口（统一抽象）

`src/lib/payment/types.ts` —— 所有端共用的统一接口：

```typescript
export interface PaymentAdapter {
  fetchProducts(): Promise<ProductInfo[]>           // 拉商品（含价格，展示付费墙）
  purchase(productId: ProductId): Promise<PurchaseResult>  // 发起购买，返回平台凭证
  restore(): Promise<PurchaseResult[]>              // 恢复购买（iOS/Google 订阅）
}
```

各端只实现这个接口：
- `iosIap.ts` → StoreKit 2
- `googlePlay.ts` → Google Play Billing（未来）
- `wechatPay.ts` → 微信支付
- `alipay.ts` → 支付宝

### 第 2 层：统一 checkout 流程（各端共用）

`src/lib/payment/checkout.ts` —— 与具体平台解耦：

```typescript
export async function checkout(productId: ProductId): Promise<CheckoutResult> {
  const adapter = getAdapter()                      // 按 platformName() 选适配器
  const order = await createOrder(productId)        // ① 服务端下单，拿 order_no
  const result = await adapter.purchase(productId)  // ② 平台支付
  const verified = await verifyOrder(order.orderNo, result) // ③ 回传凭证核销
  await refreshEntitlement()                        // ④ 刷新权益
  return verified
}
```

四步统一，各端代码完全一致，只有 `adapter` 不同。

### 第 3 层：服务端统一核销（两个 RPC）

```sql
-- ① 下单：创建订单，返回 order_no
create_payment_order(p_product_id text) → json  -- { order_no, amount, ... }

-- ② 核销：校验凭证 + 幂等发权益（四端共用这一个入口）
verify_payment_order(p_order_no text, p_provider_txn_id text, p_receipt text) → boolean
```

`verify_payment_order` 内部统一：
1. 查订单（pending）→ 校验凭证（iOS verifyReceipt / 微信支付宝验签）
2. 幂等：同一 provider_txn_id 只发一次权益
3. 发权益：写 entitlements（pro 顺延 / lifetime 买断），source = 对应 provider
4. 标记订单 paid

## 四、iOS IAP 的差异化处理（唯一单独做的部分）

iOS 订阅有「续期 / 过期 / 退款」三种**服务端异步通知**，其他端没有：

**App Store Server Notifications V2**：苹果在订阅状态变化时推送服务器，需单独 webhook 接收端：
- `SUBSCRIBED` / `DID_RENEW` → 发权益 / 顺延 pro_until
- `EXPIRED` / `DID_FAIL_TO_RENEW` → 到期回落 free
- `REFUND` → 回收权益

这是唯一不能靠「统一核销」覆盖的部分。

## 五、复用性论证（为什么这样设计）

| 端 | 差异点 | 复用部分 |
|---|---|---|
| iOS | StoreKit 2 + Server Notifications | 订单表、核销 RPC、checkout 流程 |
| Android | Google Billing / 微信 / 支付宝 | 同上，只换 adapter |
| Web | 微信/支付宝网页支付 | 同上，凭证换成 prepay 结果 |
| 小程序 | wx.requestPayment | 同上，adapter 走小程序 API |

**未来接新端 = 写一个 adapter + 服务端加一个凭证验签分支，其余全复用。**

## 六、实施顺序（骨架先行）

1. **现在（资质办理中）**：
   - 写 `payment/types.ts`（统一接口）+ `payment/checkout.ts`（统一流程）
   - 服务端 `payment_orders` 表迁移 + 两个 RPC（核销逻辑 iOS 分支先留空实现）
   - iOS `iosIap.ts` 代码骨架（运行时探测，Web 构建零依赖）
2. **iOS 开发者账号下来后**：填 iOS verifyReceipt + Server Notifications 接收端
3. **营业执照下来后**：填微信 / 支付宝验签分支

## 八、待用户确认的决策点

1. **订单金额来源**：`amount_cents` 由客户端上报还是服务端按 product_id 查价？（建议服务端查价，防客户端篡改金额）
2. **iOS 开发者账号类型**：个人（1-2 天可上架）还是公司（需 D-U-N-S + 营业执照）？
   若想资质下来前就上架，先用个人账号。
3. **是否先建 `payment_orders` 表**：表结构一旦确定，后续各端都基于它，建议现在就建表 + RPC 骨架。
