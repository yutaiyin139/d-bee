# P1-E 调研结论：Android 兑换码是否隐藏 + 华为/小米内购政策

> 创建：2026-11-03 ｜ 对应审计计划 `docs/四端一致性与商业化优化-审计与实施计划-2026-11-03.md:241`
> 原任务：「决策 Android 端兑换码是否隐藏（各应用商店内购政策）；出结论文档；若须隐藏则改 `PaywallSheet.tsx:393` 的判断条件」
> 调研方式：华为/小米开发者官方文档与官方论坛原文 + 项目代码逐条核对
> **本文只做结论与建议，代码零改动**（改动涉及商业化策略，需你拍板）

---

## 一、结论先行（三句话）

1. **兑换码不需要隐藏** —— 华为官方明确认可「运营人员免费发码、用户输入后获得权益」这种**自建赠送码表**，它与「华为官方虚拟商品兑换码」是两回事。`PaywallSheet.tsx:393` 的 `!isIOS()` 判断**保持不变**。
2. **真正的上架风险不在兑换码，而在 Android 直连微信/支付宝卖会员** —— 华为《IAP Kit 接入规范》原文规定数字商品「不能独立对接支付宝、微信支付等三方支付，否则可能影响应用上架」，且**购买页禁止展示支付方式名称**。D-Bee 两条都撞。
3. **当前处于零风险窗口，不必紧急改** —— 商户号资质未就绪，`wechatPay.ts`/`alipay.ts` 的 adapter 探测返回 `null`，前端诚实降级，实际不产生真实交易。这是「**上华为前必须改**」，不是「现在就得改」。

## 二、证据：华为

### 2.1 官方论坛明确区分两种兑换码（决定性证据）

来源：[华为开发者联盟官方问答 · IAP目前支持给用户发放兑换码吗?](https://developer.huawei.com/consumer/cn/forum/topic/0203223658265479098)

华为官方回答把兑换码分成**两类**，并分别给了定性：

| 类型 | 定性 | 是否合规 |
| ---- | ---- | -------- |
| **华为官方虚拟商品兑换码** | 开发者上传码库存 → 用户在华为应用市场/游戏中心**完成购买**后取得码 → 回应用兑换。本质是「走华为渠道的销售交付方式」 | 合规（这是华为自己的通道） |
| **自建赠送码表** | 原文：「如果你的真实需求是『运营人员免费发码，用户输入后直接获得永久权益』，这属于**你自己的账户权益系统，不是 IAP 购买恢复**。可以在服务端另建赠送码表」 | **合规**，但有工程纪律要求（见 §2.3） |

**D-Bee 属于第二类。** 依据（代码与文案实证，非推测）：

- `mini/src/pages/paywall/paywall.tsx:31`：「解锁方式：兑换码（**邀请/活动免费获得，非售卖**）」
- `mini/src/pages/paywall/paywall.tsx:189`（用户可见文案）：「会员权益可通过兑换码解锁（兑换码由**邀请、活动等渠道免费获得**）」
- `db/migrations/0012-redeem-server-and-invite-throttle.sql`：自建 `redeem_codes` 表 + `redeem_by_code()` RPC，**不经任何应用商店**
- 兑换后写入的是 `entitlements.source='redeem'`，而非商店订单凭证

所以：**兑换码不是「绕过华为 IAP 卖东西」，而是「发放免费权益」**。不构成切支付。

### 2.2 官方规范禁止的是另一件事：数字商品直连三方支付

来源：[华为《IAP Kit 接入规范》](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/iap-access-specifications-V13)

**接入限制**（原文照录）：

> 数字商品（虚拟商品）要求通过 IAP Kit 接入购买能力，**不能独立对接支付宝、微信支付等三方支付，否则可能影响应用上架**。

**界面设计规范**（原文照录）：

> **请不要在应用商品购买页展示支付方式栏目信息，包括支付方式 logo、支付方式名称**（如"华为支付"、"鸿蒙支付"、"应用内支付"等）等信息。建议采用购买、订阅等按钮确认用户购买或订阅意愿。

华为开发者论坛的补充对照表（同一来源 §2.1 帖内）：

| 产品类型 | 必须用 IAP Kit | 可以用微信/支付宝 |
| -------- | -------------- | ----------------- |
| 虚拟产品（游戏道具、**会员**、虚拟货币等） | **必须** | **不允许** |
| 实物商品（电商、实物买卖） | 不强制 | 可以 |
| 生活服务（外卖、打车、酒店预订） | 不强制 | 可以 |
| 非盈利捐赠打赏 | 不强制 | 可以 |

D-Bee 卖的是**会员订阅（Pro 月/年）+ 终身买断**，属第一行「虚拟产品/会员」→ **必须走 IAP Kit**。

**代码核对：D-Bee 现状两条都撞**

| 华为规定 | D-Bee 现状 | 位置 |
| -------- | ---------- | ---- |
| 数字商品不得独立对接支付宝/微信 | Android 分支直接 `createAlipayAdapter()` / `createWechatPayAdapter()` | `src/lib/payment/checkout.ts:39-46` |
| 购买页不得展示支付方式名称 | Android/Web 渲染**两个带文字名称的支付按钮**「微信支付」「支付宝」 | `src/pages/PaywallSheet.tsx:355-376` |
| — | 文件头注释即写明该设计意图：「Android/Web → 微信支付 + 支付宝（先选商品，再选支付方式）」 | `src/pages/PaywallSheet.tsx:25` |

**但当前不产生真实交易**（所以是「上架前必须改」而非「现在就违规」）：

- `src/lib/payment/wechatPay.ts:25`：「⚠️ 当前资质未就绪：本 adapter 的 create 探测会因『未配 AppID』而返回 null」
- `wechatPay.ts:129`：「① 服务端统一下单（资质就绪后接入；**当前占位抛出「暂未开通」**）」
- `alipay.ts:142`：`fetchPrepayParams()` 同样是占位
- 即：`getAdapter()` 返回可用 adapter 但下单必失败 → 前端诚实降级提示，**不会真的收款**

### 2.3 华为对「自建赠送码表」提出的工程纪律（逐条核对 D-Bee）

华为官方原文要求：「至少需要做到：兑换码只存哈希、设置有效期和次数、服务端原子核销、防止并发重复兑换、绑定华为账号对应的业务账号、记录审计日志；客户端不能自行把本地状态改成『已购买』。IAP 查询和恢复购买仍只认真实订单，**自建赠送权益应使用独立的权益来源字段**，避免重装或换机后状态冲突。」

| # | 华为要求 | D-Bee 现状 | 判定 |
| - | -------- | ---------- | ---- |
| 1 | 服务端原子核销 | `UPDATE redeem_codes SET used_by=v_uid WHERE id=v_row.id AND used_by IS NULL` + 检查 `FOUND` | ✅ 已满足 |
| 2 | 防并发重复兑换 | 同上（条件更新天然互斥），`0012` 注释明写「原子标记使用（条件更新防并发重复兑换）」 | ✅ 已满足 |
| 3 | 码不在客户端 | `0012` 注释：「兑换码服务端库存（**前端不再硬编码，翻包拿不到**终身会员）」 | ✅ 已满足 |
| 4 | 独立权益来源字段 | `entitlements.source='redeem'`（与 IAP 的 `source` 区分开） | ✅ 已满足 |
| 5 | 重装/换机后从服务端恢复权益 | 权益存云端 `entitlements` 表，客户端不落地；`0013` 把 `grant_photo_bonus` 也改成 SECURITY DEFINER 防自造 | ✅ 已满足 |
| 6 | 客户端不能自行改本地状态为「已购买」 | 未发现本地写权益路径（`src/state/plan.tsx` 走 `refreshEntitlement()` 拉云端） | ✅ 已满足 |
| 7 | **兑换码只存哈希** | `redeem_codes.code` 是**明文** `text NOT NULL UNIQUE` | ❌ **未满足** |
| 8 | **设置有效期** | `redeem_codes` 表**无 `expires_at`** 字段（只有 `created_at`/`used_at`） | ❌ **未满足** |
| 9 | **设置次数** | 只有 `used_by` 单值（隐含 1 次），无 `max_uses`；单码单次够用，但**无法做「一码 N 次」的活动码** | ⚠️ 部分满足 |
| 10 | **绑定华为账号对应的业务账号** | 无华为账号体系（D-Bee 用手机号/微信登录） | ⚠️ 不适用 |
| 11 | **记录审计日志** | 无独立审计表；只有 `used_by`+`used_at` 可作最小痕迹，**无兑换失败/异常记录** | ⚠️ 部分满足 |

华为还给了验证要求：「验证时至少准备四组：**有效未使用码、已使用码、过期码和并发双请求**。预期只有第一组成功一次；并发请求必须只有一个成功。」
→ D-Bee 现在**测不了「过期码」**（无有效期字段）。`tools/` 下也无兑换码测试（现有 5 个测试文件：iap-checkout / numfmt / report-ratio / mini-report-ratio / mini-invite-link）。

## 三、证据：小米

### 3.1 小米**未**找到「必须使用小米内购」的强制条款

核对的官方文档：
- [小米《应用审核规范》](https://dev.mi.com/distribute/doc/details?pId=1080)「5、应用支付」共 5 条，**全部是消费者保护向**（合理定价、明码标价、不得诱导付费、明示付费功能、儿童类支付限制），**无一条要求数字商品必须走小米 IAP**。
- [小米《应用商店上架要求》](https://dev.mi.com/distribute/doc/details?pId=1322)「4、应用付费」聚焦自动续订告知、退订途径、续订前 5 日提醒、免费测试账号，**同样无强制内购条款**。
- 小米 GetApps IAP 文档定位为「revenue enhancement service」（**可选的变现服务**），而非强制通道。

**结论：小米侧，Android 直连微信/支付宝不构成上架阻断。**（这与华为形成鲜明对比 —— 华为是「否则可能影响应用上架」的强制语气）

### 3.2 但小米有一条红线与兑换码**直接相关**

小米《开发者生态政策》与《应用审核规范》均有同一条款：

> 应用内容不得含有引导、要求用户进行**异常交易**，包括但不限于**客服引导充值或添加 QQ/微信开通 VIP** 等**非应用内直接交易**形式。

**判定 D-Bee 现状：不触碰。** 依据：
- 兑换码获取途径是「邀请/活动免费获得」（`paywall.tsx:31,189`），**不是充值**；
- 应用内无「加客服微信买码/开通 VIP」的引导入口（全仓 grep 无此类文案）；
- 兑换动作在应用内完成（`redeem_by_code` RPC），属「应用内直接交易形式」。

**⚠️ 未来风险点**：一旦把兑换码变成「**加客服微信付费买码**」，就会**同时**撞：
- 小米「客服引导充值 / 添加微信开通 VIP」→ 非应用内直接交易
- 华为「切支付」（绕过官方支付渠道，属二级违规）

即：**兑换码必须保持「免费获得」属性**。这是它能合规存在的**前提条件**，不是可选项。

## 四、建议（按优先级）

### P1-E-1 · 兑换码：**不隐藏**，但补齐工程纪律（低成本、直接消解审核风险）

`PaywallSheet.tsx:393` 的 `!isIOS()` **保持不变**（iOS 隐藏是对的，Apple 3.1.1；Android/web 显示也是对的，华为官方认可自建赠送码）。

需要补的是 §2.3 的 3 个 ❌/⚠️，建议一次 migration 解决：

```sql
ALTER TABLE public.redeem_codes
  ADD COLUMN code_hash   text,          -- 只存哈希（sha256），明文列逐步弃用
  ADD COLUMN expires_at  timestamptz,   -- 有效期（NULL=永久）
  ADD COLUMN max_uses    integer NOT NULL DEFAULT 1;  -- 支持一码 N 次活动码
```

理由：这不是「应付审核」的形式主义 —— 明文码意味着**任何能读库的人（含 DBA、备份泄露、SQL 注入）都能直接给自己发终身会员**；无有效期意味着**码一旦泄露永久有效、无法止损**。华为这 6 项要求本质是安全基线，D-Bee 已满足 6/11，补齐剩下的是低成本高收益。

同时补 `tools/redeem-code.test.ts`，覆盖华为要求的四组用例（有效未使用 / 已使用 / **过期** / 并发双请求）。

### P1-E-2 · Android 支付：**上华为前**必须改（现在不必动）

若确定要上华为应用市场（`docs/Android上线前置条件清单-2026-10-29.md:3` 明确「华为/小米/OPPO/vivo/应用宝」全渠道目标），则**商户号资质就绪后、接入真实支付前**必须先做：

| 改动 | 位置 | 说明 |
| ---- | ---- | ---- |
| Android 增加「华为渠道」分支，走 IAP Kit 统一收银台 | `src/lib/payment/checkout.ts:39-46` | 华为 IAP Kit **本身支持微信/支付宝付款**（是「统一收银台」，不是「只能华为钱包」），所以不是放弃微信/支付宝，而是**改由华为收银台承载** |
| Android（华为渠道）购买页**移除支付方式按钮与名称** | `src/pages/PaywallSheet.tsx:355-376` | 改为中性「立即开通」按钮，点击直接拉起 IAP 收银台（华为界面规范强制） |
| 服务端补华为验单（`purchaseToken` 验签） | `server/` | 客户端只拿 token，**权益发放必须在服务端验单后**（华为与小米都强调这点） |

**建议决策路径**：资质就绪前先不动（当前降级态零风险）；资质就绪时把「华为 IAP Kit 接入」与「微信/支付宝直连」做成**渠道开关**（按 `platformName()` + 分发渠道判断），web 继续直连微信/支付宝（web 不受应用商店约束），华为包走 IAP Kit，其他安卓渠道（小米/OPPO/vivo/应用宝）可继续直连。

### P1-E-3 · 守住「兑换码=免费获得」这条线（零成本，但不可破）

在 `mini/src/pages/paywall/paywall.tsx:31` 与 `src/pages/PaywallSheet.tsx:391` 的注释里**固化这条约束**，防止未来商业化压力下把它改成「付费买码」—— 那会同时撞小米「客服引导充值」与华为「切支付」两条红线，且是**下架级**而非驳回级风险。

## 五、与审计计划原始预设的差异（诚实记录）

原计划 P1-E 的表述是「决策 Android 端兑换码**是否隐藏**」，隐含预设是「兑换码可能是绕过内购的违规手段」。

**调研结果与该预设相反**：
- 兑换码（自建赠送码）**被华为官方明确认可**，不该隐藏；
- 真正需要处理的是**在线支付直连三方**，而这一项原计划归在 **P1-D**（「在线支付：商户号资质未到，只出前置清单」），未识别出「华为强制 IAP Kit + 购买页禁展示支付方式」这两条硬约束。

→ 建议把 P1-E 与 P1-D **合并追踪**：P1-D 的前置清单里必须加入「华为渠道走 IAP Kit」这一项，否则资质就绪后按现设计直接接微信/支付宝，会在华为上架时被拒。
