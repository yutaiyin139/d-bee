## 八、为什么放 `/var/www` 而不是家目录（决策依据）

> 补充于 2026-10-13，源于"为什么不部署在家目录"的追问。以下为实测验证的结论。

### 8.1 硬约束：Nginx 根本读不到家目录

Nginx 主进程以 `root` 启动后，会按 `user www-data;` 降权，
**所有工作进程（worker）以 `www-data` 身份运行**：

```
root       17586  nginx: master process
www-data   27849  nginx: worker process
www-data   27850  nginx: worker process
...
```

实测 `www-data` 对两个目录的访问结果：

| 目标目录 | 权限 | `www-data` 读取结果 |
|---|---|---|
| `/var/www/d-bee` | `drwxr-xr-x` **755** | ✅ 成功，读到 20 个文件 |
| `/home/ubuntu` | `drwxr-x---` **750** | ❌ `Permission denied` |

权限位解读（三位八进制 = 属主 / 同组 / 其他人）：

- `755` → 其他人 `r-x` → 任何进程可读可进入
- `750` → 其他人 `---` → **除 `ubuntu` 本人与其同组外，一切进程都被挡住**

**结论**：网站若放家目录，Nginx 直接读不到，页面返回 403。

### 8.2 唯一的解法是把安全降级

要让 Nginx 读到家目录，只有两条路，**两条都要放宽权限**：

```bash
chmod 755 /home/ubuntu            # 或
usermod -aG ubuntu www-data        # 把 Web 进程拉进 ubuntu 组
```

代价是什么？家目录里躺着：

```
drwx------  .ssh      700   ← SSH 授权密钥、known_hosts
drwx------  .gnupg    700   ← GPG 密钥环
-rw-------  .bash_history   ← 历史命令（可能含敏感信息）
```

一旦放宽，这些**全部对 Web 进程可见**。若 Nginx 或其上的应用被攻破，
攻击者可直接读取 SSH 密钥，把「Web 漏洞」升级为「服务器登录权限」。
**这是拿最核心的安全边界去换一个目录位置，完全不划算。**

### 8.3 工程层面的额外收益

| 收益 | 说明 |
|---|---|
| 权限天然匹配 | 755 目录 Web 进程直接可读，无需放宽任何东西 |
| 服务与用户解耦 | 网站不绑定某个账号；删掉/更换维护账号，服务照常运行 |
| 工具链默认认这个约定 | 备份、监控、日志轮转的默认策略都覆盖 `/var/www`、`/etc`、`/var/lib` |
| 未来扩展不冲突 | 后续加域名、上 HTTPS、再加站点，彼此独立互不影响 |
| 交接零成本 | 任何人接手都知道先去哪找，不需要翻文档猜 |

### 8.4 对应的标准（FHS）

Linux 的 Filesystem Hierarchy Standard 对各目录职责有明确划分：

| 路径 | 职责 | 本项目对应 |
|---|---|---|
| `/var/www` | Web 服务器内容 | `/var/www/d-bee`（网站本体） |
| `/etc` | 系统与应用配置 | `/etc/nginx/sites-available/d-bee`、`/etc/postgresql/17/main/` |
| `/var/lib` | 应用的可变状态数据 | `/var/lib/postgresql/17/main/`（PG 数据） |
| `/opt` | 自成一体的第三方/独立应用 | `/opt/dbee-db/`（迁移脚本与凭据） |
| `/home` | 用户私有文件（含密钥、个人数据） | **不放服务内容**——权限必须收紧 |

**一句话**：`/home` 是给「人」用的，`/var/www` 是给「服务」用的。
把服务内容塞进人的目录，要么服务跑不起来，要么人的隐私暴露——没有第三个结果。
