# D-Bee 兑换码详细使用方法

> 版本：2026-11-10 · 对应迁移 **0048（安全加固）** + 0044（三档）· 发码工具 `tools/gen-redeem-codes.mjs`

兑换码是 D-Bee **唯一一条已完整打通、可立即使用的变现/获客通道**，且被华为官方明确认可为合规的「自建赠送码表」。本文覆盖从发码 → 兑码 → 对账 → 作废止损的完整操作链路，以及 0048 之后的安全模型。

---

## 一、兑换码是什么

- 一张 **16 位** Crockford base32 码（`0-9A-Z` 去掉易混的 `I L O U`），**无连字符、无空格**，大小写与空格不敏感。
- 分**三档**：`lifetime`（终身买断）、`pro`（限时订阅，`months` 指定月/年）。
- 一张码**只能兑换一次**；pro 档**到期不自动续费**（照抄 iOS「24 小时续订」= 虚假宣传，明确禁止）。
- 兑换后权益写入 `entitlements` 表，换设备也生效。

## 二、发码（运营侧）

### 2.1 基本命令

```bash
# 终身码
node tools/gen-redeem-codes.mjs --plan lifetime --count 5 --note "2026-11 内测"

# 月卡码
node tools/gen-redeem-codes.mjs --plan pro --months 1  --count 20 --note "月卡首发"

# 年卡码
node tools/gen-redeem-codes.mjs --plan pro --months 12 --count 20 --note "年卡首发"

# 限时码（30 天后过期，作废止损用）
node tools/gen-redeem-codes.mjs --plan pro --months 1 --count 20 --note "限时月卡" --expires-days 30

# 演练（不连库、不落盘，只打印 3 张样例）
node tools/gen-redeem-codes.mjs --plan pro --months 1 --count 3 --note "测试" --dry-run
```

### 2.2 参数说明

| 参数 | 必填 | 说明 |
|---|---|---|
| `--plan` | 是 | `lifetime`（终身）/ `pro`（限时） |
| `--months` | pro 时必填 | 时长（月），月卡=1、年卡=12；lifetime 不能带 |
| `--count` | 是 | 数量，1~500（防手滑打爆表） |
| `--note` | 是 | 批次备注，**对账唯一线索，不能空** |
| `--expires-days` | 否 | 码有效期（天），缺省=永久有效 |
| `--print` | 否 | 把明文码打印到终端（默认只落文件） |
| `--dry-run` | 否 | 演练不落库 |

### 2.3 发码后你得到什么

1. **`release/redeem-codes-<档位>-<时间戳>.txt`** —— 明文码清单（**等同现金**，勿外发/提交/贴聊天，文件已 `chmod 600` 且 `release/` 被 gitignore）。
2. **数据库 `redeem_codes` 表** —— 只存 **SHA-256 哈希**（0048 起），**不存明文**。

> 🔴 0048 之后，库里的码是哈希，**反推不出明文**。所以 `release/*.txt` 是唯一明文来源，**务必妥善保管**。丢了文件 = 这批码作废（你也不知道明文了）。

## 三、兑码（用户侧）

用户在 **Web / Android** 的付费墙（`PaywallSheet`）底部找到兑换码输入框：

1. 输入 16 位码 → 点「兑换」。
2. 服务端核销（`redeem_by_code` RPC），返回三种结果之一：
   - `ok` —— 成功，权益立即生效（前端自动刷新）。
   - `used` —— 这张码已被用过。
   - `bad` —— 码不对 / 已过期 / 被限流（三者前端都显示「兑换码不对」）。

> iOS 端**刻意隐藏**兑换码入口（Apple 3.1.1 反规避，App 内不得引导用户绕开 IAP）。

## 四、对账与盘点（运维侧）

### 4.1 按批次查（用 `note` 对账）

```sql
-- 某批次发了多少、还剩多少未用
SELECT count(*) AS total,
       count(*) FILTER (WHERE used_by IS NULL) AS unused
  FROM redeem_codes WHERE note = '2026-11 内测';
```

### 4.2 全局未用码

```sql
SELECT plan, count(*) FROM redeem_codes
 WHERE used_by IS NULL GROUP BY plan;
```

### 4.3 谁用了哪张码（只能看到 hash 与 owner，看不到明文）

```sql
SELECT used_by, used_at, plan, months FROM redeem_codes
 WHERE used_by IS NOT NULL ORDER BY used_at DESC LIMIT 20;
```

> 0048 起 `code` 列恒为 NULL（明文不再入库），对账靠 `note`（批次）+ `used_by`（使用者）+ `used_at`（时间），不靠码明文。

## 五、作废 / 止损（0048 新增能力）

**场景**：某张码泄露了，或想撤销还没被用的码。

### 5.1 有有效期 → 等它自动过期

发码时加了 `--expires-days`，到期后自动失效（返回 `bad`），无需操作。**推荐运营发码时都加有效期**，作为默认止损机制。

### 5.2 手动作废一张未用的码

```sql
-- 已知明文码，按 hash 定位并删除（只能删未用的；已用过的删了也没意义）
DELETE FROM redeem_codes
 WHERE code_hash = encode(digest('<明文码>', 'sha256'), 'hex')
   AND used_by IS NULL;
```

### 5.3 作废整个批次

```sql
DELETE FROM redeem_codes
 WHERE note = '限时月卡' AND used_by IS NULL;
```

> ⚠️ 0048 之前**没有**这个能力（码一旦发出永久有效、无法止损），这是本次加固的核心收益之一。

## 六、0048 安全模型（本次加固，务必理解）

| 加固点 | 之前（风险） | 之后（0048） |
|---|---|---|
| **存储** | `code` 列存明文 → DBA/备份泄露/SQL 注入 = 直接给自己发终身会员 | 库内只存 `code_hash`（SHA-256），明文只落 `release/*.txt` |
| **有效期** | 无 `expires_at`，码永久有效、无法止损 | 新增 `expires_at`，可设 N 天有效期，过期自动失效 |
| **节流** | 接口无频次限制（靠 2^80 码空间硬扛） | 新增 `redeem_attempts` + `redeem_throttled`，60s 内失败 ≥5 次即拒 |

**对外契约完全不变**：RPC 签名 `redeem_by_code(text) → text`、返回值仍只有 `ok/used/bad`，前端**零改动**。

**为什么用 SHA-256 而非 bcrypt**：码空间 2^80 本身不可字典反查，无需慢哈希抗爆破；SHA-256 是 pgcrypto 内置 `digest()`，零额外依赖，且确定性（同一码 hash 唯一，天然支持 UNIQUE 索引 + 等值匹配）。慢哈希反而让 UNIQUE 无法建立在确定性值上。

## 七、与盈利的关系（战略定位）

兑换码**不是**直接变现工具（它必须**免费获得**，否则撞「切支付」下架红线），但它是**最便宜的获客 + 拉新引擎**：

- 邀请好友 → 双方得蜜糖积分 → 积分可兑 `Pro 1 天`（100 分）或 `Pro 30 天`（2600 分）或 `AI 拍照 1 次`（50 分）。
- 这构成**免费的病毒式增长闭环**，为「最终付费」蓄水；兑换码则是给「内测 / 合作 / 补偿」等场景的**定向发放**手段。

---

## 八、一条不能碰的红线

- **Web/App 引导绝不能指向「加客服微信买码」** —— 这同时撞小米「客服引导充值」和华为「切支付」两条下架级红线。
- 兑换码必须保持「邀请 / 活动 / 补偿**免费获得**」属性，绝不能作为**付费购买**的替代收款方式。
