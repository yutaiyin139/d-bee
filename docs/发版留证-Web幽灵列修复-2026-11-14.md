# 发版留证 · Web 幽灵列修复（22:30，V1.7.7 第二次热修）

> 触发：用户测「编辑份量」报两处问题 —— ① mini 端「编辑份量」按钮过长、输入新份量点保存后不生效且不退出编辑态；② Web 端保存未生效，且报「服务器版本不匹配，请更新应用后重试」。
> 结论：**mini 与 Web 是同一个后端根因**，与份量上限 2000 无关。本轮只重发 Web，版本仍 **V1.7.7 不升版**。

## 一、根因（生产侧实证，非推测）

前端 `updateMealGrams` 往 PATCH 的 patch 里写了 **`updated_at`**，但生产库 `public.meal_entries` **没有这一列**：

- `db/migrations/0030-schema.sql:81-101` 建表列清单只有 19 列，无 `updated_at`；同批 `0030` 给 `profiles` / `entitlements` / `payment_products` / `payment_orders` / `recipes` 都补了 `updated_at`，**唯独漏了 `meal_entries`**。全库迁移中也没有任何一条给该表加过此列。
- 旧注释「meal_entries 无 updated_at 触发器，靠前端写入维护」是错误假设：没有列，就无从维护。
- 结果：PostgREST 返回 `PGRST204 Could not find the 'updated_at' column of 'meal_entries' in the schema cache` → 前端 `src/lib/errmsg.ts:40`（mini 同 `:18`）把 `schema cache` 映射成中文「服务版本不匹配，请更新应用后重试」。

**只读连生产库实证**（`sudo -S -u postgres psql -d dbee -tA -c "SELECT column_name FROM information_schema.columns …"`，密码走 stdin、不落盘不打印）：

```
id, owner_id, log_date, meal_type, food_name, quantity_text, grams, calories,
protein_g, carb_g, fat_g, source, image_url, ai_note, health_score, created_at,
sodium_mg, fiber_g, added_sugar_g
HAS updated_at: False
```

**为何两端表现不同**：
- Web：请求被 PostgREST 拒绝 → `saveEdit` catch 显示「服务版本不匹配」（用户可见）。
- mini：同一请求失败 → `saveEdit` catch 只把错误写进页面顶部 `notice err`（热量卡之前），用户当时已滚到「今日餐次」区根本看不到 → 观感即「点保存没反应、也不退出编辑态」（`setEditingId(null)` 只在成功分支执行，属合理设计）。
