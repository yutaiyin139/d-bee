## 一、现状快照（截至今天）

### 收费体系（三档）

| 档位 | 价格 | 权益 | 数据落点 |
|---|---|---|---|
| free | 免费 | 每日 3 次 AI 拍照、条码不限、报告近 7 天、AI 问答限流 | `entitlements.plan='free'` |
| pro | ¥18/月 · ¥128/年 | 拍照不限、报告 30 天、导出、长文本复盘 | `plan='pro'` + `pro_until` |
| lifetime | ¥328 | 永久全部 | `plan='lifetime'` + `pro_until=null` |

- **当前无真实支付**：商品价格（`PRICE_*`）只是展示，点击无支付动作；真实解锁靠「兑换码」。
- **兑换码已服务端化**（0012）：`redeem_codes` 表 + `redeem_by_code` RPC，前端无明文码。

### 邀请拉新 + 蜜糖积分（消耗型积分）

- **三条积分来源**统一走 `honey_ledger`（流水式，`UNIQUE(owner_id, reason, ref_id)` 防重复）。
- **积分有效期 12 个月**，过期记 `expire` 负流水（0011）。
- **兑换表**：100 分 = Pro 1 天，2600 分 = Pro 30 天，50 分 = AI 拍照 1 次。

## 二、发现的问题（按严重度排序）

### 🔴 P0-1　邀请码枚举爆破的节流是「半成品」，实际不生效

**现象**：
- 0012 migration 创建了 `invite_attempts` 表 + `invite_throttled()` 函数；
- schema.sql 注释写明「bind_invite 已重写：接入节流，返回增加 throttled 状态码」；
- 前端 `bindInvite` 的返回类型也声明了 `'throttled'`。

**但**：0012 里**没有重写 `bind_invite` 的函数体**。当前云端运行的 `bind_invite` 仍是 0009 版本，
它：
1. 从不调用 `invite_throttled()`；
2. 从不往 `invite_attempts` 写任何记录；
3. 返回状态码只有 `ok/invalid/self/already`，没有 `throttled`。

**后果**：邀请码是 6 位（字母表 32 字符，约 10 亿组合），虽然枚举空间不小，但**节流形同虚设**——
任何登录用户可以无频次限制地反复调 `bind_invite` 猜码（虽然猜中的直接收益有限，但「防止枚举」这条风控
当初是作为 P1-3 立项的，现在等于没做）。

**修复**：补一段 migration，重写 `bind_invite`：开头判 `invite_throttled(auth.uid())`，
每次尝试（成功/失败）都写 `invite_attempts`，被限流时返回 `'throttled'`。这是纯 SQL 补丁，
前端 `bindInvite` 已兼容该返回值，无需改前端。

---

### 🔴 P0-2　四个核心积分/徽章函数「有调用、无版本化 SQL」，是幽灵函数

**现象**：以下函数在**前端被大量调用**，但函数体**不存在于任何 migration 文件**，只在 schema.sql 注释里被提及：

| 函数 | 前端调用点 | 说明 |
|---|---|---|
| `grant_honey` | `api.ts grantHoney()` | 发积分的核心入口 |
| `redeem_honey` | `api.ts redeemHoney()` | 积分兑换闭环 |
| `unlock_badge` | `api.ts unlockBadge()` | 徽章解锁 |
| `get_inviter_by_code` | （预留） | 按码查邀请人 |

**后果**：这四个函数是「当时在云端手工/临时工具建的，但没有沉淀成 migration」。这意味着：
1. **换环境/重建数据库时会丢失**——schema.sql 只是注释，`db/migrations` 里没有可复现的 DDL；
2. **无法审计其安全性**——比如 `grant_honey` 到底是 SECURITY INVOKER 还是 DEFINER？有没有校验
   `amount` 上限、`reason` 白名单？`redeem_honey` 有没有正确做「扣积分 + 发权益」的原子事务？
   现在**没有任何版本化脚本能回答这些问题**。

**修复**：把这四个函数的实际 DDL 从云端导出，补成一个 migration（如 `0013-ghost-functions.sql`），
同时借机审计其实现是否符合预期（详见 P1-2 的担忧）。

### 🟡 P1-1　兑换闭环可能「套娃」：积分换 Pro，再用 Pro 免费用 AI，反向倒贴

**需要核算的经济账**（这是我最担心的一条，但需要你拍板是否算「坑」）：

- 邀请 1 个有效好友（7 日打卡达标）的完整收益 = 新人 +300 分 + 7 天 Pro；邀请人 +300 分。
- 2600 分 = Pro 30 天，100 分 = Pro 1 天。

按这个兑换率，**一个人只要有约 9 个有效邀请（2600 分）就能换 30 天 Pro**，而 30 天 Pro 的市场价是 ¥128。
也就是说，拉新奖励的「积分价值」折合人民币约 **每 100 分 ≈ ¥4.3**（按 2600 分=¥128 折算）。

这本身是产品设计问题而非漏洞，但有两条要警惕：

1. **AI 拍照成本 vs 积分价值**：50 分换 1 次 AI 拍照，等于 1 次 AI 拍照成本约 ¥2.15（按上述折算）。
   如果免费用户通过「刷打卡积分」换 AI 拍照，成本可能低于真实 AI 调用成本，形成「免费额度被积分兑换
   无限放大」的漏洞。**建议**：确认 `ai1Scan` 兑换是否与免费 3 次叠加、是否有每日上限。

2. **Pro 兑换的边际**：100 分 = Pro 1 天，但 Pro 1 天的订阅价折合 ¥18/30 = ¥0.6/天。用积分换 Pro 1 天
   的成本（100 分 ≈ ¥4.3）远高于直接订阅（¥0.6），用户不会这么换——这其实是**好的**（不亏）。
   但要确认 `redeem_honey` 里 `pro30Day`（2600 分）和 `pro1Day`（100 分）**没有**出现
   「2600/100=26 天，但 30 天档只要 26 天的分」这类定价倒挂。目前 100×26=2600 恰好相等，无倒挂。

**结论**：定价本身无倒挂，但 **`ai1Scan` 兑换（50 分）是最大的经济漏洞点**，需要确认它与免费额度的
叠加关系和单日上限。

### 🟡 P1-2　`redeem_honey` 的原子性与 `grant_honey` 的入参校验「不可审计」

由于 P0-2 的幽灵函数问题，`redeem_honey` / `grant_honey` 的实现是黑盒。有两类风险**必须**借补 migration 时核实：

1. **`grant_honey` 是否校验 `amount` 上限和 `reason` 白名单**：如果 `grant_honey` 是 SECURITY INVOKER
   且不校验入参，那么**任何登录用户可以通过前端 devtools 直接调 RPC 给自己发任意积分**（比如
   `grant_honey('checkin_meal', 'x', 999999)`）。这是最危险的一条——积分兑换 Pro 的闭环一旦能伪造，
   等于免费拿会员。

2. **`redeem_honey` 是否「扣积分 + 发权益」在同一事务**：如果不是，可能出现「扣了分但没发权益」
   或并发下「积分被扣两次」。

**修复优先级最高**：先审计这两个函数，再谈其它。

### 🟡 P1-3　打卡积分「删除收回」只覆盖 `checkin_meal`，饮水/运动可刷

`refund_checkin_honey_by_date`（0011）只收回 `checkin_meal`（+5 分），**没有**对应地收回
`checkin_water`（+2）和 `checkin_exercise`（+2）。

饮水/运动都有「撤销/删除」入口（`undoLastWater` / `deleteExercise`），但删除后**不会**收回已发的
打卡积分。这意味着：
- 用户可以「记一笔饮水达标 → 拿 2 分 → 撤销 → 再记 → 再拿」，因为 `checkin_water` 的 ref_id 是日期，
  当天删掉再记仍是同一天，UNIQUE 防重复**不生效**（因为负流水没记）。

**修复**：参照 `refund_checkin_honey_by_date` 的逻辑，补 `checkin_water` / `checkin_exercise` 的收回，
或统一用一个「当日打卡积分重算」函数，删除/撤销后按当天实际状态重算差额。

### 🟢 P2-1　`monthlyInviteCapOk`（月度邀请返佣 3000 分上限）是死代码

`invite.ts` 里的 `MAX_MONTHLY_INVITE_HONEY = 3000` 和 `monthlyInviteCapOk()` 没有任何调用点。
当初立项（P1-2）标注「价值低、风险低，留待后续」。**目前邀请返佣无上限**，理论上一个用户无限拉新
无限拿积分。鉴于「积分只能平台内兑换、不可提现」，实际危害有限，但**上线付费前应补上**，否则
羊毛党可以用脚本批量注册拿积分换 Pro 再转售。

---

### 🟢 P2-2　`activate()` 里 `source` 硬编码为 `'apple'`

`plan.tsx` 的 `activate()` 函数（支付回调统一入口）里，无论 pro 还是 lifetime，`source` 都写死 `'apple'`。
这意味着将来接入微信/支付宝支付时，如果忘记改这里，**所有支付来源都会被记成 Apple**，
影响后续的退款审计、Apple 3.1.1 合规核查（Apple 会核对你的 IAP 来源）。

**修复**：`activate()` 应接收 `source` 参数，或至少用占位 `'pending'` 而非 `'apple'`，接入支付时按
真实渠道传入。

## 三、审查结论

**总体判断**：体系骨架是扎实的——积分流水式记账 + UNIQUE 防重复 + SECURITY DEFINER 跨用户发分 +
RLS 隔离，方向都对。但存在 **2 个 P0、3 个 P1** 需要在上线付费前解决，核心是：

1. **P0-1 邀请节流没接上**（风控空转）；
2. **P0-2 四个幽灵函数无法审计**，其中 `grant_honey` / `redeem_honey` 的入参校验一旦缺失，
   **等于任何人可伪造积分换终身会员**——这是整套体系最大的单点风险。

**建议的修复顺序**：
1. 先审计 `grant_honey` / `redeem_honey` 真实实现（导出 DDL）→ 确认是否可伪造积分（P0-2 → 可能升级为 P0-0）；
2. 补 `bind_invite` 节流 migration（P0-1）；
3. 补饮水/运动删除收回（P1-3）；
4. 补月度返佣上限接线（P2-1）；
5. 修正 `activate` 的 source 硬编码（P2-2）。

### 复查发现的新遗留问题（待决策）

**🔴 P1 — `release_ai_quota`（INVOKER）是额度绕过漏洞**（✅ 已于 16:28 修复，见下）：
- 该函数用 `GREATEST(count - amount, 0)`，最多清零、不会负数，但**任何登录用户可在 devtools
  调 `release_ai_quota(today, 'scan', 3)` 把当日已用额度清零**，等于免费用户白嫖无限次拍照。
- 根因：函数信任前端「只在识别失败时调用」，但它是 INVOKER，无法区分调用来源是否真的对应一次失败。

**✅ 修复（migration 0014「预占 token」机制，2026-10-16 16:28 用户拍板「现在做」）**：
1. 新增 `ai_quota_claims` 预占表：consume 时生成 md5 token 落表，记录「扣的是基础还是奖励额度」。
2. `consume_photo_quota` 重写为 SECURITY DEFINER + 返回 token 列。
3. 新增 `release_photo_quota(token)`：凭 token 一次性精确退还（扣奖励还奖励、扣基础还基础），
   每个 token 只能退一次——彻底杜绝「无真实 consume 就 release」和「重复 release」。
4. `release_ai_quota` 废弃：REVOKE authenticated 执行权限。
5. 前端 `plan.tsx` 用 ref 保存最近 token，`refundAiQuota` 凭 token 释放；`api.ts` 删除死代码
   `releaseAiQuota`。

**附带修复**：原 `releasePhotoQuota` 无法区分「扣的是奖励还是基础」，统一还基础额度，存在
「扣了奖励却还基础 → 凭空多出额度」的隐性问题；token 机制一并解决了这个退还不精确的问题。

**验证**：typecheck 0 错、build 成功（主包 438.55kB）；云端函数返回类型确认为
`TABLE(allowed, used, remaining, token)`。

**🟢 P3 — `consume_ai_quota`（INVOKER）接受任意 feature/limit**：只能「消耗」不获益，
  仅可能污染 ai_usage 数据，低风险，暂不处理。
