### 1.5 三处重复收敛定稿（18:35 · 已授权）

**总原则**：一个数据只在一处露脸、一个动作只有一个入口；**用户点名保留的模块一个不删、不折叠、不挪位**。手段优先级 = 职责切分 > 文案消歧 > 结构删减；🔴 **结构删减本轮一律不用**——上一版建议的「把 4 格收进折叠分组」会多一次点击，不符合「好操作」，且 4 格真正的问题并非位置，见收敛 3。

#### 收敛 1 · 双积分入口 → 职责切分

- **实证**：`src/pages/ProfileScreen.tsx:447-458` 账户区卡片 `🍯 蜜糖积分 · 邀请好友` → 副文案「查看积分与兑换」→ `setInviteOpen(true)`；`mini/src/pages/profile/profile.tsx:560-563` 同构。宫格第 2 项拍板为「蜜糖积分」，会形成两个同职责入口。
- **决策**：账户区卡片标签收敛为「**邀请好友**」，卡内只承载邀请码 / 已邀请数 / 邀请动作；积分余额与兑换明细归宫格「蜜糖积分」。两者仍指向**同一个 `InviteSheet`**（Sheet 内分「积分明细 / 邀请奖励」两段），**不新增本地状态**。
- **动了**：1 处标签文案（主端 + mini 同构）；**没动**：功能、入口数量、弹层、数据字段、兑换码逻辑。
- **授权依据**：§七-2 已事先写明「改标签会动用户要求『文案不改』的模块」，用户看过代价后仍授权收敛，属知情授权。

#### 收敛 2 · 「数据统计」↔ 报告 tab → 深链

- **实证**：`src/App.tsx:275` 底部 tab「报告」；列表第 4 项「数据统计」为本次新增。
- **决策**：列表项改「**查看完整报告**」，右侧 `↗`（其余 3 项保持 `›`），点击 = 切到既有报告 tab，**不新建页面、不重复实现 `computeReport()` 聚合**。列表仍 4 项。
- **动了**：1 处文案 + 箭头语义；**没动**：4 项结构、报告页、底部 3 tab、数据来源。
- **可访问性**：沿用既有 `list-line` 的 `role="button"` / `tabIndex=0` / `onActivateKey`，补 `aria-label="查看完整报告，切换到报告页"`，触控目标 ≥44px。

#### 收敛 3 · 4 格数值 → 「今日目标」摘要（🔴 推翻上一版判断）

- **实证**：`src/pages/ProfileScreen.tsx:460-479` / `mini/src/pages/profile/profile.tsx:587-607` 的 4 格 = `target.calories` / `profile.current_weight_kg` / `target.protein_g` / `target.carb_g · fat_g`，来自**现场 `calcTarget()`**；而 V1.7.6「体重管理方案 · 每日方案」展示同一组营养目标，按护栏只读**落库派生字段**。故上一版判为「↔ 健康档案核心指标」不准确：真正重复对象是「每日方案」，且是**两套计算口径**（项目铁律明令防此类浮点漂移）。
- **决策**：4 格原位保留、不折叠、不删，收敛为「**今日目标 · 只读摘要**」：
  1. 数值改从 `@dbee/shared/healthPlan.ts` 同一展示模型读取，**移除本区块现场 `calcTarget()`**，与方案页共用真源与 `roundTo()` 展示层舍入；
  2. 整块可点 → 打开「体重管理方案」并锚定「每日方案」段；
  3. 4 格与列表第 1 项由「两处重复」变为「摘要 → 详情」父子关系；「当前体重」是即时值、健康档案是趋势曲线，语义不同不冲突。
- **动了**：区块标题（加「今日目标」+「摘要 · 点按进方案」）、取值来源、点击行为；**没动**：4 格形态、位置、4 个数值项、任何保留清单内模块。
- 🔴 **实施影响面**：`tools/four-end-consistency.test.ts` 手写舍入行号快照（当前基线 `ProfileScreen.tsx:174,175,540`）可能因移除 `calcTarget()` 位移 → 须按铁律更新基线并做红验证；`tools/health-plan-consistency.test.ts` 补「我的页不出现 `calcTarget()`」断言（`stripComments()` 后、实际使用匹配）；mini 同构。

### 3.2 代码实证：我们实际能连什么

`src/lib/health/brand.ts` 的 `detectHealthVendor()` 已覆盖 `apple` / `huawei` / `xiaomi` / `vivo` / `oppo` / `android-other` / `wechat-miniprogram` / `web`；`SYNCABLE_ANDROID_VENDORS` 白名单 = **华为、小米**；`isHealthConnectable()` = 微信小程序 ∨ HealthKit 可用 ∨ 安卓厂商健康可用。

| 平台 | 实际能力 | 定稿呈现 |
| --- | --- | --- |
| iOS 原生 | Apple 健康 HealthKit 真同步 | 「真同步 · iOS」，可连接 / 已连接 |
| Android 华为 / 小米 | 厂商 SDK 真同步（资质未就绪时降级引导） | 「真同步 · 安卓」 |
| 微信小程序 | 微信运动 `wx.getWeRunData`（规划中，诚实降级） | 「小程序 · 规划中」 |
| Android vivo / OPPO | `canSync: false`，仅引导查看对应健康 App | 「引导查看」，**不给可点的绑定按钮** |
| 普通浏览器 Web | `vendor: 'web'`，恒不显示连接入口 | 提示「在 App 中可连接健康应用」 |

### 3.3 定稿设计

- 形态：单态 `SmartDeviceSheet`，标题「智能设备」，复用 `Sheet.tsx` 外壳。
- **分区 A「健康应用 · 现在可连接」**：按当前平台由 `getHealthVendor()` 动态渲染，状态标签区分「真同步 / 引导查看 / 规划中」；连接与解除连接复用「我的 › 健康数据源」既有 `connectHealth()` / `disconnectHealth()` / `isHealthConnected()`，档案页不重复写状态。
- **分区 B「连接状态」**：当前状态 / 今日步数 / 活动消耗（`syncFromHealth()` / `estimateActivityKcal()` / `step_goal`）。
- **分区 C「更多设备 · 后续支持」**：智能体脂秤 / 智能营养秤 / 智能跳绳 / 智能腕带 / 第三方智能秤 / 血糖仪应用。只列名称 + 「后续支持」说明，**零可点绑定按钮、零假功能**。
- **扩展预留（对应「后续可以连接多种智能设备」）**：设备目录与状态枚举下沉 `@dbee/shared/myPage.ts`，形如 `HEALTH_DEVICE_CATALOG: { key, label, status: 'available' | 'guided' | 'planned' }[]`。未来接硬件时只需把 `status` 从 `planned` 改 `available` 并对接 SDK，UI 无需重构。
- **本轮不做**：设备绑定表、蓝牙 / 厂商 SDK、体脂 / 血糖等医疗数据采集与展示（与 `legal.ts` 非医疗建议红线一致）。真接硬件需新增 `device_bindings` 表 + 迁移 + 资质评估，属独立一轮。

| 项 | 规格 |
| --- | --- |

| 间距 | 8 · 12 · 16 · 24px；卡内 padding 11~12px |
| 圆角 | 外层卡 14px / 内卡 8px / 胶囊 99px |
| 组件 | 全部复用 `Sheet.tsx`（`role="dialog"` `aria-modal` + `useModalA11y`）、`.card` / `.list-line` / `.stat-grid` / `.section-title` / `.chip` 既有类；mini 用 `hp-*` 同构类并按 designWidth 750 做 2 倍换算 |
| 八态 | 默认 / hover / active / focus-visible / disabled / 加载 / 空 / 错误，每个入口齐备 |
| 无障碍 | 正文对比 ≥4.5:1（WCAG AA）、触控目标 ≥44px、色带配档位文字 + 三角指示 + 数值 + `aria-label` 四重非色彩编码、所有 `role="button"` 带键盘 `onActivateKey` 与 `tabIndex`、进度条带 `aria-valuenow` |
