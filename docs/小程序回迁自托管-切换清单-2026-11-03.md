## 〇、结论先行

**回迁比预想的简单，但有一个硬坑。**

- 🟢 **好消息**：小程序用到的 **22 个 RPC 全部**在自托管迁移里已存在，**11 张业务表 + RLS 全部**齐备（见 §二）。SDK 的路径前缀 `/.cloud` 与自建网关**完全对齐**（见 §三）。所以自托管侧的 schema 与函数**不用新建**。
- 🔴 **硬坑**：**身份模型不兼容**。云库小程序用户 uid 形如 `wx:<openid>`，而自托管网关的 `owner_id` 是 19 位纯数字串、`ident_kind` 只允许 `phone/email`。回迁必须扩展身份表 + 补微信登录路由（见 §四）。这是工作量的大头，不是改个 endpoint 就行。
- 🔴 **阻断**：域名不可用（无 A 记录 / 未备案 / 无 HTTPS）+ 微信小程序 request 合法域名需备案后才能加。这些不解决，切过去就是「所有网络请求失败」（见 §一）。

**一句话**：配置层是「改一个 endpoint」，但服务端层是「补一条微信登录链路 + 扩身份模型」，且全部被备案卡住。

## 一、本轮已落地的可控准备（已完成，可验证）

### 1.1 endpoint 开关（默认零改变）

新增 `mini/src/lib/backend.ts`（零依赖纯函数，便于单测），`cloud.ts` 改为从它取 endpoint：

```ts
const target = resolveBackendTarget()          // 默认 { kind:'cloud', endpoint: CLOUD_HOST }
export const publicConfig = { ..., endpoint: target.endpoint, ... }
export const BACKEND_KIND = target.kind         // 供 legal.ts 区分公示口径
```

- **默认 = 当前线上行为**：不设任何环境变量 → `cloud`（WorkBuddy 云），产物 endpoint 逐字仍是 `https://zilv-mifeng.app.workbuddy.host`。
- 切自托管需**双确认**：`D_BEE_BACKEND=selfhost` **且** `D_BEE_SELFHOST_READY=true`。
- 🔴 **只换 endpoint，其余三项（resourceId / publishableKey / oauthRelayBaseUrl）不动** —— 核对主端 `src/cloudConfig.ts:133-138` 得出：切到 d-bee.cn 后这三个值与云库版**逐字相同**（resourceId/publishableKey 是 SDK 资源标识与公开访问键，网关按 `WB_PUBLISHABLE_KEY` 校验；oauthRelayBaseUrl 只服务网页扫码登录，小程序走 `signInWithWechat` 用不到）。

### 1.2 双层护栏（实测校准）

| 层 | 位置 | 触发时机 | 实测 |
| -- | ---- | -------- | ---- |
| 构建期 | `mini/config/index.ts` 调 `resolveBackendTarget()` | Node 执行配置文件时 throw，**中断构建** | `D_BEE_BACKEND=selfhost` 缺 READY → `build:weapp` **exit=1** ✅ |
| 运行时 | `mini/src/lib/backend.ts` 的 throw | 小程序启动、加载 cloud.ts 时 | 兜底第二层 |

🔴 **为什么必须两层**：webpack **不执行**被打包的模块代码，所以只有 `backend.ts` 的 throw 时，误切的包照样能构建成功（实测 `build:weapp` exit=0），等发出去、用户打开才发现。`config/index.ts` 由 Node 在构建期执行，复用**同一个** `resolveBackendTarget()`（不另写判断，两层逻辑不漂移），才能把误切挡在构建期。

实测四场景全过：默认→构建成功且产物连云端；selfhost 缺 READY→构建失败；不认识的值（如 `self-host`）→构建失败；selfhost+READY=true→构建成功且产物 endpoint 指向 d-bee.cn。

### 1.3 测试

`tools/mini-backend-switch.test.ts`（**22 项**，零 mock —— backend.ts 无依赖，避开了 `@tarojs/taro` 裸包名 mock 不到的坑）。红绿验证：破坏「双确认门」→ 3 项红；破坏「不静默兜底」→ 多项红；恢复后全绿。

## 四、🔴 身份模型差异（回迁的真正工作量，需现在决策）

这是「改 endpoint」之外最硬的一块。**云库与自托管的用户标识形态不同：**

| 维度 | 云库（WorkBuddy，小程序现用） | 自托管（网关，主端现用） |
| ---- | ---------------------------- | ------------------------ |
| 用户 uid / owner_id | `wx:<openid>`（SDK `signInWithWechat` 返回，见 `auth.ts:77`、SDK 注释） | **19 位纯数字串**（`identity.mjs:99`，HMAC 签发，与 profiles.owner_id 同构） |
| 身份表 | 平台侧 TCB custom uid | `app_users`，`ident_kind` CHECK **只有 `phone`/`email`**（`0031:29`） |
| 登录端点 | `/v1/login-wechat`（平台实现，code 换 openid） | 网关**无此路由**（`app.mjs:79-85` 只有 verification/signin/signup/token/user/me/signout） |
| 微信配置 | 平台侧持有 | 网关 `config.mjs` **无任何 WECHAT 配置** |

### 回迁当天必须补的（服务端，非小程序）

1. **网关补 `POST /.cloud/auth/v1/login-wechat`**：收 `{ code, appid }` → 调微信 `code2session` 换 openid → 签发/查 `app_users` → 返回与现有 `sessionPayload`（`auth.mjs:162-187`）**同构**的 session（`access_token`/`refresh_token`/`sub`/`role:'authenticated'`…）。SDK 的 `postForSession` 只认这个结构，返回体必须对齐，否则 `parseSession` 失败。
2. **`app_users.ident_kind` 扩展 `wechat`**：一次 migration 把 CHECK 从 `IN ('phone','email')` 改为 `IN ('phone','email','wechat')`；`ident_hash` 存 `HMAC-SHA256('wechat:'+openid, IDENT_PEPPER)`（复用 `identity.mjs` 现有哈希，把 kind 拼进被签内容防跨类型碰撞）；`ident_masked` 存 openid 掩码（满足 `app_users_masked_is_masked` 的 `LIKE '%*%'` 约束）。
3. **网关加微信凭据配置**：`config.mjs` 补小程序 `appId` + `AppSecret`（走 `deploy/apply-vision-key-update.py` 的既有密钥机制，🔴 **绝不用 `deploy-gateway.sh`** —— `load_secret` 缺失会 `rand_hex` 重置 `IDENT_PEPPER` → 全站身份永久失效）。
   > ⚠️ 易混淆：`config.mjs` 里 grep `appid` 会命中 `SMS_TENCENT_SDKAPPID`（`:127-128,339`，腾讯云**短信**的 SDKAppID，纯数字如 1400xxxxxx），那**不是**微信小程序 appId。当前网关确实没有任何微信登录凭据，别被这个命中误导成「已经配好了」。

### 🔴 owner_id 映射决策（数据归属，需拍板）

云库小程序用户的业务数据（meal_entries 等）owner_id 是 `wx:<openid>` 形态；自托管是 19 位数字。回迁时两条路：

- **路 A（推荐，因当前全是测试数据）**：不迁移云库小程序用户数据，回迁后微信用户**在自托管重新建号**（新 19 位 owner_id）。代价：测试数据丢弃（用户已明确「现有的数据都是测试数据」）。最干净，无映射风险。
- **路 B（若届时已有真实用户）**：建 `wx:openid → 新19位owner_id` 映射表，全业务表 owner_id 批量改写。**高风险**（外键、honey_ledger 部分唯一索引 `honey_ledger_once(owner_id,reason,ref_id)`、ai_usage `UNIQUE(owner_id,usage_date,feature)` 都要跟着改），须单独设计 + 全量备份 + 灰度。

> 📌 决策点：回迁当天先确认「云库小程序是否已有真实用户数据」。若仍全是测试数据 → 走路 A，本清单 §四 的 1/2/3 做完即可切；若有真实用户 → 必须先立项做路 B 的映射迁移，**不能直接扳开关**。
