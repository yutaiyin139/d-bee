## 2. 🔴 本轮新发现的四个硬阻塞（此前文档未记录）

### 阻塞 1：`minSdk 24` vs Health Connect 稳定版要求 `minSdk 26`

| 项 | 实测值 |
|---|---|
| 项目 `android/variables.gradle:2` | `minSdkVersion = 24`（compileSdk/targetSdk 均 36） |
| `connect-client` 最新稳定版 | **1.1.0**（2025-10-08），官方 get-started 口径要求 **API 26+** |
| 放宽到 minSdk 24 的版本 | **1.2.0-alpha05**（2026-08-12）起，当前 1.2.0-alpha06（2026-08-26）—— **仍是 alpha** |

→ 直接 `implementation 'androidx.health.connect:connect-client:1.1.0'` **构建必失败**（manifest merger / minSdk 校验）。二选一：
- **A（推荐）**：`minSdkVersion 24→26`，放弃 Android 7.0/7.1。2026 年国内占比已极低，但属**产品决策**，且改后要重跑四端护栏 + 真机回归。
- **B**：用 `1.2.0-alpha06`（支持 minSdk 24），代价是 alpha 版 API 可能变动、无稳定性承诺。

### 阻塞 2：整个 Android 构建**零 Kotlin 支持**

`grep kotlin android/build.gradle android/app/build.gradle native-plugins/dbee-health/android/build.gradle` → **0 命中**。
而 Health Connect 客户端是 **Kotlin suspend API**（`aggregate()`、`getGrantedPermissions()` 全为挂起函数）。

→ 必须新增：Kotlin Gradle 插件 + `kotlinx-coroutines` + 插件模块 `apply plugin: 'kotlin-android'` + Java↔Kotlin 回调桥接（现有插件是 Java）。
这是**构建链改造**，不是加个依赖，风险面比规划文档 §4.7 描述的大。

### 阻塞 3：`healthVendorToDb()` 缺 `health_connect` 映射 → HC 连接后来源写不进去

`packages/shared/src/healthVendor.ts`：

```ts
export type HealthVendorDb = 'apple' | 'health_connect' | 'huawei' | 'xiaomi' | 'werun'  // ← 类型含 health_connect
export function healthVendorToDb(vendor: string): HealthVendorDb | null {
  switch (vendor) {
    case 'apple': return 'apple'
    case 'huawei': return 'huawei'
    case 'xiaomi': return 'xiaomi'
    case 'wechat-miniprogram': return 'werun'
    default: return null          // 🔴 health_connect 落到这里 → 返回 null
  }
}
```

而 0053 迁移的 CHECK 约束**已包含** `health_connect`、`isHealthConnected()` 也依赖来源匹配：

```ts
const dbVendor = healthVendorToDb(v.vendor)
await saveProfile({ health_connected: true, ...(dbVendor ? { health_vendor: dbVendor } : {}) })
//                                                    ↑ null 时整个字段被省略
```

→ 后果：HC 接通后连接态会写成「**有 connected、无 vendor**」，`isVendorConnected()` 命中「旧数据回退布尔」分支 → **WX-4 刚修好的跨端串台问题在 HC 上重新出现**（Android 连 HC 后，小程序会误判「微信运动已连接」）。
→ 当前**不是线上 bug**（无任何端写 `health_connect`），但是 HC-2 的**必踩陷阱**。必须在 HC-1 就补，且要先红验证。

### 阻塞 4：`HEALTH_APP_CATALOG` 与 `brand.ts` 均未预留 HC 位

- `HEALTH_APP_CATALOG` 仍 **6 行**（apple/huawei/xiaomi/vivo/oppo/weapp），D1-A 拍板要新增的「系统健康（Health Connect）」行**未做**；`WATCH_BIND_HC_NOTE` 文案已写「正在接入中」，目录却无对应行 → 名实不符。
- `HealthVendor` 枚举无 `health_connect`，且 `detectHealthVendor()` 靠 **UA 关键字**识别；而 HC 是**跨品牌统一层**，UA 根本探测不出来 → 必须改为「插件运行时返回 `availability`」的能力探测（规划 §3 已设计该字段，但插件未实现）。
- `healthCatalogKeyForVendor()` 是「一行匹配一机型」，D1-A 要求放宽为「一行可匹配多机型」。

## 3. 战略层结论：两条路线**都被外部因素卡住**，但卡的性质不同

| 路线 | 卡点 | 可控性 | 判断 |
|---|---|---|---|
| **厂商 SDK**（华为/小米） | 华为个人开发者资质要求「应用需**上架华为应用市场**」→ 上架卡 **App 备案**（管局审核中，硬阻断）；审核另需约 15 工作日 | 🔴 **不可控**，被备案链死锁 | 短期无法启动，勿投入 |
| **Health Connect** | minSdk / Kotlin 构建链 / 国行覆盖率 | 🟠 前两项**完全可控**（纯工程）；第三项需真机实测 | **唯一可自主推进的路线** |

🔴 **必须诚实指出的产品风险**：Health Connect 本体需 **Android 9(API 28)+**，且 Android 13 及以下要从 **Google Play 商店**安装 HC APK；Android 14+ 才并入系统框架。**国行 ROM 普遍无 Play 服务** → 大量国内设备可能根本装不上 HC。规划文档 §2 已记「华为运动健康、vivo 健康、欢太健康未集成 HC；小米 Mi Fitness 部分版本可手动开启但重启静默掉线」。

→ 这意味着 **HC 是「架构亮点」而非「国内覆盖率解药」**：它能覆盖装了 HC 的设备（国际版 ROM、Wear OS、Zepp/Fitbit 用户、部分小米），但**不能**替代华为/小米 SDK 覆盖国行主力机型。两者并行不冲突的定位（规划 §2 结论）依然成立，但**排期上 HC 先行**是因为它不卡审批，不是因为它覆盖更广。

→ **HC-0 真机覆盖率矩阵是这条线的价值判据**，且**只能用户本人跑**（需真机 + 各品牌设备）。在 HC-0 出结果前投入 HC-2 全量原生实现，有「写完发现目标机型装不上 HC」的返工风险。

## 4. 实施计划（按「不依赖外部审批」优先排序）

### P0 · 决策与前置（需用户拍板，不写代码）

| # | 事项 | 建议 |
|---|---|---|
| **D-A** | minSdk 24→26，还是用 `1.2.0-alpha06` | **升 26**。Android 7.x 占比可忽略，稳定版优先于 alpha |
| **D-B** | HC-0 真机覆盖率矩阵谁跑 | 只能**用户本人**；建议先跑 2–3 台主力机型（华为/小米/其它）出最小可用表，再决定 HC-2 投入力度 |
| **D-C** | 华为资质是否启动 | **暂不启动**（被 App 备案死锁）；备案下来后再评估 |
| **D-D** | 阻塞 3（`healthVendorToDb` 缺映射）是否**立即**独立修复 | **建议立即修**，不等 HC。它是潜在 bug 且改动面极小（1 个 case + 护栏先红后绿），与 HC 排期解耦 |

### P1 · HC-1 接口占位与真源补齐（**零外部依赖，可立即开工**）

不依赖任何资质、审批、真机，纯前端 + shared + 护栏：

1. 补 `healthVendorToDb('health_connect') → 'health_connect'`（阻塞 3）
2. `HealthVendor` 枚举加 `'health_connect'`；`detectHealthVendor()` 增「HC 能力优先于 UA 品牌」的分派位（能力由插件 `availability` 提供，未接插件时不返回该 vendor，保证零回归）
3. `HEALTH_APP_CATALOG` 加第 7 行「系统健康（Health Connect）」（D1-A）；`healthCatalogKeyForVendor()` 放宽为一行可匹配多机型
4. 新增 `src/lib/health/connect.ts`：与 `healthkit.ts`/`android.ts` 同接口的占位适配器（`isHealthConnectAvailable()` 恒 false，插件未注入时行为与现状**逐字节一致**）
5. 门面 `isHealthConnectable()` / `syncFromHealth()` / `connectHealth()` 加 HC 分派分支（**HC 优先 → 厂商 SDK 兜底 → 引导**）
6. 护栏：**先写断言 → 红验证 → 再改源码**；新增/放宽必须确认注入真生效（护栏四铁律）
7. 改 shared 后**必须重跑 shared build** 再验门禁（`dist` 陈旧 = 护栏读 src 假绿，已踩三次）

**验收**：全量门禁绿（当前基线 31 文件/1413 项，会因新增断言上升）、两端 typecheck 0、Web 产物探针确认「HC 未接插件时零行为变化」。

### P2 · HC-2 原生实现（需 Android 真机构建，**建议等 HC-0 结果**）

1. 构建链：Kotlin 插件 + 协程 + `connect-client`（阻塞 1、2）
2. `AndroidManifest.xml`：只申**读**权限 `READ_STEPS`/`READ_ACTIVE_CALORIES_BURNED`/`READ_DISTANCE`（不申 `WRITE_*`、不申历史/后台权限）+ `<queries>` provider 可见性 + `ACTION_SHOW_PERMISSIONS_RATIONALE` 说明入口
3. 新增 `HealthConnectReader.kt`：`getSdkStatus` 三态早退 → `getOrCreate` → **每次读前** `getGrantedPermissions()` 复查 → `aggregate()`
4. `DbeeHealthPlugin.java` 桥接 Kotlin Reader，返回真实值 + `availability` 字段；厂商 SDK 骨架保留为 fallback
5. 写 `profiles.health_vendor='health_connect'`（依赖 P1 第 1 条）

🔴 **读数三条铁律**（规划 §4.5，踩了会静默错数据）：
- 用 `aggregate()` **不用** `readRecords()` —— 前者按用户设定的应用优先级**自动多源去重**
- **不要写死 `dataOriginFilter` 包名** —— 2026-06 起设备本地步数 DataOrigin 从 `android` 包名改为 device-specific SPN，按包名过滤会静默漏步数
- 时间窗起点用**设备本地时区当天零点**，不用 UTC（否则今日步数跨时区错位）
- `activeKcal` 是否含 BMR **须真机与厂商 App 对照**，未确认前保守不采信为「活动能量」

### P3 · 真机验证（铁律 #13：本地绿 ≠ 线上绿）

- 真机读数与厂商 App 数值对齐（小时级延迟允许）
- 双通道冲突：HC 与华为/小米同时有数时按「**单一来源优先**」而非相加，`effectiveBurnKcal` 不得虚高
- 撤销权限后 `status='denied'` + 引导文案正确；HC 未安装时 `unavailable` 早退**不降级成 0 步**

### P4 · 发布与合规（发版前必须完成）

- Play Console **Health apps declaration**（逐个读类型说明用途）—— 未声明时用户连接 HC 会看到**系统错误弹窗**
- 国内应用市场健康数据合规评估
- 隐私政策 §五：健康数据属**敏感个人信息** → 单独告知 + 单独同意 + 撤销即删（与 WX-5 同一批法务工作）
- 对外话术按 HC-0 实测表**分机型**表述，不宣称「全机型支持」；🔴 不碰 `legal.ts`「不构成医疗诊断」红线（心率/睡眠即使读到也不得出诊断色带、燃脂心率、疗效承诺）

## 5. 红线（施工时逐条遵守）

- 🔴 原生包禁用 `npm run build`（白屏）；native 与 web 共用 `dist/`，`build:web` 会删 `dist/legal/` → 部署前必须重跑并比对入口 js 文件名

- 🔴 绝不跑 `deploy-gateway.sh`；本线**不涉及网关改动**（HC 是设备本地读取，无服务端链路）
- 🔴 删文件先评估 + 等确认（含构建工具内部清理 `dist`/`mini/dist` 等等价动作）
- 🔴 minSdk 变更属**影响全端产物**的决策，改后须真机回归，不能只靠本地绿

## 6. 一句话结论

Android 端「**门面已就绪、原生为零**」：前端五层里 ①②③ 完备且被护栏钉死，改造面很小；真正的工程量在 ④ 原生层，而它同时卡着 **minSdk 24（需升 26 或用 alpha）**、**零 Kotlin 构建链**、**国行 HC 覆盖率未知** 三道门。厂商 SDK 路线被 App 备案死锁，短期不可动。

建议顺序：**先修阻塞 3（独立小改）→ HC-1 接口占位（零外部依赖）→ 用户跑 HC-0 真机矩阵 → 按覆盖率结果决定 HC-2 投入力度**。
