## 一、目前连在哪里

**一句话**：数据不在你的腾讯云服务器上，而在 **WorkBuddy 云服务托管的 PostgreSQL** 里；你的服务器只做「反向代理 + 静态托管」。

```
   用户浏览器
        │
        ├─── 静态资源（HTML/JS/CSS/图标）─────► 腾讯云 150.158.51.106 / Nginx
        │                                          （/var/www/d-bee，纯静态）
        │
        └─── 数据请求 /_cloud/、/auth/ ────► Nginx 反代 ──► WorkBuddy 云端
                                              （改写 Origin/Referer）      │
                                                                           ▼
                                                             PostgreSQL 17.11
                                                             库 postgres-6o15js8c
```

| 数据库角色 | `cloudbase_postgres_postgres_6o15js8c` |

| 资源 ID | `wbcs_45DQ4I52Uv2NUAKAJkWdq1` |
| 云端入口 | `https://zilv-mifeng.app.workbuddy.host` |
| 前端接入点 | `${window.location.origin}/.cloud/database/rest/<表名>` |
| 认证 | WorkBuddy 云端 auth（手机验证码 / 邮箱 / 微信），当前 3 个终端用户 |

**自托管站点如何连到云端**：Nginx 把 `/.cloud/`、`/auth/` 反代到云端域名，并**改写 `Origin`/`Referer`**
为已登记的官方来源 —— 因为云端有来源白名单，新域名不加这个改写会被 403 拒绝。这一层已经在跑，
配置见 `deploy/nginx.conf.example`。

**为什么只连数据库不需要改前端**：`src/cloudConfig.ts` 里 endpoint 取的是**运行时**的
`window.location.origin`，所以同一份构建产物在 IP / 自建域名 / 官方域名下都会把请求发给「当前来源」，
再由 Nginx 转出去。换域名不用重新构建。

## 二、体检结果

按严重度排列。**最严重的是第 1 条**：

### 🔴 1. 项目里没有任何 SQL 文件，schema 只活在云端

全项目搜 `*.sql` / `schema` / `migration` —— **零命中**。这意味着：

- 数据库结构**无法复现**：换环境、灾备重建时无据可依
- **无法审计**：改过什么、谁改的、为什么改，没有任何记录
- **无法回滚**：上线前无法预演，出事无法还原
- 前端代码有 Git 之外的手工备份习惯，数据库却完全裸奔

✅ **已修复**：本次已反向导出完整基线 → `db/schema.sql`（表 + 索引 + RLS + GRANT），并建立
`db/migrations/` 变更目录与规范。见第三节「第 0 层」。

### 🟢 2. ~~三张表缺业务索引，随数据增长会变慢~~ ✅ 已修复（2026-10-13）

| 表 | 旧索引 | 高频查询 | 修复后 |
|---|---|---|---|
| `meal_entries` | 仅主键 | `WHERE owner_id=? AND log_date=?` | ✅ 复合索引 `(owner_id, log_date)` |
| `water_logs` | 仅主键 | 同上 | ✅ 同上 |
| `exercise_logs` | 仅主键 | 同上 | ✅ 同上 |
| `weight_logs` | ✅ `UNIQUE(owner_id, log_date)` | 同上 | 本就达标 |

App 每次开屏都要按「当前用户 + 今天」查这几张表，报表页还要查日期区间。修复前只有主键索引，
是**每次操作都会走的热路径**，用户量或记录数一上来就是最明显的性能瓶颈。

✅ 已执行：`db/migrations/0001-performance-and-hardening.sql`（3 个复合索引，当前数据量下瞬时完成）

### 🟢 3. ~~未登录角色对全部 7 张表持有增删改查权限~~ ✅ 已修复（2026-10-13）

平台建表时自动给 `anon`（未登录）播撒了 `SELECT/INSERT/UPDATE/DELETE`。

**这不是漏洞**：未登录时 `auth.uid()` 返回 `NULL`，而策略 `owner_id = NULL` 的结果是 `NULL` 而非 `TRUE`，
所以 RLS 会把所有操作挡掉 —— 我核对了全部 16 条策略，都形如 `owner_id = auth.uid()`，逻辑是对的。

**但它是单层防护**：只要哪张表的 RLS 被误关（`DISABLE ROW LEVEL SECURITY`）或策略写错一处，
该表全部用户数据立刻对未登录者开放，没有任何第二道门。

本 App 没有任何需要匿名读取的内容（认证走 `/auth/` 端点，不经过这些表），因此可安全撤销。

✅ 已执行：`REVOKE ALL ON <7 张表> FROM anon`。现在 GRANT 层先行拒绝 —— 未登录请求直接得到
`42501 permission denied`，不再到达策略层，防护升级为「**GRANT + RLS**」双层。（连带修复见第四节）

### 🟡 4. RLS 策略风格不统一

`profiles` / `meal_entries` / `weight_logs` 用 4 条分命令策略（select/insert/update/delete 各一条），
其余 4 张表用 1 条 `FOR ALL`。**语义等价**，不影响安全，但审计时容易看漏，维护也不便。

### 🟡 5. 缺账号级删除能力（合规相关）

代码里有 `clearAllRecords()`（清空记录，保留账号）和 `exportAllData()`（JSON 导出），
但**没有「注销账号」**。个人信息保护法要求提供删除权 —— 现在用户只能删记录，不能删账号本身。
备案阶段这不是必查项，但既然隐私政策里承诺了用户可删除数据，建议补一个注销入口（级联删除 7 张表数据 + 删认证账号）。

### 🟡 6. `updated_at` 靠前端维护，无触发器

`profiles` / `entitlements` 有 `updated_at` 字段但没有 `ON UPDATE` 触发器，时间戳由前端写入。
多端并发或前端漏写时会出现时间戳不准。低频问题，优先级低。

### ⚪ 7. 平台侧备份策略未在公开文档中说明

我查了 WorkBuddy 官方文档与云服务技能文档，**没有找到**关于自动备份、保留时长、数据导出的说明。
这不能推断为"没有备份"，但**不能假定有**。规划里必须自带兜底方案（见第 2 层）。

### 第 1 层 · 数据归宿决策（定版时做，二选一）

**路线 A：继续用 WorkBuddy 云托管（当前状态）**

| 维度 | 评价 |
|---|---|
| 成本 | 零运维、零额外费用 |
| 开发效率 | 认证（手机/邮箱/微信）开箱即用，AI 大模型免密钥 |
| 数据主权 | ❌ 数据在平台侧，导出/迁移需自行实现 |
| 可控性 | ❌ 无法自定义复杂 SQL、定时任务；容量与性能不可控 |
| 锁定风险 | 中 —— 认证体系绑在平台，迁移成本高（见下） |

**路线 B：自建 PostgreSQL / Supabase（腾讯云上自跑）**

| 维度 | 评价 |
|---|---|
| 成本 | 服务器已有（4核4G），但认证需要自己接短信服务商 + 微信开放平台 |
| 数据主权 | ✅ 完全自主，可随时备份、迁移、审计 |
| 可控性 | ✅ 任意 SQL、索引、定时任务、物化视图 |
| 迁移成本 | **认证是大头，不是数据**（详见下表） |

**迁移工作量的真实构成**（这是做决策的关键）：

| 层 | 迁移难度 | 说明 |
|---|---|---|
| **数据** | 🟢 极低 | 7 张表结构简单、数据量近乎为零。导出 JSON → 建表 → 导入，**不到 1 天** |
| **API 调用** | 🟡 中 | SDK 是 PostgREST 风格（`from().select().eq().insert()`），语义与 Supabase 一致。但路径不同（现为 `/.cloud/database/rest/*`，Supabase 为 `/rest/v1/*`），需 Nginx 重写路径 + 换鉴权头。技术可行（我们已在做类似反代改写），但**不是零改动** |
| **认证** | 🔴 高 | 手机验证码要自己接短信服务商（需签名报备）、微信登录要自己申请开放平台应用并配回调、现有 3 个用户要迁移。**数天到两周**，且备案域名通过后要重新跑通回调 |
| **AI 调用** | 🟡 中 | 现在免密钥走云端视觉大模型；自建后需自行申请模型 key |

**我的建议**：

- **现在不要迁。** 认证迁移的成本远大于收益，而数据量小到迁移本身不构成理由。
- **定版时只做一个决定**：是否打算长期自持数据（收费 / 正经运营 / 用户量预期上千）。
  - 若**是** → 在**用户数还小于 100 时**迁（那时认证迁移只需处理少量账号，成本最低）
  - 若**否** → 安心用托管，把第 2 层的备份做扎实即可
- **无论走哪条路，第 0 层和第 2 层都要做** —— 它们是纯收益，不因路线选择而改变。

### 连带修复（0001 暴露的上游问题）

撤销 `anon` 权限后，未登录首页那个「读 `entitlements`」的请求从「200 空数组」变成「401」，
在浏览器控制台留下红字报错 —— 回归脚本据此判 FAIL。

**根因不在数据库**：`src/state/plan.tsx` 的 `PlanProvider` 挂在 App 最外层（连登录页也包着），
挂载即**无条件**读云端；而 fetch 的 401 属于网络层错误，**无法被 JS 的 try/catch 消除**。

**修法**：让权益状态跟随登录态 —— 订阅 `cloud.auth.onAuthStateChange`（SDK 订阅时会立即回放一次
`INITIAL_SESSION`），未登录直接跳过、登录后自动刷新。顺带修掉一个既存缺陷：原先只在挂载时读一次，
**用户登录后权益不会刷新，必须整页刷新才生效**（`refresh` 此前没有任何调用点）。

修正后实测：未登录时云端数据请求数 **0**、console 错误 **0**。
