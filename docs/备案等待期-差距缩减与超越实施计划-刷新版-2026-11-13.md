### 2.4 常见误判纠偏（写进纪律）

| 误判 | 事实 |
| --- | --- |
| 根路径 403 = 云库还在线 | 平台网关通用响应，无判别力 |
| `401 invalid_client` = 数据库还在、只是没权限 | 是**凭据撤销 / 应用注销**；数据库层在线时返回的是 `DATABASE_42501` |
| `cloud_service inspect count=0` = 应用不存在 | 只是**当前会话**的本地清单；应用由早期另一任务创建，账号级 `db_list_tables` 才准 |
| 下线应用 = 停库 | 官方明示「下线不删除云服务数据」；只有**删除应用**才释放 |
| `publishableKey` 是已删应用的孤儿 | 见 §2.3，是**在役自托管配置** |
| 删了云库应用 = 数据面已闭环 | 还差 B1：微信线上 mini 包版本须用户到公众平台确认 |

### 2.5 🔴 顺序偏离如实记录

11-12 20:15 决策的**稳妥路径①**是「先重传 mini 新包 → 体验版六项验收 → 再停库」。用户 11-13 10:04 **直接删除了应用**，未先重传 mini 包。

- **不粉饰**：这一步顺序偏离已发生。若微信线上体验版仍是旧 cloud 包，那些包的云端调用现在会失败 —— 这**本就是删库的期望结果**（旧包本不该继续写云库），但实际效果是测试用户可能短暂断服务。
- **不夸大**：11-12 11:52 曾实证体验版请求全打 `d-bee.cn`（`chat/completions` 200、`release_photo_quota` 200），但**这不构成 11-13 当前包版本的证明**。
- **补救只有一步**：用户到微信公众平台「版本管理」确认线上/体验版包；若仍是旧 cloud 包，按 S1.1 重传新版本并重设体验版，再做六项验收。工程侧无法代做。
