## 〇、一页结论

**这 5 张截图没有改变战略判断，反而把「别抄什么」照得更清楚。**

截图里的薄荷是一个「记录维度很宽 + 会员营销很密 + 内容电商很重」的成熟产品：5 个 tab、8 种快捷记录、8 个工具入口、4 处会员横幅。按项目既定的 A/B/C 三分类：

- 这些大部分属 **A 类规模差距**（食物库、内容、商城、社区、供应链）与 **已定案范围护栏**，一人团队追不上也不该追；
- 真正属于 **B 类功能差距** 的只有几处「每天都会碰到」的交互，其中两项（全字段编辑、回收站）**已在蓝本 S1.2/S1.3 排期**；
- 本轮截图带来的**新发现只有一条主线**：薄荷把「身体数据 + 目标进度」做成了**看得懂的一页**（BMI 色带、BMR 数值带解释、第 N 天 / 剩余天数 / 还差几公斤），而我们**算全了但没讲给用户听**。这是零后端、零迁移、复用现有计算就能补的「已有能力显性化」（D12），性价比高于任何新记录维度。

**一句话建议**：后续要「完善增加」的，不是再加 8 种记录类型，而是 ① 先把已在排期的 S1.2/S1.3 做完 ② 把已经算出来的目标与身体数据讲清楚 ③ 把 7 天报告的入口提到首页。其余截图功能维持「不做 / 不排」。

## 三、本轮新发现：四个「看起来该抄、其实不能抄」

这几条比补哪个功能更重要，直接决定增补清单的边界。

| # | 截图功能 | 为什么不能照抄 |
| --- | --- | --- |
| 1 | **燃脂心率 103~138 次/分** | 我们没有心率数据源（HealthKit 插件只读步数 + 活动能量，`DbeeHealthPlugin.swift`）；且 `legal.ts:384` 明确「不提供医疗诊断、健康咨询或营养处方…需要减重增重等专业指导请咨询执业医师」。要做须新采集敏感生理数据 + 政策改版 + 单独同意。 |
| 2 | **便便 / 血糖 / 围度 / 生理期 / 日记** | 血糖等属敏感个人信息（PIPL 单独同意 + 告知），且偏离「饮食记录」定位；围度/睡眠已列「等待期不排」；日记涉及自由文本存储与导出链路。 |
| 3 | **运动 `*0.9` 回补系数** | 我们是 **50% 回补**（`nutrition.ts`），且这个 50% 已写进 `transparency.ts` 的透明化说明。改系数是产品决策，不是对齐动作；照抄会当场制造口径漂移。 |
| 4 | **「人均减重 6.2 斤」「平均每月减重 3.4 斤 多省 72 元」「0 元用 3 个月」「0.1 元加赠体脂秤」** | 效果承诺 + 价格诱导型营销，撞《广告法》第 4 条与项目「不做渠道首月低价刺客 / 不自动续费」品牌红线（11-11 已整体回退首月半价）。**截图恰好反证了我们「更干净」的定位**。 |

另外两条边界提醒：

- **「上周状态分」是无口径分数**：我们连度量基线都还在等 S1.6，此时做一个没有定义的分数，等于自己制造「会员货不对板」同源的口径问题。若要周反馈，只做「有据可查的一句结论」。
- **「协助分析肥胖原因」** 逼近医疗/营养诊断边界，与 `legal.ts:384` 冲突；我们已有的 `CoachSheet` 问答与「饮食体检」应保持在「参考值 / 用户自填」表述内。
