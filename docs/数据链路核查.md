# 数据链路核查：应用到底在读写哪个数据库

> 核查时间：2026-10-13 20:25（GMT+8）
> 核查方式：源码 + 服务器 nginx 配置 + 浏览器真实请求抓取 + 两库实例指纹对照，四路互证

---

## 一、结论（一句话）

**线上应用读写的是 WorkBuddy 云托管的 PostgreSQL（库 `postgres-6o15js8c`），
不是服务器本机刚装的 `dbee` 库。**

服务器本机的 `dbee` 目前是**一份静态镜像副本**，没有任何应用在用它——
它不会随线上数据自动更新。

---

## 二、四路证据

### 证据 1：前端把请求发往「当前来源」（源码）

`src/cloudConfig.ts` 的 endpoint 解析策略是 `window.location.origin`：

| 访问入口 | 前端 endpoint | 数据请求实际去向 |
|---|---|---|
| `https://zilv-mifeng.app.workbuddy.host` | 该域名本身 | 直连云端（天然同源） |
| `http://150.158.51.106`（当前线上） | `http://150.158.51.106` | 同源 → 本站 Nginx → 反代到云端 |
| 本地 `localhost` 开发 | 回退 `CLOUD_HOST` | 直连云端 `zilv-mifeng.app.workbuddy.host` |

即：**浏览器从不直连数据库**，它请求的是网站的 `/.cloud/...` 路径，
由 Nginx 决定转发到哪里。

### 证据 2：Nginx 把 `/.cloud/` 转发到了云端（服务器配置）

`/etc/nginx/sites-available/d-bee`：

```nginx
upstream dbee_cloud {
    server zilv-mifeng.app.workbuddy.host:443;   # ← 指向上游云端，不是本机
    keepalive 16;
}

location /.cloud/ {
    proxy_pass https://dbee_cloud;
    proxy_set_header Host   zilv-mifeng.app.workbuddy.host;
    proxy_set_header Origin "https://zilv-mifeng.app.workbuddy.host";
    ...
}
location /auth/ { proxy_pass https://dbee_cloud; ... }   # 同理
```

配置里**没有任何一处**指向 `127.0.0.1:5432` 或本机 PG。

### 证据 3：浏览器真实请求全部同源（外网实测）

用 `deploy/probe-data-route.mjs` 从公网打开 `http://150.158.51.106/` 抓包：

```
【同源 · 本站】 150.158.51.106 —— 6 个请求
    GET /
    GET /assets/index-INMRO-hI.js
    GET /assets/index-CyoItpt0.css
    GET /favicon.png
    GET /.cloud/auth/v1/user/me          ← 认证
    GET /.cloud/database/rest/v1/profiles ← 数据

指向 /.cloud/ 或 /auth/ 的请求：2 个
  其中同源（走本站 Nginx 反代）：2 个
  其中直连云端域名（跨域）：0 个
```

端到端探测返回：`HTTP 401 | server=nginx | ACAO=https://zilv-mifeng.app.workbuddy.host`
—— 401 是未登录的正常拒绝（说明请求已被服务端处理），
且 `Access-Control-Allow-Origin` 是**云端应用的应答头**，证明请求确实透传到了云端。

### 证据 4：两个库是不同实例（指纹对照）

| 特征 | 云端（应用实际使用） | 服务器本机 `dbee` |
|---|---|---|
| 库名 | `postgres-6o15js8c` | `dbee` |
| 服务地址 / 端口 | `9.20.183.144:50635` | 回环 `127.0.0.1:5432` |
| 实例启动时间 | 2026-09-28 01:30 | 2026-10-13 18:12 |
| 表 owner | `cloudbase_postgres_postgres_6o15js8c` | `postgres` |
| 集群 system_identifier | —（平台侧不暴露） | `7696093270768368131` |
| 版本串 | `PostgreSQL 17.11 ... gcc 10.2.0` | `PostgreSQL 17.11 (Ubuntu 17.11-1.pgdg24.04+2) ... gcc 13.3.0` |
| 本机 PG 的连接数 | — | **仅 1 个（就是核查本身）** |

端口、启动时间、owner、编译串全不同 → 两个独立实例，不存在「同一个库的两种访问方式」。

## 三、需要留意的两点

### 1. 两边数据是脱钩的（重要）

服务器 `dbee` 是 **2026-10-13 18:12 那一刻云端数据的快照**。
之后线上任何新增/修改**都不会自动进入 `dbee`**。

刷新方式（任选）：
- 重跑 `db/migrations/0002-mirror-to-local-pg.sql`（幂等，可重复执行，只补新数据）
- 或等每日 03:30 的自动化导出 JSON 快照后按需导入

### 2. 云端托管 ≠ 不属于你

云端的 `postgres-6o15js8c` **就是本项目自己的库**（7 张表、16 条 RLS、数据归本账号），
只是**托管方是 WorkBuddy 云服务**（承载在腾讯云中国境内节点）。
「数据在谁的机器上」和「数据属于谁」是两件事，当前状态是：
**数据属于你，机器是平台的**。

## 四、若要改成「应用直连我们自己的库」

当前架构没有自建后端，浏览器通过 Nginx 直连平台的 PostgREST 风格 API。
要切到本机 `dbee`，缺的不是数据库（已经有了），而是这三层：

| 缺什么 | 说明 | 工作量 |
|---|---|---|
| REST API 网关 | 本机 PG 只开了 SQL 端口 5432，浏览器不能直接说 SQL；需要 PostgREST 之类的服务把表映射成 REST | 中 |
| 认证体系 | 现在登录/注册/短信验证码全部依赖云端 auth；切换需自建或保留云端 auth 只换数据层 | 大 |
| 连接身份注入 | 本机 RLS 靠 `SET app.user_id` 生效，需网关按登录态自动注入（连接池 `SET LOCAL`） | 中 |

**折中方案**（推荐顺序）：
1. 保持云端为主库，先把每日快照 + `dbee` 镜像当作**备份与演练环境**（零改造，立即可用）
2. 真要迁移时，先只替换「数据库」这一层（装 PostgREST + 注入 `app.user_id`），认证先继续用云端
3. 认证也自建才是完全自主，属于大工程，建议在备案与真实用户量明确后再评估
