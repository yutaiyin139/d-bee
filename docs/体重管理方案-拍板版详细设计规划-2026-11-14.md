## 二、【关键】事实纠正：`created_at` 本来就有

上一版规格 §五 写「`Profile` 没有创建日期字段，第 N 天 / 达成日不显示、不编造」。**该判断在数据库层是错的**，现更正：

| 事实 | 证据 |
| --- | --- |
| `profiles` 表有 `created_at timestamptz NOT NULL DEFAULT now()` | `db/schema.sql:35`（表定义末两行） |
| `getProfile()` 用 `select('*')`，`created_at` **已经随读返回** | `src/lib/api.ts:69-73`、`mini/src/lib/api.ts:242-246` |
| 只是前端 `Profile` interface **未声明该字段**，所以组件取不到 | `src/types.ts:13-40`、`mini/src/lib/api.ts:39+` |
| `saveProfile()` 走 `PROFILE_WRITABLE` 白名单，新增字段必须登记 | `src/lib/api.ts:52-59`、`mini/src/lib/api.ts:235` |

结论：**「不编造」纪律依然成立，但结论从「不能做」改为「可以做，且不必新建表」**。上一版把 ④ 与「历史方案需新表 + 0045 删号联动」并列，是过高估计了成本；`created_at` 是 `profiles` 行内既有列，删号删整行即天然联动，无需改 0045，RLS 行级策略也自动继承。

## 三、第 ④ 项详细设计规划（第 N 天 / 达成日）

### 3.1 两条路径对比，推荐 B

| | 路径 A：直接用 `created_at`（零迁移） | 路径 B：新增 `plan_started_at`（推荐） |
| --- | --- | --- |
| 数据库改动 | 无 | 一条可空列 + 一次回填（`0050`） |
| 「第 N 天」语义 | 账号注册至今 | **当前方案生效至今** |
| 改目标后 | 天数不重置，仍显示「第 300 天」 | 重置为「第 1 天」 |
| 老用户 | 显示几百天，与当前目标无关 | 回填 `created_at` 作近似起点，标注为近似 |
| 与「确认后自动调整方案」一致性 | **冲突**：用户刚从减脂改增重，却看到「第 300 天」 | 一致：方案整体随目标切换 |
| 风险 | 数字自相矛盾，属变相编造 | 一次轻量生产库变更，需授权 |

**推荐 B 的核心理由**：本产品的关键承诺是「改目标确认后，健康管理方案自动调整」。若时间轴沿用账号创建日，切换目标后页面会出现「增重增肌 · 第 300 天」这种自相矛盾的状态——视觉上没报错，语义上却是错的。A 可作为「暂不授权迁移」时的降级，但必须在 UI 上把标签改成「使用第 N 天」，不得写「方案第 N 天」。

### 3.2 数据库：`db/migrations/0050-plan-start-date.sql`（仅文稿，待授权执行）

```sql
-- 0050-plan-start-date.sql
-- 体重管理方案：当前方案的起始日，用于「第 N 天」与「按每周节奏推算达成日」。
-- 可空 + 回填，避免对既有档案施加强约束；profiles 已启用 RLS，新增列自动继承行级策略。

ALTER TABLE public.profiles
  ADD COLUMN IF NOT EXISTS plan_started_at timestamptz;

-- 既有档案回填：以账号创建日作为近似方案起点（诚实标注为近似，不假装有精确历史）。
UPDATE public.profiles
   SET plan_started_at = created_at
 WHERE plan_started_at IS NULL;
```

约束与联动：
- **不设 `NOT NULL`**、不设默认值、不加索引（该列只随 profile 单行读取，无查询条件）。
- 0045 真删号删 `profiles` 整行 → 该列随之消失，**无需改 0045**。
- 不触碰 `LEGAL_UPDATED`、不动网关、不跑 `deploy-gateway.sh`（该脚本缺 `IDENT_PEPPER` 会重置全站身份，属永久锁死级地雷）。
- **本轮不执行**：生产库应用需单独授权，执行方式沿用 `tools/server-apply-0045.sh` 的既有范式，先备份再应用，应用后用只读探针核对列存在与回填行数。

1. **首次完成引导**：`Onboarding` 保存 profile 时，patch 内带 `plan_started_at: new Date().toISOString()`。两端各一处。

### 3.4 展示层纯函数（下沉 `@dbee/shared`，四端单一真源）

新增 `buildPlanTimelineCore()`，与 `buildHealthPlanViewCore()` 并列导出。设计要点：

```ts
export interface PlanTimeline {
  state: 'ok' | 'no_start' | 'no_rate' | 'reached' | 'too_far' | 'keep'
  dayIndex: number | null          // 第 N 天，从 1 起
  startDateLabel: string | null    // 例 '2026-11-03'
  goalDateLabel: string | null     // 例 '2027-04-18'；null 时按 state 显示对应兜底文案
  estimateNote: string             // '按当前每周节奏推算，实际进度会随记录变化'
}

export function buildPlanTimelineCore(input: {
  planStartedAt: string | null
  todayKey: string
  goal: HealthPlanGoalKey
  currentWeightKg: number | null
  targetWeightKg: number | null
  weeklyRateKg: number | null
}): PlanTimeline
```

计算口径（**唯一权威 = `@dbee/shared` 的 `numfmt.ts` / `datefmt.ts`**，禁止自写 `toFixed` / `Math.round(n*f)/f` / 手写日期毫秒运算）：

- `dayIndex = diffDays(planStartedAt, todayKey) + 1`；`diffDays` 复用 `datefmt.ts`，全程按**日期键**计算，不按时间戳差（避免跨时区 / 夏令时把「今天」算成昨天）。
- `daysNeeded = ceil(|target − current| / |weeklyRate| × 7)`；`ceil` 结果经 `roundTo` 归一后交由 `shiftDate(todayKey, daysNeeded)` 生成达成日。
- `goal === 'keep'` → `state: 'keep'`，`goalDateLabel: null`，UI 显示「维持当前体重，不设达成日」；`dayIndex` 仍显示。
- `planStartedAt == null` → `no_start`，只显示兜底文案「补充起始信息后显示进度」，**不编造**。
- `weeklyRate` 为 `null`/`0`/`NaN` 或 `current`/`target` 缺失 → `no_rate`，显示「按当前节奏暂无法推算」。
- `|target − current| < 0.1` → `reached`，显示「已达成目标体重」。
- `daysNeeded > 1095`（3 年）→ `too_far`，不显示具体日期，避免给出失去意义的远期数字（沿用 `src/lib/report.ts:207` `forecastGoal()` 的 3 年上限精神）。

**【必须】口径隔离**：方案页**禁止引用 `forecastGoal()`**。`forecastGoal` 是「基于 ≥3 条体重记录的最小二乘趋势外推」，报告页在用且依赖 `weightSeries`（方案 Sheet 拿不到）。若方案页也引用，会出现两页两个达成日、用户无法判断哪个是真的。分工明确：

| 页面 | 口径 | 文案标识 |
| --- | --- | --- |
| 方案 Sheet | 按落库周节奏理论推算 | 「预计达成日 · 按当前每周节奏推算」 |
| 报告页 | 基于实际体重记录趋势拟合 | 沿用既有「基于现有记录的推算」 |

护栏需新增断言：方案页两端组件 / 适配层 / shared 中**不得出现 `forecastGoal`**。

### 3.5 UI 落位（卡片 2「体重目标」内，进度条下方新增一行）


- 主行 14px / 500 `--ink`；「第 12 天」用 `--honey-soft` 胶囊底 + `--honey-dark` 字（13px，圆角 99，`padding 5px 12px`，复用 `chipStyle`）。

### 3.6 迁移与回滚

- 应用顺序：先备份 → 应用 `0050` → 只读探针核对列存在 + 回填行数 = 档案总数 → 再发前端。顺序颠倒会让线上老版本 profile 读到 `undefined`，已有 `no_start` 兜底不白屏，但会出现文案降级。

- 代码回滚：`git revert` 单笔提交 + 从 `prebuild-*` 备份回传旧产物。

## 四、第 ① 项：红黄绿色带详细设计（采纳，配两项硬性约束）

### 4.1 配色：低饱和四段，与米色底同一色温

用户要「好看一些」，做法是**保留薄荷的彩色渐变信息密度，但把饱和度压到自律蜜蜂的柔和色阶**——高饱和红绿会与 `--bg #fbf8f1` 打架，也更像营销页。

| 档位 | BMI 区间（成人通用参考值） | 色值 | 角色 |
| --- | --- | --- | --- |
| 偏瘦 | < 18.5 | `#8FB8D9` 雾蓝 | 色带第 1 段 |
| 标准 | 18.5 – 23.9 | `#79B98A` 柔绿 | 第 2 段 |
| 偏重 | 24.0 – 27.9 | `#E8B95C` 蜜黄 | 第 3 段 |
| 超重 | ≥ 28.0 | `#D98174` 陶红 | 第 4 段 |

- 色带高 **8px**、圆角 99、`overflow:hidden`，四段用 `flex` 等宽或按区间比例（推荐等宽，避免刻度视觉误导）。
- 指示器：`--honey-dark #96600a` 三角（10px）+ 当前档位胶囊（该档色作底、`--ink #2a2723` 深字）。**色块上不用白字**——浅色底白字对比度不足，达不到 WCAG AA。
- 档位文字 12px `--ink-3`，四档横排于色带下方；数值「当前 BMI 18.7」18px / 500 置于色带上方。
- 新增 `calcBmiCore()` 放 `@dbee/shared`：`weight / (height/100)²`，只走 `roundTo(x, 1)`；`height_cm` 缺失时不渲染色带（不编造）。

### 4.2 【必须】四重非色彩编码（色觉可访问性）

红绿色盲是最常见色觉障碍，红黄绿连续带对这部分用户**等于无色**。所以色带只承担氛围，信息必须同时由四条通道承载：

1. **文字档位**：四档标签「偏瘦 / 标准 / 偏重 / 超重」始终可见；
2. **位置编码**：蜂蜜黄三角指示器落在哪一段，是独立位置线索；
3. **数值**：`BMI 18.7` 与档位胶囊并排，数值本身可判读；
4. **屏幕阅读器**：色带容器 `role="img"` + `aria-label="当前 BMI 18.7，位于标准参考区间"`。

档位措辞一律用**中性区间词**（偏瘦 / 标准 / 偏重 / 超重），**禁止**「健康 / 不健康 / 风险 / 正常 / 异常」等判断词。

### 4.3 【必须】合规包装：一行说明，不动法务正文

`src/content/legal.ts:384` 明确「本服务不提供医疗诊断、疾病治疗、健康咨询或营养处方……不要依据本服务的数据做出医疗决定」。红黄绿四段带容易被读成「健康分级」，因此色带下方固定一行 12px `--ink-3`：

> 通用 BMI 参考区间，仅用于理解数值，不构成健康评估或医疗建议

并在现有「这些数字怎么来的」折叠区（`TransparencyNotes`）新增一条说明，写清：区间为通用参考值；BMI 不区分肌肉与脂肪；本页不提供任何健康判断。

**这是采纳 ① 的配套约束，不是推翻 ①**：色带照用户要求用彩色，只把「这是医学结论」的误读用文案隔离。不改 `LEGAL_UPDATED`（改日期会让全体老用户重弹同意窗，属产品决策），不改法务三页正文。

### 4.4 护栏（新增两类断言）

- 运行时两端组件**不得出现**判断词「健康 / 不健康 / 疾病风险 / 正常 / 异常」与医学词「诊断 / 处方」；
- 两端组件**必须同时包含**「文字档位 + `aria-label` + 免责说明」三项，用 `every()` 断言（**不得用字符串拼接 `A()+B()`，会假绿**）；
- 色值断言：四段色值在两端逐字一致，且色带容器有 `role="img"`。

### 三目标态差异（补充时间行）

| | 减脂 | 增重增肌 | 保持体重 |
| --- | --- | --- | --- |
| 进度条 | 有 | 有 | 无（±1.0 kg 波动带） |
| 时间行 | 第 N 天 → 预计达成日 | 第 N 天 → 预计达成日 | 第 N 天 +「维持当前体重，不设达成日」 |
| 双卡 | 期望减重 / 还需减重 | 期望增重 / 还需增重 | 本周体重 / 带内天数 |
| 每周节奏 | −0.5 kg | +0.4 kg | 维持 |
