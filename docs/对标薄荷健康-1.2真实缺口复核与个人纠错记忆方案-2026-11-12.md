### 1.1 复核中新增的三条事实（原表没写，会影响方案）

1. **数据层其实完全支持全字段编辑**。`0030-full-selfhost-mirror.sql:81-99` 的 `meal_entries` 已有 13 个业务字段（`food_name` / `calories` / `protein_g` / `carb_g` / `fat_g` / `sodium_mg` / `fiber_g` / `added_sugar_g` / `quantity_text` / `grams` / `source` / `ai_note` / `health_score`）。缺口 #1 是**纯 UI + 接口白名单限制**，不是模型不支持 —— 这大幅降低改造成本。
2. **`meal_entries` 的 RLS 是行级，不是列级**。`0030:439-445` 有 `meal_entries_update_own`（`USING owner_id = auth.uid() WITH CHECK owner_id = auth.uid()`），但表级 `UPDATE` 权限意味着客户端理论上能 PATCH 任意列（`log_date` / `source` / `created_at` 等）。放开全字段编辑时**必须顺手收窄**，否则是把一个体验缺口换成一个数据完整性缺口（详见 §4.6）。
3. **`updateMealGrams` 写入了 `updated_at`（`api.ts:208`），但全库迁移中查不到该列的定义**。可能是生产侧曾手工补列、也可能存在迁移漂移。不能断言是 bug，但**实施 0050 前必须先在生产库做一次 `\d meal_entries` 实证**，否则新代码会放大不一致。

### 1.2 两条「被 11-12 改动部分缓解」的判定

- **#5 长图分享**：11-12 的 `src/lib/share.ts` 已把原生分享从 `url: 'data:image/png;base64,…'` 改为 `Filesystem.writeFile(Cache) → getUri() → Share.share({ files:[uri] })`。这意味着**任意尺寸图片都能经系统分享面板发给微信/钉钉**，长图不再有原生通道障碍，剩下的纯粹是 Canvas 排版扩展。成本比 11-11 估计的低。
- **#8 退款链**：两售卖开关 `D_BEE_XPAY_ENABLED` / `D_BEE_APPPAY_ENABLED` 默认 `false`，**当前没有实际资损**；风险在打开开关那一刻才暴露。因此它应挂在 Wave 2 梯队 D 的前置条件上，而不是现在补。

### 1.3 一条必须纠正的合规暗坑（针对原表 #3 与 Wave 4.1）

路线图 §四 Wave 4.1 草案写「先落 `ai_corrections` 表（记录用户改了什么、原识别值、菜名、**图片指纹**）」。但现行隐私政策已白纸黑字承诺：

- `src/content/legal.ts:266`：「图片：…仅用于识别食物名称与估算份量，**识别完成后不会长期保存**」
- `src/content/legal.ts:356`：「…不会在设备上留存副本」
- `src/content/legal.ts:284`：「记录数据**仅与你本人的账号关联，其他用户无法查看**」

后果有两层：

- 存**原图或可关联回原图的指纹**，与「不长期保存」承诺冲突；即使只存哈希，也需论证「不可逆、不可关联」并补充告知。
- 若把修正数据做成**跨用户公共 UGC 食物库**（薄荷的路线），会直接撞上「其他用户无法查看」，需要改隐私政策 + 重新征得同意。

**修正建议**：Wave 4.1 的「图片指纹」先删掉；私有化路线只存**结构化文本与数值**（菜名归一化键 + 营养值 + 份量），不存任何图像派生数据。这个约束反而指出了更好的产品方向，见 §三。

## 二、§1.2 这张表的三个结构性问题

1. **混列四种不同性质的东西**。能力缺口（1/2/3/5/8）、显性化（4）、主动不做（6）、游戏化道具（7）被放在同一张优先级表里。后果是「补签卡」和「全字段编辑」看起来同级，容易把一人团队最稀缺的工时投到低杠杆项。
2. **功能视角的盲区**：当前项目最大的两个「缺口」根本不在这张表里 —— **上架闸门**（§1.5：软著 30–60 工作日、App/小程序备案、Mac 签名、mini 体验版重传、云库实例未停）与 **口径漂移**（§1.4：代码 3+2 次，docs 写 10 次，白皮书另写一套）。一个上不了架的产品，把 #1~#8 全补完也追不上薄荷。§1.2 应加一行「本表只列功能层缺口，不代表全局优先级」。
3. **缺「可证伪的验收口径」**。8 条都只写「未找到 / 未实现」，没有一条写「做到什么算解决、怎么测」。本文 §4.9 给出示范。

## 三、为什么选 #3（而不是看起来更急的 #1/#2）

| 判据 | #1/#2（记录体验） | #3（修正沉淀） |
| --- | --- | --- |
| 性质 | 止血：竞品有、我们没有 | 造资产：**竞品也没有** |
| 价值随时间 | 一次性，做完即封顶 | 越用越准，边际递增 |
| 是否依赖规模 | 否 | 否（个人级，不需要 UGC 量） |
| 是否撞资质/社区运营 | 否 | 否 |
| 与「超越」的关系 | 无 | 直接（见 §五） |

**薄荷健康的结构性限制**：它的护城河是「大而全的公共食物库 + UGC 公共贡献 + 社区」，数据资产是**共享、静态、面向所有人**的。用户改了某餐的菜名或热量，改的是自己那一餐的显示，不会让系统下次对他更准；要做「个人级纠错记忆」，得在公共库之上再叠一层个人覆盖层，这会稀释公共数据的一致性、增加审核与合规成本，且与其 UGC 飞轮方向相反。

**我们的结构性优势**（都是已有事实，不需要新建）：

- 隐私政策已经承诺「其他用户无法查看」—— 个人级是**唯一天然合规**的方向，公共级反而是违约方向；
- 端侧 KV 已封装：主端 `src/lib/kv.ts:90,149-151`（Web `localStorage` / 原生 `Preferences` 鸭子探测）、mini `mini/src/lib/kv.ts:13,24`（Taro Storage）；
- 功能内单独同意已有范式：`src/lib/aiConsent.ts` / `mini/src/lib/aiConsent.ts`；
- 一人团队不需要 UGC 规模、内容审核、社区运营、KOL —— 这些恰好是路线图 §七 明确不做的。

**它与 #1 是同一个闭环，不是两个项目**：现在只能改 `grams`，且按每克等比缩放，用户连「AI 把菜认错了」这类最常见的错都改不了；没有「原值 → 修正值」这一对数据，就没有任何东西可沉淀。所以本方案 = **A 解锁编辑 → B 落修正 → C 命中复用**，一条链走完。

## 四、详细方案：个人纠错记忆（Personal Correction Memory, PCM）

### 4.1 产品定义

> **「AI 会错，你改一次，它只对你记住。」**

用户剧本：

1. 拍一张「番茄炒蛋」→ AI 给 `320 kcal / 蛋白 12g / 碳水 14g / 脂肪 24g`。
2. 用户改成家常少油做法：`210 kcal`、菜名「番茄炒蛋（少油）」、份量 `200g`。
3. 系统只在本机记下：归一化菜名 → 每 100g 营养值 + 常用份量 + 修正次数。
4. 下次拍照/文字输入同名菜品，草稿区优先给「按你的记录：210 kcal」，并标注来源；**这次不调用模型、不消耗 AI 次数**。
5. 用户可随时查看 / 修改 / 清空「我的口味库」，并可导出成一个 JSON 文件带走。

一句话可验收目标：**同一用户在同一台设备上，对同一道菜的重复修正次数随使用下降，且命中私有库不再消耗 AI 额度。**

### 4.2 架构决策：一期全端侧，零上云（三条硬证据）

这是本方案最关键的取舍，直接决定合规成本与工程量。

| 维度 | 上云（新增 `ai_corrections` 表） | **端侧（本方案一期）** |
| --- | --- | --- |
| 处理目的 | 隐私政策 §二（`legal.ts:276-278`）只列三条用途：生成目标/图表、换设备恢复、安全排障。**「记住你的修正」属新增目的**，PIPL 第 14 条需重新告知同意 | 数据不出设备，不新增对第三方的提供，不改处理目的 |
| 同意窗 | 改 `LEGAL_UPDATED` = **全体老用户重弹同意窗**（项目明列的产品决策，未拍板） | 复用 `aiConsent.ts` 功能内单独同意，**默认关**，不刷 `LEGAL_UPDATED` |
| 数据权联动 | 0045 删号表数组（`0045-account-deletion.sql:57-63`，注释「护栏 9 守护；新增表必须同步」）+ `ExportBundle`（`api.ts:557-583`）+ `clearAllRecords`（`:610+`）+ 护栏 9，**四处必须同步**，漏一处即违反删号承诺 | 删号/清空时删一个 KV key |
| 网关 | 命中私有库若要省模型调用，理想位置在网关前置 → 触及 `deploy-gateway.sh`（全站永久锁死级地雷） | 客户端发起识别前先查本地库并短路，**零网关改动** |
| 迁移 | 需 0050 | **零迁移** |

**决策**：一期 `dbee:pcm:v1` 全端侧、零上云、零迁移、零网关、零 `LEGAL_UPDATED`、零新增依赖。

**诚实的代价**：换设备/重装不同步。处理方式是**如实告知 + 给数据可携带权**，而不是偷偷上云：

- UI 明写「仅保存在本机，换设备不会同步」；
- 提供「导出 / 导入我的口味库」（JSON），这反而把 §二 §2 提到的「数据可携带」品牌牌打得更实；
- 二期上云必须单独拍板（见 §六）。

> 注意 `kv.ts` 文件头已警示：WKWebView 存储紧张时会清空 `localStorage`。因此 PCM 必须设容量上限并提供导出，且**不得承载任何不可重建的关键数据**（登录态、积分、额度绝不能放进来）。

### 4.3 数据模型（端侧 KV）

```ts
// 单一 key：dbee:pcm:v1 —— 由 kvGetJSON / kvSetJSON 读写
interface PCMNutrients {
  kcal: number; p: number; c: number; f: number
  sodiumMg?: number; fiberG?: number; addedSugarG?: number
}

interface PCMCorrection {
  key: string            // 归一化菜名（去空格/全半角/括号附注/常见量词），不用图片指纹
  original: { name: string; grams: number; v: PCMNutrients }
  corrected: { name: string; grams: number; v: PCMNutrients }
  per100g: PCMNutrients  // 由 corrected 换算，计算层保持全精度
  hits: number           // 命中次数
  confidence: number     // 0..1，多次修正一致则上升、矛盾则下降
  createdAt: string      // ISO
  updatedAt: string
}

interface PCMStore {
  v: 1
  entries: PCMCorrection[]
  cap: 300               // LRU 上限，防 localStorage 膨胀
}
```

硬性约束：

- **不存 `image_url`、不存图片指纹、不存任何图像派生数据**（`legal.ts:266/356` 承诺）。
- 归一化 / 置信度 / LRU 全部写成**纯函数并下沉 `packages/shared/src/pcm.ts`**，与 `numfmt.ts` 同纪律；改后必须 `cd packages/shared && npm run build`。
- 数值：**计算层全精度，只在展示层插值那一刻**用 `roundTo(n, d)`（真源 `packages/shared/src/numfmt.ts`，主端 `src/lib/numfmt.ts` 是纯 re-export）。禁止自写 `toFixed` / `Math.round(n*f)/f`。
- 容量 300 上限 + 最近最少使用淘汰；超限不阻断主流程，静默淘汰最旧项。

### 4.5 编辑链路的安全收口（原表完全没提，但必须做）

现状 RLS 只管行不管列。放开「全字段编辑」若直接让前端 PATCH 任意列，等于用户可以伪造 `log_date`（补历史）、篡改 `source`（把手动条目伪装成 AI 或反之）、改 `created_at`。同理，路线图 W3.1 建议的「SECDEF + 入参白名单 + 只信 `auth.uid()`」方向是对的，这里给到可执行级别：

**推荐 (a)**：在 `0050` 增加 SECDEF RPC，照 `0039-rpc-trust-boundary.sql` 的既有范式（签名稳定、函数体不信任客户端、`advisory xact lock` 防并发）：

```sql
CREATE OR REPLACE FUNCTION public.update_meal_entry(
  p_id bigint,
  p_fields jsonb
) RETURNS public.meal_entries
LANGUAGE plpgsql VOLATILE SECURITY DEFINER
SET search_path = public, pg_temp
AS $fn$
DECLARE
  v_allowed text[] := ARRAY[
    'food_name','quantity_text','grams','calories',
    'protein_g','carb_g','fat_g','sodium_mg','fiber_g','added_sugar_g'
  ];
  k text;
  v_row public.meal_entries;
BEGIN
  -- ① 只认 auth.uid()，不接受调用方指定 owner
  SELECT * INTO v_row FROM public.meal_entries
   WHERE id = p_id AND owner_id = auth.uid() FOR UPDATE;
  IF NOT FOUND THEN RAISE EXCEPTION '记录不存在或不属于当前账号'; END IF;

  -- ② 白名单外字段一律拒绝（含 owner_id / log_date / source / created_at）
  FOR k IN SELECT jsonb_object_keys(p_fields) LOOP
    IF NOT (k = ANY(v_allowed)) THEN
      RAISE EXCEPTION '不允许修改字段 %', k;
    END IF;
  END LOOP;

  -- ③ 值域校验（与 GRAMS_LIMIT 同源、热量/宏量非负且有上界）
  --   NUMERIC 比较后再 UPDATE，避免前端传 Inf/NaN/负数污染统计
  -- ④ 由服务端统一写 updated_at，不信任客户端时间
  UPDATE public.meal_entries
     SET food_name      = COALESCE((p_fields->>'food_name'), food_name),
         quantity_text  = ..., grams = ..., calories = ...,
         protein_g = ..., carb_g = ..., fat_g = ...,
         sodium_mg = ..., fiber_g = ..., added_sugar_g = ...,
         updated_at = now()
   WHERE id = p_id AND owner_id = auth.uid()
   RETURNING * INTO v_row;
  RETURN v_row;
END
$fn$;
```

- `GRANT EXECUTE ... TO authenticated`；**不授 `dbee_app` 之外的越权角色**。
- 🔴 **不走 `deploy-gateway.sh`**；RPC 经现有 PostgREST 通道，网关零改动。
- 🔴 `0050` 顺带 `ADD COLUMN IF NOT EXISTS updated_at timestamptz`，但**先在生产库做 `\d meal_entries` 实证**（§1.1 第 3 条），确认是否已有该列，避免重复/漂移。
- **备选 (b)**：`REVOKE UPDATE ON public.meal_entries FROM authenticated` + `GRANT UPDATE (col1, col2, …)` 列级授权。更轻，但字段扩展要改 grant，且无法做值域校验，故不推荐。

**关于回收站（#2）：本方案不捆绑。** 它牵动软删列 + 恢复 RPC + 定时清理 + `refundCheckinHoney` 的「恢复时是否重发积分」防刷逻辑 + 0045 删号数组 + `ExportBundle` + `clearAllRecords`，是另一个完整项目。建议按路线图排在 Wave 3 后半，单独开单。

### 4.7 隐私与 AI 标识合规清单

1. 端侧存储不改变「向第三方提供」清单，不上传、不新增处理目的 → **不刷 `LEGAL_UPDATED`**（项目纪律：刷新会让全体老用户重弹同意窗）。

## 五、从「补齐」到「超越」：诚实的三段论

用户说「最终要超越薄荷健康，虽然短期不可能」。这个判断是对的，而且「短期不可能」不是士气问题，是可以列清楚的硬闸门：

| 段 | 事实 | 目标 |
| --- | --- | --- |
| **短期（现在 → 上架）** | 软著 30–60 工作日（全局最长边）、App/小程序备案、Mac + Xcode≥26 + `DEVELOPMENT_TEAM`、mini 体验版重传、云库实例停用 T+7、公安备案 12-06 前回填、两收款开关默认 false、Web 暂不收费 | **先活到有真实用户**。此时谈超越毫无意义 |
| **中期（差异化）** | 上架后，用「无广告 / 无营销推送 / 不首月低价 / 随时导出随时删光 / AI 会错但你说了算」建立可信度 | 在**可信度**这一个维度上超过薄荷，不比功能数 |
| **长期（结构性超越）** | 私有纠错记忆累积成「只属于你的口味库」，越用越准、越用越少调模型 | 在**「谁说了算」**这一维度反转主客关系 |

### 5.1 把「超越」重新定义成可证伪的东西

不要在 DAU、功能数量、食物库条数上定义超越 —— 160 万条公共库、社区、KOL、电商，一人团队十年也追不上，且路线图 §七 已明确不做。可行的定义是：

> **薄荷＝用户适应它的库；自律蜜蜂＝库适应用户。**

这不是口号，因为它有四个可证伪标志（都需要先埋点，阈值拿到真实数据后再定，不拍脑袋）：

1. 老用户第 30 天的 **AI 修正率显著低于** 第 1 天（系统在学他）；
2. **私有库命中占比** 持续上升，且命中的餐次更少被二次修正；
3. 用户能**完整导出 / 删除**自己的口味库，且换设备可自行带走（薄荷的公共库资产不属于用户）；
4. 「无开屏广告 / 无营销推送 / 不做渠道首月价 / 不自动续费」写进对外承诺且**长期不破**（11-11 已整体回退首月半价，这条红线目前是干净的）。

### 5.2 为什么薄荷难跟（结构性，不是努力程度）

- 它的核心资产是**共享的公共食物库 + UGC 贡献 + 社区流量**。叠一层「个人覆盖」会让公共数据一致性变复杂，且与其「大家共建一个库」的飞轮方向相反。
- 它的商业模式依赖会员 / 电商 / 广告，「尽量不收集、端侧优先、不上传」是它**不能讲**的承诺；我们讲，是因为我们本来就小、本来就自托管、隐私政策本来就写了「其他用户无法查看」。
- 反过来，**这也是我们的风险**：端侧不同步会伤「换设备」体验；一旦用户量起来、为了同步而上云，就会重新面对薄荷那套合规与审核成本。所以「不收集」必须作为**长期品牌红线**，而不是一期的技术妥协。§4.2 的取舍因此不只是工程决策，是产品定位决策。

### 5.3 一句实话

这个方案**不会让我们短期超过薄荷**，它甚至不增加一个新功能入口的可见度。它做的是：把「AI 识别不准」这个所有饮食 App 都被骂、且大厂因为库太大而最难改的痛点，变成「用户改一次就永久改善、且只对他改善」的资产。**先在上架闸门之后，把这一件事做到竞品做不到，比把 §1.2 八条全补完更接近「超越」。**
