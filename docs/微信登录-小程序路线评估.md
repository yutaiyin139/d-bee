# 「先用微信小程序登录」路线评估（2026-10-14）

> 触发问题：企业主体注册仍在推进中，能否先用微信小程序解决微信登录？
> 结论：**取决于你要解决的是哪个目标。小程序能解决「微信生态入口」，解决不了「App 内微信登录」。**
> 本文补充 `docs/微信登录接入.md`，不覆盖其结论。

---

## 一、先把目标拆开，否则会做错方向

「微信登录」在本项目里其实是三个不同的目标，被同一句话盖住了：

| # | 目标 | 现状 | 小程序能否解决 |
|---|---|---|---|
| 1 | **Web / PWA 端微信登录** | ✅ 已可用（V1.0.1 起） | 不需要——已有云 Relay 扫码，且不占用自己的 AppID |
| 2 | **原生 App 内微信登录** | ❌ 卡住 | **不能**（见 §三，硬性限制） |
| 3 | **微信生态内的独立入口**（小程序本身） | 未开始 | ✅ 可以，且个人主体即可启动 |

**关键认知**：目标 2 卡住的真正原因不是「没有微信资质」，而是两条：
1. 微信开放平台「移动应用」需开发者资质认证，而**个人主体无法完成开放平台认证/绑定**；
2. 云端 `cloud.auth.signInWithWechat(code, appid)` 只支持**小程序** `jscode2session`，
   移动应用的 code 需走 `sns/oauth2/access_token`，接口不同、不能混用。

第 2 条是**云端能力缺口**，与微信资质无关。即使拿到企业主体、拿到移动应用 AppID，
云端不补接口，App 内微信登录依然跑不通。

---

## 二、依据（可复查）

### 云端接口

`@tencent-ai/workbuddy-cloud-sdk` 的 `signInWithWechat(code, appid)`（`lib/index.d.ts:442`）文档原文：

> 小程序 wx.login 的 code 换 Genie session。试用与正式是两套独立**小程序**，
> 必须带当前账号的 appid（`wx.getAccountInfoSync().miniProgram.appId`）。

→ **小程序是云端唯一原生支持的微信登录形态**。这一点上你的直觉是对的。

### 微信官方规则（developers.weixin.qq.com）

- 「个人类型账号暂不支持微信认证。」
- 「微信开放平台账号必须完成开发者资质认证才可以绑定同主体小程序。」
- UnionID 机制的前提是：多端**绑定到同一个微信开放平台账号**。

→ **个人主体小程序拿不到 UnionID**，只有 openid。而 openid 是「小程序维度」的，
   App / 公众号 / Web 各自不同 → **无法把同一个人在小程序与 App 之间认成同一账号**。

### 备案

境内小程序自 2023-09 起备案全量强制，个人/企业与 Web 站备案同理，整体约 7–20 个工作日。
**小程序绕开的是「开放平台移动应用审核」，绕不开备案。**

## 三、为什么小程序救不了「App 内微信登录」

即便做了小程序，App 里点「微信登录」也没有任何一条通路能连过去：

- 小程序运行在微信自己的运行时里，`wx.login` 在 App 的 WebView / 原生层**不存在**；
- 用户从 App 跳到小程序再跳回来，需要一个「把身份递回来」的通道，而这个通道的
  身份凭据必须是 **UnionID** 级别（否则小程序签发的 token 无法在 App 侧被信任）；
- UnionID 需要开放平台绑定 → 回到企业主体。

**唯一不需要 UnionID 的变体**：小程序只当一个「一次性授权码发放器」——
App 展示二维码 → 用户微信扫码进小程序 → 小程序把一次性 code 写到云端 →
App 轮询取 code 换自己的会话。技术上可行，但成本约等于自建一套扫码登录中继，
且用户要多走「跳出 App → 打开小程序 → 跳回来」三步，**体验明显差于 §四的方案 B**。

## 四、三条可执行的路线

### 路线 A：注册个人主体小程序，作为独立新入口

- **能拿到什么**：微信生态内的可搜索、可分享、可扫码的产品入口；微信登录（openid 维度）可用
- **前置**：个人身份证 + 未占用邮箱 + 实名微信号；小程序备案 7–20 工作日
- **代价 / 天花板**：
  - 不能开微信支付（会员/订阅收不了钱）；2026-08 起个人主体开放虚拟支付，但仅限部分类目
  - 无 UnionID → **不能与 App / Web 统一账号**，将来必须做一次「主体变更 + 老用户重新关联」
  - 类目受限：**医疗健康是个人主体禁区**。D-Bee 需按「工具 / 生活记录」类目报备，
    能否过审要实测（食物热量记录属工具属性，风险中等）
- **判断**：如果目的是「尽快有一个微信里的产品入口」，值得做；**如果目的是解 App 的登录，无意义**

### 路线 B：App 内微信登录改走「系统浏览器 + 深链」，复用云 Relay（推荐用于解目标 2）

- **思路**：app 内不调微信 SDK，而是用系统浏览器打开云 Relay 的 OAuth 扫码页
  → 用户在浏览器里完成扫码 → 回跳一个 **已备案的 HTTPS Universal Link**
  → 系统把控制权交回 App → App 沿用一个 code 换会话
- **好处**：
  - **完全不需要微信开放平台移动应用资质**，绕开企业主体依赖
  - 复用 Web 端已在跑的云 Relay，不新增后端
- **代价 / 前置**：
  - 需要一个**已备案的 HTTPS 域名**挂 `apple-app-site-association`（即 `d-bee.com.cn` 的备案）
  - 需要向云服务方确认：`signInWithOAuth` 的 `redirectTo` 是否允许白名单外的自定义地址
  - 必须实现「浏览器回到 App」的兜底（用户手动切回 App 时轮询会话态）
- **判断**：这是**唯一能在企业主体落地前让 App 拥有微信登录**的路

### 路线 C：什么都不做，等企业主体 + 云端接口

- 企业主体下来后 → 开放平台认证 → 移动应用 AppID → 云端补「移动应用 code 换会话」
- **判断**：最干净，但被两个外部依赖串行阻塞；建议**并行启动 A 或 B**，不要空等

## 五、建议

1. **不要为了解 App 的登录去做小程序**——它在原理上解不了，会白花 2–4 周。
2. **真正该并行推进的两件事**：
   - 向 WorkBuddy 云服务方提交工单，问清单一问题（见 §六）——这是所有路线的共同卡点，
     也是唯一「不花自己工期、只花沟通成本」的推进
   - App 内微信登录按**路线 B** 预研：先把 `d-bee.com.cn` 备案跑起来
     （同时它也是 App 备案、Universal Link 的共同前置）
3. **小程序（路线 A）按商业价值单独决策**，不要捆绑在登录问题上：
   现在做 = 换一个微信里的获客入口 + 牺牲账号互通；等企业主体 = 一步到位但更慢。
   若 D-Bee 的获客强依赖微信搜索/分享，个人主体小程序可以先做，但**必须接受后续主体变更
   与老用户重新关联的一次性成本**。

## 六、需要向云服务方确认的问题（可直接复制）

1. `cloud.auth.signInWithWechat(code, appid)` 是否**只会**走小程序 `jscode2session`？
   是否有支持移动应用 `sns/oauth2/access_token` 的接口或排期？
2. `signInWithOAuth({ provider: 'wechat', redirectTo })` 的 `redirectTo` 是否支持
   白名单外的自定义地址（如 `https://d-bee.com.cn/auth/callback` 或自定义 scheme）？
   若支持，原生 App 走系统浏览器 + 深链即可复用现有 Relay，无需移动应用资质。
3. 上述两者的服务端是否校验 `redirectTo` 必须与注册来源同源？
