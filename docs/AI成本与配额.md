# AI 能力来源、免费额度与成本

> 面向：D-Bee 运营 / 发版决策
> 更新：2026-10-13（V1.0.0）

---

## 一、系统的 AI 能力来自哪里

D-Bee 自己**不持有任何模型**，也没有配置过 API Key。所有 AI 能力都来自
WorkBuddy 云服务的 `cloud.llm` 模块：

| 项 | 值 |
|---|---|
| 调用方式 | `POST {当前站点来源}/.cloud/llm/chat/completions`（仅流式 SSE） |
| 凭据 | `publishableKey`（公开标识，写在 `src/cloudConfig.ts`）+ 用户登录态 JWT |
| 密钥 | **无需** API Key；SDK 不暴露任何厂商密钥或接入地址 |
| 路由 | nginx 把 `/.cloud/` 反代到 `zilv-mifeng.app.workbuddy.host` |
| 模型选择 | 运行时读 `cloud.llm.models.list()`，取 `isDefault` 的那个 |

当前默认命中的是模型目录里的 **`auto`** ——「自动为每个任务匹配最优模型，积分倍率随之浮动」。

### 平台按「积分」计费

模型目录会返回每个模型的 `credits` 字段（倍率，仅供展示）。同一份目录下差距很大：

| 模型 | credits | 视觉 | 备注 |
|---|---|---|---|
| `hy3` | x0.00 | 支持 | 混元思考模型 |
| `step-5-preview` | x0.00 | 支持 | 阶跃旗舰 |
| `hunyuan-2.0-thinking` | x0.04 | 不支持 | |
| `glm-5.3-flash` | x0.06 | 支持 | 原生多模态，擅长视觉理解 |
| `glm-4.6v` / `deepseek-v4.1-flash` | x0.11 | 支持 | |
| `auto`（**当前默认**） | 浮动 | 支持 | 按任务动态匹配 |
| `default` | x2.20 | 不支持 | |

> ⚠️ 口径说明：SDK 明确把 `credits` 定义为**展示信息，不是余额或账单事实**，
> 用量、配额、账单都不通过 SDK 暴露，只能去 WorkBuddy 控制台看。
> 所以上表用于**相对比较**，不要当作精确报价。

## 二、免费 10 次是怎么算的（超过 10 次会怎样）

**关键前提：10 次是 D-Bee 自己的产品规则，不是平台限制。**
`src/lib/entitlement.ts` 里 `FREE_DAILY_AI = 10`，想改改这一个常量就行。
该常量只在前端，作为 `p_limit` 参数传给云端 `consume_ai_quota`，数据库里不存字面量——**改常量即生效，无需任何数据库迁移**。

### 计数规则

| 维度 | 规则 |
|---|---|
| 周期 | 按**本地自然日**累计，次日 0 点自动重置 |
| 池子 | 单一计数器，`ai_usage` 表 `feature='scan'` |
| 共用范围 | 拍照识别、文字描述解析、包装兜底识别、AI 问答（首页入口 + 聊天面板） |
| 不消耗次数 | 扫码查商品库（走 Open Food Facts 公开 API）、手动搜索食物库、记录饮水/体重/运动、近 7 天报告、首次生成个性化计划 |
| 周额度 | 报告 AI 解读单独计数，每周 1 次，**周一**重置（`FREE_INSIGHT_PER_WEEK`） |
| Pro | 全部不限次数 |

### 超过 10 次时发生什么

第 11 次起前端**直接拦截**，不发起 AI 请求，弹出付费墙并说明：

> 今日 10 次免费 AI 已用完（拍照识别、文字解析、包装识别与 AI 问答共用），明天 0 点自动重置。
> 升级 Pro 可不限次数。手动添加食物、扫条码、记录饮水体重运动、查看近 7 天报告都不受影响。

也就是说，**用尽额度不会让应用不可用**，只是 AI 相关入口降级为手动记录。
不存在「超出后按量扣费」——免费用户不会被意外收费。

### 额度用完之后用户还能做什么

- 手动从 1180 条食物库里搜索/分类添加
- 扫商品条码查营养表
- 记录饮水、体重、运动
- 看近 7 天报告与图表（30 天趋势是 Pro 功能）
- 查看首页的饮食体检、营养素进度等**离线规则引擎**结果（`src/lib/foodInsight.ts`，不消耗 AI）

## 三、要不要配置自己的 API Key？

**结论：V1.0.0 不需要，建议维持现状。**

### 三条路径对比

| 方案 | 成本 | 工作量 | 风险 |
|---|---|---|---|
| **A. 维持 `cloud.llm`（推荐）** | 平台按积分结算 | 0（已上线） | 无密钥泄露面 |
| **B. 维持 `cloud.llm` + 换成零积分模型** | 有机会降到 0 | 改 1 个函数（`ai.ts` 的 `pickModel`） | 输出质量需重新验证 |
| **C. 自建 API Key** | 按厂商价目表付费 | 需新增服务端中转 + 鉴权 + 限流 | 密钥管理、多家兼容层、运维 |

### 为什么 V1.0.0 不自建

1. **密钥不能放前端。** D-Bee 是纯静态站点（nginx 托管 `dist/`），前端代码对所有人可见。
   把 API Key 写进前端等于公开泄露；必须新增一个服务端中转服务。
2. **自建要补齐一套后端。** 服务端中转不只是转发请求，还要处理登录态校验、
   按用户限流（否则免费额度形同虚设）、超时重试、错误归一化——这是新的一条产品线，
   不是「配个 Key」这么简单。
3. **平台的模型目录足够用。** 目录里有 30+ 个模型，含多模态（拍照识别必需的视觉能力），
   自建的话要自己维护多家厂商的接口差异。
4. **现阶段量级不够。** 免费用户每天 10 次的上限本身就把成本封顶了，
   真实付费用户还没起来，谈不上成本压力。

### 什么信号出现时该切换

- 日活上来、需要**精确成本核算**与分层定价（比如按次数卖包）
- 需要锁定**特定模型**（自研 / 微调 / 合规要求）
- 需要**真正防住额度绕过**（见下节「已知限制」）

### 如果只是嫌积分花得快——先换模型，比换 Key 更立竿见影

`src/lib/ai.ts` 的 `pickModel()` 现在挑的是 `auto`（倍率浮动）。
把饮食识别这类结构简单的任务换成目录里的零积分模型（`hy3` / `step-5-preview`，
两者都支持图片），有机会把 AI 成本压到 0，改动只有几行。

代价是失去了 `auto` 的自动择优，识别质量需要用真实照片回归验证。
**建议做法**：V1.0.0 先维持 `auto` 保证体验，等有真实用量数据后再决定是否降级模型。
具体该换成哪个模型、以及换之前要先做什么，见下面的第四节。

## 四、模型选型建议（如果将来决定换）

> 当前状态（V1.0.0）：**维持 `auto` 不变**。下面是换模型时的决策依据，不是待办。

### 硬性筛选条件

D-Bee 最重的活是**拍照识别食物和包装**，所以模型必须 `supportsImages: true`。
这一条直接排除掉 `glm-5.1` / `glm-4.7` / `glm-4.6` / `kimi-k2-thinking` /
`hunyuan-2.0-thinking` / `minimax-m2.5` / `deepseek-v3-2-volc` 等一批模型
（`hunyuan-2.0-thinking` 还额外标了 `disabledMultimodal: true`，双重排除）。

### 视觉可用的候选（按倍率排序）

| 模型 | 倍率 | 输入 / 输出上限 | 官方定位 |
|---|---|---|---|
| `step-5-preview` | x0.00 | 1M / 64K | 阶跃 StepFun 面向真实任务的旗舰基模 |
| `hy3` | x0.00 | 192K / 64K | 混元思考模型 |
| `hy3-x` | x0.05 | 192K / 64K | 同上 |
| **`glm-5.3-flash`** | **x0.06** | 1M / **131K** | **原生多模态，擅长视觉理解与专业任务** |
| `space-bunny` | x0.08 | 1M / 128K | 推理速度极快（匿名模型，来源不明，慎用于生产） |
| `deepseek-v4.1-flash` | x0.11 | 1M / 128K | 原生多模态 |
| `glm-4.6v` | x0.11 | 128K / 32K | 视觉专用 |
| `deepseek-v4-flash` | x0.17 | 1M / 50K | |
| `minimax-m3` | x0.25 | 512K / 64K | 原生多模态 |
| `glm-5.3` / `glm-5.2` | x0.79 | 1M / 64K | 旗舰，识别任务用不上 |

### 首选：`glm-5.3-flash`

1. **定位最对口** —— 目录里唯一明确写「擅长视觉理解」的，正是 D-Bee 的核心场景
2. **输出上限 131K，候选里最高** —— 一餐三四道菜时 JSON 很长，
   「输出被截断 → 解析失败」是最常见的翻车方式，余量值钱
3. GLM 系列中文食物常识扎实，`米饭 200 克 / 鸡蛋 50 克` 这类常识换算不易跑偏
4. 倍率 x0.06 处于低位

### 零成本备选：`step-5-preview`

倍率 x0.00、1M 上下文、阶跃旗舰。唯一顾虑是名字带 `preview`，
稳定性无 SLA 保障，可能随时变更或下架 —— 适合先试水，不建议长期依赖。

### 不建议 `hy3`

虽然同为 x0.00，但输出上限只有 64K，一餐多菜时 JSON 余量偏紧。

### 换模型之外更值得先做的一件事

给所有 JSON 类调用加上：

```ts
response_format: { type: 'json_object' }
```

现在 D-Bee 完全靠提示词约束 + `extractJson()` 事后容错（剥 ```json 围栏、截 `{` 到 `}`）。
该参数能在服务端**强制**合法 JSON，直接降低解析失败率。识别失败重试会再扣一次额度，
省下的是真金白银。（并非所有模型都支持，换完需实测。）

### 改哪里

`src/lib/ai.ts` 的 `pickModel()` —— 现在取目录里 `isDefault` 的那个（即 `auto`），
换成指定 id 白名单即可，同时保留「无可用模型时给出可读报错」的既有行为。

### 换模型的三条纪律

1. **倍率只是展示信息**，不是账单事实。SDK 不暴露用量与账单，真实消耗去控制台核对
2. **延迟不可控**：候选模型几乎全是思考模型（`onlyReasoning: true`），
   而 SDK **不支持传思考强度** —— 可传的采样参数只有 `temperature` / `top_p` /
   `repetition_penalty`（`top_k` 明确无效）。`reasoning` 那几个字段是给设置界面预填用的。
   所以选思考模型就等于接受它的延迟，必须实测「拍照 → 出结果」的等待时间
3. **必须真机回归**：拿**一餐 3-4 道菜**的照片试，这是最容易暴露漏项与 JSON 截断的场景

## 五、已知限制（V1.0.0）

1. **额度计数在客户端发起。** `ai_usage` 表的行受 RLS 保护（只能读写自己的），
   但用户理论上可以绕过 UI 直接调 REST 把自己的 `count` 改成 0。
   要根治必须把 AI 调用收到服务端并做服务端限流——与「自建 Key」是同一个工程。
   当前判断：免费用户作弊的收益极低（每天多几次识别），不值得为它引入一套后端。
2. **日期口径。** 周期按客户端本地日期计算。服务端会做合理性校验：
   若传入日期与服务器 Asia/Shanghai 日期相差超过 1 天，以服务器日期为准，
   防止通过调设备时间重置额度。
3. **无用量告警。** SDK 不暴露用量接口，积分消耗需人工去 WorkBuddy 控制台查看。

## 六、运维速查

```bash
# 查看今日各用户的 AI 用量（云端）
#   通过 db_exec_sql(mode=read)
SELECT owner_id, usage_date, feature, count FROM ai_usage ORDER BY usage_date DESC;

# 调整免费额度：改 src/lib/entitlement.ts 的 FREE_DAILY_AI / FREE_INSIGHT_PER_WEEK
# 调整默认模型：改 src/lib/ai.ts 的 pickModel()

# 相关迁移
db/migrations/0003-atomic-ai-quota.sql   # 原子占用 / 退还（V1.0.0 引入）
```

### 为什么需要 0003 这个迁移

V1.0.0 之前，额度是「先读 count → 再写 count+1」，两次请求之间没有锁。
手机和电脑同时使用、或开多个标签页时，两个请求都会读到同一个旧值再各自写回，
**计数会互相覆盖**，额度限制可被轻松绕过。

现在改为数据库函数 `consume_ai_quota`：在服务端一条语句内完成「判断是否超限 + 自增」，
配合 `ai_usage(owner_id, usage_date, feature)` 唯一约束，并发也不会超发。
配套 `release_ai_quota` 在 AI 调用失败（报错/超时）时退还，避免用户白扣次数。
函数为 `SECURITY INVOKER`，RLS 照常生效，`owner_id` 一律取 `auth.uid()`，无法伪造。
