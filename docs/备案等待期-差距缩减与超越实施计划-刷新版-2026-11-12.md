## 一、一页结论：把「超越」从窗口期里拿出来

| 问题 | 14:22 原版口径 | **22:25 刷新口径** |
| --- | --- | --- |
| 等待期的定位 | 「把产品变成可度量、可信任、可复利」，窗口期就开始攒 C 类结构性资产 | **先把上架前所有前置清干净、把产品打磨到「能正式用、够顺手」**；结构性资产后移 |
| 前期目标 | B 清零 + C 拉开（并行） | **只做跟随**：能上架、能用、和主流产品一样顺手、数据可信 |
| 超越的起点 | P2.4 PCM 在窗口内起步 | **有 30 天真实用户样本之后**，且单独拍板 |
| 最大的差距 | 能力矩阵里的 B 类功能条目 | 🔴 **不是功能清单，是「还没正式上架 + 真实用户≈0」**；功能补得再齐，没有用户就没有「差距缩小」的载体 |
| 怎么算没白等 | 每张交付单带可证伪验收 | **四端可正式访问 + 数据面单一可信 + 首份真实基线在盘 + B 类 L1 缺口闭环** |

> 一句话：**先做一个「功能够用、干净好用、真能装上」的产品，再谈和薄荷不一样。** 用户 21:36 提的「简洁、好操作，规则推广到四端」不是排版偏好，是「跟随」这条主线里最便宜、最可感知的一层 —— 它决定用户第一次打开时觉得像不像个成熟产品。

### 1.1 为什么必须把节奏后移（三条硬理由）

1. **没有任何真实分布可依据**。Web 虽已上线，但双收款开关 false、mini 线上包仍是旧包、Android 未分发、iOS 未正式上架；此时做「方案库 / 提额 / UGC 聚类」都是猜，上架后大概率被真实反馈推翻（原版 §3.1 已论证）。
2. **全局关键路径全在用户本人 / Mac / 管局手里**：mini 体验版重传与重设、云库实例停用、公安备案号回填、Mac 重打包、软著与 App/小程序备案批复。工程侧再快也解不开这几步；计划若把重心放在「工程侧堆功能」，会掩盖真正的瓶颈。
3. **一人团队 6–12 周只能并行 2–3 条线**。原版 P2 有 6 项且互相硬依赖（P2.1→P2.2→P2.4 需 0050 迁移），窗口内做完不现实；不砍就会留下一堆「开了头没验收」的半成品，反而增加发版风险。

| **B 功能** | 全字段编辑 / 回收站 / 月报长图 / 多维身体数据 / 方案库 | 窗口内尽量清零 | **前期只补 L1 高频刚需**（编辑、回收站）；其余推到有真实反馈之后 |

### 3.2 🔴 本次梳理的三条新结论

**① 当前最大差距是「没有真实用户」，不是「功能少」。** 薄荷累计 1 亿+ 用户、16 年积累；我们四端代码就绪度很高，但**没有一端走完正式发布链**。此时把资源投在「方案库 / 个性化 / 超越叙事」上，等于在没有载体的地方优化。→ **前期跟随的第一优先级 = 把 B1~B5 的上架闸门走完。**

**② 「跟随」必须写成可证伪定义，否则又变成感觉。** 满足以下 4 条才算跟上：
- 四端均可被普通用户正式访问/安装（Web ✅ / mini 提审通过 / Android 商店 / iOS 中国区）；
- 数据面单一可信（B1 + B2 闭环，云库不再 200）；
- `tools/growth-report.sql` 产出**首份非草稿**指标快照并写入日志；
- B 类 L1 缺口（全字段编辑、回收站）在四端可用且有护栏。

**③ 产品成熟度是「跟随」里最便宜的一层，应规则化而非单点修。** 用户 21:36 要求「简洁、好操作、推广到其他端」，对应的不是某一处 UI，而是一条跨端规则：**说明性/次要内容默认收起、主操作一屏可达、四端同款手势**。21:50 的折叠交互是这条规则的第一个实例。建议把它写成一张「跨端交互规则清单」，后续每个新页面套用，而不是每次等用户发现。

沿用原版 §4 末尾 + §七范围护栏，并收紧：
