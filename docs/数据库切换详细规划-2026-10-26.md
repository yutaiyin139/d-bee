| **Web**（http://150.158.51.106） | ✅ **自建 PG** | `src/cloudConfig.ts` 取 `window.location.origin`，线上 nginx `/.cloud/` 已反代到 `127.0.0.1:8080` 网关（dbee-gateway → PostgREST → PG） | 已完成，无需动作 |

### 各端对云库的具体依赖明细

三端（Android/iOS/小程序）走的是**同一套云端服务**，依赖面完全一致：

1. **认证**：云库 `auth` schema（`auth.users`，id = sub = owner_id，手机号明文存储）。登录发码/验码/签发 JWT 全在云端，端上无感知。
2. **业务数据读写**：通过 WorkBuddy Cloud SDK 的 `/.cloud/database/rest/...`（PostgREST 协议）直连云库表：`profiles`、`meal_entries`、`water_logs`、`exercise_logs`、`honey_ledger`、`ai_usage`、`leaderboard` 等全部业务表。
3. **AI 教练**：`/.cloud/llm/chat/completions` 由云端代理（deepseek-flash / qwen）。
4. **存储**：云库 `storage` schema（食物照片等，如有使用）。
5. **小程序特有**：微信登录 `wx.login() → code → /v1/login-wechat`（**云端独有端点**，code2session 的 appid/secret 配置在云侧）。

自建侧（Web 端在用的）对应能力：网关已模拟 Supabase Auth 协议（`/.cloud/auth/v1/verification、/verify、/signin、/signup、/token`）+ PostgREST 反代 + LLM 代理 + Apple IAP 校验，**功能面覆盖三端所需，唯独没有 `/v1/login-wechat`**（见风险 R3）。

### 自建网关的实际使用量（近 7 天巡检）

- 网关日志：仅 14 次 auth、6 次 llm 调用；nginx `/.cloud/` 访问 36 条（5 个 IP，多为巡检/测试）。
- 自建库近 3 天写入 ≈ 0（只有 10-24 那 1 个 Web 注册账号的 2 条记录）。
- **真实用户流量 100% 在云库**，云库 10-26 当天仍在持续写入。

**自建库有、云库没有的**：

- `profiles` id=19（owner `1792845025064566575`，newbie 蜜糖 150）——10-24 Web 端注册产生。
- 云库还缺 `apple_*`、`schema_migrations`、`quota_bonus_newbie_retire_log`、`leaderboard_cache` 等自建侧新增表。

### 2.2 已发生的账号分裂事故（必须修复）

手机号 **186\*\*\*\*4728**（iOS 测试用户）：

| 身份 | owner_id | 数据 |
|---|---|---|
| 云库（iOS 端登录） | `2110364580268998656` | 6 餐 / 4 蜜糖 / 4 次 AI —— **真实数据** |
| 自建库（10-24 Web 端登录） | `1792845025064566575` | 0 餐 / 150 newbie 蜜糖 —— 空壳 + 新手奖励 |

同一人两个身份、数据割裂。根因：两套发号体系（云平台发号 `210/211` 开头 vs 自建 `newOwnerId()` 时间戳 `179` 开头），Web 端切自建后同手机号再登录即生成新账号。

### 2.3 合并可行性（已验证 ✅）

- `auth.users.id = profiles.owner_id = JWT sub`，云库手机号明文可取 → **映射键完备**。
- 两库 owner_id 号段天然分离（`210/211` vs `179`）→ **无主键冲突**。
- 自建库各表 ID 序列全部 ≤ 云库 max(id) → **数据行 ID 无冲突**，合并后需校准序列。
- 现成迁移模式：`db/migrations/0036-data-sync-from-cloud.sql`（云库在线 `jsonb_each_text(to_jsonb(t))` 拼幂等 SQL，`ON CONFLICT DO NOTHING` + `OVERRIDING SYSTEM VALUE`），可直接复用作最终同步工具。

## 三、什么时候切？——时机判定

**核心判断：切换不是「要不要」的技术问题，而是「HTTPS 何时就绪」的资质问题。**

原生端 ATS 与小程序合法域名都强制 HTTPS，而 HTTPS 的前提链是（`deploy/setup-https.sh` 三前提 + 备案约束）：

```
备案主体变更完成（个人→企业，🟡 进行中）
   └→ 域名 d-bee.com.cn 过户到公司名下（管局核对 WHOIS 与备案主体一致）
        └→ A 记录解析到 150.158.51.106 并生效
             └→ 80 端口公网可达（certbot HTTP-01 校验；大陆服务器未备案会被拦截）
                  └→ setup-https.sh 一键签发 Let's Encrypt
                       └→ 三端才能指向 https://d-bee.com.cn
```

**时间估计**：域名过户（公章到手后 1–3 天）→ 备案变更（初审 1–2 + 管局 1–20 工作日）。乐观 2 周、保守 4 周。⚠️ 已知坑：若管局不允许直接变更、被迫「注销重备」，**注销后域名停解析直到新备案通过**——所以必须先确认本省支持直接变更再动手（腾讯云备案控制台会直接提示）。

**分端切换时机**：

| 端 | 切换时机 | 说明 |
|---|---|---|
| Web | ✅ 已切 | 无动作 |
| Android | HTTPS 就绪后，随下一次 APK 重打 | 注入 `VITE_NATIVE_ENDPOINT` 即可，构建脚本已预留 |
| iOS | HTTPS 就绪后，与 V1.7.1 Mac 重打合并 | 避免打两次包；若 Mac 重打先行（修流式），则数据面切换留到下一次提审 |
| 小程序 | HTTPS 就绪 + 域名 ICP 备案生效后 | 双前提：wx.request 合法域名必须 HTTPS 且已备案；且注意小程序自身主体变更备案期冻结发版（1–20 工作日）——**切库版本必须排在小程序新备案完成之后** |

**过渡期策略（现在 → HTTPS 就绪）**：三端继续用云库，**不动**。此期间云库是唯一真实数据源，自建库仅 Web 端少量写入。分叉靠切换日的「最终同步」一次性收口（0036 模式重放），不做持续双向同步（复杂度不值得）。

### 阶段 1：账号映射与数据合并（HTTPS 就绪前完成工具与演练）

**1.1 身份映射表**：从云库 `auth.users` 导出 (id, phone)，对自建 `app_users` 按手机号匹配（`ident_hash = HMAC(phone, IDENT_PEPPER)` 验证），生成映射：

- 云库账号 → 自建 `app_users` 补插（**沿用云库 owner_id**，即 `210/211` 号段直接进自建库，保证三端切换后 JWT sub 不变、数据零改写）；
- 无手机号纯微信账号（如有）→ 走 R3 方案处理。

**1.2 186\*\*\*\*4728 分裂账号修复**（映射表的特例，人工确认）：
- 以云库 `2110364580268998656` 为存活身份（有真实数据）；
- 自建壳账号 `1792845025064566575` 的 150 newbie 蜜糖并入存活身份（写 `quota_bonus_newbie_retire_log` 留痕），壳 profile 标记废弃；
- 同手机号在 `app_users` 只留一条（ident_hash 唯一约束天然保证）。

**1.3 数据合并脚本**：复用 0036 模式生成 `0041-data-sync-final.sql`：
- 全部业务表按 owner_id 幂等补齐（`ON CONFLICT DO NOTHING` + `OVERRIDING SYSTEM VALUE`）；
- 冲突策略明确：**按 (id) 主键去重，云库为准**（过渡期云库是唯一活跃写入方；自建侧 Web 写入极少且已含在 profiles id=19 特例中，单独保留）；
- 末尾校准所有序列 `setval(..., max(id)+1)`；
- 附精确回滚段（0036 同款）。

**1.4 演练**：在自建库开一个 scratch schema / 临时库跑一遍合并 + 校验行数对账表（云库每张表 count 与合并后自建库 count 一致），工具固化。

### 阶段 2：切换执行（HTTPS 就绪日，T-0）

顺序严格如下，全程约 1–2 小时：

1. **T-0 最终同步**：重放 1.3 脚本（幂等，增量收口当日新数据）→ 对账行数全绿。
2. **Web 端确认**：已在自建库，无需动作，仅回归验证。
3. **Android**：`VITE_NATIVE_ENDPOINT=https://d-bee.com.cn npm run build` → cap sync → 重打 APK（vc+1）→ 分发。
4. **iOS**：同注入 → Mac 重打 → TestFlight/提审（与 V1.7.1 流式修复合并一次提审）。
5. **小程序**：`mini/src/lib/cloud.ts` endpoint 改 `https://d-bee.com.cn` → 微信后台「request 合法域名」添加 → 提审（**前提：小程序主体新备案已完成**，否则排队等）。
6. **网关侧**：确认 `DBEE_PROD=1`、真短信通道、CORS/Origin 白名单含三端来源；CapacitorHttp 场景下原生请求由 OriginProxy 插件补 Origin 头（阶段 2 已接入，无需改码）。
7. **验证清单**：每端各跑一遍「登录（老账号手机号收码）→ 记一餐 → 喝水打卡 → AI 教练问答 → 蜜糖余额/排行榜」，确认 owner_id 与切换前一致（JWT sub 未变即数据无缝）。

### 阶段 3：观察期与云库释放（T+0 → T+30）

- **观察期 2–4 周**：云库**保持只读可用不注销**（作为回滚兜底）；每日对账脚本比对两库增量（预期：云库增量归零，自建库承接全部写入）。
- **云库释放条件**（全部满足才执行）：
  1. 三端线上版本均已指向自建（iOS 老版本占比 < 5%，ASC 可查）；
  2. 云库连续 14 天零写入；
  3. 自建库备份异地化 + 恢复演练通过；
  4. 最终全量归档云库（pg_dump 存档，含 auth.users 手机号映射表）。
- 释放后：云端应用 `wbapp_w6iIU6TqTyHvJxESPTxBTy` 下线，`CLOUD_HOST` 常量与回退逻辑从代码中移除（cloudConfig.ts / mini cloud.ts 各一处）。

## 五、回滚方案

| 场景 | 回滚动作 | 耗时 |
|---|---|---|
| 切换后自建库故障（T+0 当天） | 三端回退：原生重新注入 `CLOUD_HOST` 打包（Android 可即时分发 APK；iOS 走加急审核或引导用户暂用 Web）；小程序回退旧版本（微信后台可回滚线上版本） | 小时级（Android/Web）～天级（iOS） |
| 合并数据出错 | 自建库恢复 T-0 前夜 03:30 备份 + 重放合并脚本修复版；云库全程未动，随时可切回 | < 1 小时 |
| 观察期内发现慢性问题 | 云库仍在（只读），增量数据从自建库反向导出补回云库（0036 反向），三端回退 | 天级 |

**回滚的底气来自两条纪律**：① 切换日前云库不做任何破坏性操作；② 自建库每日备份 + 异地副本。
