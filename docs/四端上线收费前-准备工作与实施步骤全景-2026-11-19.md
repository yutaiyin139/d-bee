## 一、口径定义（🔴 先读这节，否则会误判进度）

### 1.1 「正式上线」的分端定义

| 端 | 本文「正式上线」的定义 | **不含** |
| --- | --- | --- |
| **Web** | 公开可访问的信息展示 + 定价站 | 不含在线收款（**已定案：暂不收费、恒零收款入口、不办 ICP 经营许可证**）→ 🔴 **「Web 开启收款」这个议题不存在** |
| **mini** | 微信**正式版**切 selfhost 新包（默认不收钱） | 不含体验版 / 内部测试；不含虚拟支付售卖 |
| **Android** | 应用商店上架分发 **+** 可收款 | 不含本地归档包；不含 `internal_test` 点对点 |
| **iOS** | **中国区 App Store** 上架 | 不含 TestFlight 内部测试（另列短路径） |

🔴🔴 **「TestFlight 内部测试 / 体验版 / 开发版」均不等于正式上线。**
🟢 **备案审核期间，开发版 / 体验版 / 真机调试不受限，仅禁正式发布**（依据：工信部《关于开展移动互联网应用程序备案工作的通知》）。

### 1.2 「上线就绪」≠「收费就绪」（核心区分）

| 维度 | 含义 | 卡点性质 |
| --- | --- | --- |
| **上线就绪** | 产物能合法触达用户（分发 / 发布 / 上架） | 主要卡**备案 + 资质 + 用户本人 GUI 动作** |
| **收费就绪** | 用户点「购买」能真实扣款并正确发放权益 | 主要卡**生产迁移 + 网关部署 + env + 平台商品 + 资损铁律** |

🔴 **两者不可互相推论**：产物上线 ≠ 能收款；能收款 ≠ 能上架。**Web 就是极端例子——已上线，但永不收费。**
🔴 **App 备案下证只推进「上线就绪」，对「收费就绪」零贡献**（唯一间接帮助：mini 虚拟支付进件需要备案完成，见 §3.2-B ④）。

## 二、跨端共通前置（四端收费共享的地基）

### 2.1 双开关（构建期字面量，🔴 不是运行时探测）

| 开关 | 驱动面 | 当前值 | 护栏 |
| --- | --- | --- | --- |
| `D_BEE_XPAY_ENABLED` | mini 付费墙 + mini `legal.ts` 法务口径 + Web 引导文案 + Web 法务 §六 | **false**（`.env.example:74` 空值） | 护栏 6 / `xpay-consistency` 7 项 |
| `D_BEE_APPPAY_ENABLED` | **Android 付费墙支付按钮 + Web「去 App 购买」引导**（🔴 一个变量同决定两端） | **false**（`.env.example:75` 空值；`vite.config.ts:74` 默认 `'false'`，非 `true`/`false` 直接抛错） | 护栏 20-B |

🔴 **为什么开关必须是构建期决定**（真源 `mini/src/lib/xpayEnabled.ts`）：售卖能力一开，**付费墙展示价格**与 **`legal.ts` 法务口径**必须**同批变**（此前写的是「免费提供、不销售任何商品或服务、不涉及在线支付」）。微信审核会核「页面展示内容与隐私政策/用户协议是否一致」，两者不同步 = **可判驳回项**。若用运行时探测决定文案，法务文本会**随网络结果漂移**：同一个包在服务端 503 时显示「免费提供」、200 时显示「收费售卖」，而用户已同意过的那份协议是**构建时确定的字符串**。
🟢 **推论**：开关是构建期字面量 → **产物里可直接 grep 到实际开关值**（验收清单第 3 项）。
🔴🔴 **④⑤⑥ 任一未就绪就开开关**：用户点购买撞到 `-15008/-15010/-15014`，**且法务口径已改成收费** = **审核驳回 + 用户投诉 + 《广告法》第 4 条虚假宣传三重风险**。**先配平台，再开开关。**
