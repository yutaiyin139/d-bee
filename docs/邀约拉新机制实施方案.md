# 邀约拉新机制 · 蜜糖积分体系设计定稿（v3）

> v3 融合了自律茄子式「打卡赚积分 + 社群 + 成就徽章」三大能力，
> 与 v2 的「邀请拉新 + 消耗型积分」合并为**一套完整激励闭环**。
> 严格对标竞品（自律茄子 + Cal AI）+ 国内合规红线。

---

## 〇、设计总纲（一句话）

**三条积分来源（打卡 / 邀请 / 成就）汇聚成「蜜糖积分」，通过社群传播放大声量，最后在平台内单向兑换消耗——无现金、不可提现、不可转让。**

```
打卡赚积分 ┐
邀请拉新   ├──→ 蜜糖积分 ──→ 兑换消耗（Pro / AI / 模板）
成就徽章   ┘        ↑
                    └── 社群（纯传播，不产积分）
```

---

## 一、蜜糖积分（核心资产，v2 不变）

| 项 | 定稿 |
|---|---|
| 名称 | 蜜糖积分（UI 简称「积分」） |
| 属性 | 平台内消耗型积分，**不可提现 / 不可转让 / 不可兑换现金** |
| 记账 | 流水式（正负记账），余额 = SUM(有效入账 − 消耗 − 过期) |
| 有效期 | 每笔入账 1 年，过期自动失效；兑换优先扣最早到期 |
| 出口 | 单向：Pro 时长 / AI 额度 / 高级模板 |

> 合规红线（不可动摇）：①不叫「币」；②绝不提现/变现；③禁用「返现/躺赚/拉人头赚钱」话术；④明确写「无现金价值、不可转让」。

## 二、积分来源一：打卡赚积分（自律茄子核心，新增）

对标自律茄子「完成目标/打卡 → 虚拟奖励」，把「打卡」变成日常积分来源。

### 2.1 每日打卡

| 行为 | 积分 | 说明 |
|---|---|---|
| 每日记一餐（≥1 条饮食记录） | +5 | 与现有 `streak.ts` 打卡口径一致（某天 ≥1 条饮食即打卡） |
| 每日饮水达标（≥ 目标量） | +2 | 复用 `waterTargetMl` |
| 每日运动 ≥ 1 次 | +2 | 复用 `exercise_logs` |

> 每日积分**封顶 9 分**（5+2+2），防止刷分。**每日 0 点按自然日独立结算，不累计结转。**

### 2.2 连续打卡里程碑（与现有 streak 里程碑联动）

现有 `MILESTONES = [3, 7, 14, 21, 30, 60, 100]` 已有「达成 N 天里程碑」庆祝提示，这里**把里程碑升级为「积分 + 徽章」双奖励**：

| 里程碑 | 积分 | 徽章 |
|---|---|---|
| 3 天 | +15 | 初露锋芒 |
| 7 天 | +40 | 一周自律 |
| 14 天 | +80 | 半月坚持 |
| 21 天 | +120 | 习惯养成 |
| 30 天 | +200 | 月度自律 |
| 60 天 | +400 | 两月高手 |
| 100 天 | +800 | 百日蜂王 |

> 去重：复用 `streak.ts` 的 `streak7Date` 思路，每个里程碑「达成日期」作 grant_key，断签重来不会重复领。

### 2.3 打卡与邀请的「达标」共用同一判定

邀约奖励里的「7 日内完成 ≥5 天打卡」与这里「连续打卡」是两套口径，**必须区分清楚**：

- **邀约达标**：受邀后 **7 个自然日内**、**累计** ≥5 天有饮食记录（不要求连续）。
- **连续打卡里程碑**：**连续** N 天（`streak.ts` 的 current）。

两者独立，各自有独立 grant_key，不冲突。

## 四、积分来源三：成就徽章（自律茄子成就系统，新增）

徽章是「里程碑的可视化 + 社交货币」，**徽章本身不直接发积分**（避免「集徽章换钱」的踩线感），只作为**荣誉展示 + 分享素材**；只有少数「里程碑徽章」与打卡积分联动（见 2.2）。

### 4.1 徽章体系（首批 12 枚，克制不泛滥）

| 类别 | 徽章 | 解锁条件 |
|---|---|---|
| 打卡 | 初露锋芒 | 连续 3 天 |
| 打卡 | 一周自律 | 连续 7 天 |
| 打卡 | 习惯养成 | 连续 21 天 |
| 打卡 | 百日蜂王 | 连续 100 天 |
| 记录 | 火眼金睛 | 累计拍照识别 50 次 |
| 记录 | 扫条码达人 | 累计扫码 30 次 |
| 记录 | 食谱创作者 | 创建 3 个自定义食谱 |
| 健康 | 饮水达人 | 单日饮水达标 10 天 |
| 健康 | 运动新星 | 累计运动 20 次 |
| 健康 | 减重 3kg | 体重较起始 −3kg |
| 社群 | 伯乐 | 成功邀请 3 位有效好友 |
| 社群 | 月度蜂主 | 当月有效邀请 TOP 达标 |

### 4.2 徽章展示

- 个人页「成就墙」：已解锁彩色、未解锁灰色剪影（含解锁条件提示，驱动用户行动）。
- 打卡里程碑命中时，Dashboard 弹「🎉 达成 + 徽章点亮」提示（复用现有 `streak-hit`）。

## 五、社群（传播载体，自律茄子「社区互动」，新增）

**定位：社群是「传播放大器」，不产生积分**（守住「社群奖励=变相拉人头」的合规边界）。

### 5.1 站内轻社交（纯产品内，不依赖微信）

| 能力 | 说明 |
|---|---|
| 分享打卡成果 | 一键生成「今日打卡卡片」（分数/等级/连续天数/徽章），分享到微信/小红书 |
| 分享徽章 | 解锁徽章时生成「徽章卡片」可分享 |
| 分享月度榜单 | 邀请榜/打卡榜的「我的排名」卡片 |

### 5.2 榜单（自律茄子「挑战/活动赛制」克制版）

| 榜单 | 维度 | 周期 |
|---|---|---|
| 自律榜 | 连续打卡天数 | 实时 |
| 邀请榜（蜂主榜） | 有效邀请数 | 月度 |
| 减重榜 | 减重公斤数 | 月度 |

> 榜单只展示 **Top 50 + 我的排名**，不展示真实姓名（昵称脱敏），避免攀比焦虑与隐私问题。

### 5.3 微信社群（外部，需营业执照）

- 官方微信群/企微群：二维码入口，做「社群专属身份」（月度蜂主等）。
- **依赖营业执照，V1 只留入口占位**，不实际运营。

## 六、数据模型（v3 增补）

在 v2 基础上，新增徽章表：

```sql
-- 成就徽章（一人多枚，去重）
CREATE TABLE public.badges (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id   text        NOT NULL DEFAULT auth.uid(),
  badge_key  text        NOT NULL,          -- 徽章唯一 key（如 streak_7）
  unlocked_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (owner_id, badge_key)              -- 防重复解锁
);
```

- 徽章**不落积分**（除 2.2 里程碑联动那批，走 `honey_ledger`）。
- 打卡/邀请/徽章三条来源的积分**统一走 `honey_ledger`**，`reason` 扩展：
  `checkin_daily / checkin_water / checkin_exercise / streak_milestone / invitee_register / invitee_checkin / inviter_register / inviter_checkin / redeem / expire / refund`。

## 十一、实施前坑排查（2026-10-16 最终复查结论）

对现有代码链路逐项排查后，确认**无阻塞性坑**，但有以下 6 个「必须按既定方式实现」的要点，实施时严格遵守：

### 坑 1：邀请码绑定的「按码查邀请人」必须用安全函数绕过 RLS
- `invite_links` 有 RLS（`owner_id = auth.uid()`），新用户**看不到别人的邀请码行**，不能直接 `select * where code = X`。
- **正确做法**：`get_inviter_by_code(p_code)` 用 `SECURITY DEFINER`（项目首次引入，需验证云端支持）+ `SET search_path = public`，只返回匹配码的 `owner_id`，不返回其他字段。
- ⚠️ 若云端 SDK 不支持 `SECURITY DEFINER`，则降级方案：把 `invite_links` 的 `code` 列做成「可公开只读」的独立视图/策略（仅 code → owner_id 映射，不含敏感字段）。**阶段 1 先验证这一点，是唯一的技术未知点。**

### 坑 2：绑定时机 = `verifyOtp` 成功后（已有 session，无时序问题）
- 注册流程是 `sendOtp` → `verifyOtp`（返回 `completed`，含 `isExistingUser`）。
- **绑定时机**：`verifyOtp` 成功、session 建立后，若本次是**新用户**（`isExistingUser === false`），前端调用 `bindInvite(code)`。
- 老用户登录**不触发**绑定（避免重复绑定/覆盖）。
- 坑点已排查：`auth.uid()` 在 session 建立后可用（现有 `grant_photo_bonus` 已证明）。

### 坑 3：与现有 streak7 奖励不冲突（两套独立体系）
- 现有 `quota_bonus`（source=`streak7`，奖励 2 次 AI 拍照额度）与新的「连续打卡里程碑发蜜糖积分」**是两套东西**：
  - `streak7` → 发的是 **AI 拍照次数**（进 `quota_bonus`）
  - 里程碑 → 发的是 **蜜糖积分**（进 `honey_ledger`）
- 两者 grant_key 不同（前者是「连续段第 7 天日期」，后者是「里程碑达成日期」），**不会互相误触发**。实施时保持各自独立触发点。

### 坑 4：每日打卡积分的「结算时机」要防重复 + 防漏
- 每日积分（记餐+5/饮水+2/运动+2）不能「每次记一笔就 +5」（一天记 3 餐会 +15）。
- **正确做法**：按「当日是否达成」发一次，用 `honey_ledger` 的 `UNIQUE(owner_id, reason, ref_id)` 防重复，`ref_id` = 当日日期（如 `checkin_daily|2026-10-16`）。
- 触发点：Dashboard `load()` 后、已有当日记录时结算；或保存记录后结算。**优先走 RPC 函数 `grant_honey` 原子发放（ON CONFLICT DO NOTHING）**，与 `grant_photo_bonus` 同范式。

### 坑 5：邀约「7 日内 ≥5 天打卡」是累计口径，不是连续
- 与 `streak.ts` 的「连续」不同。需要一个独立函数 `checkInviteCheckin(invitedDate, loggedDates)`：统计 `invitedDate` 之后 7 个自然日内，有饮食记录的天数 ≥5。
- 数据来源：`listMealsBetween(invitedDate, invitedDate+6)` 的 distinct log_date 计数。
- 触发点：受邀人每次打卡后检查；达标发双向积分，`UNIQUE(owner_id, reason, ref_id)` 防重复（ref_id = 邀请关系 id）。

### 坑 6：兑换「Pro 时长顺延」要处理「已是终身会员」边界
- 终身会员（`plan='lifetime'`）不能兑换 Pro 时长（无意义），兑换商城应对 lifetime 用户**隐藏或置灰 Pro 兑换项**。
- `entitlements.pro_until` 顺延：已是 pro 则 `pro_until + 天数`；是 free 则 `now() + 天数`；是 lifetime 则拒绝。
- 复用现有 `saveEntitlement`，但需在兑换函数里先读当前 entitlement 判断。

### 结论
以上 6 点均有明确实现路径，**唯一技术未知点是 `SECURITY DEFINER` 是否被云端 SDK 支持**（坑 1），将在阶段 1 第一时间验证；若不支持，走降级方案（code 公开只读映射），不影响整体进度。

**可以开始实施。**
