### 1.2 云库实例：还活着，别被 403 骗了

| 探测 | 结果 | 判读 |
| --- | --- | --- |
| `GET /` | **403**「链接不完整」 | 只是**平台分享链接失效**，不是实例释放 |
| `GET /.cloud/database/rest/v1/profiles`（带 `x-wb-webapp-access-key`） | **401 `DATABASE_42501 permission denied for table profiles`** | 🔴 **PostgREST 真实响应 → 数据库在线、可写** |
| 同上（无 key） | 401 `invalid_client ... credential is invalid or revoked` | 网关层凭据校验，不能用来判断数据库死活 |
| `/.cloud/healthz` | 404 `invalid_request` | 该云环境无此端点 |
| `https://d-bee.cn/.cloud/healthz` | **200** `{"ok":true,"db":{"ok":true,"database":"dbee"}}` | 自建库健康 |

⚠️ 纠偏：早前用 Supabase 风格 `apikey`/`Authorization` header 得到的 `invalid_client` 是**探测头用错**，
不是「凭据已撤销」。用 SDK 真实 header `x-wb-webapp-access-key` 才能看到数据库层响应。

iOS 残留的精确性质（已追到调用链，避免夸大）：

### 1.4 依赖面：停库不会误伤全站

四端与云库共用同一把 `publishableKey` / `resourceId`，但自建网关只在
`server/lib/auth.mjs:157` 做**本地字符串比对**；`deploy/gateway/gateway.env.template` 注释明写
「自托管下只是应用标识，不承担安全职责，留空则跳过校验」→ 网关**不回连云库验签**。
自建侧实测 `healthz` 200、`login-wechat` 路由在位、`dbproxy` 鉴权在位。

⚠️ **另一个平台依赖，与云库实例不是一回事**：Web 扫码登录仍走
`https://www.workbuddy.cn/v2/as/genie-baas/oauth`（`src/cloudConfig.ts:164`、`AuthScreen.tsx:280`
`signInWithOAuth`）。**停云库实例不会断它**；若「完全抛开」的目标是连 WorkBuddy 平台都不依赖，
那是重写 Web 登录链路的独立产品决策，本日不擅自改。mini 用 `signInWithWechat`，已不依赖该 relay。
