### 一、🟢 查证推翻一个既有疑虑：公钥模式合规，项目实现零改造

- 旧文档 `P1-D在线支付实装前置清单-2026-11-03.md:84` 曾建议「推荐**证书模式**而非公钥模式」，而项目实现是**公钥模式**（`apppay.mjs:203-206` `verifyAlipayNotifySignature` 直接用 `alipayPublicKey` 验签，无证书链、无 `app_cert_sn`）→ 本轮怀疑是缺口。
- 查官方《接口加签方式说明》（`docs.open.alipay.com/58/103541`）原文：**「除资金支出类场景外，都可以使用密钥加签方式；红包（原现金红包）、转账到支付宝账户必须使用证书加签方式，其他场景可以选择使用密钥或证书。」**
- **结论：`alipay.trade.app.pay` 属收单类、非资金支出类 → 公钥模式完全合规，无需重写验签。** 🟢 B7 工程量从「可能重写」降为「只填 env」。
- 🔴 **决策痕已记入文档**：一个 APPID 只能配一种加签方式 → 将来若做发红包/转账到账户，须整体切证书模式 + 重配全量密钥 + 重新部署网关（生产变更）。**现在选公钥模式 = 明确暂不做资金支出类玩法。**

### 二、🔴 本节最高危发现：支付宝「应用签名」不能照抄 baseline 的 signerMd5

- 官方《应用平台信息如何配置(Android 版)》（`opendocs.alipay.com/support/01rgk5`）：应用签名**必须用支付宝官方 `GenSignature.apk` 在真机上获取**（从 Android 分享 SDK/DEMO 包内取工具 → 装手机 → **须先把目标 APK 装上**，否则报「应用签名报错请检查包名是否正确」→ 输入包名 → 获取并复制）。
- 🔴 **不得直接把 `apk-distribution.baseline.json:16` 的 `signerMd5=0abe7fc5005987ed9b6eae9a45fb9dc9` 填进去**：那是 `apksigner verify --print-certs` 口径；微信开放平台认这种 32 位小写无冒号 MD5，但**支付宝 GenSignature 的算法/格式口径不保证一致**。若不一致 → 线上拉起签名校验失败，且**只在真机复现，本地测不出**。

### 三、🔴 支付宝客户端 AppID 只是「门禁」，与微信侧机理本质不同

- **微信侧**：客户端 AppID 真交给原生 SDK（`wechatPay.ts:136` `plugin.initialize({ appId })`）→ 填错在 SDK 初始化/拉起阶段就失败，**报错早、看得见**。
- **支付宝侧**：客户端**不签名、不算价、不传 AppID 给支付宝** → `alipay.ts:129` `plugin.pay({ orderStr: prepay.orderStr })`，orderStr 完全由**服务端**构造并本地 RSA2 签名（`apppay.mjs:353-370`，`appId: cfg.alipayAppId`）。客户端 `VITE_ALIPAY_APPID` 唯一作用是 `alipay.ts:94,110` 的**非空门禁**。
- **后果不对称**：服务端 `ALIPAY_APP_ID` 填错 = **资损级**（下单参数错/回调验签失败，用户付钱拿不到权益）；客户端填**任意非空垃圾值** = 门禁被骗过 → **假按钮，且比微信侧更隐蔽**（微信假按钮在 SDK 阶段就挂）。
