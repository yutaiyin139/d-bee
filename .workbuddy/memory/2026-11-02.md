**🔴 实测推翻我自己上一轮写进手册的判据（重要教训）**：
- 手册写「`dist/assets/index-*.js` 必须只有 1 个，>1 = 构建残留，rm -rf dist 重跑」——**错的**。
  干净构建本就产出 2 个：`index-OZL5R3d6.js`（入口，被 index.html 引用）+ `index-aKGgE7sY.js`
  （被入口**动态 import** 的 chunk）。**铁证**：11-01 被当成「残留」的那个 hash 与今天干净构建
  完全相同（hash 由内容决定 → 它一直是合法 chunk）；且 web 与 native 两次构建该 hash 也相同。
- 正确判据：先 `ENTRY=$(grep -oE 'assets/index-[A-Za-z0-9_-]+\.js' dist/index.html | head -1)`，
  **只查入口**。此判据天然免疫残留（残留文件不会被 index.html 引用）。真要找残留看 mtime 是否与入口同批。
- 另一处错：`grep -oE "function describe\(...\)" dist/assets/index-*.js` 永远空输出 ——
  `describe()` 是 `index.html` 里的**内联脚本**，assets 全目录零命中。
- 教训：**判据必须在真产物上实跑，且要能区分「合法产物」与「异常产物」**。
  上一轮我看到 2 个 index-*.js 就直接归因「构建残留」，没验证 hash/mtime/引用关系 →
  写出一个会误判合法构建的自检命令，比没有自检更危险（会让人 rm -rf 反复重打、仍「不通过」）。
