## pgAdmin「表全空」诊断（16:52，已确诊）
用户反馈：pgAdmin 4 连自建库查表全是空的。诊断脚本 deploy/diag-pgadmin-empty.sh + diag-auth-uid.sh（已入库）实测结论：
- **数据在**：superuser 视角 profiles=18、meal_entries=97、honey_ledger=29、app_users=3、schema_migrations=42（迁移已推进到 42，比昨天记录的 40 又多了 2）。
- **根因 = RLS**：21/23 张表开了 row level security，策略全是 `owner_id = auth.uid()`；`auth.uid()` 依次读 GUC `app.user_id` → `request.jwt.claim.sub` → `request.jwt.claims->>'sub'`，pgAdmin 裸会话三者皆无 → uid=NULL → 所有行被过滤。实测复现：`SET ROLE dbee_app; SELECT count(*) FROM profiles` = **0**（superuser=18）；设 `request.jwt.claims={"sub":"2109837240191418368"}` 后同角色可见 1 行——机制验证闭环。
- **例外**：app_users 有针对 dbee_app 的 force 策略 `gateway_ident_access(true)`，所以 pgAdmin 里 app_users 应能看到 3 行（用户说"全空"可能没注意或没刷）。
- **为什么 App 正常**：PostgREST 每个请求都注入 JWT claims GUC，RLS 按登录用户放行；pgAdmin 是"无 JWT 上下文的裸连接"，天然被全滤。
- **pg_hba 现状**：远程只放行 dbee_app@办公网段（114.254.3.0/24、114.246.239.129/32）连 dbee 库；postgres 仅 127.0.0.1——所以用户只能用 dbee_app 连，必然撞 RLS。
- **给用户的解法**：① 临时——pgAdmin Query Tool 先跑 `SELECT set_config('app.user_id','<owner_id>',false);`（session 级）再查表；② 长期——建 `dbee_admin` 角色（LOGIN+BYPASSRLS+只读授权）+ pg_hba 加办公网段行，等用户拍板再动。
- **顺带复核**：5432 仍 `listen_addresses='*'` 0.0.0.0 监听（阶段0 待办 0.1 仍有效）。
- SSH 教训：.env 的 DBEE_USER/DBEE_PWD 是**数据库角色**凭据（dbee_app），SSH 必须用 IP/USER/PWD（ubuntu）——第一次跑错被 AuthenticationException 打回。
