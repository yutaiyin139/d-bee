   `GRANT SELECT`——但**GRANT 是追加语义，不撤销已有权限**。写权限是 0002 建库时给的
   （`0002:226-229` 对 7 张表 GRANT SELECT,INSERT,UPDATE,DELETE），0015 的 REVOKE 从未在 dbee 库执行，
   0030 镜像只再 GRANT 一次 SELECT、**不会 REVOKE 掉 0002 留下的写权限**。
   **强证据**：0002 授权的那 7 张表里，被 0015 要求收权的正是 entitlements+ai_usage，**两张全失效**；
   0015 要收的另 4 张（honey_ledger/badges/quota_bonus/invite_links）**不在 0002 清单里，全部封住**。
   「在 0002 清单内→失效，清单外→生效」完全对应根因 1。
   💡 **与 0033 是同一个坑**（dbee_app 的 DELETE 也是 GRANT 追加语义留下的，0033 修法正是先 REVOKE ALL 再精确 GRANT）
   ——同一教训在两处各踩一次。
2. **生成器完全不抓 `pg_constraint`**：只读 `pg_indexes` + `information_schema.columns`，UNIQUE 靠**硬编码字典**。
   CHECK/外键/触发器无任何抓取逻辑 → 0016 丢失是**必然**。`0030-schema.sql` 里 16 处 CHECK 字样
   **全部是 `CREATE POLICY … WITH CHECK` 子句**，零个数据完整性约束。
3. **覆盖式迁移无法用存在性判版本**（见方法②）。
4. **没有迁移追踪表**（`to_regclass('public.schema_migrations')` → NULL），状态全靠文件头注释 + README 表格，两者都严重滞后。
   → 这就是「为什么没人发现」：0016/0026/0027 都在云库执行过（云库是当时真相源），10-20 切自托管用镜像重建，
   **镜像丢了三样东西，重建后无任何机制比对「迁移清单 vs 库实际状态」**。

### 实施计划（详见文档 §五、§六）

**执行顺序关键：先修工具再修数据**（P0-3/P0-4 → P0-1 → P0-2），否则中途任何一次镜像重建都会把 0034 成果冲掉。
- **P0-1** 新建 `0034-security-and-integrity.sql` 一次补齐五项（a 收 2 表写权限 / b 补 10 个 CHECK /
  c 补 grant_honey newbie(150) / d 作废存量 newbie bonus / e 补 bind_invite daily_limit）。
  c、e 都是覆盖式 → 必须连 0013、0009/0017 的**全部**白名单一起写，否则覆盖丢分支。
- **P0-2 前端必须配套改**（否则 REVOKE 会打断功能）：`api.ts:402` `consumeAiQuota` 有个**静默 `catch{}` 降级**
  → `bumpUsage`（:347）直写 ai_usage，REVOKE 后必抛错。**判断：这个降级路径本身就是漏洞**
  （绕过服务端原子限制，注释自己承认「并发下会互相覆盖」，正是 0015 要封的东西）→
  改为 **fail-closed**（RPC 不可用返回 `{allowed:false}` 拒绝服务，而非 fail-open 静默直写）。
  理由：AI 有真实成本，fail-open = 「函数一出问题就免费无限用」；且该 RPC 与主链路同生共死。
  entitlements 侧无此问题（前端只有 `getEntitlement()` 的 select，无写调用，REVOKE 后零影响）。
- **P0-3** 修生成器：①GRANT 前无条件 `REVOKE ALL ON ALL TABLES … FROM authenticated` 再精确 GRANT
  （照抄 0033 范式）②实抓 pg_constraint 的 CHECK/外键 ③UNIQUE 字典改实抓。
- **P0-4** 建 `schema_migrations`（version/name/applied_at/checksum）+ `tools/migration-audit.sh`
  把三类探针固化为可重复脚本，纳入 `db-healthcheck.sh` 部署后必跑。**价值最高：P0-1 修这次的洞，P0-4 修「下次还会再发生」。**
- **P1**（Android 企业注册完成 → 支付线解锁）：P1-1 Apple 验签放网关（**必须在 P0-1 之后**，
  否则「网关能写 entitlements」与「用户也能写」混在一起无法区分合法发放与越权；REVOKE 后写 entitlements
  的唯一通道只剩服务端函数，可审计）；P1-2 Android 支付（`payment_orders.provider` 是 text **无 CHECK 约束**，
  加 'google' 无需改表；建议先只做 Google Play + Apple，国内安卓渠道按上架优先级再排）；
  P1-3 **实测新发现**：`payment_products` 有 3 行商品数据但**对 authenticated 无任何权限**
  （不在 TABLE_GRANTS 字典）——前端目前不直读（定价走 PRODUCT_IDS 常量 + 服务端查价）故暂不报错，
  但「金额由服务端查价」需确认读取路径通，或显式 GRANT SELECT（只读无风险）。
- **P2**（企业注册解锁）：P2-1 华为 Health Kit 硬门槛是**上架华为应用市场**（不是企业资质，资质已完成）。
  ⚠️ **实测发现设计缺口**：连接状态用 `profiles.health_connected` 单布尔，方案写「华为复用同一字段 ✅零改动」，
  但**多平台并存会互相覆盖**（iPhone 连了 Apple、华为机连了华为，两端抢同一布尔位，换设备登录看到错误的「已连接」）
  → 建议 `0035-health-provider.sql` 加 `profiles.health_provider text`（apple/huawei/xiaomi/null）或改子表，
  **华为端开工前定最省**；`src/lib/health/index.ts:76/115` 需同步适配。
- **P3** 结构加固：①PG 收回 listen_addresses 到回环 + 安全组关 5432（实测监听 0.0.0.0，仅 pg_hba 白名单兜底、ufw inactive，
  自托管已闭环不再需远程直连）②`db/README.md` 表格补全到 0034（现只到 0003 已完全失效）
  ③**`0020` 有两个同号文件**（ai-consent / badge-weight-lost-fix，本次确认都已生效），但同号会让
  「按序号应用」与 schema_migrations 主键出问题 → 重命名 0020b 或追踪表用 name 做主键
  ④遗留债 `llm.mjs:44` 硬编码 `supportsImages:true`（DeepSeek 无 vision，配上 LLM_API_KEY 后拍照识别会坏）。
