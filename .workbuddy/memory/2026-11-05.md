## 「小程序是 10.29 版本」排查 → 不是构建问题，是写死的日期字符串

用户报「开发者工具编译后还是 10.29 版本」。**产物完全正常**：`mini/dist` 52 个文件全是当天 17:35，
无一残留；11-03~04 各提交的特征文案（`永久无广告`/`积分兑`/`备案号`/`较起始`）解码后全部命中。
真凶是 `mini/src/content/legal.ts` 写死 `const UPDATED = '2026 年 10 月 29 日'`，
由 `legal.tsx:47` 渲染成「最后更新：…」。**代码是新的，只有这个日期字符串是旧的。**

🔴 **两条排查方法论教训（都栽过一次）**：
1. **grep 中文必假阴性** —— webpack/Taro 把中文字符串转义成 `\uXXXX`，直接 grep 中文得 0 命中，
   据此误判「产物是旧的」必错。必须先 `t.encode('utf-8').decode('unicode_escape', errors='ignore')` 再搜。
2. **日期正则要容空格** —— 源码写的是 `'2026 年 10 月 29 日'`（数字与年月日之间**有空格**），
   用 `2026年10月29日` 搜 → 漏掉最关键证据，一度得出「dist 里根本没有 10-29」的错误结论。
   → 搜中文/日期字面量一律用宽松正则（`\s*`），别照抄肉眼看到的形态。

📌 **微信开发者工具的「编译」不跑 Taro 构建**，只重载 `dist/` 现有产物。
   改完源码必须先 `cd mini && npm run build:weapp`（或 `dev:weapp` watch），再回工具编译。

### 关键设计决策（都在代码里留了注释）
- **hint 文案刻意不写「登录即表示同意」**：那是默示同意声明，PIPL 下对个人信息处理有争议，
  也与本项目「文案如实化」纪律相悖（P0-C 刚清过一批虚假承诺）。只做中性告知。

  → 文案**不写方位词**，用两端逐字一致且抗 UI 调整的「请通过『联系我们』」。

  那句话恰好在没有页脚的法律页里被读到 → 指路会二次失实。（我一开始写成「页脚『联系我们』」，
