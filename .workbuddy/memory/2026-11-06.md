## 🔴🔴 22:00 · 生产登录故障：根因 = certbot 的 301 把 POST 降级成 GET

### access.log 里有用户手机的完整请求链 = 铁证
```
223.104.3.167 [06/Nov/2026:21:34:17] "GET  /.cloud/auth/v1/token"         404   referer=http://d-bee.cn/
223.104.3.167 [06/Nov/2026:21:34:24] "POST /.cloud/auth/v1/verification"  301   ← 关键
223.104.3.167 [06/Nov/2026:21:34:24] "OPTIONS /.cloud/auth/v1/verification" 204

```
**referer 是 `http://d-bee.cn/`（HTTP，无 s）** → 页面本身从 http 加载。

### 根因链（逐环实证，无推断）
1. `nginx -T` 查到 80 端口块里有 **certbot `--nginx` installer 自动注入**的两条：
   ```nginx
   if ($host = www.d-bee.cn) { return 301 https://$host$request_uri; } # managed by Certbot
   if ($host = d-bee.cn)     { return 301 https://$host$request_uri; } # managed by Certbot
   ```
   （`/etc/nginx/sites-available/d-bee`，mtime **11-06 14:51** = B2 HTTPS 那次）
2. **浏览器对 301 的历史兼容行为 = POST→GET 降级**（301/302 规范上允许，307/308 才强制保留方法）。
3. 网关 `app.mjs:64,79` 只注册 `POST /.cloud/auth/v1/verification` → 收到 GET → **404「未知端点」**。

### 🔴 决定性复现（我一开始用错了 curl 参数，差点误判「curl 复现不了」）
```bash
# ❌ -X POST 会强制重定向后仍用 POST → 得 401，看起来「没问题」
curl -L -X POST http://d-bee.cn/.cloud/auth/v1/verification   # → 401 invalid access key
# ✅ --data 不加 -X，让 curl 像浏览器一样按 301 语义降级 → 精准复现用户故障
curl -L --data '{"phone":"…"}' http://d-bee.cn/.cloud/auth/v1/verification
#    → final_code=404  redirects=1  body={"message":"未知端点 /.cloud/auth/v1/verification"}
# 对照：https 直连同端点 → 401 invalid access key（路由存在、POST 正常，只是缺 access key = 正常鉴权拦截）
```
📌 **纪律**：用 curl 验「重定向是否降级方法」时**绝不能用 `-X POST`**（它会覆盖 curl 的重定向方法推断），
   必须用 `--data`/`-d`。这次 `-X` 让第一次验证给出「final_code=401」的**假阴性**，我差点据此判「无法复现」。
   → 与本轮前面 4 次同型：**工具用法本身错误会制造假证据**，比没有证据更危险。

### 为什么「中午能登录」

那时 nginx **还没有** 80→443 的 301（配置 mtime = **14:51**）→ POST 直达网关。

（`resolveEndpoint()` 取 `window.location.origin`，页面不刷新就不会变。）

### 修复（两层互补，都需批准后才执行）
| 层 | 改法 | 覆盖范围 | 生效条件 |
|---|---|---|---|

### nginx 301→308 已生效 + 修掉脚本两个真实缺陷（`c8ca776`）

1. **reload 后立即验证会撞上旧 worker**。`systemctl reload` 在「新 worker 已起」时就返回，
   而 nginx reload 是**优雅退出** —— 旧 worker 继续处理已接手的连接，且**持有旧配置（301）**。

   三条独立证据确认配置正确：①服务器内部 `curl -v` = `POST→308→POST→401`（方法保留）
   ②access.log `150.158.51.106` 两条 `POST 308` + `POST 401` ③`127.0.0.1:8080` 直连网关 `POST→401`。
   → 修法：reload 后 `sleep 8`；5a 再加 3 次重试（连续 3 次 404 才判真失败）。
2. **不可重入**：已应用后重跑报 `命中 0 行 ≠ 2，配置形态与预期不符` —— 误导性消息，
   真实含义是「早就改好了」。→ 加 `ALREADY` 分支（301=0 且 308=2 → 跳过改动直接验证）。
   **这不是美观问题**：certbot renew 若把 301 注回来，本脚本必须能原样重跑，
