# D-Bee 数据备份

## 一句话

数据托管在 **WorkBuddy 云服务的 PostgreSQL** 上（不在腾讯云服务器），因此备份不经服务器，
而是走平台的**只读 MCP 通道**，每天把 7 张业务表全量导出为一份 JSON 快照。

## 为什么这么做

| 方案 | 结论 |
| --- | --- |
| 服务器上 `pg_dump` + cron | ❌ 服务器上没有数据库；且云端数据库未开公网直连 |
| 本地脚本直连云端 REST | ❌ `anon` 表权限已在 0001 补丁中撤销，本地脚本无凭据可用（这是刻意的） |
| **平台只读通道 + 全量 JSON 快照** | ✅ 无需额外凭据，符合最小权限，数据量小（每用户约 4200 行/年）成本可忽略 |

## 产物

```
db/backups/
  2026-10-13.json          # 每日一份，含 tables（7 表全量） + row_counts
  FAILED-2026-10-20.md     # 仅在当天备份失败时出现（不会写空备份覆盖）
```

备份文件结构：

```json
{
  "generated_at": "...",
  "source": "workbuddy-cloud-postgres",
  "schema_ref": "db/schema.sql",
  "tables": { "profiles": [...], "meal_entries": [...], "...": [] },
  "row_counts": { "profiles": 3, "meal_entries": 0, "...": 0 }
}
```

表结构定义见 `db/schema.sql`（与线上一致的反向导出基线）。

## 调度

- WorkBuddy 定时任务「D-Bee 每日数据备份」，**每天 03:30** 执行
- 保留策略：**滚动 30 天**，更早的 `.json` 自动删除
- 查询语句固定在 `db/backup.sql`，单条语句一次取全（减少往返与出错面）

## 怎么校验备份有效

1. 文件能被 `JSON.parse` 解析；
2. `row_counts` 与 `tables.<表>.length` 一致；
3. 抽一行核对 `owner_id` 是否与线上用户一致。

最近的自动校验记录：2026-10-13，`profiles=3 / water_logs=3`，与线上查询结果一致。

## 恢复怎么做

数据量小，恢复即**逐表回灌**：

1. 用 MCP 的 `migrate` 模式（管理员角色，绕过 RLS）按 `db/schema.sql` 建表；
2. 把备份文件里的 `tables.<表>` 数组拆成 `INSERT` 语句（保留 `id` 与 `owner_id`，避免外键/归属错乱）；
3. 回灌后核对 `row_counts`。

> ⚠️ 恢复会写入生产库，人工确认后再执行，不要交给自动化。
